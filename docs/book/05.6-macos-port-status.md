# macOS / Apple silicon -- port status, measured matrix, performance reference

Three parts: **A** what builds and serves on the **mid-tier box** (newer-generation Apple silicon, 36 GB unified,
Metal working set 30.15 GB); **B** the independent **Ultra-class** datapoint
(192 GB unified); **C** the falsified-candidate table. The decode
*rules* live in `05.7-apple-silicon-inference-architecture.md` and
`04.5-wgsl-naga-msl-kernel-rules.md`.

**No numerical-parity claim is made anywhere on this page.** Metal evidence is
functional/tolerance checks against CPU (and `nv_quant`) oracles, behavioural
gates (coherence, byte-determinism across restart, ASR round-trip), or
bit-identity across load paths. There is no CUDA-vs-wgpu agreement suite: the
`parity_*` family was deleted on the rule that two implementations agreeing is
not an oracle (`05.1-wgpu-status.md` §1).

**The two machines are not interchangeable.** Part A is module- and
serving-level on a newer-generation Apple-silicon box whose logs are not in this repo; Part B is end-to-end
over HTTP on an Ultra-class box with 5.7x the working set, and B is the only box where
the 31B/35B NVFP4 checkpoints fit. Never quote a number without its machine and
its measurement point, and prefer re-measuring.

# Part A -- Port status

## A1. Building on macOS

`metal` does **not** imply `wgpu`. `Cargo.toml` defines `metal` without
`nv-kernels/wgpu`, and the wgpu chat arm in `registry_from_env` is
`#[cfg(all(not(feature = "cuda"), feature = "wgpu"))]`. **Build
`--features metal,wgpu`** or every chat and completions route compiles out.

```sh
nix develop .#no-models --command bash -c '
  export CC=$(command -v cc) CXX=$(command -v c++)
  cd rust && cargo build --release --features metal,wgpu'
```

- `.#no-models` sets `profile=null` and realizes no model hub; the default shell
  pulls ~25 GB of HF weights.
- `flake.nix` pins `nix-hug` as `path:../nix-hug`, so **no `--override-input` is
  needed**.
- Source the dev env under **bash, not zsh** -- the shellHook's cmake-shim PATH
  entry does not survive zsh sourcing (`is cmake not installed?` in
  sentencepiece-sys / whisper-rs-sys).
- `export CC/CXX` is mandatory: bare `clang` resolves to the unwrapped libclang
  binary with no libc++ headers (`'cstdint' file not found` in esaxx-rs).
- `export LIBRARY_PATH=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/lib:...`
  fixes `ld: library not found for -liconv` where the nix apple-sdk xcrun
  resolves in-shell ships no `libiconv.tbd`. Needed on the mid-tier box, not on the Ultra-class one.
- After a build with a broken compiler, wipe
  `target/release/build/{whisper-rs-sys,sentencepiece-sys,esaxx-rs}-*` -- a
  poisoned CMakeCache survives the fix.
- A nix-store shim named `say` shadows `/usr/bin/say`; use absolute paths for
  test-audio generation.

Darwin devshell facts: `SPEACHES_PROFILE=macos`,
`SPEACHES_CARGO_FEATURE=metal,wgpu`, `ORT_DYLIB_PATH` pointing at the nix
onnxruntime dylib. `ort` is load-dynamic, so `ORT_DYLIB_PATH` must be exported at
runtime too.

## A2. Metal kernel coverage

40 `nv-kernels` wgpu suites plus 10 in `nv-layers`/`nv-specdecode`/`nv-models`
run green on a Metal adapter (mid-tier Apple silicon, `shader_f16=true`, `f16_in_f32=true`,
subgroup reported 4..64, 3 coop_mat configs all 8x8x8 with `gemm_tile=None`).
Run with `NV_KERNELS_WGPU_REQUIRE=1` so a missing adapter fails instead of
greening.

Two Metal-specific structural facts:

- **No coop_mat gemm tile.** wgpu-hal reports Metal's subgroup range as a
  hardcoded 4..64 rather than querying the device, so every coop path
  (`gemm_nvfp4`, `moe_grouped`, subgroup-adaptive) skip-passes and only scalar
  paths are Metal-verified; the runtime probe returns 32, so the gate is on the
  wrong signal. A second, independent blocker: `coop_gemm_tile` searches for a
  16x16x16 f16->f32 tile while wgpu-hal Metal reports only 8x8x8.
- **`tanh()` must not come from the WGSL builtin.** naga lowers it to Metal's
  fast-math tanh, imprecise mid-range and wrong at large |x|. The software
  polynomial `nv_tanhf` lives in the shared `wgsl/dequant.wgsl` prelude and is
  used by `gelu_tanh_mul`, `residual_scale`, `gemv_w4a16` and `graph_decode`;
  with it those kernels are bit-exact against their oracles including the
  softcap extremes, without it all four fail on Metal only.

**That is the shape of divergence a cross-backend comparison cannot see and a
host oracle can**: all four kernels were bit-exact against CUDA on NVIDIA Vulkan
while wrong on Metal, because the defect was in a builtin both sides agreed
about. What caught it was each kernel's own CPU oracle, run on the adapter that
had the problem; `05.2-kernel-parity-matrix.md` names those oracles.

One shared-kernel fix came out of this platform: `ue4m3_decode` in
`dequant.wgsl` used `(1.0 + m * 0.125) * exp2(f32(e) - 7.0)`, and Metal's `exp2`
is relaxed-precision, so `exp2(-6.0)` returned 2 ULP low and corrupted every
ue4m3 scale decode. It now uses the exact bit construction `e4m3_decode` uses.

## A3. What serves, and how to enable it

All of the below run through `chat_engine_wgpu` on Metal. Routing is by
`classify_wgpu_model`; point `NV_CHAT_MODEL_DIR` (or `NV_WGPU_CHAT_MODEL_DIRS`)
at a snapshot and the id appears in `/v1/models`. The third documented spelling,
`NV_CHAT_MODEL_DIRS` (plural), is a silent no-op on non-CUDA builds --
`chat_engine/build.rs` never reads it, so you get `nv-engine chat disabled` and
no chat routes.

A row saying a graph exists and is routed to does **not** say this box can serve
the checkpoint. ✗ rows have their checkpoint on **no** machine here -- not in
`~/.cache/huggingface/hub`, not realized in `/nix/store`; `gpt-oss` is not even
pinned in `flake.nix`.

| model | module | wired weights | passes/token | notes |
|---|---|---|---|---|
| ✓ `google/gemma-4-E4B-it` (bf16 or `-qat-w4a16-ct`) | `gemma4_e4b_wgpu` | ~4 GiB at w4a16 | 762 | the reference path; every serving lever below applies to it |
| ✗ `openai/gpt-oss-20b` | `gpt_oss_wgpu` | 12.84 GiB | 416 | experts stay MXFP4 on-GPU, no dequantized copy. No weights and no `flake.nix` pin -- never run here |
| ✗ `Qwen/Qwen3.5-9B` | `qwen3_5_dense_wgpu` | 16.75 GiB | 488 | dense-hybrid bf16, 24 GDN + 8 full-attention layers. Pinned twice, neither pin realized |
| ✗ `google/gemma-4-26B-A4B-it` | `gemma4_moe_wgpu` | 16.50 GiB | 963 | experts quantized to w4a16 g=32 on load. Routing + config parse proven, no safetensors snapshot here (GGUF only, BF16 shards are LFS stubs) -- the decoder has never emitted a token |
| ✓ `RedHatAI/Qwen3.6-35B-A3B-NVFP4` | `qwen3_5_moe_wgpu` | 20.98 GiB | 1106 | needs the streaming loader; Part B has the Ultra-class figures |
| ✓ `poolside/Laguna-XS-2.1-NVFP4` | `laguna_wgpu` | ~21 GiB | 40 layers | NVFP4 experts (256 top-8) + bf16 attention; plain M=1 decode, no wgpu spec. Degenerates on prose `/v1/completions` -- it is a code model, not a server defect |

Per-model facts not obvious from the code:

- **E4B** auto-detects `weight_packed`/`weight_scale` per module
  (compressed-tensors pack-quantized, symmetric int4, group 32), fuses qkv and
  gate_up by row-concat, and dispatches w4a16 GEMV entries. Everything except the
  int8 lm_head is token-stream-identical to the unfused/stepped path by bitwise
  gate.
- **gpt-oss-20b** needs per-head attention sinks (the sink logit joins the softmax
  max and denominator only) and sliding window 128 on even layers, neither of
  which the cuda flash kernel can express -- which is why wgpu is its default slot.
  Serving filters harmony channels: `visible_text` decodes with specials kept and
  emits only final-channel text, so analysis CoT and `<|channel|>`/`<|return|>`
  markup never reach `content`, and tool-call channels are filtered rather than
  surfaced as `tool_calls`. Its KV is bf16 not fp8 and chunked prefill is not
  wired.
- **Qwen3.5-9B** clones the MoE pass graph and swaps every NVFP4 projection for
  the bf16 GEMV; the DeltaNet/attention/KV shaders are byte-identical copies, so
  the pipeline cache dedupes them, and the vision and mtp tensors interleaved in
  the shards are never referenced.
- **Laguna-XS-2.1** classifies off `model_type: laguna` / `LagunaForCausalLM` and
  serves through `laguna_wgpu` (feature `laguna-wip`, which the binary's `wgpu`
  feature pulls in) on the real ~21 GiB checkpoint. **Serving is plain M=1 greedy
  decode: spec-decode is CUDA-only** and `spec_route_eligible` stays E4B-only.
  Parity is claimed behaviourally -- coherent, on-topic code continuations,
  greedy-deterministic and byte-identical across restarts -- not numerically: the
  step-0 forward agrees with the CPU oracle to 0.73 bf16 ULP but step>=2 argmax
  drifts within the oracle's own substrate-noise band (a non-order-replicating
  NVFP4 oracle amplified by the discrete top-8-of-256 router). The port's shape
  and its four architecture traps are `05.8-laguna-wgpu-status.md`.
- **gemma-4-26B-A4B** routes on `enable_moe_block` **before** the dense/E4B
  split; routing on the id instead silently drops every expert weight. w4a16 was
  chosen over NVFP4 for the experts because NVFP4's activation quantization
  visibly degraded real-weight quality (worst relative error 0.034 -> 0.007).
  Greedy argmax runs on the **raw bf16 logits, pre-softcap**: tanh is monotone so
  this is argmax-equivalent in exact math, but computing `30*tanh(raw/30)` in f32
  collapses every |raw|>~270 to exactly 30.0 and turns greedy into a tie-lottery
  over special tokens. Sampled requests still see those saturated logits.

**Streaming weight loader.** `WeightSource::{Host,Loader}` plus `from_loader()`
on every wgpu decoder writes mmap slices straight into mapped-at-creation wgpu
buffers, so on unified memory there is no intermediate host copy and the
CPU-resident checkpoint never coexists with the GPU upload. On E4B this roughly
halves both load peak footprint and load time, perf-neutral and
token-bit-identical. The serving path uses it.

**Speculative decoding** is default-on for eligible greedy requests on the E4B
engine, with the learned **assistant** drafter
(`gemma-4-E4B-it-qat-q4_0-unquantized-assistant`, 183 MB) **whenever its
checkpoint dir resolves** -- `default_assistant_dir()`
(`chat_engine_wgpu/learned.rs`) scans the HF hub for a snapshot containing
`model.safetensors`, and where it does not resolve the effective drafter is
`suffix` (that is the case on the Part B box; do not carry the assistant claim
there). `NV_WGPU_SPEC=0` is the kill switch and the only disabling value;
`NV_WGPU_SPEC_DRAFTER=suffix` forces the checkpoint-free suffix automaton, also
the fallback when the checkpoint is absent or a propose errors. Eligibility is
greedy-only (`needs_logits()` false -- no sampling, penalties, logit_bias,
logprobs or guided grammar); `NV_WGPU_SPEC_K` defaults to 8 clamped 1..=8 so
verify stays at M <= 9.

The drafter's architecture and checkpoint contract are
`03.1-mtp-drafter-notes.md`. What matters here: it runs as its own wgpu pass list
(72 passes, replayed k times per round with a single k-token readback), shares
the backbone's GPU embed table and reads the live fp8 KV in place, so there is
**zero KV readback** -- 1.0 ms/step against 33 ms for a candle-CPU forward, which
is what converts the tau win into wall-clock. Drafting is gated on the shared
accept EMA (`NV_WGPU_SPEC_ASSISTANT_EMA_FLOOR`, default 2.05, just above the 2.0
init, so the assistant arms only on evidence); below the floor the round is a
plain `decode_step` and suffix proposals are restricted to long matches
(`NV_WGPU_SPEC_PROBE_MIN_MATCH`, default 16) acting as free re-entry probes.
Prose never drafts; structured content arms within ~10 rounds. Floor 0 restores
always-on drafting. The assistant is the fastest spec arm on prose and
adversarial; suffix wins structured, because chain verify costs ~7.5 plain steps
per armed M=9 round and only suffix's 0.97 accept clears that break-even.

Losslessness, not speed, is the ship criterion, and it is asserted three ways: a
CPU harness drives perfect / constant-wrong / random / adversarial drafters
against a hash model and checks `commit_len-1 == LCP(draft, continuation)` every
round plus a seeded property test; the real-checkpoint serving A/B asserts
spec-on completions byte-identical to spec-off on four prompts (structured,
prose, a window-crossing 538-token prompt, a rejection-heavy adversarial pattern)
across engine reloads; and sampled requests are byte-identical because they take
the plain-loop route. KV rollback is a `pos` counter rewind only.

**Guided decoding** is the shared device-independent `chat_engine::build_guided`
(`05.1-wgpu-status.md` §4.4 item 6), so it is not a Metal surface. Its one
interaction with this page: an active grammar makes `needs_logits()` true, which
forces the host-logits readback path and auto-disables spec decode.

**The speech surface is not macOS-specific and is not described here.**
`07-speech-stack.md` owns Kokoro, Punkt segmentation, the nv-omni vocoder and
its streamer, and the ECAPA-TDNN voice profiles; `06-serving-surface.md` owns
their HTTP contracts. The macOS-relevant facts are only that all of them run on
CPU here (A7) and that `/v1/voice-profiles` needs
`Qwen/Qwen3-TTS-12Hz-0.6B-Base` -- the CustomVoice checkpoint carries no
`speaker_encoder.*` tensors and returns 400 `voice_profile_unsupported`, while
Base has an empty `spk_id` map, so named speakers and profiles cannot be served
from one instance.

enables and anything else disables. On CUDA, `gemma4_e4b.rs` gates on

An A/B written the wgpu way on a CUDA box compares int8-on to int8-on. See
`08.4-PERFORMANCE.md`.

## A5. Numbers of record

**Box: the mid-tier one, 36 GB unified, macOS 26.x.** Not Ultra-class numbers; Part B's are.
Every rate lives in `perf/runs.jsonl` with its basis; nothing on this page
carries a figure.

Method for every row: fixed-prompt decode, `--release`, strictly serial,
idle-gated (`top` >= 85% idle, no compute co-tenant), interleaved A/B back to
back on the same binary, medians over at least two runs. **Absolutes taken
outside an idle window are materially inflated; only in-process interleaved
ratios survive a co-tenanted run.** Label which you have.

**The regression gate is a golden hash, not a time.** `md5(generated ids)` over
the 400-token essay is `c9073a59...` on the default and `NV_WGPU_CHAIN=4` paths,
and `012f8b4f...` on the int8-lm_head record path; the 46-token stream is
`f63cea88...`. A default-preserving change must reproduce them. A hash that stops
reproducing is either a real behaviour change or a rebuilt basis -- decide which
before pinning a new one, because a silently re-pinned golden gates nothing.

Chunked prefill on the Qwen3.5-9B dense graph is **bit-identical to the m=1
loop** (0 of 248,320 logit lanes differ) only on the legacy escape arms
(`NV_Q3D_PF_COOP=0 NV_Q3D_PF_ATTN_TILED=0 NV_Q3D_PF_SCAN_WY=0`), where it outruns
m=1; the tensor-ops (coop) arm at M=16 reaches an order of magnitude beyond it.
The default prefill stack is the coop + WY-scan + tiled fp8-kv-attention path at
M up to 256, which trades that bit-identity for throughput inside the ppl gate --
re-measure any prefill rate on the arm being quoted.

Fleet-wide, skipping lm_head + argmax on non-final prefill positions is worth a
double-digit-percent warm win on every MoE and dense model measured. It is
prefill-only and does not touch decode.

## A6. Ops hardening

- **`ORT_DYLIB_PATH` fails loud.** A path that does not exist aborts before any
  model load with a message naming the variable and the bad path; an unset
  variable with no dylib at `~/.nix-profile/lib/libonnxruntime.dylib` logs a WARN
  naming it. The onnxruntime session build runs on a worker thread under a
  **120 s timeout**, so `Models::get_or_init` cannot hang forever when ort cannot
  dlopen.
- **Boot states which chat models loaded and their wired GiB**, from
  `proc_pid_rusage` `ri_phys_footprint` (`getrusage` maxrss elsewhere) -- the
  number that matters on unified memory, since RSS under-reports Metal buffers by
  ~4x.
- **`/v1/models` is deterministic**: `voice_names()` sorts, where the Kokoro
  `voices` array used to come from a `HashMap` and shuffle between boots.
- **Diarization 503 carries `service_unavailable_error`** and names both required
  files and `SPEACHES_PLUS_MODELS`.
- **Kokoro load failure is non-fatal** -- it warns and disables like diarization
  and speaker embedding rather than taking down STT and realtime -- and
  `voices.bin` loads *before* `phonemize::init` so a corrupt archive fails before
  the phonemizer is globally initialised.

## A7. Known limitations (production-relevant)

- **Cold start is closed by the boot-time warmup (A4).** Residual: the warmup runs
  per model at build time, so a multi-model boot pays a seconds-class serial cost
  per model, and the first request after another model has been serving can still
  pay a residency swap on a memory-tight box. (The 26B MoE decoder additionally
  runs a warmup decode step inside `from_loader`.)
- **Diarization needs an export step.** `diarizen-segmentation.onnx` is not built
  here (`rust/scripts/export-diarizen-onnx.py`), so `/v1/audio/diarization` is 503
  and `diarized_json` degrades to one null-speaker segment per whisper segment --
  well-formed and **indistinguishable from a real single-speaker result**.
- **OCR has no checkpoint here.** Both backends 503 naming their env var (B7,
  `06.3-ocr.md`).
- **Realtime outbound ordering.**
  `realtime::order_harness::tier2::tier2_i12_concurrent_emitters_preserve_order`
  is a sanctioned red test pending the single outbound sequencer
  `06.2-concurrency-and-ordering.md` describes.
- **Omni any-to-any: out of scope on macOS** (user decision). No endpoint, no
  runnable checkpoint here; the audio-in -> spoken-reply gate is a GPU-box concern.
- **Eagle3 / DFlash spec paths are CUDA-only**: the macOS spec path is the
  assistant+suffix pair on E4B only.
- **gpt-oss-20b harmony budgets.** Small `max_tokens` can be consumed entirely by
  the analysis channel and return empty content with `finish=length`; the final
  channel opens and answers correctly at a generous budget.
- **`transcribe_ct2_long` hard-chops audio > 30 s** at 30 s boundaries with no
  overlap and no VAD alignment, so words straddling a boundary are dropped or
  mangled. Byte-exact round-trips of >30 s audio only succeed when a sentence
  pause happens to cover the mark. Fix belongs to the STT lane.
- **CPU talker is well slower than realtime**; streaming fixes time-to-first-audio
  only, so long playback underruns. Realtime needs the talker on Metal/wgpu.
- Everything here is **single-tenant**. No batch=32 throughput, no 24 h soak.

## A8. Kill list

Falsified as defaults, each kept opt-in behind a bitwise gate:

- **Verify-attention seam swap -- reverted.** `attn_decode_small_m_fp8` (fp8-byte
  KV + per-slot scales, fused over up to M=10 rows) is bitwise-identical to
  `attention_fp8_decode` called M times and faster than that baseline, but the
  *model-side* swap into E4B's `verify_chain` regressed the structured prompt
  severely (one workgroup per q-head with a barrier-serial position loop, versus
  the flash-rows stage's split-k fan-out) and diverged the adversarial spec stream
  from plain greedy on a near-tie argmax flip, because verify no longer matched
  the decode path's split-k flash arithmetic bit-for-bit.
  `VERIFY_ATTN_SEAM_TODO` in `gemma4_e4b_wgpu.rs` records it. **Constraint for any
  future attempt:** serving losslessness pins verify to argmax-equality with
  `decode_step` on every token, so a replacement must be per-row bit-identical to
  the decode split-k flash -- same split/warp position assignment, same warp-sum
  merge order, same `fd_exp`.
- **Attention head-chain fusion** (`NV_E4B_WGPU_FUSE_ATTN=1`): removes 114
  dispatches/token, but interleaved idle-gated pairs put the mean at a small
  regression with a confidence interval excluding the modeled win. A falsification
  with power: the fused kernels re-do a full block reduce per head row where the
  unfused pair amortized one launch over all heads.
- **Subgroup bf16 lm_head** (`NV_E4B_LMHEAD_SG=1`): bitwise-identical to the tree
  head by construction (the butterfly is order-isomorphic at lane 0), but at the
  lm_head shape the kernel is DRAM-bound and reduction style does not matter.
  `NV_E4B_LMHEAD_SG_WG=128` is a trap at vocab 262144: 65536 groups exceeds the
  65535 per-dim limit, so the grid doubles with half the subgroups dead.
- **Head argmax fold** (`NV_E4B_WGPU_FUSE_HEAD=1`): saves one dispatch and one
  vocab-sized f32 re-read; the modeled win is orders below measurement power and
  clean interleaved pairs gave a null.
- **Workgroup-shared x staging in GEMV**: regressed severely because wgpu
  zero-initializes workgroup memory per launch, so a 12 KB smem array adds a
  zero-fill loop to every GEMV workgroup. Retryable now that
  `zero_initialize_workgroup_memory` is per-pipeline-stage -- but mlc-llm's
  Apple-Ultra-tuned GEMV also chooses `LOAD_V_SHARED = False`, so expect neutral.
- **Chunked prefill as a *token-changing* default** -- rejected once on a 1-token
  sg16 drift, then fixed at the root and shipped ON (A4). The fix is the
  interesting part: the mk kernels run the *exact* sg16 GEMV accumulation per
  token (same 16-lane k-partition, same fma sequence, same butterfly) with the
  weight vec4 loaded once per k-step and reused across all m tokens, so chunked
  prefill writes bit-identical KV to stepped decode.

## B3. Measured performance

**A performance number on this tree has a shelf life measured in hours.** The
chat baselines here were invalidated twice in one day -- once by upstream default
flips (`ATTN_FP8_DEFAULT_ON`, `NV_WGPU_SPEC`), once by concurrent in-tree kernel
lanes (NOZI-all, flash-1 zero-init removal, GEMV scale-pack, the fp8-KV split
autotune, the shape-aware selector) which moved the 31B by far more than either
flip. **A number is quotable only as a `perf/runs.jsonl` row**, which carries its
commit and basis by construction.

All three checkpoints (`google/gemma-4-E4B-it` bf16 at 762 passes/token,
`nvidia/Gemma-4-31B-IT-NVFP4` at 728, `RedHatAI/Qwen3.6-35B-A3B-NVFP4` at 1106)
load, reach server-ready over HTTP and settle to a small steady RSS after a
load-time peak; both NVFP4 checkpoints serve, which is the first run of either on
Apple silicon. **Size a host by the transient, not the checkpoint**: the 31B's
load-time peak during weight streaming, before buffers move to GPU, is nearly
twice its on-disk size -- almost certainly why the 36 GB box was SIGKILLed.

Chat method: `max_tokens=128` x 3 back to back with identical prompt and output
so token counts match exactly, basis e2e wall (HTTP + prefill + decode). Two
attributes a rate row cannot show: **prompt length differs across rounds** (four
are in circulation), and **`NV_WGPU_NVFP4_V2` is bit-exact on the MoE and not on
the 31B** -- the Qwen output sha holds at `6c17b420e444` across the arm while the
31B sha moves `d9d48e450730 -> a035f44c8312`, so never describe the 31B column as
bit-exact.

**Isolating a default flip works here and is the method to copy**: turn the new
default back off in an otherwise identical process and require the prior to
reproduce inside its spread **and** the emitted text to revert byte-for-byte.
`ATTN_FP8_DEFAULT_ON` moves the 31B only; `NV_WGPU_SPEC` moves E4B greedy only and
is the entire E4B delta; the MoE has no fp8 path and is not spec-eligible, so it
is the untreated control and stayed inside its own spread. Any spec-on sign is
prompt-specific -- here the suffix drafter was barely working for it (near-unity
τ, almost no drafted rounds).

**Sampled requests are a different régime.** `NV_WGPU_FAST_SAMPLER` (default ON)
is inert at temperature 0 -- greedy takes an in-shader argmax and never reaches
the sampler -- but on sampled requests it replaces an O(V log V) host sort at
V=262144, output byte-identical either way. The saving is a near-constant host
cost per token regardless of model size, so it dominates precisely where the model
is fastest: **every greedy-only comparison here understates sampled serving**,
most of all for the MoE. Sampled rates are prompt-sensitive -- a different prompt
of the same length shifted all three uniformly, including the bf16 control no
NVFP4 kernel can touch. **Do not compare them to Part A's module-level ms/tok**:
these go through Axum on a different machine, and an apples-to-apples
module-level decode loop on this box has never been run.

Behavioural results hold on all three checkpoints at temperature 0 with
byte-identical 128-token completions across 3 runs each: coherent factual answers,
`stop` sequences, `n>1` (cap 16), `logprobs`/`top_logprobs`, seed determinism at
temp 0.8, clamped `max_tokens`, forced-function tool calls, guided JSON, and SSE
framing with `[DONE]` and `include_usage`. Laguna XS 2.1 also reaches the wgpu
decode loop here; its first serving rate came off a debug build under memory
pressure and is explicitly **not** a number of record
(`05.8-laguna-wgpu-status.md`).

**STT.** **whisper.cpp on Metal is several times faster** than faster-whisper CT2
here, on both boxes, and most of the gap is that CT2 logs the saved fp16 compute
type as unsupported and converts to float32, so the CT2 path runs fp32 on CPU on
Apple silicon. All six `response_format`s (`text`, `json`, `verbose_json`, `srt`,
`vtt`, `diarized_json`) return 200 on **both** backends, validated by a scripted
cue checker over 4 subtitle files (sequential indices, `HH:MM:SS,mmm` / `.mmm`
form, `end >= start`, non-decreasing starts, no cue past the audio duration, no
empty text): **0 problems**. CT2's 13-vs-14 cue split against whisper.cpp on the
60.55 s clip confirms correct chunk-offset stitching across the 30 s
`CHUNK_SAMPLES` boundary, and `text`/`json` transcripts are byte-identical
between the two backends.

**The recorded OCR page rate is a CPU number, not a Metal one.** `ocr_device()`
(`src/oapi/ocr.rs`) selects Metal **only** when `NV_OCR_DEVICE=metal` is set
explicitly; the default `Auto` arm auto-selects *cuda only* and otherwise falls
through to `Device::Cpu`, and the published page rate was taken with the variable
unset. A Metal OCR path exists and is opt-in but has never been measured, so any
"OCR on Metal" comparison against the CPU figure compares two different devices.
Enforced by `ocr_device_defaults_to_cpu_without_cuda`, which asserts
`device_label(&ocr_device()) == "cpu"` on a non-CUDA build with `NV_OCR_DEVICE`
unset. Load/warmup/request timings for VAD, Kokoro, wespeaker embedding, PII
classify and DeepSeek-OCR-2 all live in `perf/runs.jsonl`.

## B5. Pass and dispatch counts

**A "pass" in this codebase is one dispatch.** `gemma4_wgpu.rs`'s `Pass` is
`{pipeline, bind, grid}`, pushed once per `dispatch_workgroups`, and
`pass_count()` is `passes.len()`. The server's `passes/token=` log field counts
dispatches, not wgpu compute passes. E4B is **930 pre-fusion and 762
post-fusion** (-168 = 4 x 42 layers, from the three rmsnorm fusion chains). "All
dispatches go into ONE compute pass" is a statement about *encoding* -- one wgpu
compute pass, one submit -- orthogonal to the count, and it does not make them
concurrent.

Counts rebuilt from the graph builders rather than from a log reproduce exactly:
31B **728** = 60 layers x 12 + layer-0 rms + gather + embed-scale + 2 lm_head +
softcap + 2 argmax (240 of the 728 are the NVFP4 path -- 120 gemv + 120
row-quantise); Qwen3.6 **1106** = 30 linear layers x 27 + 10 attention layers x
29 + 6.

The Qwen3.6 boot field has been observed at both **1106** and **1136** (the +30 is
one dispatch per linear layer from an intervening kernel lane). The derivation
above sums to 1106 -- re-derive from the graph builder before quoting either. The
31B's **728** was confirmed from two independent sources (boot field and
`Gemma4Wgpu::pass_count()`). Log-reading trap: the field sits inside ANSI colour
escapes, so `grep '=1136'` returns nothing -- strip first:
`sed $'s/\x1b\\[[0-9;]*m//g' <log> | grep passes_per_token=`.

## B6. NVFP4 v2 GEMV kernels (`gemv_nvfp4_v2`)

`nv-kernels` module `gemv_nvfp4_v2` carries six structurally distinct NVFP4 GEMV
kernels on the identical shipping buffer contract, every variant bit-exact at
every config against a per-variant order-replicating CPU oracle (175/175 on the
seven production shapes, 100/100 on ragged shapes). Gate:
`cargo test --release --features metal,wgpu -p nv-kernels --test
wgpu_gemv_nvfp4_variants -- --test-threads=1`.

- **The winner is shape-dependent and `gemv_nvfp4_v2::select(n, k)` encodes the
  measured best per production shape** (its unit test asserts exactly that).
  Multi-row float-decode `fmlut` wins the large shapes by a wide margin over the
  shipping tree kernel; at n=512 multi-row starves on workgroup count and `fdec`
  wins; at k=512 `warp` wins.
- **Both flags default OFF** (`NV_WGPU_NVFP4_V2` in `gemma4_wgpu.rs`,
  `NV_Q3_WGPU_NVFP4_V2` in `qwen3_5_moe_wgpu.rs`) because the swap is not
  bit-identical end to end: tree and `fmlut` sum k-blocks in different orders
  (`tree_and_fmlut_differ_only_by_block_summation_order`: 1 row in 8192 at max
  1 bf16 ULP), enough to flip a greedy argmax -- Gemma-4-31B diverges at generated
  token 7 while Qwen3.6 is byte-identical on the same probe.
- **`dot4I8Packed` has no native Metal instruction**: the integer/SWAR decode
  family ablates to a structurally lower ceiling than pure-float decode.
  `gemv_nvfp4.rs`'s `the_hot_path_decodes_without_a_lookup_table` assertion is
  CUDA-correct and Metal-wrong; it should be feature-gated, not deleted.
- 31B per-token weight bytes, derived and verified: **11.71 GB NVFP4 + 18.36 GB
  bf16 = 30.07 GB/token** (attention q/k/v/o and `lm_head` stay bf16). No honest
  e2e effective-GB/s exists for the Qwen3.6 MoE; none is given.
- Remaining headroom is decode ALU, not memory: two untried levers are a
  load-time nibble remap in the weight loader and f16 decode (`shader_f16` is
  true here).

## B9. Per-dispatch GPU profiler (`NV_WGPU_PROFILE=1`) -- unusable on this adapter

**Do not set `NV_WGPU_PROFILE=1` on a server you care about.** The first profiled
31B request kills the Metal counter sample buffer allocation, invalidates the
device, and -- worse than crashing -- returns **HTTP 200 with
`completion_tokens: 0` and truncated content**: a silently wrong answer. The pass
budget is not a constant (`PROFILE_MAX_PASSES = 1792` calibrated in isolation; the
server fails at 728 with the 31B resident and a whisper Metal context alive), so
no single constant can be correct. The instrument tax is two quantities, per
submit and per dispatch -- never quote one us/dispatch figure. Attributing the 31B
token per kernel remains open.

**The "most of the 31B token is not weight streaming" prior survives an indirect
test**: well over half of the token was removed (zero-init removal, GEMV
scale-pack, shape-aware selection) with byte-identical output, so **the majority
of the old token was removable overhead, not bandwidth**. The 31B
effective-bandwidth measurements were measuring overhead, and the roofline "gap"
they imply is correspondingly smaller.

## C7. Hardware verdict

Six structurally distinct NVFP4 GEMV kernels, all gated bit-exact against
per-variant order-replicating CPU oracles (B6), settle four things:

- **A structural clone alone is not sufficient.** Porting the in-tree fast-GEMV
  pattern while keeping the integer decode bought a real win on one 31B shape and
  nothing on the other. Structure by itself buys nothing at large K.
- **Multiple output rows per simdgroup is the biggest structural lever**, and
  **activation prescaling is the load-bearing trick** on top of row-blocking.
  Both are exactly what MLX and llama.cpp do.
- **Two predictions refuted**: `vec4` loads as an unconditional ingredient, and
  one winning geometry per model (C6).
- **One the literature did not predict**: `dot4I8Packed` has no native Metal
  instruction, so the whole integer/SWAR decode family is capped well below what
  pure-float decode ablates to.

**A multi-fold kernel win became a marginal token win, and that is the result.**
The e2e saving actually **exceeded** the kernel-level projection -- the gap is
that NVFP4 GEMV is a minority share of the 31B token, so even a *free* GEMV caps
the token win low. The token is not a weight stream: the effective end-to-end
rate is a small fraction of roofline and of llama.cpp's demonstrated rate while
the best *kernel* reaches about half of llama.cpp's. The unallocated
(non-weight-stream) time is therefore the binding constraint, and
concurrent-dispatch and fusion campaigns stay **unarbitrated** until the
per-dispatch timeline exists -- nothing measured so far distinguishes drains from
non-GEMV kernel time. Do the timestamp breakdown before either.
