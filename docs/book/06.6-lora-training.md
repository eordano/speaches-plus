# LoRA training -> serve here

> **Just want it to run?** `rust/scripts/lora-quickstart.sh` does the whole native
> pipeline (data -> trained adapter -> load/route check) end to end in ~2 min, no
> PyTorch, GPU or download. Same flow as `examples/lora/train_lora.ipynb`.

Two routes produce a LoRA adapter this server loads and serves on the Gemma4
(`gemma4-e4b`) text tower, both writing the standard PEFT layout the loader consumes:
`adapter_config.json` (`peft_type=LORA`, `r`, `lora_alpha`, `target_modules`, …) plus
`adapter_model.safetensors` holding `base_model.model.<module>.lora_A.weight` /
`.lora_B.weight`. Serving is wgpu/E4B only, one engine per adapter — see
[`06.5-lora-design.md`](06.5-lora-design.md) §12.

## 1. unsloth / HuggingFace-PEFT route

Train on your own GPU with the stock ecosystem and drop the adapter directory in here;
no PyTorch is needed on the serving host, and nothing about the recipe is
repo-specific: stock unsloth `FastLanguageModel.get_peft_model(model, r=8,
lora_alpha=16, lora_dropout=0.0, bias="none", use_rslora=False, use_dora=False,
target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"])`
over any Gemma-3/4 text checkpoint, your own SFTTrainer/TRL loop, then
`model.save_pretrained("my-lora")`; plain HuggingFace PEFT (`LoraConfig(...)` +
`get_peft_model` + `save_pretrained`) is byte-compatible. rsLoRA is supported.
**DoRA is not** — `use_dora=True` saves `lora_magnitude_vector` tensors, which the
loader detects and fails on clearly rather than silently mis-loading.

Copy `my-lora/` onto the serving host, point the server at it via
`NV_LORA_ADAPTER_DIRS` (comma/colon-separated `name=path` specs; a bare path uses the
directory name as the id), then select it by id in the chat request's `model` field:

```bash
export NV_LORA_ADAPTER_DIRS="my-lora=/srv/adapters/my-lora"
```

The server discovers any directory containing `adapter_config.json` (`oapi/lora.rs`),
validates it, and at model build time calls `E4bLora::from_peft_dir`
(`nv-models/src/gemma4_e4b_wgpu.rs`), which loads through
`nv_weights::lora_adapter::LoraAdapter::load`. `normalize_module_name` maps the stock
text-tower namespace (`base_model.model.model.layers.*`, `model.embed_tokens`) onto the
serving graph's `model.language_model.layers.{i}…` — **a pure rename, no numeric
change**; adapters already in `model.language_model.*` are left byte-identical.
`nv-weights/tests/lora_stock_compat.rs` pins it: a stock-layout fixture loads with
correct `r`/`alpha`/scaling and every module routes to its serving name, the same
weights in either namespace load to bit-identical served tensors
(`NAMESPACE_EQUIV_MAXABS 0.000e0`), our own adapters load unchanged, DoRA fails clearly.

## 2. native route (`nvk-train`, no PyTorch)

```bash
NV_DETERMINISTIC=1 \
NVK_PKG=nv-models NVK_FEATURES= NVK_LANE=loratrain \
  rust/scripts/nvk.sh run --bin nvk-train -- \
    --base   <model.gguf | dir-with-config.json+model.safetensors> \
    --data   data.jsonl \
    --out    my-lora \
    --rank   8 --alpha 16 \
    --target q,k,v,o,gate,up,down \
    --steps  100 --lr 0.05 --seed 7
```

or `rust/scripts/nvk-lora.sh train --base model.gguf --data data.jsonl --out my-lora
--rank 8` for defaults plus a post-train load/route check.

Flags (`nv-models/src/bin/nvk-train.rs`): `--base` a `.gguf` (bf16 dequant) or a
dir with `config.json` + `model.safetensors`; `--data` jsonl, one object per
line, `{"ids":[u32,...]}` | `{"text":"..."}` |
`{"prompt":"...","completion":"..."}`; `--rank` / `--alpha` (alpha defaults to
rank, giving unit scaling); `--target` a subset of `{q,k,v,o,gate,up,down}`;
`--steps` AdamW steps (`0` writes an untrained identity adapter); `--lr`,
`--seed`. `NV_DETERMINISTIC=1` makes the run bit-reproducible. Output is the
same PEFT layout in the `model.language_model.*` namespace, served exactly as in
§1.

`train_runner::run` is the driver: `load_base` -> `build_targets` ->
`LoraTrainable::new` per target -> `Linear::attach_lora(TrainingLoraHook)` -> AdamW
loop -> `serving_equivalence` check -> `save_peft_raw`. `build_targets` is
Gemma4-specific: it splits the fused `qkv_proj` into q/k/v component slices and
`gate_up_proj` into gate/up, naming modules
`model.language_model.layers.{i}.self_attn.q_proj` and so on. **Training requires a
materialised bf16 base weight** and bails with a "needs host dequant" error on a
packed nvfp4 or fp8 base it cannot dequant. `rust/scripts/nvk-lora.sh check
/srv/adapters/my-lora` validates any adapter — it prints `r`, `alpha`, scaling and the
matched module count, and fails clearly on a DoRA adapter or one matching no Gemma4
text projection.

### Memory placement for large CUDA bases

The frozen base is built once and trained against, so its residency matters
independently of the training step. On a **packed-NVFP4 base** packed tensors dequant
to F32 **on the host** and only the final cast tensor moves to the GPU, because a
full-size F32 dequant temporary held on-device roughly doubles the resident footprint
on the 60-layer 31B model and OOMs the load; every other tensor loads straight through
to the training device, and the inner loader keeps the raw packed checkpoint on the
host so it is never co-resident with the dequanted bf16 base on the GPU. A **dense
bf16 base** is held resident on the GPU as **bf16, not F32** — F32 residency for the
full 31B dense model is ~126 GB, so halving it is what makes full-depth training fit
on this box at all; activations still run in F32 through the differentiable candle
matmul fallback, so only the frozen base's storage dtype changes and backward-pass
precision is unaffected. On CPU (`dtype=F32, device=Cpu`) every move is a no-op, so
the CPU path is byte-unchanged and the base stays F32.

### Why a fast kernel must never see a training activation

`nv-layers` builds tensors with `BackpropOp::none()` at eleven sites — seven
hand-written CUDA GEMMs in `linear.rs`, four rope outputs in `rope.rs`. A tensor built
that way is a graph **leaf**: candle does not backprop through it, so **a training
step routed into one contributes no gradient at all — not a wrong gradient, none — and
nothing errors.** The damage is larger than the layer it happens in: with
`y = base(x) + lora(x)` the adapter on *that* layer still trains through its own
branch, so the loss keeps falling and the run looks healthy, but no gradient reaches
`x`, so every adapter in an **earlier** layer is either dead or training on the
gradient of a model whose base is disconnected. A falling loss is therefore not
evidence that any of this is fine, and no existing suite would have gone red.

Two dtype gates keep those sites off the training path, and they point in opposite
directions: `linear.rs` fast paths require **BF16** activations, so F32 training falls
through to the differentiable `matmul_fallback`, while `Rope::apply` dispatches to the
CUDA kernel for **F32** — exactly what training carries, with the trainer escaping
only because `dense_train.rs` calls `apply_candle` directly. **Neither gate is a
coincidence worth relying on, and both invert under an ordinary optimisation**: moving
training activations to BF16 for speed arms all seven linear sites, and rewriting that
one `apply_candle` call to the dispatcher arms both rope sites. So the sites themselves
check `Tensor::track_op()` — candle's own "is this on an autograd graph" — and divert
to the differentiable path when it is true. `track_op()` is false for every inference
tensor, because candle leaves `op` as `None` when no input tracks, so the check costs
inference nothing and the training trajectory is unchanged.

`NV_ALLOW_LEAF_GRADIENT_LOSS=1` restores the superseded behaviour on every one of
those sites, at the cost of the silent zero above. It exists to A/B the diversion and
to unblock anyone who measured on the old path; **it is not a tuning knob, and no
published number is measured with it set.** The suite is
`nv-layers/tests/linear_backprop_leaf.rs`, each row pairing a positive control (a
gradient reaches the input) with a negative control under
`NV_ALLOW_LEAF_GRADIENT_LOSS=1` (the leaf comes back), because without the negative
half the positive half would be green whether or not the diversion existed.

### The trainer runs a second implementation of the model

`dense_train.rs` does not call the forward that serving calls: it calls a parallel
differentiable one at every layer — `forward_candle` for all eight norms,
`apply_candle` for rope, a local `naive_sdpa` in place of flash attention — because
the serving paths are hand-written kernels with no backward. **An adapter is therefore
trained against one model and served against another, and any drift between the twins
lands silently in the weights.** Each twin is held to its serving counterpart within a
budget derived from f32 roundoff over the reduction width (`16 * eps_f32 * sqrt(n)`),
not from the divergence it is bounding; `nv-layers/tests/train_serve_skew.rs` covers
the norm and rope pairs in both F32 and BF16, and both rows fail on a 0.01%
perturbation to either side. **The pairs must be compared on untracked inputs** — a
tensor on an autograd graph diverts the serving path to the candle one, which would
compare `forward_candle` against itself and pass unconditionally, so both rows assert
`!track_op()`. `naive_sdpa` is held to an independent f64 attention written out by
hand in `nv-models/tests/train_attention_oracle.rs` rather than to flash attention,
proving the trainer's attention *correct* without depending on the serving kernel
being reachable from a test: its rows cover the causal case, a sliding window and a
key run longer than the query run, fail on a 0.1% scale perturbation or a wrong GQA
head map, and carry negative controls asserting that the window changes the answer,
that not all query heads produce the same output, and that the oracle never softmaxes
a row attending to nothing.

**Queries carry the cache offset; keys are absolute.** With `stored` keys and
`seq` queries, query `i` sits at position `stored - seq + i` and key `j` at
position `j`. Spelling it the other way round — offsetting the keys and leaving
queries at `0..seq` — puts every query before every key, so for `stored > seq`
the first query row attends to nothing and its softmax runs over an all-`-inf`
row, giving NaN rather than a wrong number. Training feeds `stored == seq`,
which makes the offset zero and the two spellings identical, **so nothing
catches this until a KV cache reaches the trainer.**
