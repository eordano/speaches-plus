# LoRA training -> serve here

> **Just want it to run?** `rust/scripts/lora-quickstart.sh` does the whole native
> pipeline (data -> trained adapter -> load/route check) end to end in ~2 min, no
> PyTorch, GPU or download. Same flow as `examples/lora/train_lora.ipynb`.

Two routes produce a LoRA adapter this server loads and serves on the Gemma4
(`gemma4-e4b`) text tower, both writing the standard PEFT layout the loader consumes:
`adapter_config.json` (`peft_type=LORA`, `r`, `lora_alpha`, `target_modules`, …) plus
`adapter_model.safetensors` holding `base_model.model.<module>.lora_A.weight` /
`.lora_B.weight`. Serving is wgpu/E4B only, one engine per adapter — see
[`06.5-lora-design.md`](06.5-lora-design.md) §12.

## Native Laguna NVFP4 training

The fine-tuning endpoint selects `laguna_train::run` for Laguna checkpoints,
including `poolside/Laguna-XS-2.1-NVFP4`. Packed bases require a CUDA build and
BF16 activations. Their frozen expert weights stay in the checkpoint's native
NVFP4 representation; loading does not expand the complete base or construct a
second grouped expert copy. Dense checkpoints retain their existing CPU/CUDA path.
Packed checkpoints select CUDA automatically when `NV_TRAIN_DEVICE` is unset;
an explicit CPU selection returns an error instead of expanding the base.

This trains attention LoRA adapters on `q`, `k`, `v`, `o`, and `g` across all
layers. The packed expert weights remain frozen. Expert forwards use the native
quantized linear path. `QuantLinearOp` propagates input gradients with a transient
BF16 reconstruction of one weight matrix at a time, using the checkpoint weight
scale independently of its activation scale. Optimizer state belongs only to the
adapters. Training memory also includes activations and temporary GEMM storage.
The input-gradient rule is first-order straight-through differentiation of the
quantized linear; packed values and quantization scales are frozen. Training rows
retain the existing 512-token limit.

`laguna_train_routing::forward` detaches the top-k expert choice while keeping the
selected sigmoid scores and normalization differentiable. Missing or non-finite
adapter gradients fail the job before an optimizer update. Packed training rejects
`NV_ALLOW_LEAF_GRADIENT_LOSS=1`. Job metrics expose `packed_linears`,
`grouped_moe_copies`, and `base_dtype` (`NVFP4+BF16` for the packed path).

The suite covering full native packed training (`laguna_train_nvfp4`) requires an
idle CUDA host, `NV_LAGUNA_TEST=1`, and `NV_LAGUNA_DIR` pointing to the real packed
checkpoint. Run it through `rust/scripts/nvk.sh` with `NVK_PKG=nv-models`,
`NVK_FEATURES=cuda`, and a named `NVK_LANE`. The router finite-difference suite
and `linear_quant_backprop_leaf` cover routing gradients and non-unit checkpoint
scale handling separately. These are gradient and artifact checks; task-quality
acceptance requires an evaluation corpus.

## WGSL QLoRA route (wgpu, browser-shaped)

`nv-ocr-web/src/train/e4b/` is the E4B twin of the dots.ocr browser trainer in
[6.11](06.11-ocr-browser.md): an explicit forward and backward schedule over
the `nv-kernels` qlora WGSL set, no autograd, f32 activations on the host
between dispatches, fp32 LoRA A/B on a top-`grad_layers` window, a
candle-semantics AdamW, and the same PEFT pair `E4bLora::from_peft_dir` loads
onto the serving graph. What it replays
(`E4B_SCHEDULE_REPLAYS_THE_SERVING_LAYER_ALGEBRA_WITH_THREE_RESIDUAL_BRANCHES`)
is `gemma4_e4b_wgpu::emit_layer` at m>1: pre-norm, separate q/k/v projections,
per-head q/k/v RMSNorms (v with a unit weight), NeoX rope with each layer
type's theta and partial angle count, grouped attention at scale 1.0 with the
512-token window on sliding layers, post-norms on every branch, GeGLU with the
tanh-argument clamp every serving fold uses, the per-layer-input gate and
projection as a third residual branch, and the per-layer scalar on the way
out; the head is the tied embed table under `final_logit_softcapping`, which
the CE kernel applies through `W4Head.softcap`.

The base it trains against is the bf16 `google/gemma-4-E4B-it` text tower
quantized at load into mlx affine u4 gs64 through `nv_quant::mlx_affine`
(`E4B_TRAINER_QUANTIZES_THE_BF16_TEXT_TOWER_TO_MLX_AFFINE_U4_GS64_AT_LOAD...`),
every projection and the head alike; norms, layer scalars and the per-layer
embedding rows stay f32. The per-layer input rows are token constants (embed,
projection, projection norm and the per-layer table are all frozen), so they
are computed once per sample and ride the bucket as an aux channel with no
gradient. KV sharing is honoured as in serving: layers past `first_kv_shared`
take the rope'd k and normed v of their source layer from a stash filled while
the frozen prefix streams through, and the backward of such a layer drops its
dK/dV, which is exact only while the source is frozen -- so the window must
not contain a kv source
(`E4B_WINDOW_LAYERS_MUST_NOT_OWN_A_KV_SOURCE_BECAUSE_DK_DV_OF_A_SHARED_LAYER_ARE_DROPPED`;
at the default `grad_layers 8` the window is layers 34..41, all shared from
layers 22 and 23).

The suite covering the route is `nv-ocr-web/tests/e4b_train_gate.rs`
(`NV_E4B_TRAIN_TEST=1`, `NV_E4B_DIR` or the hub snapshot, `NV_E4B_TRAIN_STEPS`,
default 6): six chat turns tokenized through the snapshot's `tokenizer.json`
with the model turn as the completion, six steps at rank 16 over the top 8
layers, asserting finite descending losses, a bitwise-identical second
repetition, and that the written adapter loads on the serving graph with no
skipped module and eight LoRA passes per window layer. Run it through
`NVK_LANE=<lane> NVK_PKG=nv-ocr-web NVK_FEATURES=browser rust/scripts/nvk.sh
test --test e4b_train_gate -- --ignored --nocapture`. On an RTX PRO
6000 (wgpu Vulkan, NVIDIA 590.48.01) against the pinned bf16 snapshot the
gate prints losses 1.764540, 1.328894, 0.880882, 0.543328, 0.332288, 0.177595
at about 7 s a step, both repetitions bit-identical, a 12.5 MB adapter over 40
modules (q, o, gate, up, down on layers 34..41; k and v have no projection on
kv-shared layers) that the serving graph loads with 64 passes, and 4.1 GiB of
device memory at peak. Like the dots arm it is an opt-in, test-gated route
until a corpus instrument blesses it; the `nvk-train` route below stays the
default trainer.

### The browser split

The tab never sees the bf16 tower (12 GB, with a 5.6 GB per-layer embedding
table). `nvk-e4b-window-dump` (an `nv-ocr-web` example under the `browser`
feature) runs the frozen prefix natively once per sample at batch one and
writes what the window consumes
(`WINDOW_DUMP_IS_THE_E4B_TWIN_OF_THE_DOTS_VISION_DUMP`): one safetensors per
row holding `ids`, `completion_start`, `window_start`, the hidden state `h`
at `window_start`, the window layers' per-layer input rows `aux`, and the
grouped k/v of every kv source a window layer reads (`kv.22.k`, `kv.22.v`,
`kv.23.*` at the default window), about 1.4 MB per chat turn. Beside them it
writes two shards, `e4b-window-layers.safetensors` (466 MB: the nine window
projections per layer as the host quantizer's exact u32 words and f32
scales/biases, plus f32 norms and layer scalars, plus the final norm) and
`e4b-window-head.safetensors` (419 MB: the quantized tied embed table), a copy
of `config.json`, an `index.jsonl` and `e4b-window.json`
(`WINDOW_SHARDS_CARRY_THE_HOST_QUANTIZER_OUTPUT_VERBATIM_SO_THE_TAB_TRAINS_THE_SAME_W4`).
Rows are `{user, model}` JSONL, assembled as Gemma chat turns with the model
turn as the completion. The tab pushes the config and the two shards through
`train_weights_push`, hands each sample file to `e4b_sample_stage`, and runs
`e4b_train`; the adapter lands where `train_adapter_safetensors` reads it
(`E4B_TRAIN_SHARES_THE_TRAINER_STAGE_AND_ADAPTER_SLOTS_WITH_THE_DOTS_ARM`).
Inside, `run_e4b_window_qlora` packs the samples into the same length-sorted
buckets the native schedule packs, zero-pads each sample's k/v into the
bucket's grouped layout
(`WINDOW_SAMPLE_KV_IS_GROUPED_AT_BATCH_ONE_AND_ZERO_PADDED_INTO_THE_BUCKET`),
loads the window from the shards with no quantizer, and enters the step loop
(`train_window`) the full schedule uses.

The suite covering the split is `nv-ocr-web/tests/e4b_window_gate.rs`
(`NV_E4B_WINDOW_TEST=1`, `NV_E4B_DIR`, optional `NV_E4B_WINDOW_OUT` to keep
the dump for a browser run): it runs the full schedule, dumps the same six
turns, round-trips the shards and sample files through bytes, and asserts the
window run tracks the full run's losses; on the RTX PRO 6000 the window run is bitwise
the full run (the batch-one prefix and the packed-bucket prefix agree bit for
bit) and takes 47 s against the full run's 333 s, the dump itself 327 s (two
tower quantizations dominate). In Chromium under Xvfb (`Q38WEB_ARMS=e4b`,
work dir holding `web/` and `e4b-dump/`), the arm stages 885 MB of shards and
8.6 MB of samples in 0.7 s from the local server and prints
`E4B-QLORA-TRAINS`: 1.764540, 1.328896, 0.880882, 0.543328, 0.332288,
0.177595 at about 6.5 s a step, within 2e-6 of the native losses (Dawn's
WGSL compile, not the schedule, accounts for the last digit), the same
12.5 MB adapter over 40 modules.

## 1. unsloth / HuggingFace-PEFT route

Train on your own GPU with the stock ecosystem and drop the adapter directory in here;
no PyTorch is needed on the serving host, and nothing about the recipe is
repo-specific: stock unsloth `FastLanguageModel.get_peft_model(model, r=8,
lora_alpha=16, lora_dropout=0.0, bias="none", use_rslora=False, use_dora=False,
target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"])`
over any Gemma-3/4 text checkpoint, your own SFTTrainer/TRL loop, then
`model.save_pretrained("my-lora")`; plain HuggingFace PEFT (`LoraConfig(...)` +
`get_peft_model` + `save_pretrained`) is byte-compatible. rsLoRA is supported.
**DoRA is not** — `use_dora=True` saves `lora_magnitude_vector` tensors, which the
loader detects and fails on clearly rather than silently mis-loading.

Copy `my-lora/` onto the serving host, point the server at it via
`NV_LORA_ADAPTER_DIRS` (comma/colon-separated `name=path` specs; a bare path uses the
directory name as the id), then select it by id in the chat request's `model` field:

```bash
export NV_LORA_ADAPTER_DIRS="my-lora=/srv/adapters/my-lora"
```

The server discovers any directory containing `adapter_config.json` (`oapi/lora.rs`),
validates it, and at model build time calls `E4bLora::from_peft_dir`
(`nv-models/src/gemma4_e4b_wgpu.rs`), which loads through
`nv_weights::lora_adapter::LoraAdapter::load`. `normalize_module_name` maps the stock
text-tower namespace (`base_model.model.model.layers.*`, `model.embed_tokens`) onto the
serving graph's `model.language_model.layers.{i}…` — **a pure rename, no numeric
change**; adapters already in `model.language_model.*` are left byte-identical.
`nv-weights/tests/lora_stock_compat.rs` pins it: a stock-layout fixture loads with
correct `r`/`alpha`/scaling and every module routes to its serving name, the same
weights in either namespace load to bit-identical served tensors
(`NAMESPACE_EQUIV_MAXABS 0.000e0`), our own adapters load unchanged, DoRA fails clearly.

## 2. native route (`nvk-train`, no PyTorch)

```bash
NV_DETERMINISTIC=1 \
NVK_PKG=nv-models NVK_FEATURES= NVK_LANE=loratrain \
  rust/scripts/nvk.sh run --bin nvk-train -- \
    --base   <model.gguf | dir-with-config.json+model.safetensors> \
    --data   data.jsonl \
    --out    my-lora \
    --rank   8 --alpha 16 \
    --target q,k,v,o,gate,up,down \
    --steps  100 --lr 0.05 --seed 7
```

or `rust/scripts/nvk-lora.sh train --base model.gguf --data data.jsonl --out my-lora
--rank 8` for defaults plus a post-train load/route check.

Flags (`nv-models/src/bin/nvk-train.rs`): `--base` a `.gguf` (bf16 dequant) or a
dir with `config.json` + `model.safetensors`; `--data` jsonl, one object per
line, `{"ids":[u32,...]}` | `{"text":"..."}` |
`{"prompt":"...","completion":"..."}`; `--rank` / `--alpha` (alpha defaults to
rank, giving unit scaling); `--target` a subset of `{q,k,v,o,gate,up,down}`;
`--steps` AdamW steps (`0` writes an untrained identity adapter); `--lr`,
`--seed`. `NV_DETERMINISTIC=1` makes the run bit-reproducible. Output is the
same PEFT layout in the `model.language_model.*` namespace, served exactly as in
§1.

`train_runner::run` is the driver: `load_base` -> `build_targets` ->
`LoraTrainable::new` per target -> `Linear::attach_lora(TrainingLoraHook)` -> AdamW
loop -> `serving_equivalence` check -> `save_peft_raw`. `build_targets` is
Gemma4-specific: it splits the fused `qkv_proj` into q/k/v component slices and
`gate_up_proj` into gate/up, naming modules
`model.language_model.layers.{i}.self_attn.q_proj` and so on. **Training requires a
materialised bf16 base weight** and bails with a "needs host dequant" error on a
packed nvfp4 or fp8 base it cannot dequant. `rust/scripts/nvk-lora.sh check
/srv/adapters/my-lora` validates any adapter — it prints `r`, `alpha`, scaling and the
matched module count, and fails clearly on a DoRA adapter or one matching no Gemma4
text projection.

### Memory placement for large CUDA bases

The frozen base is built once and trained against, so its residency matters
independently of the training step. On a **packed-NVFP4 base** packed tensors dequant
to F32 **on the host** and only the final cast tensor moves to the GPU, because a
full-size F32 dequant temporary held on-device roughly doubles the resident footprint
on the 60-layer 31B model and OOMs the load; every other tensor loads straight through
to the training device, and the inner loader keeps the raw packed checkpoint on the
host so it is never co-resident with the dequanted bf16 base on the GPU. A **dense
bf16 base** is held resident on the GPU as **bf16, not F32** — F32 residency for the
full 31B dense model is ~126 GB, so halving it is what makes full-depth training fit
on this box at all; activations still run in F32 through the differentiable candle
matmul fallback, so only the frozen base's storage dtype changes and backward-pass
precision is unaffected. On CPU (`dtype=F32, device=Cpu`) every move is a no-op, so
the CPU path is byte-unchanged and the base stays F32.

### Why a fast kernel must never see a training activation

`nv-layers` builds tensors with `BackpropOp::none()` at eleven sites — seven
hand-written CUDA GEMMs in `linear.rs`, four rope outputs in `rope.rs`. A tensor built
that way is a graph **leaf**: candle does not backprop through it, so **a training
step routed into one contributes no gradient at all — not a wrong gradient, none — and
nothing errors.** The damage is larger than the layer it happens in: with
`y = base(x) + lora(x)` the adapter on *that* layer still trains through its own
branch, so the loss keeps falling and the run looks healthy, but no gradient reaches
`x`, so every adapter in an **earlier** layer is either dead or training on the
gradient of a model whose base is disconnected. A falling loss is therefore not
evidence that any of this is fine, and no existing suite would have gone red.

Two dtype gates keep those sites off the training path, and they point in opposite
directions: `linear.rs` fast paths require **BF16** activations, so a CUDA training
activation of either dtype now takes `Bf16LinearOp` (dx-only backward; the frozen
weight never joins the graph, where `matmul_fallback` retained a transposed
weight copy and a phantom weight gradient per call), while `Rope::apply` dispatches to the
CUDA kernel for **F32** — exactly what training carries, with the trainer escaping
only because `dense_train.rs` calls `apply_candle` directly. **Neither gate is a
coincidence worth relying on, and both invert under an ordinary optimisation**: moving
training activations to BF16 for speed arms all seven linear sites, and rewriting that
one `apply_candle` call to the dispatcher arms both rope sites. So the sites themselves
check `Tensor::track_op()` — candle's own "is this on an autograd graph" — and divert
to the differentiable path when it is true. `track_op()` is false for every inference
tensor, because candle leaves `op` as `None` when no input tracks, so the check costs
inference nothing and the training trajectory is unchanged.

`NV_ALLOW_LEAF_GRADIENT_LOSS=1` restores the superseded behaviour on every one of
those sites, at the cost of the silent zero above. It exists to A/B the diversion and
to unblock anyone who measured on the old path; **it is not a tuning knob, and no
published number is measured with it set.** The suite is
`nv-layers/tests/linear_backprop_leaf.rs`, each row pairing a positive control (a
gradient reaches the input) with a negative control under
`NV_ALLOW_LEAF_GRADIENT_LOSS=1` (the leaf comes back), because without the negative
half the positive half would be green whether or not the diversion existed.

### The trainer runs a second implementation of the model

`dense_train.rs` does not call the forward that serving calls: it calls a parallel
differentiable one at every layer — `forward_candle` for all eight norms,
`apply_candle` for rope, a local `naive_sdpa` in place of flash attention — because
the serving paths are hand-written kernels with no backward. **An adapter is therefore
trained against one model and served against another, and any drift between the twins
lands silently in the weights.** Each twin is held to its serving counterpart within a
budget derived from f32 roundoff over the reduction width (`16 * eps_f32 * sqrt(n)`),
not from the divergence it is bounding; `nv-layers/tests/train_serve_skew.rs` covers
the norm and rope pairs in both F32 and BF16, and both rows fail on a 0.01%
perturbation to either side. **The pairs must be compared on untracked inputs** — a
tensor on an autograd graph diverts the serving path to the candle one, which would
compare `forward_candle` against itself and pass unconditionally, so both rows assert
`!track_op()`. `naive_sdpa` is held to an independent f64 attention written out by
hand in `nv-models/tests/train_attention_oracle.rs` rather than to flash attention,
proving the trainer's attention *correct* without depending on the serving kernel
being reachable from a test: its rows cover the causal case, a sliding window and a
key run longer than the query run, fail on a 0.1% scale perturbation or a wrong GQA
head map, and carry negative controls asserting that the window changes the answer,
that not all query heads produce the same output, and that the oracle never softmaxes
a row attending to nothing.

**A forward oracle cannot see a missing backward, so the same suite pins the
gradient.** The attention softmax is the twelfth leaf site and the one the list above
does not reach: `candle_nn::ops::softmax_last_dim` is `apply_op1_no_bwd`, so its
probabilities carry `BackpropOp::none` and **q and k get no gradient entry at all
while v still trains** through the `probs @ v` matmul that follows — and since
`train_runner` emits `self_attn.q_proj` and `self_attn.k_proj` as *default* targets
and their `B` is zero-initialised, `AdamW::step` skips them in silence and they merge
as an exact no-op with the loss falling the whole run. `naive_sdpa` therefore scores
through `nv_layers::attn::softmax_last_dim_that_keeps_q_and_k_on_the_graph`, which
takes the composed tracked softmax only when `track_op()` is true and leaves serving
on the identical fused call. **The MoE arm carries the same two pins, and a thirteenth site the dense arm does not
have.** `gemma4_moe`'s own private `naive_sdpa` scores through the same helper, and its
oracle is a separate one because that function applies **no attention scale** where
`dense_train`'s does — a named constant records that so the difference is not read as a
bug and "fixed". Its KV cache round-trip is the thirteenth leaf: `Gemma4KvCache::write_at`
stores this step's keys and values with an in-place `Tensor::slice_set`, which copies
bytes into a buffer that is not a `Var` and returns `()`, so `cache.view` hands back a
narrow of that buffer and **k and v reach the loss through nothing** while q still trains
its own way into the scores — the exact inverse of the softmax leaf, and invisible to a
gradient oracle that only probes the attention function. `gemma4_moe` therefore splices
this step's live keys and values over the tail of the view before scoring, which changes
provenance and not a byte. **An optimisation that swaps a functional op for an in-place
one severs autograd silently**, which is why the artifact row below exists.

**The row that catches what an oracle cannot: read the adapter back.**
`train_moe_adapter_artifact.rs` and `train_batched_forward.rs` drive `train_runner::run`
end to end with `TrainArgs::default_targets()`, then open the written
`adapter_model.safetensors` and require every `lora_B` to be off zero. That row, not the
gradient oracle, is what found the KV leaf — after the softmax fix q trained and k and v
were still exactly zero. Under `NV_ALLOW_LEAF_GRADIENT_LOSS=1` the same rows go red
naming the dead modules **while the loss still falls**, which is the property being
guarded.

`train_attention_oracle.rs` pins that backward against an
**independent f64 central difference of the independent f64 attention**, every element
of q, k and v probed, on a budget of `512 * eps_f32` derived from the op's f32 cast
rather than from the values it bounds; a row feeding the same central difference the
Jacobian that forgets to subtract the probability-weighted mean (`p * dy` instead of
`p * (dy - sum(p * dy))`) must miss by orders of magnitude, or the gradient rows are
not gates. Under `NV_ALLOW_LEAF_GRADIENT_LOSS=1` the leaf comes back and those rows
fail at "received no gradient entry at all" — that negative half is what makes the
positive half mean something.

**Queries carry the cache offset; keys are absolute.** With `stored` keys and
`seq` queries, query `i` sits at position `stored - seq + i` and key `j` at
position `j`. Spelling it the other way round — offsetting the keys and leaving
queries at `0..seq` — puts every query before every key, so for `stored > seq`
the first query row attends to nothing and its softmax runs over an all-`-inf`
row, giving NaN rather than a wrong number. Training feeds `stored == seq`,
which makes the offset zero and the two spellings identical, **so nothing
catches this until a KV cache reaches the trainer.**
