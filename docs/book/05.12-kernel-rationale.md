# Kernel rationale: the constraints the CUDA and WGSL sources cannot state

The tree carries no comments, so the design constraints behind `nv-kernels`
live here: the layout invariants a kernel depends on, the launch shapes it
refuses, and the structural facts that decided one arm over another. Everything
below is a property of the code as it stands; each rule names the symbol it
governs, never a line number.

Figures appear only where they are the *basis* of a rule — the ratio that makes
a trade land one way rather than the other. They are not a scoreboard: a
quotable performance number comes from a `perf/runs.jsonl` row with its
`run_id`, under the rules in `08.4-PERFORMANCE.md`.

---

## 1. Grid-axis guards

### 1.1 The refusal code is deliberately not the driver's

`include/nvk_grid.cuh` defines `NVK_MAX_GRID_X` (2147483647),
`NVK_MAX_GRID_Y` and `NVK_MAX_GRID_Z` (65535 each), and `NVK_ERR_GRID_AXIS`
(-9).

`NVK_ERR_GRID_AXIS` is **not** `cudaErrorInvalidConfiguration`. A guard that
returns the driver's own code makes "the launcher refused before touching the
device" indistinguishable from "the driver rejected the launch" — which is the
entire provenance the guard exists to provide. It also makes the refusal
untestable: a test asserting 9 passes just as happily with the guard deleted,
because the unguarded launch returns 9 too. The guards are negative-controlled
for exactly that reason (`guard_refusal_conv`, `guard_refusal_gemv`,
`guard_refusal_lora`, `guard_refusal_verify`).

The value is negative so it cannot collide with a `cudaError_t`. Launchers in
this crate already return -1/-2 for argument validation.

### 1.2 The axis rule

A **sequence length rides x**, whose limit is 2^31-1. Only small enumerations —
KV head count, fused-slice count, active-adapter count, spec-decode tree width,
batch — ride y or z, whose limit is 65535 each.

The rule is not stylistic. Putting a sequence length on y capped
`dequantize_kv_fp8_paged_kernel` at 65535 tokens on a stack whose
`max_position_embeddings` is 262144: a 160k prefill died with
`cudaErrorInvalidConfiguration` (rc=9) at position 64512, because the next
`VERIFY_PREFILL_CHUNK`=1024 chunk made the length 65536 — exactly one over.
`n_kv` is 4 (full) or 16 (sliding) and fits y trivially.
`kv_fp8_paged_long_context` is the suite that holds this.

An over-limit launch surfaces as `cudaErrorInvalidConfiguration` with no hint
which axis or which caller produced it, which is why every launcher whose grid
takes a caller-supplied extent on y or z refuses deterministically instead.

### 1.3 What each launcher guards

| launcher | guarded quantity | axis | status |
|---|---|---|---|
| `nv_kernels_depthwise_conv1d_silu_bf16` | `C`, the conv channel count | y | unreported |
| `nv_kernels_depthwise_conv1d_silu_bf16` | `tile_count`, the post-tiling count | z | unreported |
| `nv_kernels_dflash_accept_f32` | `m`, spec-decode draft width | y | never fired |
| `nvk_launch_gemv_bf16` | `grid.y`, `grid.z` of a caller-built `dim3` | y, z | never fired |
| `nv_kernels_argmax_f32_rows` | `rows`, spec-decode draft width | y | never fired |
| `quantize_kv_fp8_paged_kernel` | `n_tokens` on x, `kv_head` on y | y | never fired |
| `nv_kernels_dequantize_kv_fp8_paged` | `len` on x, `n_kv` on y | y | fired (§1.2) |
| `nv_kernels_derive_v_from_k_fp8_paged` | `n_kv` | y | never fired |
| `nv_kernels_lora_fused` | `n_slices`, `grid_loras` | y, z | never fired |
| `nv_kernels_lora_shrink` | `n_slices`, `grid_loras` | y, z | never fired |
| `nv_kernels_lora_expand` | `n_slices`, `grid_loras` | y, z | never fired |
| `nv_kernels_moe_gemv_swiglu_bf16_m1` | `k`, top-k routing width | y | never fired |
| `nv_kernels_moe_gemv_swiglu_bf16_mb` | `k`, `b` | y, z | never fired |
| `nv_kernels_moe_gemv_down_tail_bf16_mb` | `b`, batch | z | never fired |
| `nv_kernels_moe_grouped_fp4_gemv_m1_bf16` | `num_groups` | y | never fired |
| `nv_kernels_tree_verify_attn_bf16` | `K`, spec-decode tree width | y | never fired |
| `nv_kernels_tree_verify_attn_fp8` | `K` | y | never fired |
| `nv_kernels_kv_append_fp8` | `K` (a separate declaration) | y | never fired |
| `nv_kernels_verify_qkv_prep` | `K` | y | never fired |

"Never fired" is a statement about today's callers, not a bound; "unreported"
means no site has recorded either way.
`quantize_kv_fp8_paged_kernel` is the clearest case: its `n_tokens` is a
prefill **chunk** today (`VERIFY_PREFILL_CHUNK` = 1024), so it carries the
identical latent 65535 ceiling that §1.2 describes and would go live the moment
a caller passes an unchunked length. `n_slices` is
the count of fused weight slices (q/k/v/o/gate/up/down) and is <=8 by
convention; `grid_loras` is the count of active adapters in the batch;
spec-decode tree width is <=1024 by convention. Convention is not a bound,
which is what the guard is for.

### 1.4 Four guards that are not the boilerplate

**`nv_kernels_depthwise_conv1d_silu_bf16` guards `tile_count`, not `T`.**
`T` is tiled by `tile_t` before it reaches the grid, so the 65535 limit binds
the post-tiling count. Guarding raw `T` would refuse legitimate long contexts —
`max_position_embeddings`=262144 tiles down to well under the limit — while
missing nothing that would actually violate the CUDA grid.

**`nv_kernels_argmax_f32_rows` guards a disagreement.** `rows` rides y in
stage1 while stage2 puts the same `rows` on x. Stage2 has the right shape;
the guard covers stage1 until it does.

**`nvk_launch_gemv_bf16` returns a status rather than skipping.** It is the
sole launch chokepoint for `gemv_bf16_kernel`, and every caller today builds a
1-D grid — but the geometry is the caller's and nothing upstream bounds it.
Skipping the launch silently would leave `y` stale and report success, which is
a worse failure than the invalid launch it replaces. This site is also the one
the guard extractor cannot count: the extractor binds a guard to an axis
through the guarded **declaration**, and the axis here is a component of a
`dim3` parameter, which has no declaration to bind. Local copies named after
the synthetic identifiers are different declarations and do not help. The
hazard is closed in the code regardless.

**`nv_kernels_dflash_accept_f32` guards rather than swaps axes.** Its indexing
uses `gridDim.x` as the partition count, so moving `m` off y would mean
rewriting the kernel; a guard is the proportionate fix.

## 2. `cuda/flash_decode.cu`

### 2.1 `flash_splitk_fused_fp8_gqa_kernel`: one block per KV head

`flash_splitk_fused_fp8` gives one block to each **q** head. Its *requested*
bandwidth pins at 2.9-3.2 TB/s for every GQA group >= 8 at every context
length, while at group 1 it reaches 55-60% of the DRAM floor. The kernel is
bound by cache throughput, and the cause is structural: the eight heads sharing
a KV head each pull that head's whole K and V slab, so the same bytes cross the
cache eight times.

The GQA kernel gives one block to each **KV** head. The group's warps share one
block and one staged copy of K and V, so a position's 1 KB is fetched once
instead of once per head. Warp `w` owns q head `kvh * group + w`.

The price is two `__syncthreads()` per position where the per-warp version had
none, and the loss of the independent per-warp position streams that were
hiding load latency. In the epilogue, the block that was last for a group is
last for *every* head in it, so it finishes all of them rather than one.

### 2.2 `nv_kernels_flash_decode_gqa_fp8kv_paged`: what the launcher enforces

Warp `w` owning q head `kvh * group + w` requires `group == kFlashWarps`
exactly; the launcher rejects any other ratio. Gemma-4's global layers are 32 q
over 4 kv, which is 8.

One block per KV head also makes the split count the **only** source of
parallelism: 4 KV heads needs far more splits than the per-q-head kernel to
fill the machine.

### 2.3 `flash_splitk_fused_fp8_derivev_kernel`: V reconstructed, not read

On Gemma-4's full layers the checkpoint shares K and V, so
`V = conj_rope(K) / w_k` and the V slab is a duplicate — 5.04 GiB at 262144
context, and half the bytes the accumulate loop reads.

Two layout facts make the reconstruction register-only:

1. K arrives as `kcur[c]` covering dims `128c + 4*lane + i`, so with
   `half = HD/2` the RoPE partner of chunk `c` is chunk `c + nck/2`
   **in the same lane**.
2. The accumulator layout is a local choice — the epilogue reduces out of
   `sacc[warp][d]` — so `acc` is indexed in K's strided layout here rather
   than the contiguous layout the read-V path uses.

**The angle comes from `inv_freq`, not from the cos/sin tables.** A table row
is 2048 B per position against the 512 B of V saved, which makes the table a
net loss. `inv_freq` is position-independent.

**The product is formed in double.** At full context `p * inv_freq[j]` reaches
~2.6e5 radians, where f32 has no absolute precision left: the error is 1.093x
against 1.075x at position 262143 and identical at position 0, so f32 looks
fine until it is not.

**`HD` is a template parameter** so `nck`/`nlo` are compile-time. Under a
runtime bound the unroll breaks, the per-lane K values land in **local**
memory, and the kernel loses 15x of its bandwidth to spill traffic rather than
to any of the arithmetic it is trading for.

**Every load is issued before any is consumed.** Fusing the load and the decode
into one loop serialises four dependent load-use pairs and costs more than all
the arithmetic this kernel adds.

**The RoPE angles are computed once per position, outside the accumulate loop,
and only for chunk 0.** ptxas predicates a short `if` rather than branching, so
a double multiply and an `__sincosf` sitting inside the 8-iteration inner loop
**execute** on every lane whatever the guard says: 82 us with `rope_angles`=64
and 82 us with `rope_angles`=0, against 16.5 us with the same code deleted.
Only chunk 0 can carry a rotated dim while `rope_angles` <= 128, since chunk
`c` starts at dim `128c`; the launcher enforces the bound.

**The optional cos/sin table is packed**, `rope_angles` wide rather than
`head_dim/2`. At 64 angles that is 512 B per position — exactly the V bytes
this kernel stops reading — and unlike V it is one array shared by every q-head
block, so it leaves DRAM once per position and hits L2 for the rest.

**The gain is applied as a reciprocal multiply, not a divide.** A double
division in this loop costs more than every other operation in it.

### 2.4 `nv_kernels_flash_decode_derivev_fp8kv_paged`: what the launcher enforces

The reconstruction pairs chunk `c` with chunk `c + nck/2`, which is the RoPE
partner only when `HD` splits into an even number of 128-dim chunks; the
launcher admits `HD` = 512 alone, which is four such chunks. The packed-table
path reads four angles per lane as one `float4`, so `rope_angles` must be a
multiple of 4 and both packed tables must be present together.

## 3. `cuda/kv_fp8_paged.cu`

### 3.1 Where the read path gets `(cos, sin)`

`kAngleTable` reuses the entries the forward pass used, so the table's angle
error cancels exactly — but the tables cost 4x the bandwidth they save.
`kAngleF32` and `kAngleF64` recompute from `inv_freq`, which is free, and
differ only in how `p * inv_freq[j]` is formed: f32 loses absolute precision at
deep positions because the product reaches ~2.6e5 radians.

Passing the `[max_seq, half]` tables costs `2*half*4` = 2048 B per position
against the 512 B of V it saves. The only affordable source is `inv_freq`,
position-independent and therefore read once, at the cost of the table's exact
cancellation.

### 3.2 `derive_v_from_k_fp8_paged_kernel`: why V is derivable

Gemma-4's full-attention layers set `attention_k_eq_v`, so V is not a separate
projection: both norms see the same raw tensor, `v_norm` carries weight 1 while
`k_norm` carries a scalar, and only K is rotated. So
`V = conj_rope(K) * (1 / w_k)`, and the cache is storing a value it could
recompute.

Positions index the same cos/sin table the forward pass used — reusing the
stored entry with `sin` negated, **not** asking for a negative position — which
is why the table's angle error cancels instead of accumulating. The proof is
`rocq` `RoPE.v`, `round_trip_error_is_the_gain_defect`.

## 4. `include/nvk_smem_optin.cuh`

`cudaFuncSetAttribute(cudaFuncAttributeMaxDynamicSharedMemorySize)` is
**process-wide per kernel function** — not per launch, not per stream. The
natural "compute smem for this shape, set the attribute, launch" sequence is
therefore a race between any two host threads launching the same kernel at
different shapes: whoever calls last wins, and a launch asking for more than
the attribute currently holds is rejected with `cudaErrorInvalidValue`.

The failure rate on `gemv_bf16`'s site before the fix was 3 in 40 fresh
processes of `parity_gemv_bf16_i8`, and 25/25 clean after. Serving is where it
bites rather than the suite: two decode threads with different row counts on
one kernel is exactly the interleaving.

`raise_dynamic_smem_optin_never_lowering_it` is therefore **monotonic** — only
ever raise, never lower — so a smaller concurrent shape cannot pull the
attribute out from under a larger one already in flight. A launch may always
ask for less than the granted maximum.

`nvk_max_dynamic_smem_optin` uses a function-local static with a lambda
initializer, so the device query runs exactly once even under concurrent first
callers. `static int x = -1; if (x < 0) {...}` is the racy spelling it
replaces: two threads both see -1, both run the query, and one can publish 0
from a transient failure.

## 5. WGSL kernels

### 5.1 `wgsl/q3m_attn.wgsl`

**Bindings are concatenated to fit the guaranteed budget.** `cos` and `sin`
ride one buffer and `q_norm` and `k_norm` ride another, because the merged q+k
entry point is one binding short of the 8 a storage-buffer bind group is
guaranteed. Both are plain concatenations, so every element the kernel reads is
the same word it read from the split pair.

**`ar_norm_rope` is the row's arithmetic only**, with loads and stores left to
the caller, so an entry point only ever names the bindings it actually touches.

**`q3w_attn_norm_rope_f32` emits the bf16 round trip inline.** Flash decode
wants q in f32; the separate cast pass read back exactly the bf16 word this
kernel had just packed, so doing the same round trip here is bit-identical and
one dispatch shorter.

**`q3w_attn_norm_rope_qk` appends k's heads to q's grid.** q and k differ only
in which buffer a row comes from and which norm weights it uses, and a
workgroup owns exactly one row — so the merged grid retires a whole dispatch
without changing any row's arithmetic.

### 5.2 `wgsl/q3m_delta.wgsl`

`q3w_delta_recurrent` is the serial reference. The other entry points are
bit-exact twins of it; `delta_parity` in
`nv-models/tests/qwen3_5_moe_wgpu.rs` is the pin, and
`qwen3_5_moe_delta_split.rs` covers the split variants.

**`q3w_delta_recurrent_u4` is not a spill fix.** The serial kernel has no
function-space array to spill — the generated MSL holds only scalars in the
thread address space, with `dr_kb`/`dr_qb` in `threadgroup`. What the MSL does
show is two other things:

1. The decay pass **stores** `dr_state[p]` and the update pass loads it back.
   naga cannot disambiguate the store at iteration `i` from the load at `i+1`
   on the same `read_write` buffer, so all 256 iterations become dependent
   memory round-trips. The stored value is exactly `dr_state[p] * ge`, so
   recomputing it in the update pass drops one full write pass over the state
   (4 -> 3 passes, -25% traffic) **and** turns the decay loop into a store-free
   load loop the compiler can pipeline.
2. naga emits `force_loop_bounding` — a `uint2` decrement plus an `all()`
   compare — on **every** iteration of every runtime-bounded loop. A 4-way
   unroll amortises that over 4 real iterations.

Bit-exactness holds because the fma chains for `kv_mem` and `outv` are issued
in the same order, and `dr_state[p] * ge` is a deterministic f32 multiply that
gives the same bits recomputed or reloaded.

**`q3w_delta_recurrent_l32` and `q3w_delta_recurrent_u4l32` are lane splits.**
The recurrence is independent per `(head, lane)`: lane `l` touches only the
column `dr_state[h*dk*dv + i*dv + l]` and `dr_out[h*dv+l]`. Nothing crosses
lanes except the broadcast reads of `dr_k`/`dr_q`, so cutting the lane range
across `workgroup_id.y` changes no arithmetic and no order.

They exist because at the served shape (`n_v`=32) the 128-wide kernels launch
exactly 32 threadgroups onto 76 cores, leaving 58% of the GPU idle for the
whole dispatch. `grid.y` raises the threadgroup count without touching the
thread count.

In the lane-split entries `dr_k`/`dr_q` are read from device rather than staged
in workgroup memory: the address is uniform across the threadgroup, and
dropping the two `var<workgroup>` arrays also drops naga's single-thread
zero-init prologue (1 KiB) and its barrier, neither of which these entries can
amortise over only 32 lanes.

**`q3w_delta_recurrent_u8` is a deeper unroll of the same family.** The 4-wide
twin runs at 204.8 GB/s against a 738.5 GB/s roofline, and the lane-split arm
proves the shortfall is not threadgroup count: 4096 lanes x 4 loads in flight
is ~64 KB, where saturating this memory system wants a few hundred. Unroll
depth is the only knob that adds bytes in flight without changing the order of
either fma chain.

### 5.3 `wgsl/q3m_moe.wgsl`

`q3w_router_topk_tree` is the k-successive-reductions arm and is kept as the
**control** for the rank-counting `q3w_router_topk`, not as a fallback. Both
are bit-identical to
the serial router, so only their cost distinguishes them, and a claim about
that cost needs both arms in the same process. `NV_Q3_WGPU_ROUTER_TOPK=tree`
selects it.

### 5.4 `wgsl/q3m_q8e.wgsl`

`q3w_gemv_i8g_f32` is the same group-scaled dot product as
`q3w_gemv_i8g_experts` but writes f32 at a row offset. `lm_head` needs both:
the head is emitted in row **chunks** because a binding may not exceed
`max_storage_buffer_binding_size`, and the logits that argmax and the KL
instrument read are f32. Rounding logits to bf16 on the way out would lay the
output's own quantization noise on top of the weight noise a flip battery is
trying to measure, so the packed writer is not reusable here. It is single-slot
only — no expert selection, no per-slot x stride — because `lm_head` is one
dense GEMV.

### 5.5 `wgsl/laguna_moe.wgsl`

`lgw_moe_router_topk` reduces max **by value, ties to the lower index**. That
matches the serial scan's strict `>` over ascending `i`, and `ref_route`'s
`.then(a.cmp(b))`.

## 6. The harness the kernel gates run under

### 6.1 `rust/scripts/chainlib.sh`

The chain-runner conventions, written once and sourced by every chain script:

```sh
source chainlib.sh
chain_init "$HOME/tmp/wf/<round>"              # sets CHAIN_LOG + gate dir
gate NAME TIMEOUT_S -- env FOO=1 rust/scripts/nvk.sh test ...   # serialized via gpuq
gate_host NAME TIMEOUT_S -- cargo test ...     # host-only, no GPU lock
gate_expect NAME 'test result: ok'             # assert on the gate's own log
prefetch NAME TIMEOUT_S -- huggingface-cli download ...  # runs OUTSIDE the GPU lock
chain_wait_marker FILE REGEX TIMEOUT_S         # wait on another chain, bounded
chain_summary                                  # table of NAME/RC/DUR, rc!=0 if any gate red
killpat 'ladder_eagle3'                        # kill-by-pattern that can never self-match
```

`gate` forces rc=97 when a zero exit sits alongside a red harness line, because
a green rc with `test result: FAILED` in the log is a chain bug, not a pass.

`killpat` cannot self-match: `pgrep -f` is run by `pgrep`, whose own cmdline
contains the pattern, but `pgrep` excludes itself; the function additionally
drops `$$`, its ancestors, and the sourcing shell, so an agent driving a chain
cannot shoot it.

### 6.2 `rust/scripts/sweep-workspace.sh`

Per-package features are not uniform, and getting them wrong looks exactly like
breakage. `nvk.sh` defaults every `NVK_PKG` to `--features cuda`, and the
packages in `PACKAGES_WITHOUT_A_CUDA_FEATURE` do not declare one, so they fail
with "does not contain this feature: cuda" and a reader counts that many broken
crates that are fine. `THE_ONLY_PACKAGE_THAT_ALSO_NEEDS_WGPU` is the other half
of the asymmetry.

### 6.3 `rust/scripts/batch-engine-ab.sh`

`BA_RINGFP8_ARM=1` runs the default config (ring on) with the paged fp8 decode
kernel serving ring layers, instead of falling back to `gather_layer` plus
dense bf16 flash. `try_decode_attention_fp8` refused every `layer_sliding`
layer, which `from_gemma4_hybrid` sets for 50 of Gemma-4-31B's 60 layers, so
the default path dequantized the sliding window per layer per step. The
physical mapping is already agreed: `write_at` and `view` both index through
`table_for_layer`. The comparison arm is `nospec-batched`, the same config with
the flag off.
