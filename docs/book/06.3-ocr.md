# OCR -- nv-ocr + DeepSeek-OCR-2 + dots.ocr + GOT-OCR2 + LightOnOCR-3

Five independent OCR backends behind one trait boundary (`nv_ocr::OcrBackend`,
`nv_ocr::OcrEngine`), all served by `POST /v1/ocr`. This page is the record for
OCR: architecture, env knobs, measured matrices and limitations. **OCR numbers
should not be quoted from anywhere else**, and every measured value lives in
the private run ledger with its basis. The HTTP request/response surface and the
backend-resolution rules are 06-serving-surface.md.

## Verdict

Against **vLLM 0.26 serving the same DeepSeek-OCR-2 checkpoint under the
canonical recipe**, quality is a win and speed is a loss. Quality is 22 wins /
9 ties / 5 losses of 36 measured cells, and all 5 losses are markup emission or
single characters that vanish under the markup-neutral protocol — **no measured
recognition deficit on any page in any corpus**. dots.ocr is the quality winner
on real captures and the speed loser. Single-page latency and batched throughput
are behind. The isolated decode step beats vLLM's only on the graphed bf16
decode, which CUDA serving does not run: it decodes the NVFP4 decoder eagerly
(DeepSeek-OCR-2 below).

## Architecture

Classical (CPU). `rust/crates/nv-ocr` reimplements the tesseract LSTM
runtime natively: traineddata/unicharset/recoder parsing, a VGSL network-spec
interpreter and float LSTM inference (int8 dequantized at load, AVX-512 VNNI /
AVX2 matvec with runtime dispatch), an arena-based CTC prefix beam search over
recoder codes (no DAWG hook yet), and a classical preprocessing stack: Sauvola
binarization, coarse-to-fine deskew (+/-45° coarse sweep handing off to +/-5°
fine only on a 1.25x score margin), speckle filtering, page-region background
suppression, whitespace-gutter column detection with column-major reading order,
and line/word segmentation. Recognition is line-parallel (`NV_OCR_THREADS`).
Weights are the stock `eng.traineddata` (tessdata_best / tessdata_fast) —
**we run tesseract's own models, so accuracy is tesseract-class by
construction**, verified against the 5.5.2 CLI.

DeepSeek-OCR-2 (GPU). `nv-models/src/deepseek_ocr/`. Vision path:
`preprocess.rs` (dynamic tiling — Gundam nx768x768 tiles plus a 1024 global
view, also Base1024/Base768) -> `sam.rs` (SAM ViT-B window attention) ->
`compressor.rs` (16x token compressor) -> `visual_flow.rs` (Qwen2-style head,
1280-d features). `decoder.rs` is the 3B-MoE decoder (64 experts, top-6,
raw-prob routing without renormalization, unconditional shared expert) with a
bf16 KV cache, the canonical vLLM-recipe ngram suppression as default (windowed
30/90, `<td>`/`</td>` whitelist) and NVFP4 decoder linears on cuda —
weights-only 4-bit quantized from the bf16 checkpoint at load through the same
`Nvfp4Factory` shape as dots (embed, `lm_head`, norms and sub-`MIN_TILE`
projections stay bf16). Non-cuda loads resolve bf16; `NV_OCR_DEEPSEEK_QUANT`
selects `nvfp4`, `w4` or `w8` explicitly, and any other value takes the device
default (`DecoderPrecision::from_quant_env_value`). Mean raw CER over the 16
070/071 fixtures is 0.0286 bf16 vs 0.0288 nvfp4 (gate 0.10), rows
`dsocr2-bf16-baseline` / `dsocr2-nvfp4-arm` / `dsocr2-nvfp4-m1gemv-arm` in
the private run ledger. The cost: NVFP4 decoders cannot use the CUDA graph,
so serving decodes eager at 49.5 tok/s vs 133.8 graphed bf16 on those
fixtures (92.9 tok/s, CER 0.0271, with the opt-in `NV_NVFP4_M1_GEMV=1`
bf16-activation gemv); what it buys is ~3.5x smaller decoder projection
weights. The Verdict's speed cells and the isolated-decode-step-beats-vLLM
claim were measured on the graphed bf16 decode, which serving does not reach:
only `DeepSeekOcr2Pipeline::load(.., DecoderPrecision::Bf16)` from the examples
and benches loads it. `decoder_graph.rs` is that CUDA-graphed decode step —
bf16 only: static KV to ctx 8192, device-side MoE routing plus indexed grouped
expert GEMV, plus the slot-batched routed-expert gemv (bit-identical to
sequential launches). `pipeline.rs` owns checkpoint loading, prompt assembly and
vision-feature scatter into `<image>` placeholder runs.

Repetition-loop detection. `decoder.rs::detect_loop` scores a trailing
256-token window every `LOOP_CHECK_STRIDE` (64) tokens on a dominant period
p <= 64 (>= 70% of positions matching `seq[i] == seq[i-p]`) or 8-gram diversity
<= 0.45, firing after 2 periodic or 3 low-diversity hits and backtracking to the
onset. Output is truncated and, for free-OCR prompts, one grounding-markdown
retry runs, kept only if it yields strictly more loop-free tokens.
**Truncation alone is a wash under NED — the
retry is the lever**; the clean 071 corpus is byte-identical with the detector
on. All three decode paths run the check mid-decode, so a loop costs ~64 wasted
tokens rather than the whole budget.

dots.ocr (GPU). `nv-models/src/dots_ocr/` — 1.7B: a 42-layer NaViT-style
vision tower plus a stock Qwen2 decoder with qkv bias and no q/k norm (the
mirror image of `qwen3.rs`) and an untied `lm_head`. Unlike DeepSeek-OCR-2 it is
a layout model. Decoder linears (q/k/v/o + MLP; embed and `lm_head` stay
bf16) load as NVFP4 weights-only 4-bit under `NV_DOTS_DEC_PRECISION=nvfp4`
(cuda only, same `Nvfp4Factory` shape as deepseek). The default stays bf16
because nvfp4 fails the quality bound: mean raw CER over the 16
070/071 fixtures is 0.0736 bf16 vs 0.1913 nvfp4 (gate 0.10), with catastrophic runaway generations on
two fixtures, and it is also slower at batch-1 (nvfp4 m=1 pads GEMM to the
128-row tile; `NV_NVFP4_M1_GEMV=1` is the untried lever). Rows for both arms
are in the private run ledger (`dots-bf16-baseline`, `dots-nvfp4-arm`). The default
prompt asks for a JSON array of
`{bbox, category, text}` elements in reading order, parsed by a tolerant
`parse.rs` that falls back to raw text when the JSON is invalid, with
`LayoutAll` / `LayoutOnly` / `PlainOcr` prompt modes. `preprocess.rs` is NaViT
dynamic resolution under the Qwen2-VL processor contract (`patch_size` 14,
`merge_size` 2, CLIP mean/std, `smart_resize` to a multiple of 28 under a pixel
budget) with no tiling and no global view, so **vision-token count tracks page
area** — 3615 tokens on a 1400x1900 fixture but 10764 on a 3840x2160 real
capture.

GOT-OCR-2.0 (GPU). `nv-models/src/got_ocr/` — SAM-B vision plus a Qwen2
decoder, plain and format modes, wired as `backend=got`. On cuda the decoder
linears default to NVFP4 (weights-only 4-bit, quantized on load through the
shared `Nvfp4Factory`; lm_head/embed and the vision tower stay bf16), and
`NV_GOT_DEC_PRECISION=bf16` takes that default too (`got_precision`). The CER
bound holds for both formats — worst-fixture CER 0.0000 bf16 / 0.0266 nvfp4
against the 0.05 bound, at speed parity on the fixture corpus (the private run
ledger `got-bf16-arm` / `got-nvfp4-arm`). Off-cuda stays
bf16/f32 — the nvfp4 gemm is a cuda kernel. CLIs, under
`cargo run -p nv-models --features cuda`: `--example dsocr -- [--markdown]
[--nvfp4] [--base1024|--base768] [--max-new N] <image>...` and
`--example dots_ocr -- [--layout-only|--plain] [--json] [--max-new N]
[--max-pixels N] [--out DIR] <image>...`.

LightOnOCR-3 (wgpu decoder). `src/oapi/ocr_lighton.rs` serves
`lightonai/LightOnOCR-3-0.8B`, a `Qwen3_5ForConditionalGeneration` checkpoint,
with no model code of its own: the Qwen3 vision tower
(`chat_multimodal_qwen3::Qwen3VisionMm`, candle, on the OCR device) emits the
image rows, `Qwen3_5DenseWgpu` prefills them through
`prefill_tokens_with_image_rows` under the M-RoPE rows of
`build_mrope_positions_matching_hf_get_rope_index`, and decode is greedy with
the shared `detect_loop` stop. The page is fit to a 2048 px longest edge (the
model card's render target) before the processor's `smart_resize`. Two
prompts are in distribution and nothing else: the empty prompt transcribes to
markdown (`mode=plain` and `mode=markdown`), and `grounding` prefixes every
block with `![label](x1,y1,x2,y2)` in 0-1000 page units (`mode=layout`,
`mode=layout-only`), which `parse_grounding` rescales to source pixels and
serves as the same `LayoutBox` list dots.ocr returns. Its `text` joins the
blocks that transcribe page text; `image`, `header_image` and `footer_image`
blocks carry a description of the picture and stay in the layout only. The
backend needs the `wgpu` feature; a build without it logs the refusal and
leaves the backend absent.

On Apple GPUs the bf16 checkpoint prefills on the 16-row bf16 gemm: the 8x8
coop tile carries only MLX affine projections, so prefill dominates the page.
`NV_OCR_LIGHTON_W4_DIR` names an MLX affine-w4 snapshot of the same checkpoint
(`prithivMLmods/LightOnOCR-3-0.8B-MLX`, `4bit/`); the decoder takes its weights
from there while the vision tower, tokenizer and config stay on
`NV_OCR_LIGHTON_DIR`. That route needs two decoder arms the engine keeps
opt-in for Qwen3.5: `NV_Q3D_AFFINE_CHUNKED_PF_V2_...=1` builds the chunked
prefill graph image rows enter through (without it the load refuses by name),
and `NV_Q3D_PF_COOP_AFFINE=1` moves the affine projections onto the coop tile.
Under both, on an M2 Ultra, prefill drops to roughly a sixth of the bf16 arm
and the 071 and 070 families hold their neutral CER.

## Weight dtype follows device capability, not CUDA

A dots.ocr load picks its tensor dtype from `Device::bf16_default_to_f32()`, so
bf16 on cuda and on Metal, f32 only on CPU. Metal has a bf16 GEMM
(`candle_metal_kernels::GemmDType::BF16`), and testing `is_cuda()` instead
silently costs a Metal run double the weight traffic — which is the whole cost
on a workload that is mostly image prefill. `DotsPrecision` (bf16 / nvfp4) is a
separate axis: it selects the decoder linear format, and resolving to
`Bf16` says nothing about the dtype the tensors are actually carried in. Do not
read one as the other. The invariant is pinned by
`weight_dtype_follows_device_bf16_capability_not_a_cuda_only_test_so_metal_stops_paying_f32`.

Metal serving needs a `--features metal` build and `NV_OCR_DEVICE=metal` (or
`auto`, whose accelerator preference is enforced by
`ocr_device_auto_prefers_an_accelerator_over_cpu`). Without the feature the
device request is refused rather than silently downgraded.

## Input size is the dominant cost, and it is a config knob

For a page model the work is set by the image, not by the answer. A 300-DPI
archival scan at 5642x3761 produces **14,162 vision tokens against ~586
generated**, so the pixel budget — not the hardware — decides the wall clock.
`NV_DOTS_MAX_PIXELS` (default 11,289,600) is the lever, and it moves vision
tokens roughly linearly: 4.0 MP gives 5,046 and 2.0 MP gives 2,501, with
generated tokens flat across all three. Quote a per-page rate only with its
budget named. `dots_ocr_single_page.rs` (`NV_DOTS_PAGE`) reports
`vision_tokens`, `prepare_s` and `recognize_wall_s` separately so a slow page
can be attributed to prefill size rather than to generation; the fixture bench
does not separate them.

Lowering the budget is not free accuracy-wise and is not a quality argument on
its own: the bound that governs is the pinned fixture CER gate, not similarity
to a higher-budget run of our own output.

## wgpu / non-CUDA builds

The classical backend is pure CPU and works on every build. On no-cuda builds
the deepseek backend degrades gracefully: an unloaded backend gives
`503 ocr_backend_not_loaded` naming the env knob; the nvfp4-on-cuda default
resolves to bf16 off cuda, while a forced `NV_OCR_DEEPSEEK_QUANT=nvfp4`
gives a clean load error before touching the checkpoint (nvfp4 is cuda-only);
bf16 loads on candle-CPU (f32 vision), functional but far too slow to serve. The
DSOCR decoder runs on wgpu (`deepseek_ocr/decoder_wgpu.rs`, feature `wgpu`)
over existing nv-kernels WGSL ops with the same host-glue split as CUDA; its
Vulkan gate matches the candle CPU decoder (rel 2.4e-2, argmax identical over 5
greedy steps) and completes a real 12-layer decode step plus chunked lm_head,
but that is a correctness harness, not a serving number, since it re-uploads
weights per dispatch. `NV_DSOCR_WGPU_QUANT=nvfp4` opts the eligible decoder
linears (k a multiple of 16; lm_head/embed stay bf16) into `HostNvfp4Lin`-style
weights-only 4-bit with the shared `gemv_nvfp4` W4A4 kernels, quartering the
per-dispatch weight upload; the default stays bf16 because no real-weight wgpu
CER A/B is recorded and the two arms' one-step argmax on the real checkpoint
disagrees (`real_checkpoint_one_token_forward_on_wgpu`, `NV_DSOCR_WGPU_TEST=1`;
the tiny gate `nvfp4_arm_quantizes_only_block_multiple_k_and_tracks_bf16_logits`
bounds logit cosine against the bf16 arm). DeepSeek-OCR-2's vision tower stays candle-CPU on wgpu builds: 2-D
conv, LayerNorm(2d) and batched masked/bias attention have no WGSL kernels.

**That blocker is specific to DeepSeek-OCR-2 and does not transfer to
dots.ocr.** The dots NaViT tower has a device-resident wgpu port,
`dots_ocr::vision_wgpu::DotsVisionTowerWgpu`, riding the one M-general GEMM in
the tree — `gemm_coop_f16`, whose operands are f16, not bf16; f16 carries
three more mantissa bits than bf16, so against the F32 oracle tied to
`DotsVisionTower::forward_patches` the wgpu route is more accurate than the
CUDA bf16 path that serves today. The coop GEMM qualifies on the runtime-probed
subgroup width (`Capabilities::subgroup_width_known`) and follows the fragment
tile the adapter advertises: the fitted `tm8_tn4_sg4` plan was sized on an
8x8x8 tile at 64 accumulator dwords per lane, and on a 16x16x16-only adapter
(NVIDIA Vulkan) `resolve_plan` halves the plan's wider side until the
accumulator fits the 128-dword register budget instead of refusing the device,
while the `attn_ctx` split-K kernel — generated for the 8-wide tile alone —
yields to the plain coop arm there. So the gate excludes neither Vulkan nor
Metal adapters whose probe reports 32; on the RTX PRO 6000's `coop_mat16x16_f16`
route the tower tracks the candle tower layer by layer on real dots weights at
per-layer max_rel between 8e-5 and 6e-4. What
keeps this a capability rather than a serving path:
`DotsOcrPipeline::load` builds the candle `DotsVisionTower` unconditionally —
the wgpu tower is not wired into the pipeline — and `merger.ln_q`, GELU-erf and
their staging stay on the host (no LayerNorm wgpu kernel, no WGSL erf).

Which half to port is not a matter of taste. Vision prefill is ~96% of a page's
wall clock, so a decoder-only wgpu path accelerates the part that is already
cheap; the DSOCR decoder above is a correctness harness for exactly that reason
and re-uploads weights per dispatch. A serving claim on any wgpu OCR path owes
persistent weight residency, not just a passing parity gate.

## /v1/ocr/stream -- the SSE progress surface

`POST /v1/ocr/stream` (`oapi/ocr_stream.rs`) is `/v1/ocr` for a caller that
wants to watch: same multipart fields (`file`, `backend`, `mode`,
`max_new_tokens`), same backend resolution and `SurfaceGate`, but the response
is `text/event-stream`. Events are JSON `data:` frames typed by `type`:
`phase` (`received` → `queued` when a gate is held → `recognizing` with an
`elapsed_ms` heartbeat every second of a long decode), `meta` (decoded pixel
`width`/`height`, so a client can place boxes before the text exists),
`region` (one dots layout element: `order`, `bbox` in original-image pixels,
`category`, `text`), `delta` (text without geometry — the non-dots backends,
and dots modes that emit no elements), `done` (full text plus
`truncated`/`looped`/`elapsed_ms`), and `error`. The pipeline call underneath
is the same blocking `recognize`, so regions arrive in one burst after decode
— the stream's honesty is in its phases and heartbeats, not token-level
deltas. Anything malformed enough to refuse before work starts (bad field,
missing file, layout mode off dots) is still a plain 400/503, never a 200
stream that dies; failures after the stream opens arrive as an `error` event.
The portal's `/ocr-read` view consumes this surface through its `?intent=ocr`
websocket relay, and feeds corrections back: clicking a region after a read
edits its text, and a changed save appends to the portal's
`ocr-feedback` store — the label source for the dots QLoRA data loop
([6.10](06.10-dots-qlora.md)).

## /v1/ocr as Mistral Document AI -- the JSON surface

`POST /v1/ocr` with `Content-Type: application/json` is Mistral's OCR API
(`oapi/ocr_mistral.rs`); the multipart body on the same path stays the native
surface, and `handle_ocr_json_or_multipart` picks by content type. The shape
followed is `OCRRequest`/`OCRResponse` in Mistral's published OpenAPI spec
(`https://docs.mistral.ai/openapi.yaml`, reference
`https://docs.mistral.ai/api/endpoint/ocr`, guide
`https://docs.mistral.ai/capabilities/document_ai/basic_ocr`), so the official
`mistralai` SDKs and the curl examples work against the server with only the
base URL changed; `Authorization: Bearer` is the same `SPEACHES_API_KEY`
check every route has.

What a request carries and what it means here:

- `model`: `mistral-ocr-latest`, `mistral-ocr-2505` and `mistral-ocr-2503`
  (`MISTRAL_OCR_ALIASES`) resolve through `pick_default_backend` exactly as a
  multipart request without `backend=` does; an engine id (`backend_name`
  such as `dots`, or `engine_model_id` such as `rednote-hilab/dots.ocr`)
  names a backend. Anything else is `400 invalid_model`. `/v1/models` lists
  every loaded engine under task `ocr` plus the aliases, each alias carrying
  the engine it resolves to as `parent` (`model_rows`). The response echoes
  the requested id.
- `document`: `{"type":"image_url","image_url":<url | {"url":..}>}`,
  `{"type":"document_url","document_url":<url>}` or
  `{"type":"file","file_id":<id>}`; a missing `type` is inferred from the
  key present. A URL is a `data:` URL, an `http(s)` URL fetched under
  `NV_OCR_FETCH_MAX_BYTES` (default Mistral's document limit), or a
  `/v1/files/{id}/content` URL on any host, which resolves in-process without
  a round trip. Bytes are sniffed, not trusted by field: `%PDF` renders page
  by page through `pdftoppm` (`NV_OCR_PDFTOPPM` names the binary, `NV_OCR_PDF_DPI`
  the raster density, `NV_OCR_PDF_MAX_PAGES` the ceiling); anything else goes
  through `nv-imgdec` like every other image. No rasterizer on `PATH` is
  `501 ocr_pdf_rasterizer_unavailable`, naming `poppler-utils`; DOCX/PPTX and
  other office formats are `400 ocr_document_undecodable`.
- `pages`: Mistral's grammar (`[0,2]`, `"0,2-4"`, `"0-5"`), zero-indexed,
  applied before rasterization so unselected pages are never rendered; an
  image is page `0` and selecting only other pages yields no pages.
- `include_image_base64`, `image_limit`, `image_min_size`: `images[]` are the
  layout elements the engine labels `Picture` -- dots and lighton emit them,
  deepseek, got and tesseract emit none, so their `images` is always empty.
  Coordinates are integer pixels in the frame the engine read (the
  rasterized page or the decoded image); `image_base64` is a JPEG data URL
  cropped from that frame when asked for, else `null`. The page `markdown`
  references each kept image as `![img-N.jpeg](img-N.jpeg)` in reading order,
  the dots heading prefixes stay, tables are HTML and formulas LaTeX as the
  engine emits them; deepseek and got answer in their markdown mode, tesseract
  in plain text.
- `dimensions`: decoded width and height; `dpi` is the raster density for a
  PDF page and the CSS reference density for an image input, whose bytes carry
  no physical size the server trusts.
- `usage_info`: `pages_processed` counts the pages that ran, `doc_size_bytes`
  the fetched document.
- `bbox_annotation_format` / `document_annotation_format` (`json_schema`
  only, as Mistral states): served through the server's own
  `/v1/chat/completions` with `response_format` when `NV_OCR_ANNOTATION_MODEL`
  names a loaded chat model that accepts `image_url` parts; each kept image
  (Mistral's first-eight cap) is sent as a crop, the document as its joined
  markdown with `document_annotation_prompt`. With the knob unset the request
  is `501 ocr_annotation_unavailable` before any OCR runs. Unknown fields,
  `table_format`, `extract_header`, `extract_footer`, `include_blocks` and
  `confidence_scores_granularity` are accepted and ignored: `tables`,
  `hyperlinks`, `header`, `footer`, `blocks` and confidence scores are not
  emitted.

Errors wear Mistral's envelope,
`{"object":"error","message","type","param":null,"code"}`: request-shape
faults are `422` with `message.detail[{loc,msg,type}]` (code `1000`), an
unknown model `400 invalid_model` (code `1500`), and the backend states the
multipart surface reports (`ocr_backend_not_loaded`, `ocr_backend_load_failed`,
`ocr_backend_ambiguous`) keep their codes in the `code` field. The generative
`SurfaceGate` is held once for the whole document, so a multi-page PDF is one
admission, not one per page.

The files API Mistral clients upload through is the in-memory subset that
closes the SDK's documented flow: `POST /v1/files` (multipart `file`,
`purpose`), `GET /v1/files/{id}`, `GET /v1/files/{id}/url` (the URL points
back at `GET /v1/files/{id}/content` on the request's own `Host`),
`DELETE /v1/files/{id}`. The store is bounded by `NV_OCR_FILES_MAX_BYTES` and
evicts oldest-first; it does not survive a restart and is not a general
object store. The suite covering the surface is `ocr_mistral_route`: the
document forms and pages grammar, every refusal in the envelope, the files
flow, the recorded Mistral response example under `rust/tests/data`, and the
`NV_OCR_MISTRAL_TEST`-gated real-weight dots read of the fixture image and the
two-page PDF.

## The companion frontend

This repo exports the OCR API only; the human correction workspace is the
portal project (`projects/portal`, python, same fleet), deliberately
kept there because it owns the browser session model, the data-dir store
convention, and the dictation stack the editor's voice input rides. The
pairing is two processes:

```sh
NV_OCR_DOTS=1 speaches-plus                            # this repo, the API
PORTAL_UPSTREAM=http://127.0.0.1:8000 \
  PORTAL_OCR_BACKEND=dots \
  PORTAL_DATA_DIR=~/ocr-feedback \
  python portal/server.py                              # the workspace at /ocr-read
```

`PORTAL_UPSTREAM` needs the explicit `http://` for a plaintext upstream.
Without `PORTAL_DATA_DIR` the workspace downgrades to READ-ONLY and says
so; with it, corrections land in `ocr-feedback/feedback.jsonl` and
`scripts/ocr_feedback_to_dump.py` (this repo) turns them into training
rows.

The workspace's Training view closes the loop in-browser: it lists the
engine's models, the trained adapters (named
`YYYY-MM-DD-HH-MM-with-N-pages`), and a page picker (all corrected pages
selected by default) whose Train button drives converter → vision dump →
`/v1/fine_tuning` job, streaming stage, row split (~10% validation
holdout), and final train loss / held-out CE per run; finished adapters
hot-load and unload through `/v1/ocr/load_lora_adapter` from the same
view. Three more portal envs pair it with this repo, and any missing one
degrades the view to a message naming it: `PORTAL_OCR_TRAIN_CONVERT` (the
`ocr_feedback_to_dump.py` invocation), `PORTAL_OCR_TRAIN_DUMP` (the
`nvk-dots-vision-dump` invocation including `--dots-dir`), and
`PORTAL_OCR_TRAIN_BASE` (the mlx 4-bit snapshot the job trains against);
the engine side needs `NV_ALLOW_RUNTIME_LORA_UPDATING=1` for the
load/unload half.

The portal also carries `/ocr-full-wgpu`, the in-browser sibling of this
workspace: the same model, compiled to wasm (`nv-ocr-web`), running the same
wgpu tower and W4 graph decoder on the visitor's own GPU with no engine
process behind it. The portal's role shrinks to model delivery —
`GET /ocr-model` serves a sha256 manifest and immutable file bytes from
`PORTAL_OCR_MODEL_DIR`, landed once in the browser's OPFS — and a service
worker precaches the page and engine so the tab keeps working offline.
Corrections share the `/ocr-read` browser-local store, so pages annotated in
either view meet in one history. Architecture, gates and current execution
limits live in [6.11](06.11-ocr-browser.md).

## Budget and truncation contracts

`max_new_tokens` overrides the per-backend env budget **for one request and
nothing else** — absent or empty leaves `NV_OCR_DEEPSEEK_MAX_NEW` /
`NV_OCR_DOTS_MAX_NEW` / `NV_OCR_GOT_MAX_NEW` in force, so the default token path
is byte-identical to a request that never carried the field, and `0` or an
unparseable value is a 400 rather than a fallback. The ceiling is 131072
because that is the largest decoder `max_position_embeddings` across the
generative backends (dots.ocr): deepseek (8192) and got (32768) already clamp
`prompt + max_new` against their own rope span downstream, while dots sizes its
KV allocation as `prompt_len + max_new_tokens + 1` with no internal clamp — so
the cap bounds dots' allocation without truncating a legal request on the other
two. `/v1/ocr/batch` keeps its own budgets.

Truncation is observable on every response shape. The generative backends
surface their stop reason instead of conflating EOS with the token cap
(deepseek's `GenerateOutcome.hit_eos` on all three decode paths, dots' `hit_eos`
also OR-ed into `page.truncated`, GOT's `hit_eos`), and `/v1/ocr` maps
`truncated = !hit_eos` and `looped` into the JSON bodies and sets
`x-ocr-truncated` / `x-ocr-looped` headers on the text and markdown arms, so a
200 with half a document is distinguishable from a clean finish in every format.
The bs=N emit path propagates tokenizer decode errors as 500s instead of
returning an empty 200.

A backend is serving or it is absent — never registered-and-dead. The bs=N
engine requires the bf16 batch decode graph, so `DsocrScheduler::new` checks
`graph_supported` before routing: an NVFP4 decoder (the cuda default) plus
`NV_OCR_BATCH_SLOTS>1` lands on the single-sequence scheduler decoding NVFP4
eagerly, with the boot line naming why. If the bs=N decode thread ever dies
after that check, the process exits
(`BSN_DECODE_DEATH_EXIT_CODE_BECAUSE_A_DEAD_DECODE_THREAD_500S_FOREVER_BEHIND_A_HEALTHY_BOOT`)
rather than leaving deepseek registered behind a healthy-looking server where
every request 500s in 0.3 s. Downgrades are equally loud: `NV_OCR_DEVICE` auto
resolving to cpu (cuda compiled out or the device failing to open) and the
nvfp4-on-cuda default resolving to bf16 (nv-models/cuda compiled out) each
eprintln what was requested vs what runs — which binary you grabbed must never
silently decide your device or precision.

Confabulation is surfaced, never silently returned. Generative OCR on
hostile input (rotated handwriting) can produce fluent prose in the WRONG SCRIPT
— the archive corpus showed deepseek emitting confident Arabic from Spanish
handwriting, and digit-table floods. The server never blocks output on suspicion
(the caller may genuinely want it), but flags it:
`script=latin|arabic|cjk|cyrillic` declares the caller's prior, a response whose
letters are majority foreign to it carries `x-ocr-suspect: script-mismatch`
(needs >=40 letters for a verdict), and a digit-dominated long output carries
`x-ocr-suspect: digit-flood` with no prior needed, and generative prose from a
near-blank page carries `x-ocr-suspect: blank-page` (basis: the input's luma
histogram — pixels farther than `BLANK_INK_LUMA_DELTA_FROM_THE_MODAL_PAPER_TONE`
from the modal paper tone are ink; under
`BLANK_INK_FRACTION_UNDER_WHICH_A_PAGE_HAS_NOTHING_TO_READ` of them, any output
past the char floor is confabulated — a white 144 Mpx page once drew 913 bytes
about hair extensions from deepseek with a clean 200). Logic and thresholds are
in `oapi/ocr_suspect.rs`, with tests pinning the exact archive failure cases.

## Image ingestion -- one decoder for every surface

Every image entering the server — `/v1/ocr` multipart, chat `image_url`
data-URLs, the PII redaction endpoints, the nv-models bench harnesses — decodes
through `nv-imgdec` (`decode_rgb8` / `decode_oriented`), which owns these rules:

- Containers: png, jpeg (incl. CMYK and progressive), webp, gif (first
  frame), bmp, tiff. Unknown bytes get a 400 naming this list
  (`SUPPORTED_IMAGE_FORMATS`), not a bare decoder error.
- EXIF orientation is applied before any model sees pixels. A portrait phone
  JPEG used to reach the towers sideways, where every backend's output degrades
  to noise; the PII analyze/render pair uses the same oriented frame so
  redaction rectangles stay aligned with OCR coordinates.
- Alpha composites onto white
  (`ALPHA_MATTE_WHITE_KEEPS_TRANSPARENT_DOC_INK_READABLE`): dark text on a
  transparent background reads as ink on paper. The previous `to_rgb8()` path
  matted onto black, which turned such documents unreadable end to end.
- Decompression bombs fail before allocating: dimensions are read from the
  container header and anything over
  `MAX_DECODE_PIXELS_CAPS_RGB8_BUFFER_AT_512MB` (178 MP) is a clean 400, while a
  144 MP flatbed scan still decodes.
- 16-bit, grayscale and palette sources normalize through the same gate; the
  suite is the nv-imgdec unit tests plus the `NV_IMGDEC_CORPUS`-gated
  `corpus_sweep_real_world_files_decode_or_error_cleanly`.

Vision preprocessors bound their output for any input shape. `nv-omni
smart_resize` and `gemma4 target_resolution` re-assert their pixel / patch
budgets after the round-to-factor and short-side clamps: a degenerate aspect
input (a 1x1,000,000 strip) previously escaped the budget through the
`.max(1)`/`.max(unit)` clamps — omni could upscale it to 114 MP and the gemma4
tower could receive 784k patches while the prompt reserved 256 tokens. Now the
long side gives way so the budget holds for every input
(`smart_resize_never_exceeds_the_pixel_budget_even_for_degenerate_aspects` and
the `gemma4_vision_gate` budget assertions). Aspect-ratio legibility at the
extremes is per-backend: dots preserves aspect up to 200:1 and rejects beyond;
got squashes to 1024x1024 (upstream behavior); deepseek tiles up to
`NV_DSOCR_MAX_TILES`.

## Rotation: the caller states it; auto-detection reads the text-line axis

Real phone photos of documents are routinely content-rotated with no EXIF
(WhatsApp strips it), and rotation is the dominant OCR failure on such input: on
a 9-photo handwritten-journal corpus, dots was the only backend recovering text,
deepseek confabulated fluent other-script prose (the worst failure mode —
confident hallucination), got returned junk. `/v1/ocr` therefore takes a
`rotate` field (`cw90`, `180`, `ccw90`; decode -> rotate -> re-encode before any
backend sees pixels), and that is the reliable path today.
`NV_OCR_AUTO_ORIENT=1` enables the content-rotation detector
(`oapi/ocr_orient.rs`), which stays default-off: the axis half holds on real
photos, the 180-flip half does not.

The axis question is answered from layout topology, never from texture.
`detect_content_rotation` asks only whether the text lines run across the page
or down it, and it asks connected components, not pixels: `page_region` trims
the frame to the paper by paper-pixel density, so the dark desk under a
photographed book cannot set the ink threshold; `ink_blobs` isolates ink at
`GLYPH_INK_PERCENTILE_KEEPS_TOUCHING_CURSIVE_LINES_APART`, whose tighter
percentile keeps dense cursive lines from merging into one blob (the 6 %
`PEN_INK_PERCENTILE_EXCLUDES_RULED_GRID_LINES` still drives the polarity pass);
`glyph_neighbour_axis` takes, per glyph-sized blob, the direction to its nearest
neighbour within `NEIGHBOUR_REACH_IN_GLYPH_SPANS` and averages those as doubled
angles, **so the mean is the line axis, invariant to script, pen and which way
up**; and `axis_of` returns with it the fraction of directions within 15 deg of
that mean, which a structureless page scores at 1/6 by construction, making it a
calibrated confidence gated at
`ALIGNED_FLOOR_ADMITS_CURSIVE_AT_0_30_REJECTS_ENGRAVING_TEXTURE_AT_0_13` below
which the detector abstains. `rule_elongation_axis` is the fallback for a page
whose ink is rules rather than glyphs, where elongated blobs vote their own
orientation and only a near-unanimous vote is taken.

Texture statistics cannot answer it, and they all fail the same way. Ink
run-length ratio, projection-profile variance at 512 px and 1280 px, profile
autocorrelation, and structure-tensor gradient orientation over the pen mask all
report "vertical" for an upright printed page (vertical stems dominate)
and for a sideways handwritten one — 9/9 on a corpus whose ground truth is
uniform, 0/64 on upright documents, i.e. a signal that is really a constant.
**Any new axis candidate is measured on both corpora below before it is
believed; one corpus alone cannot tell a detector from a stub.**

| gate | corpus | bar | measured |
|---|---|---|---|
| `orient_corpus_sweep_when_pointed_at_real_photos` (`NV_OCR_ORIENT_CORPUS=<dir>`) | 9 phone photos of handwritten Spanish journals on grid paper, ground truth `ApplyCw90` | >= 8/9 | 9/9, and 36/36 over all four pre-rotations, zero wrong turns |
| `upright_conformance_pages_are_never_given_a_quarter_turn` (always on) | the 16 `070`/`071` fixture pages, all upright | no quarter turn, ever | 0 quarter turns, 15/16 left alone; over four pre-rotations 53/64, of which the axis half is right on 62/64 |
| `upright_page_is_left_alone` + `every_rotation_is_detected_and_undone` | synthetic ruled page | 4/4 | 4/4 via `rule_elongation_axis` |

Both fixture cases the axis half leaves unanswered are the same page, the 1892
sparse engraving, whose blob directions sit at the 1/6 uniform rate — it
abstains rather than guess, which is the designed behaviour and the reason the
floor exists.

The 180-flip half is the weak one, and it is why the detector is off by
default. `looks_left_aligned` compares the spread of first-ink and last-ink
columns, which separates a left-margin page from its upside-down self only when
the right edge is ragged; a centred or justified block gives it nothing. It is
right on all 36 journal cases and 15 of 16 upright fixture pages, and the one it
misses it turns upside down. Raising `POLARITY_MARGIN_KEEPS_CURRENT_ON_TIES`
buys a missed flip in place of a wrong one rather than fixing it — at 1.5 the
journal sweep drops from 36/36 to 33/36 and the fixture sweep does not improve —
so **the next lever is a real up/down cue, ascender/descender mass asymmetry per
line, not a bigger margin.**

## The gemma4 vision tower encode path

Serving always hands the tower a full row-major patch grid, and
`Gemma4VisionTower::forward` detects that shape and takes the full-grid route:
pooling is one reshape/permute/mean instead of an `index_select` + `mean` pair
per pooled cell, and attention takes `nv_layers::attn::flash_attn` (the
event-fenced candle flash wrapper) on CUDA when the tower runs bf16/f16
(`NV_MM_VISION_DTYPE=bf16`). Every other route — f32 towers, CPU, masked
patches, any captured body — uses batched materialized-score attention in f32,
because candle-flash-attn launches on the legacy NULL stream
(`CANDLE_FLASH_ATTN_LAUNCHES_ON_THE_LEGACY_NULL_STREAM_SO_EVERY_CALL_IS_EVENT_FENCED`)
and a legacy launch inside a capture is `CUDA_ERROR_STREAM_CAPTURE_IMPLICIT`.
Rope and the q/k norms stay f32 on every route; the suite is
`full_grid_fast_path_matches_the_irregular_path_on_the_same_patches`.

Because the encode is fixed-shape per resolution bucket it is CUDA-graph
capturable via `NV_VISION_GRAPH=1` (default off), one graph per
`(grid_w, grid_h)` bucket up to
`VISION_GRAPH_BUCKET_CAP_BOUNDS_GRAPH_MEMPOOL_ACROSS_RESOLUTIONS`. **The
captured body is not the eager body**:
`THE_CAPTURED_BODY_ALLOWS_ONLY_LAYOUT_INFO_FREE_OPS` states why every gather,
permute, broadcast, reduce and candle-flash launch must be replaced by matmuls
against plan-precomputed tensors and per-head weight slices before a replay is
sound. That trade buys launch-bound towers a multi-fold win and costs
compute-bound ones outright (the 16-layer E4B tower, whose clipped linears also
pay an f32 clamp round-trip per site), which is why the default stays off.
Capture also requires a bf16/f16 dense tower on a `Device::new_cuda_with_stream`
device; anything else runs eager and says so on stderr. Parity and
replay-freshness are gated by `gemma4_vision_graph_capture` plus the `#[ignore]`
`e4b_real_tower_graph_parity_and_encode_wall` real-weights row behind
`NV_GEMMA4_VISION_REAL_TEST=1`.
`NV_PROF_VISION=1` prints per-forward wall attribution, device-synced between
stages, so it is an attribution tool, not a benchmark; the full-grid route
reports `rope=0` because its rope tensors are built in the plan.

## Measurement protocol and standing results

All GPU runs serialize via `gpu-run.sh` with occupancy idle-gated before and
after. vLLM 0.26 runs under the canonical recipe (ngram 30/90 +
`{128821,128822}` whitelist, temperature 0, `skip_special_tokens=False`,
`enable_prefix_caching=False`, `mm_processor_cache_gb=0`) — **without it vLLM
degenerates and the comparison is worthless**. Numbers live in the private run ledger;
quality arms are `real5/score.py` over the Real5-OmniDocBench sample and the 071
fixtures, speed arms are `ocr-batch-bench` / `ocr-bsn-bench` against a named
pipeline, one process per arm; the speed cells below were measured on the
graphed bf16 decode those benches load, not on the NVFP4 eager decode CUDA
serving runs. Standing shape: quality on the 071 fixtures has
DSOCR-2 and dots exact, classical trailing, vLLM worst, and on real captures
dots.ocr beats vLLM decisively while DSOCR-2 holds a Real5 margin; latency loses
modestly to vLLM per page while the isolated decode step wins and time to first
steady page wins severalfold; throughput at c=20 is a multi-fold loss whose
cause is the decode asymptote plus a front end that cannot keep the batch fed —
not recognition and not decode math.

Measurement rules this page has already paid for:

- Never quote a ratio without naming its corpus and `max_new`. Mixing
  protocols is how the withdrawn multi-fold figures happened.
- **No recorded number may be scaled by a kernel-level ratio to manufacture a
  new one.** Re-run the cell, adding the machine and the commit; a ratio whose
  corpus is named and whose hardware is not is still unquotable. Never measure
  on a contended box or a mid-mutation tree, and never reuse another lane's
  binary — that is the defect class that produced the withdrawn figures.
- **A per-page figure taken from separate processes each paying one-time cost is
  indistinguishable from a per-page cost** — run the second page. And a
  GPU-busy fraction over the whole process span is the wrong denominator for a
  decode-step change; restrict it to the decode window.
- Throughput arms must use 20 distinct pages. Repeating a small page set is
  known not to bias the canonical cell, but it would hide any vLLM feature
  keying on repeats.
- The Apple-silicon DeepSeek-OCR-2 page rates are candle CPU, reproducible
  only with `NV_OCR_DEVICE=cpu` set explicitly. **No `NV_OCR_DEVICE=metal`
  s/page figure exists anywhere** — do not manufacture one by comparison.

Resolution policy (resolved by a powered N=100 falsification study):
base1024 degrades most Real5 pages and no cheap pre-OCR predictor discriminates
safe pages — every candidate AUC lands below router grade given the NED
downside. Default gundam; use base1024 only for known-slide/landscape feeds.
Bucket policy: slot starvation at c=20 is real, but the throughput it buys
costs more mean latency than it is worth — the serial vision front end is the
binding cap, not slots — so the default stays `[1,2,4,8]` and
`NV_DSOCR_BSN_BUCKETS` is the throughput-over-latency knob.

The 4096-token deepseek budget is ample for markdown mode. Grounding
wrappers bill against `NV_OCR_DEEPSEEK_MAX_NEW` at a multiple of raw tokens per
visible token (small pages pay the largest ratio), and over the 070/071 fixtures
no page comes near the cap. A denser page would surface as `x-ocr-truncated: true`, which is the
signal to revisit — not a reason to pre-raise. A caller that hits it raises the
budget for that request with `max_new_tokens`; the env value stays the floor
everyone else gets.

Warm boot. Steady-state DSOCR-2 vision is fast; the seconds-class cost that
used to hit the first request is one-time warmup, paid at boot because
`DeepSeekOcr2Pipeline::load` runs a full `generate_tokens` at
`max_new_tokens: 1` (the CUDA decode graph is captured lazily, so warming only
the tower would leave a residual in first prefill). It is not lazy CUDA
module loading (`CUDA_MODULE_LOADING` LAZY vs EAGER: no effect), and
preprocessing is a small, already-parallelised slice — do not re-blame either.

## Per-backend fast-path knobs

All four backends carry an opt-in env knob that trades nothing or almost nothing
for speed. **With the knob unset every default path is byte-identical to the
pre-knob code.** The corpus is the 16 conformance fixtures (11 `070-ocr-*` +
5 `071-ocr-layout-*`), raw Levenshtein CER under whitespace-squash norm —
not the markup-neutral NED the 071 gate uses, so these do not compare against
the quality cells above. Batch-1, GPU idle-gated, one warmup image discarded,
baseline and fast arm in the same session and binary. Each knob buys a real
page-rate win with CER equal or better.

- `NV_OCR_INT8=1` (classical) quantizes the float tessdata_best model
  per-row to int8 at load and routes the whole forward onto the existing
  `matvec_i8` AVX-512 kernels. It is faster and slightly more accurate than
  float best (deterministic), and far more accurate than native tessdata_fast.
  The dominant `Lstm(ni=96,ns=512)` layer runs multi-fold faster; e2e is capped
  by layout, CTC beam decode, and convolve/PNG costs.
- `NV_DSOCR_FAST_RES=base1024` replaces Gundam tiling with a single 1024
  global view (257 vision tokens). On the fixture corpus it is faster with CER
  improving — but this does not transfer to real captures (see the
  resolution policy above), so the default stays Gundam and base1024 is for
  known-slide/landscape feeds. `base768` is faster still but pushes CER outside
  tolerance: available, not recommended.
- `NV_DOTS_FAST_KV=1` and `NV_GOT_FAST_KV=1` switch decode from the
  accurate-mode `slice_assign` into a full preallocated KV buffer (which
  re-copies O(max_seq_len) per layer per token and feeds flash_attn a
  non-contiguous narrow) to a grow-by-concat cache that copies only the live
  length and hands flash_attn a contiguous view. Output is bit-identical on
  all 16 fixtures; decode dominates GOT per-image time, so the whole kernel win
  lands on the page rate. Same computation, so grow-by-concat is the natural
  future default.

On this corpus: classical CPU int8 is the fastest per page at the cost of the
worst-tier CER; DeepSeek-OCR-2 base1024 is both the fastest GPU option and the
most accurate overall; GOT-OCR-2.0 sits between; dots.ocr is the slowest with
classical-tier raw CER, its 071 losses being reading-order divergence on dense
tabular layouts rather than recognition failure. Negative result that stands:
`NV_SAM_FLASH=1` does not reduce GOT encode time and regresses CER.

## Current limitations

- Long tables and table structure are untested; the OmniDocBench-class signal
  comes from a 100-page Real5 sample, not the fixtures.
- Classical layout resolves multi-column reading order by whitespace gutter
  detection (`layout.rs::detect_column_zones`) but has no table structure. The
  detector is guarded the way `speckle_filter` is: a run of >=6 consecutive line
  bands must share an ink-free gutter, every resulting column must be >=25% of
  the run's text width and >=1.2 median glyph heights of gutter, and each column
  must carry ink in >=60% of the run's bands. **Below that signature the page
  keeps the bit-identical line-major path**, which is what keeps ruled tables
  from being read column-wise. On the 100-page Real5 sample, classical CPU:
  overall NED 0.7395 -> 0.6950, Scanning 0.5654 -> 0.5011, Warping
  0.8045 -> 0.7725, Screen-Photography 0.7042 -> 0.6257, Illumination
  0.7856 -> 0.7387, Skew 0.8376 -> 0.8370; 85/100 pages byte-identical, 15
  changed, none regressed. Real captures stay degraded relative to clean
  scans — use DeepSeek-OCR-2 or dots.ocr for photographs.
- Inverted pages (light ink on dark) rest on an area heuristic in `ink_is_dark`
  that mislabels 6/100 Real5 pages; correcting the threshold measured neutral,
  so it stands. **Two replacement estimators are falsified, not merely
  untried.** Erosion survival (ink as the class that vanishes under a box
  erosion) labels the dark class `survival ~ 0.85-0.96` and the light class
  `~ 0.54-0.84` on ordinary dark-on-light pages, i.e. backwards, because
  text strokes punch holes in the paper class and depress its survival more
  than the strokes' own thinness depresses theirs. Local-sign minority (ink as
  the minority sign of the deviation from a box-blurred local background, radius
  `min(w,h)/150`, δ=16, consulted only when the area rule already says "light
  ink") is a wash-to-loss: Real5 overall NED 0.6950 -> 0.6959, median
  0.7315 -> 0.7318, both worse, flipping the same page set the falsified 0.80
  area threshold did. **Do not retry area-threshold tuning and do not retry
  local-sign polarity.** A future attempt needs a signal separating a dark
  border around light text from light text on a dark slide; every measure
  tried so far scores those within 0.01 of each other.
- No numerical parity claim vs vLLM for DeepSeek-OCR-2: greedy outputs match
  exactly on 7/19 page-runs. Against the HF reference it is much stronger —
  4/5 byte-identical greedy streams on the 071 pages (the fifth differs only in
  whitespace padding inside a table cell), vision tower to ~1e-4 in fp32. Where
  we differ from vLLM on 071 it is vLLM diverging from the reference, on a
  token-identical prompt.
- Greedy tokens are path- and process-sensitive at ulp level (legacy vs
  kernel-path decode differ on 2/5 pages; one binary produced 211 vs 210 tokens
  across two processes). CERs are unaffected and graphed==eager holds.
- Grounding-mode box coordinates are emitted but unvalidated (the upstream
  reference rendering is itself buggy — compare raw `<|det|>` tokens only).
- NVFP4 decoders are unsupported by the CUDA graph (no stacked bf16 experts) and
  fall back to eager with a stderr notice.
- Ngram suppression defaults to the canonical vLLM recipe: CER-identical to the
  old size-20 ban on the 5-page corpus, table-heavy pages unmeasured.
- dots.ocr is markedly slower than DeepSeek-OCR-2 on large real captures because
  NaViT scales vision tokens with page area.
