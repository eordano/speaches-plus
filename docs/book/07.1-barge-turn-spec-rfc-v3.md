# RFC: Realtime Session State Machine (v3)

**Status:** v3 **Supersedes:** v2 **Scope:** `/v1/realtime` WebSocket and
WebRTC sessions.

The normative specification for one realtime session in speaches: state
machine, wire protocol, error semantics, configuration surface, conformance
suite. MUST/SHOULD/MAY per RFC 2119. Self-contained; deviations are bugs
unless surfaced as proposed amendments. Every number here is a **normative
spec constant** -- a timeout, window size or threshold -- not a measurement,
so none carries evidence; a measured figure entering this file carries its
own basis tuple inline (`08.4-PERFORMANCE.md` governs that).

**Configurability principle.** Every parameter named here is a **default**;
§17 is the single source of truth for names, types and default values.
Implementations MUST accept operator overrides at server startup and client
per-session overrides via `session.update` (§11.2) for every §17.1-§17.7
(session-scoped) parameter. §17.8-§17.9 (process-scoped) are
operator-configurable at startup and immutable mid-session.

## 0. Preamble

### 0.1 Goals

A wire-compatible drop-in replacement for OpenAI's Realtime API surface, with
three additions, each in the deviation register (§0.2) so client SDKs are
updated knowingly rather than surprised at integration time: a
**server-issued truncation event** distinct from client truncate (§9.3), an
**end-of-utterance gate** decoupling turn detection from VAD (§6), and an
**inspector lane** for live debugging (§14).

### 0.2 Deviation register vs OpenAI Realtime API

This register is normative: implementations claiming v3 conformance MUST
match the v3 behavior.

| v3 behavior | OpenAI behavior | Client impact |
|---|---|---|
| `conversation.item.assistant_truncated` (server-issued, §9.3) | `conversation.item.truncated` for both client request and server fact | Clients written against OpenAI's SDK miss the new event type unless updated. Splitting the source lets clients render them differently and lets trace canonicalization preserve it. |
| `response.done.audio_end_ms` on ALL statuses including `completed` (§8.5) | present only on `cancelled`/`incomplete` | OpenAI clients ignore the extra field. It unifies "what did the user actually hear" across success and failure and the trace harness requires it. |
| `error.code = client_too_slow` (§7.4) on outbound queue overflow | no analog | New code; clients treat unknown codes as fatal regardless. |
| Inspector lane at `/v1/inspect` (§14.1) | no analog | None -- separate transport. |
| `eou.*` configuration namespace (§6, §17.3) | no analog | Server-side only; clients see no new wire fields. |
| `turn_detection.{neg_threshold, min_speech_duration_ms}` (§17.2) | no analog | New optional fields; the Silero state machine needs hysteresis (`neg_threshold` to leave a speech segment) and a `min_speech_duration_ms` post-filter, and without them VAD diverges audibly on the same audio. Defaults preserve prior v3 behavior. |
| `session.{no_speech_prob_threshold, avg_logprob_threshold}` (§17.4) | no analog | New optional fields, both defaulting to `null` (gate disabled). The duration-aware noise gate suppresses Whisper's plausible text on coughs, breaths and silence before it reaches the LLM. |
| `EouKind::Vad` means "sweep-based VAD" (§6.2, §17.3) | n/a -- `EouKind` is a v3-only namespace | Clients pinning `eou.kind = "vad"` get a 3-s ring sweep with hysteresis plus `min_speech_duration_ms` filtering; trailing-silence detection is window-shaped rather than sample-shaped. |

### 0.3 Event-name evolution and aliases

OpenAI has shipped two generations of names for several outbound events: the
2024-Q3 "flat" names (still what Azure's mirror ships) and the post-2024-Q4
revision (OpenAI's GA docs) that moved audio-bearing events into the
output-item structure with `output_` prefixes and renamed `created` to
`added` for server-emitted item events.

| Spec field | Old name (recognized alias) | New name (canonical) |
|---|---|---|
| New conversation item | `conversation.item.created` | `conversation.item.added` |
| Item finalized | *(not present)* | `conversation.item.done` |
| Assistant audio chunks | `response.audio.delta` | `response.output_audio.delta` |
| Assistant audio done | `response.audio.done` | `response.output_audio.done` |
| Audio transcript chunks | `response.audio_transcript.delta` | `response.output_audio_transcript.delta` |
| Audio transcript done | `response.audio_transcript.done` | `response.output_audio_transcript.done` |
| Text deltas | `response.text.delta` | `response.output_text.delta` |
| Text done | `response.text.done` | `response.output_text.done` |

**Emitter conformance.** A v3 server emits the New name. It MAY additionally
emit the Old name as a back-compat duplicate; it MUST NOT emit only the Old
name. A server emitting BOTH keeps them **contiguous** (no other events
interleaved) and reuses the same `event_id`, so clients dedupe trivially.

**Client conformance.** A v3 client MUST accept either name as the same
event. Replay tools and conformance harnesses canonicalize to the New name
before comparison (§15.4).

**Client-emitted (inbound) names are unchanged and have no aliases.**
`conversation.item.create`, `response.create`, `response.cancel`,
`input_audio_buffer.{append,commit,clear,truncate}` are spelled as in §10.1.

The Old names stay valid through v3.x; v4 drops them. Fixtures under
`conformance/fixtures/` use the New names. Two newer OpenAI event families
are normative in v3: `conversation.item.retrieve` / `retrieved` (§7.5, §10.1,
§10.3 W9) and `output_audio_buffer.{clear,cleared,started,stopped}` (§8.6,
§10.1, §10.3 W10-W11).

## 1. Terminology

- **Session.** One client connection to `/v1/realtime`, identified by a
  server-generated `session_id`.
- **Turn.** One user utterance plus its assistant response, if any.
- **Item.** An ordered conversation entry (user audio, user text, assistant
  message, tool call, tool result).
- **Buffer.** A region of input audio with VAD bookkeeping; one buffer is one
  prospective user item.
- **Response.** An assistant generation pass: LLM streaming plus optional TTS.
- **Drain.** The interval between the LLM completing and the last TTS audio
  frame leaving the wire.
- **Commit.** Sealing a buffer and dispatching it to STT.
- **Pacer.** The component metering TTS frames onto the wire at wall-clock
  cadence.
- **EOU.** End-of-utterance -- "did the user finish their thought?". Distinct
  from VAD, "is there speech right now?".
- **Backchannel.** A turn-yielding utterance ("uh-huh", "yeah") that
  acknowledges without claiming the floor.
- **Discriminator.** The variant tag of a sum-typed phase value, exposed as a
  `kind()` method.
- **Trace.** The ordered emit log of one session, the conformance artifact
  (§15). A **conformance fixture** is a checked-in `(input, expected
  canonical trace)` pair (§15.6).

## 2. Session model

A session owns exactly one `SessionState`:

```
SessionState { session: SessionPhase, vad: VadPhase, resp: RespPhase }
```

All three are **sum types**; each variant carries exactly the fields
meaningful in that phase, encoded in the host language's most precise
sum-type form (§2.6).

Every state transition runs under a single session mutex. After every
transition, `check_state(state) -> Result<(), Violation>` runs (§2.4).
Violations terminate the session with `internal_state_error` (§10.5); they
are not logged-and-ignored.

### 2.1 SessionPhase

```
SessionPhase ::= Pending
               | Active     { created_at_ms }
               | Terminated { reason: TerminationReason }
```

- `Pending` on accept, before `session.created` is emitted.
- `Active` after `session.created`. Inbound events other than transport
  control are rejected before `Active` with `code: "session_not_active"`.
- `Terminated` is absorbing: further inbound events are ignored and the
  transport is closed. `reason` is one of `client_closed`, `max_duration`,
  `internal_state_error`, `vad_failed`, `stt_failed`, `model_load_failed`.

### 2.2 VadPhase

```
VadPhase ::= Silent
           | Speaking { item_id, audio_start_ms, partial_task }
           | Stopped  { item_id, audio_start_ms, audio_end_ms,
                        commit_timer, hard_cap_timer }
```

- `Silent` is the resting phase: VAD monitors, no buffer is open.
- `Speaking` is entered when Silero confirms voiced audio. A buffer opens
  with `item_id` and `audio_start_ms`; the partial-transcription task runs if
  enabled (§5).
- `Stopped` is entered when Silero confirms end-of-speech. `audio_end_ms` is
  set; `commit_timer` (EOU-controlled, §6) and `hard_cap_timer` (§6.3) are
  armed in parallel.

VAD transitions fire only while `SessionPhase == Active`.

### 2.3 RespPhase

```
RespPhase ::= None
            | Predicted { id, item_id, epoch, runner }
            | Created   { id, item_id, epoch }
            | Streaming { id, item_id, epoch, played_ms, planned_ms }
            | Drain     { id, item_id, epoch, played_ms, planned_ms }
            | Finalized { id, item_id, epoch, status, played_ms, transcript }
```

- `None`: no response in flight. `response.create` is accepted only here.
- `Predicted`: the optional speculative phase entered when the server
  dispatches the upstream LLM BEFORE EOU confirms. Tokens accumulate in the
  per-response `runner`; nothing is on the wire and no `response.*` event has
  been emitted. On EOU confirmation `Predicted -> Created` emits
  `response.created` and flushes the buffer in one burst (§8.1.2); otherwise
  `Predicted -> None` cancels the runner and discards the buffer, so no
  `response.*` event ever leaves and the client never observed the
  speculative response. `Predicted` is invisible to wire-level observers
  except via that burst, which W12 (§10.3) exempts.
- `Created`: `response.created` has been emitted; the LLM is being requested.
- `Streaming`: LLM tokens arrive and TTS frames are paced to the wire.
  `played_ms` reflects the pacer's wall-clock position (§7.3).
- `Drain`: the LLM completed but `played_ms < planned_ms`. The session stays
  busy until drain completes or `drain_cap_ms` expires (§8.3).
- `Finalized`: a brief observable state during emission of `response.done`.
  Implementations may compress this to the emit step without a stored
  variant; the discriminator MUST still be exposed for the inspector lane.

`epoch` is a monotonic counter incremented on every transition that retires a
response (cancel, complete, drain-cap expiry). Work tagged with a stale epoch
is discarded; this is the cancellability mechanism (§8.4, §9). `played_ms` is
a shared atomic counter readable without the session mutex (§7.3);
`planned_ms` is the total TTS duration the response intends to deliver,
accumulated as TTS chunks are produced.

### 2.4 Invariants

`check_state` enforces these under the session mutex on every transition:

- **I1 -- Mutual exclusion.** `vad == Speaking` => `resp ∉ {Created,
  Streaming, Drain}`. The barge-in path (§9) collapses one into the other
  atomically.
- **I2 -- Single-slot response.** At most one of `Created`, `Streaming`,
  `Drain`, `Finalized` per session. A second `response.create` while
  `resp != None` is rejected with `response_already_active`.
- **I3 -- Buffer immutability.** A sealed buffer (§3.2) accepts no further
  audio appends and emits no further VAD events.
- **I4 -- Response terminality.** Every emitted `response.created(id=R)` is
  paired with exactly one terminal `response.done(id=R)`.
- **I5 -- Epoch monotonicity.** Epoch strictly increases over the session
  lifetime, regardless of how a response retired.
- **I6 -- Buffer-conversation consistency.** While a buffer is open with
  `item_id=A`, the conversation contains no user item with `id=A` and
  `status="in_progress"`. The user item is created on commit, not on speech
  start.
- **I7 -- Rotation-at-commit.** Buffer rotation (§3.2) happens synchronously
  with commit, not on `Speaking -> Stopped`. The EOU re-entry path (§6.6)
  reuses the same buffer's `item_id` and `audio_start_ms`, which is only safe
  if rotation has not yet occurred.
- **I8 -- Session monotonicity.** `SessionPhase` follows
  `Pending -> Active -> Terminated`. No other order; no rewind.
- **I9 -- Conversation/wire consistency.** Every accepted inbound
  `conversation.item.create` is followed by exactly one outbound
  `conversation.item.added` (or its alias `conversation.item.created`, §0.3)
  for the same id, and the in-memory conversation contains the item before
  the outbound event is emitted.

`check_state` is a callable function the §15.5 property fuzzer drives
directly. A violation raises an internal error and terminates the session
(§10.5).

### 2.5 Lock discipline

Exactly one session mutex. Every state field read or write that informs an
emission decision happens under it. Emissions themselves happen *outside* it:
observe-and-record-under-lock, emit-after-release. §9.1 spells this out for
barge-in; the same pattern applies everywhere.

### 2.6 Sum-type encoding requirement

Implementations MUST encode `SessionPhase`, `VadPhase` and `RespPhase` in the
host language's most precise sum-type form, so that **the §2.4 invariants
become unrepresentable rather than runtime-checked where the language
permits**. Variants that don't need a field don't get one (`RespPhase::None`
carries no `id`). Rust: an `enum` with per-variant fields. Go: a sealed
interface with one struct type per variant. TypeScript: a discriminated union
with no shared fields. Python: a frozen `dataclass` hierarchy with `match`
dispatch, or `pydantic` discriminated unions with `Literal` discriminators.

A single struct carrying a `kind` discriminator plus the pooled fields of
every variant does NOT satisfy this requirement: it forces every invariant to
be runtime-checked rather than ruled out by the type.

## 3. Input audio buffers

### 3.0 Internal audio pipeline

Server-internal audio on the input path (VAD, partial STT, final STT,
EOU-audio) is canonically **16 kHz mono f32**. Inference call boundaries
(Silero, Whisper, Wespeaker, Pyannote) require f32 regardless.

Resampling from input rates (8 / 16 / 24 / 48 kHz) targets 16 kHz mono via
polyphase (`rubato`, `libsamplerate`, or equivalent).

The output (TTS) pipeline is asymmetric and does NOT round-trip through
16 kHz; see §12.4.

### 3.1 Buffer lifecycle

```
Buffer { id: ItemId, audio: Audio16kMono, audio_start_ms: Option<Millis>,
         audio_end_ms: Option<Millis>, sealed: bool }
```

A session maintains at most one open buffer (`current`) plus a sealed buffer
map keyed by `item_id`, retained per §3.4.

### 3.2 Rotation

Rotation is bound to commit (§7.1), not to `Speaking -> Stopped`. While the
EOU gate (§6) holds the `commit_timer`, the buffer is `Stopped`-but-not-
rotated; a fresh `vad.speech_started` in that window cancels the timer and
the buffer returns to `Speaking` with the same `item_id` and
`audio_start_ms`. That reuse is impossible if rotation happens on `Stopped`
-- hence I7.

On rotation: the current buffer's `audio_end_ms` is set to the commit point
if not already set, `sealed` becomes `true`, the buffer moves to the sealed
map keyed by its `item_id`, and a fresh empty buffer with a new `item_id` is
installed as `current`. Sealed buffers are read-only.

### 3.3 Append semantics

Audio arrives via the WebRTC RTP track (decoded, resampled per §3.0) or the
`input_audio_buffer.append` data-channel event (base64 PCM at the
session-configured `input_audio_format`). Both converge at one buffer-append
routine applying the §3.0 canonicalization. Appends are ignored when
`SessionPhase != Active`, or when the current buffer is sealed (impossible by
construction; checked as a debug assertion).

Accepted `input_audio_format` values:

| Value | Wire rate | Wire encoding | Use |
|---|---|---|---|
| `pcm16` | 24000 | s16 LE mono | desktop / browser default |
| `pcm16_16k` | 16000 | s16 LE mono | matches internal rate; no resample on ingress |
| `g711_ulaw` | 8000 | µ-law | telephony (Twilio, Asterisk PSTN) |
| `g711_alaw` | 8000 | A-law | telephony (EU PSTN) |

WebRTC offers OPUS at 48 kHz regardless of `input_audio_format`; the field
governs only the WebSocket / data-channel append path.

### 3.4 Sealed-buffer retention

A sealed buffer's audio is referenced for inspector replay (§14) and for a
subsequent `conversation.item.truncate` against a user item. Two rules apply
independently:

1. **Drop on transcription complete.** When
   `conversation.item.input_audio_transcription.completed(item_id=A)` is
   emitted (§7.2), the sealed buffer for `A` is dropped.
2. **Recent-window cap.** The sealed map retains at most the most recent `K`
   entries (default `K = 4`, `sealed_buffer_retention_count` in §17). Older
   sealed buffers evict FIFO.

A long-running session therefore retains at most `K * sizeof(audio)` bytes of
sealed audio regardless of duration.

## 4. VAD

### 4.1 Model and frame contract

Silero VAD v5 is the default. The server SHALL compute end-of-speech on
per-frame inference output. Frame contract for v5:

- Storage rate / format: 16 kHz mono per §3.0.
- Inference call: convert to **float32** at the call boundary if storage is
  s16 (single multiply per sample; vectorizes).
- Inference window: **512 samples (32 ms)**.
- **Context window: 64 samples** prepended to each inference window, drawn
  from the trailing 64 samples of the previous chunk. Omitting the context
  window makes the model emit its idle baseline (~5e-4) regardless of input.
- `sr` input: rank-0 tensor (scalar `int64`).
- `state` input: `[2, batch=1, 128]` float32, persisted across calls within a
  single utterance and zeroed on speech end.

Frame contract for v6 (when the upstream ONNX export stabilizes): same sample
rate; window and context sizes per the v6 model card. `vad_model` selects v5
(default) or v6 (§17.8).

### 4.2 Tunable parameters

`threshold`, `prefix_padding_ms`, `silence_duration_ms` and
`barge_in_delay_ms`, with types, defaults and ranges in §17.2.
`prefix_padding_ms` is subtracted from the VAD-confirmed cursor when
publishing `audio_start_ms`:
`audio_start_ms = max(0, vad_confirmed_cursor_ms - prefix_padding_ms)`.
`silence_duration_ms` is the trailing silence required to declare
end-of-speech. All are runtime-mutable via `session.update.turn_detection`
(§4.5).

### 4.3 Detection events

The VAD subsystem emits exactly `vad.speech_started(audio_start_ms)` and
`vad.speech_stopped(audio_end_ms)`, both carrying millisecond timestamps
relative to session start. The signals are processed under the session mutex;
the resulting phase transitions and outbound events follow §7 and §9.

### 4.4 Failure mode

If the VAD model fails to load at startup the server fails to start; VAD is
not optional. If per-frame inference fails during a session, the session
terminates with `error.code = "vad_failed"` and HTTP 5xx semantics (§10.5).

### 4.5 Hot reload

`session.update.turn_detection` is accepted at any time during `Active`:

- **`threshold`**: takes effect from the next inference window.
- **`prefix_padding_ms`**: applied to the next `vad.speech_started`. An
  in-flight Speaking buffer's `audio_start_ms` is not retroactively adjusted.
- **`silence_duration_ms`**: an armed `commit_timer` is rescheduled with the
  remaining time computed against the new duration. If the new value places
  the fire time in the past, commit fires immediately.
- **`barge_in_delay_ms`**: takes effect for new barge-in attempts; a sleeping
  `barge_in_task` keeps its original delay.
- **`type: "none"`**: an in-flight Speaking buffer transitions to Stopped at
  the moment of update; `commit_timer` and `hard_cap_timer` are not armed, so
  commit fires on `input_audio_buffer.commit`.
- **`type: "server_vad"` after `"none"`**: the next audio chunk starts
  detection; no retroactive analysis.

Updates emit `session.updated` echoing the full session object so the
client's view stays consistent.

## 5. Partial transcription

When a partial-STT model is configured, a `partial_transcription_task` runs
while `vad == Speaking`. It re-runs STT on the current buffer every
`partial_interval_ms` (default 500) and emits
`input_audio_buffer.partial_transcription` per result. It is cancelled on
`vad: Speaking -> Stopped` and restarted on `Stopped -> Speaking` (the EOU
re-entry case, §6.6). At most one partial task exists per session.

Partial transcripts are ephemeral hints: the partial and final models may
differ, so clients do not rely on the partial text matching the final
transcript. With no partial-STT model configured, partial events are not
emitted.

## 6. Turn detection

Turn detection answers "did the user finish their thought?", which VAD's "is
there speech right now?" is necessary but not sufficient for: silence alone
misfires on natural pauses, enumerations, addresses and hesitations.
Implementations support the turn-detection modes selected via `eou.kind`
(§6.2), all of which share the same hard-cap timer (§6.3), failure policy
(§6.5) and cancellation path (§6.6).

### 6.1 Architecture

Pipeline: audio frames -> Silero VAD -> `vad.speech_*` events. On
`speech_stopped` the classifier is dispatched by `eou.kind` (§6.2): `vad` ->
no call, `text` -> §6.2.1, `audio` -> §6.2.2, `fusion` -> §6.2.3. The
classifier returns `p ∈ [0, 1]` (or "no classifier" for `vad`), which feeds
`delay_curve(p, threshold, k)` (§6.4) producing `delay_ms ∈ [min, max]`; for
`kind = vad`, `delay = silence_duration_ms` (§4.2). A `commit_timer` then
races the `hard_cap_timer` (§6.3); whichever fires first commits.

VAD's `speech_stopped` is the necessary trigger for every mode. Classifier
evaluation fires **once on STT-final** (§6.6) -- not on partials, not on a
periodic timer.

### 6.2 Modes

| `eou.kind` | Behavior | Notes |
|---|---|---|
| `vad` | No classifier call. Wait = `turn_detection.silence_duration_ms` (§4.2). Hard cap (§6.3) still races as a safety net. | Cheapest, no model dependency. Misfires on natural pauses; users tune `silence_duration_ms` by feel. |
| `heuristic` | Linguistic-cue heuristic over the partial transcript (final-token punctuation, filler-word tail, sentence boundary). No model. | §6.2.4. Runs in microseconds. |
| `text` | Distilled LM scores `p = P(turn-end \| context)` over the last K conversation turns + partial transcript. | §6.2.1. Reference: `livekit/turn-detector`. |
| `audio` | Audio-encoder + linear head scores `p = P(turn-end \| waveform)` over the last `audio_window_ms` of buffer at 16 kHz. | §6.2.2. Reference: `pipecat-ai/smart-turn-v3`. |
| `fusion` | Both `text` and `audio` heads run; outputs combined via `eou.fusion_rule`. | §6.2.3. Cost = sum of both heads. |
| `integrated` | The conversation LLM emits an `<\|im_end\|>` probability inline with token streaming, eliminating a separate classifier round-trip. | §6.2.5. Lowest latency when the upstream LLM supports it. |

Implementations MUST support `vad`, `text`, `audio` and `fusion`.
`heuristic` and `integrated` are OPTIONAL extensions; an implementation that
does not support them MUST reject `session.update` setting them with
`eou_kind_unsupported`. Default `kind = vad` preserves silence-only behavior;
operators wanting production-quality turn detection set `text`, `audio` or
`fusion`.

The classifier's output `p` MUST be clipped to `[0, 1]` at the boundary. NaN,
infinity or out-of-range probabilities are uncertainty per §6.5.

#### 6.2.1 `kind = text`

Reference model: **`livekit/turn-detector` v0.4.1-intl** (Qwen2.5-0.5B
distilled from a 7B teacher; 14 languages; INT8 ONNX, 396 MB on disk,
~500 MB RAM; ~50 ms CPU per evaluation; LiveKit Model License -- custom, not
OSI-approved).

Input contract: the last `eou.context_turns` (default 4) of conversation
history followed by the partial transcript so far, rendered with the model's
chat template (`<|im_start|>role\ncontent<|im_end|>\n...`), truncated **left**
to `eou.max_context_tokens` (default 128) so the most recent content
survives, with the trailing `<|im_end|>` of the final user message stripped
before scoring. Output: `p = softmax(logits)[<|im_end|>_token_id]` at that
trailing position.

Implementations MAY swap the reference model for any text classifier
conforming to this input/output shape. The per-language threshold table
shipping with the model SHOULD be loaded as the default for `eou.thresholds`
(§6.4); operators override per session.

#### 6.2.2 `kind = audio`

Reference model: **`pipecat-ai/smart-turn-v3`** (Whisper-Tiny encoder +
linear head; 8 M params; INT8 ONNX, 8 MB; ~12 ms CPU per evaluation;
23 languages; BSD-2-Clause).

Input contract: the last `eou.audio_window_ms` (default 8000) of the buffer
at 16 kHz mono f32, normalized to `[-1, 1]`, padded per
`eou.audio_pad_alignment ∈ {leading, trailing}` -- smart-turn requires
`leading`, zero-padding on the left so audio sits at the **end** of the input
vector. Mis-aligning produces silently degraded predictions. Output:
`p = sigmoid(head_logit)`.

#### 6.2.3 `kind = fusion`

Both classifiers are dispatched concurrently and combined via
`eou.fusion_rule`:

| Rule | Formula | Bias |
|---|---|---|
| `noisy_or` | `1 - (1 - p_text)(1 - p_audio)` | Aggressive: either head firing suffices. Over-fires on independent-noise events from one head, producing *more* false cuts than linear rules. Compatibility-only; not recommended. |
| `max` | `max(p_text, p_audio)` | Same firing direction as noisy-OR, less smooth. |
| `mean` | `(p_text + p_audio) / 2` | Both heads must agree to score high. Identity to `weighted` at `w = 0.5`. |
| `weighted` | `w · p_text + (1 - w) · p_audio`, `w = eou.fusion_weight_text` (default 0.5) | Tunable, fixed-weight, non-input-conditioned linear combiner. |
| `gated` (default) | `r = g · p_audio + (1 - g) · p_text`, `g = σ(W · x)` over a per-call feature vector `x` | Learned, **input-conditioned** linear combiner. Requires trained gate weights. |

`gated` is the default because the hierarchy `gated > weighted-fixed >
OR-style` holds both in Chen et al., ICASSP 2022 (*Gated Multimodal Fusion
with Contrastive Learning for Turn-Taking Prediction*, arXiv:2204.10172) and
on `pipecat-ai/smart-turn-data-v3-test`. When `gated` is configured but the
caller cannot supply per-call features, or the implementation lacks trained
gate weights, the fallback is `weighted` at `w = 0.5` -- exactly Chen et al.
§3.3's degenerate form of gated fusion (`g = σ(0) = 0.5`), so the fallback is
paper-aligned rather than a hidden substitution. Implementations MAY emit
`fusion_rule=gated, features_supplied=false` in telemetry to expose the path.

Implementations MUST support `noisy_or`, `max`, `mean` and `weighted`.
`gated` is an extension: implementations MAY support it and MUST surface
support via `extensions.fusion_rules` in `/v1/realtime/capabilities`; those
that do not MUST reject `session.update` setting `eou.fusion_rule = gated`
with `eou_fusion_rule_unsupported`.

Fusion latency is `max(text_latency, audio_latency)` when the heads run in
parallel (recommended), `text_latency + audio_latency` sequentially;
implementations SHOULD parallelize. If either head fails (timeout, error,
NaN) it is treated as `p = 1` per §6.5 -- its absence does not block fast
commit, the other head's score becomes the verdict, and fusion degrades
gracefully to single-head.

#### 6.2.4 `kind = heuristic`

A model-free linguistic-cue heuristic over the partial transcript: terminal
punctuation (`. ! ?`) on the last token scores high; open-clause endings
(comma, conjunction, hesitation marker like "uh", "um") score low; an empty
or whitespace-only transcript scores `p = 0`, deferring to the silence timer.

The exact scoring function is implementation-defined; the contract is only
the input/output shape (partial transcript in, `p ∈ [0, 1]` out).
Conformance fixtures pin behavior on canonical inputs ("hello." -> high,
"hello," -> low, "" -> 0). Heuristic mode runs in microseconds with no model
dependency -- the intermediate point between `vad` and `text` for deployments
that cannot ship the `text`/`audio` model artifacts.

#### 6.2.5 `kind = integrated`

The conversation LLM streams an `<|im_end|>` probability inline with token
generation. The server reads it without a second classifier round-trip,
eliminating the §6.3 race on the EOU side; the hard-cap timer still arms in
parallel as a structural safety net per §6.3.

Input contract: the upstream LLM advertises predicted-response support in its
capabilities (an OpenAI-compatible `predicted_outputs` field or equivalent),
and `default_realtime_model` is one whose `<|im_end|>` token probability is
exposed during streaming. Output:
`p = P(<|im_end|> | streamed prefix)` at the most recent streaming token
boundary.

When `integrated` is selected but the upstream LLM does not expose the
probability, the session SHOULD fall back to `kind = vad` for its lifetime
per §6.5 row 1, with a single warning logged.

Integrated mode is a Speaches extension; wire-compat clients see no new
fields, and observe the same `commit` / `response.created` sequence as the
other kinds.

### 6.3 Hard cap with mandatory parallel timer

A hard cap, `silence_hard_cap_ms` (default 5000), bounds the total wall-clock
between `speech_stopped` and commit **regardless of EOU verdict, EOU
inference latency, or EOU function-call hang**. This bound is normative.

The hard cap MUST be implemented as a parallel timer racing the EOU-derived
commit timer. It MUST NOT be implemented as a clamp on the EOU verdict's
`delay_ms`: a clamp does not fire if the EOU function itself stalls (model
warmup, ONNX hang, classifier deadlock).

#### 6.3.1 Mandatory pattern

```
on vad.speech_stopped(audio_end_ms):
    arm hard_cap_timer  = deadline(now + silence_hard_cap_ms)
    arm eou_call        = race(hard_cap_timer,
                                timeout(eou.inference_timeout_ms,
                                        classifier(context)))

    verdict = await eou_call
    if verdict == hard_cap_fired:
        emit eou.hard_cap_fired { phase: "during_eou", score: null }
        commit()
        return

    p     = clip(verdict.p, 0.0, 1.0)
    delay = delay_curve(p, threshold[lang], min, max)   # §6.4

    arm wait = race(hard_cap_timer, sleep(delay))
    result = await wait
    if result == hard_cap_fired:
        emit eou.hard_cap_fired { phase: "during_wait", score: p }
    commit()
```

Two structural properties this enforces. **The hard cap is a deadline derived
once and observed twice** -- while EOU computes, and again while the
verdict-derived delay sleeps; the clamp form
(`delay = min(delay, hard_cap)`) evaluates the bound only after EOU returns
and so cannot guard a stalled call. **Both observation points emit
`eou.hard_cap_fired` with a `phase` discriminator**, so traces distinguish
"EOU stalled" from "EOU returned but the score was low and
`delay > hard_cap`" -- the discriminator is what diagnoses production hangs.

`vad.speech_started` during either await cancels both arms and unwinds per
§6.6.

### 6.4 Decision math

The post-stop commit delay is
`delay_curve(p, threshold, min_delay_ms, max_delay_ms)`:

```
if p < threshold:
    return max_delay_ms                                  # below threshold: wait

k       = eou.curve_k                                    # default 12
x       = (p - threshold) / (1 - threshold)              # ∈ [0, 1]
s_raw   = 1 / (1 + exp(-k · (x - 0.5)))                  # logistic
s_norm  = (s_raw - s_raw(0)) / (s_raw(1) - s_raw(0))     # ∈ [0, 1]
return  round(max_delay_ms + (min_delay_ms - max_delay_ms) · s_norm)
```

The curve is gradual near `threshold` and steep near `p = 1`: confident
verdicts collapse toward `min_delay_ms`, low-confidence ones toward
`max_delay_ms`. Higher `k` sharpens the curve around the midpoint, lower `k`
linearizes it; default `k = 12` matches LiveKit's shipped behavior and
operators tune it via `session.update`. Conformance fixtures pin `delay_ms`
outputs to **+/-5 ms or +/-2%, whichever is larger**, accommodating
floating-point divergence.

For `kind = vad` this section does not apply: the wait is simply
`turn_detection.silence_duration_ms` (§4.2).

#### 6.4.1 Threshold resolution

```
threshold = eou.thresholds[input_audio_transcription.language]
         ?? eou.p_threshold
```

`eou.thresholds` is a `map<lang, f32>` exposed via `session.update` (§17.3),
defaulting to **empty**; without entries every language uses
`eou.p_threshold` (default 0.5). Optimal thresholds vary across languages in
published reference tables (LiveKit ships 14 entries, Pipecat smart-turn 23),
so operators serving non-English traffic SHOULD populate `eou.thresholds`
from their model's published table or their own calibration. The spec does
not mandate it: calibration is deployment-specific and one global threshold
suffices for many production cases.

#### 6.4.2 Defaults

| Field | Default | Rationale |
|---|---|---|
| `eou.kind` | `vad` | Preserves current speaches behavior on upgrade. |
| `eou.min_delay_ms` | 500 | LiveKit's shipped default. |
| `eou.max_delay_ms` | 3000 | LiveKit's shipped default. |
| `eou.p_threshold` | 0.5 | Mid-curve; works as a global default for any classifier. |
| `eou.curve_k` | 12 | LiveKit's shipped curve. |
| `eou.silence_hard_cap_ms` | 5000 | Bounded above the 99th percentile of legitimate user pauses. |
| `eou.inference_timeout_ms` | 250 | Sized for `text` (~50 ms CPU) and `audio` (~12 ms CPU) with 5x margin. |
| `eou.context_turns` | 4 | LiveKit ships 6; smart-turn doesn't use this. 4 is the convergence point. |
| `eou.audio_window_ms` | 8000 | Smart-turn's documented window. |

### 6.5 Failure policy (canonical, single rule)

**On any EOU uncertainty, treat the verdict as `p = 1` and use
`delay_ms = min_delay_ms`. The hard-cap timer continues to race per §6.3 and
provides the upper bound -- though it almost never fires in this mode because
`min_delay_ms ≪ silence_hard_cap_ms`.**

One rule, applied uniformly to every uncertainty source:

| Cause | Treated as |
|---|---|
| Model fails to load at startup | The session falls back to `kind = vad` for its lifetime; warning logged once. |
| Inference timeout (`inference_timeout_ms` exceeded) | `p = 1`, `delay = min_delay_ms` |
| Inference returns an error | `p = 1`, `delay = min_delay_ms` |
| Inference returns NaN, infinity, or a value outside `[0, 1]` | `p = 1`, `delay = min_delay_ms` |
| Tokenizer returns empty / chat template fails | `p = 1`, `delay = min_delay_ms` |
| For `kind = fusion`: one head fails | the failed head is treated as `p = 1`; the other head's score becomes the verdict |

The rule errs toward responsiveness: a fast commit on a broken EOU costs a
possibly-premature cut, waiting on a broken EOU costs dead air. The hard cap
remains the structural upper bound on wait time, but the failure path does
not stack extra silence on top of broken inference.

This is **fast-commit on uncertainty**. Implementations preferring
slow-commit MAY configure `eou.failure_p_default = 0.0` (default `1.0`) and
`eou.failure_delay = "max"` (default `"min"`) per session.

### 6.6 Trigger and cancellation

The classifier is invoked **once per turn, on STT-final**, not on partials
and not on a periodic timer. `vad.speech_stopped` fires and arms
`commit_timer` and `hard_cap_timer` in parallel per §6.3; STT keeps consuming
audio past `speech_stopped` and produces a final transcript chunk within
~200-500 ms (model-dependent); on STT-final the classifier dispatches with
the finalized transcript (plus the last `eou.context_turns` of conversation
context for `kind = text`, or the buffered audio for `kind = audio`); the
verdict resolves the `commit_timer`'s `delay_ms` per §6.4; whichever timer
fires first commits.

If a new STT-final chunk arrives during the wait (streaming STTs that emit
multiple finals per utterance), the classifier MAY re-run with the latest
verdict superseding the previous one. Implementations that fire only on the
*first* STT-final per turn are conformant.

If `vad.speech_started` fires during the §6.3 race, whether EOU is computing
or the verdict-derived delay is sleeping:

1. Both `commit_timer` and `hard_cap_timer` are cancelled.
2. The in-flight EOU computation, if any, is cancelled. A late verdict whose
   computation outlived cancellation is discarded by checking the buffer's
   `audio_end_ms` is still set when it resolves.
3. The buffer returns to `Speaking` (same `item_id`, `audio_start_ms`
   preserved, `audio_end_ms` cleared).
4. No `input_audio_buffer.committed` is emitted.
5. The partial-transcription task is restarted.
6. The inspector emits `{lane: "eou", kind: "cancelled",
   payload: {cancelled_by: "speech_started", ...}}` per §6.7.

### 6.7 Telemetry

Per EOU evaluation, implementations emit `InspectorEvent`s on the `eou` lane
(§14.1 envelope, not the wire), shaped
`{ lane: "eou", kind: <kind>, payload: { ... } }`, with the lane-level
correlation fields (`session_id`, `seq`, `ts_mono_ns`, `ts_wall`,
`corr.{turn_id,item_id,response_id}`) populated by the relay per §14.1.

A trace alone -- without server-side log access -- MUST suffice to attribute
a commit decision to a specific signal, score, threshold and timer. That is
the contract letting operators debug turn-detection regressions from
production captures.

**`kind = "scored"`** -- once per classifier evaluation returning a verdict,
including degraded fallbacks per §6.5.

| Payload field | Type | Notes |
|---|---|---|
| `eou_kind` | enum | `vad` \| `heuristic` \| `text` \| `audio` \| `fusion` \| `integrated` |
| `score` | f32 | clipped to `[0, 1]`; absent for `eou_kind = vad` |
| `score_text` | f32? | individual head when `eou_kind = fusion` |
| `score_audio` | f32? | individual head when `eou_kind = fusion` |
| `fusion_rule` | enum? | `noisy_or` \| `max` \| `mean` \| `weighted` (when `eou_kind = fusion`) |
| `threshold` | f32 | after `eou.thresholds[lang]` resolution |
| `language` | string | the row of `eou.thresholds` consulted |
| `curve_k` | f32 | the `k` used for the §6.4 curve |
| `input_chars` | u32? | for text-side input |
| `input_audio_ms` | u32? | for audio-side input |
| `delay_ms` | u32 | from §6.4 |
| `elapsed_ms` | u32 | wall-clock spent in classifier |
| `failure_reason` | enum? | when §6.5 fired: `timeout` \| `error` \| `garbage_prob` \| `tokenizer` |

**`kind = "hard_cap_fired"`** -- when the §6.3 timer wins the race, whether
or not the EOU call had returned: `phase` (`during_eou` \| `during_wait`),
`score` (f32?, the last verdict if `phase = during_wait`, null otherwise),
`eou_kind`.

**`kind = "cancelled"`** -- when the race is unwound by §6.6:
`cancelled_by` (`speech_started` \| `commit_event`), `eou_kind`.

**`kind = "fallback"`** -- once per session when a model fails to load and
the session degrades to `kind = vad` per §6.5 row 1: `from_kind`
(`text` \| `audio` \| `fusion`), `to_kind` (always `vad`), `reason` (loader
error message, truncated to 256 chars).

## 7. Commit and transcription

### 7.1 Commit

A commit fires when `vad == Stopped` and `commit_timer` (or
`hard_cap_timer`) expires, or when `input_audio_buffer.commit` is received in
any non-`Terminated` state. On commit:

1. Buffer length is checked against `min_speech_ms` (default 100, §17.4). If
   below, the commit is rejected with `input_audio_buffer_commit_empty` and
   the session returns to its pre-commit phase (`Stopped -> Silent`, buffer
   cleared).
2. The buffer is rotated (§3.2).
3. `input_audio_buffer.committed(item_id, previous_item_id)` is emitted.
4. `conversation.item.added(item)` is emitted with `status: "in_progress"`.
   The in-memory conversation contains the item before this event leaves the
   wire (I9). Recognized alias: `conversation.item.created` (§0.3).
5. STT is dispatched on the sealed buffer.

### 7.2 Transcription

When STT completes:

1. `conversation.item.input_audio_transcription.completed(item_id,
   transcript, usage)` is emitted.
2. The conversation item's status becomes `"completed"`.
3. The sealed buffer for `item_id` is dropped per §3.4 rule 1.
4. If `turn_detection.create_response == true`, the transcript is non-empty,
   and `audio_ms >= min_speech_for_response_ms` (§17.4), a response is
   auto-created (§8.1).

If STT fails: an `error` event is emitted (§10.5), the conversation item
becomes `status: "incomplete"`, and no response is auto-created.

### 7.3 played_ms semantics

`played_ms` is the wall-clock cursor of the pacer (§8.2), bumped **after the
encoded audio packet has been written to the transport** -- not at synthesis
time, not on receiver acknowledgement. A send into an internal writer queue
does not count; only a successful write to the transport socket counts.
Synthesis time is too early (a 20 ms frame can spend tens of ms in the
encoder queue); receiver-ack is too late (WebRTC SCTP/RTP surface no
application-layer acks and clients buffer 50-200 ms in their jitter buffer
regardless).

`played_ms` is shared between the response task and observers as an atomic
counter readable without the session mutex. Observers sample it at
well-defined transition points (cancel, drain, terminal). Reads use acquire
semantics, writes release semantics (or the language equivalent).
Implementations expose `played_ms` to the §9 barge-in path as a callable
that, invoked under the session mutex, returns the value committed before the
most recent transport write.

For WebSocket transports without an explicit transport-write boundary,
`played_ms` is bumped after the WebSocket `Write` call returns without error.
Client-side WebSocket buffering is out of scope; §7.4 backpressure applies.

### 7.4 Backpressure

If the transport writer cannot keep up:

- `response.output_audio.delta` and
  `response.output_audio_transcript.delta`: the pacer blocks on
  `write_sample` (or equivalent) and the encoder throttles naturally;
  `played_ms` continues to reflect successful writes.
- All other events: a bounded queue (default `outbound_queue_cap = 256`,
  §17.6). On overflow the session terminates with `client_too_slow` -- a slow
  client breaking wire invariants is a worse failure mode than a
  disconnection.

### 7.5 Item retrieval

A client MAY ask the server to re-emit a single conversation item in full,
including payload (e.g. user-audio PCM) that the original
`conversation.item.added` omitted to keep the wire light.

**Inbound: `conversation.item.retrieve { event_id?, item_id }`**, valid in
`Active`. The server looks up `item_id` in the in-memory conversation:

- Found -> emit one `conversation.item.retrieved { event_id?, item }` where
  `item` is the FULL representation: `id`, `type`, `role`, `status`,
  `content[]`. For `type: "user_audio"` the audio payload MUST be present as
  base64 PCM at the session's `input_audio_format`; for assistant items the
  transcript and any TTS audio (base64 PCM at `output_audio_format`) MUST be
  present.
- Not found -> emit `error { code: "item_not_found", event_id }`.

Retrieval is **stateless**: it advances no phase, triggers no
`conversation.item.added/done`, and does not affect `played_ms` or
`audio_end_ms`. It MAY be issued at any phase including mid-response.
Sealed-buffer retention (§3.4) governs audio availability -- a `user_audio`
item whose sealed buffer has been dropped returns `item_not_found` rather
than a partial item.

## 8. Response lifecycle

### 8.1 Creation

A response is created by a `response.create` inbound event in `resp == None`,
or automatically after a transcription completes (§7.2).

#### 8.1.1 Creation from `None`

1. `resp` advances `None -> Created { id, item_id, epoch }` under the mutex.
2. `response.created(response)` is emitted.
3. The response task is spawned; it drives §8.2-§8.4 until terminal.
4. `instructions`, `modalities`, `tools` and `tool_choice` overrides carried
   by `response.create` apply for this response only and do not mutate the
   session-level fields.

#### 8.1.2 Predicted (speculative) creation

A server MAY enter `Predicted` BEFORE EOU confirms, to overlap LLM latency
with the user's tail silence. While `vad == Stopped` and the EOU commit timer
still runs, the server speculatively dispatches the upstream LLM against the
conversation history INCLUDING a hypothetical user item filled from the
running partial transcript (§5). `resp` advances
`None -> Predicted { id, item_id, epoch, runner }` under the mutex; **no
`response.*` event is emitted yet** and the `runner` accumulates LLM tokens
in a server-internal buffer. Then one of three things happens:

- **EOU confirms** (§6.6): `Predicted -> Created`, `response.created` is
  emitted, and the buffered token stream flushes as a contiguous burst of
  `response.output_text.delta` / `response.output_audio_transcript.delta`.
  The audio pipeline starts consuming the now-visible transcript and emits
  `response.output_audio.delta`. Subsequent tokens stream individually -- the
  burst applies ONLY to tokens generated before `response.created`, and is
  bounded by `predicted_flush_grace_ms` (§17.6); W12 (§10.3) exempts it.
- **EOU re-opens speech** (§6.6 re-entry): the `runner` is cancelled, the
  buffer discarded, `Predicted -> None`. No wire event ever references this
  speculative response. The hard-cap timer (§6.3) resets for the new speech
  segment.
- **Hard cap fires while still Predicted**: the speculative output is
  committed as if EOU had confirmed, per the first branch.

`Predicted` is OPTIONAL -- implementations that skip it run
`None -> Created -> ...`. Predicted-mode servers MUST still satisfy every
W-invariant in §10.3; the W12 exemption covers the burst of buffered deltas
at confirmation, not general latency.

### 8.2 Streaming

`resp` advances `Created -> Streaming` when the first LLM token or TTS frame
is produced. The response task emits, in order:

```
response.output_item.added(item)
response.content_part.added(part)
response.output_audio_transcript.delta(text)*   + interleaved per chunk;
response.output_audio.delta(audio)*             + per-chunk alignment not required
response.output_audio_transcript.done(transcript)
response.output_audio.done()
response.content_part.done(part)
response.output_item.done(item)
```

Recognized aliases (§0.3): `response.audio_transcript.{delta,done}` for the
transcript stream, `response.audio.{delta,done}` for the audio stream, and
`response.text.{delta,done}` for text-only modality (canonical
`response.output_text.{delta,done}`).

`response.output_audio.delta` carries base64 PCM frames at the session's
output sample rate. WebRTC clients receive the same audio over the RTP track;
data-channel emission is required regardless of transport so text-only
inspectors and replay tools see a complete record.

`played_ms` on `Streaming` is updated by the pacer per §7.3.

### 8.3 Drain

When the LLM completes but `played_ms < planned_ms`:

1. `resp` advances `Streaming -> Drain`.
2. The drain task waits for the pacer to reach `planned_ms`, bounded by
   `drain_cap_ms = clamp(2 * planned_ms, drain_cap_floor_ms,
   drain_cap_ceiling_ms)` with `drain_cap_floor_ms = 5000` and
   `drain_cap_ceiling_ms = 60000` by default (§17.5).
3. On natural completion the response terminates (§8.4) with
   `status: "completed"`.
4. On `drain_cap_ms` expiry the encoder is drained of any in-flight frame and
   the response terminates with `status: "incomplete",
   status_details.reason = "drain_cap"`. The unsent tail is logged.

### 8.4 Terminal

Every response terminates with exactly one `response.done(response)`.

| Status | When |
|---|---|
| `completed` | LLM and TTS drain finished naturally. |
| `cancelled` | Cancelled by `response.cancel` or barge-in (§9). |
| `incomplete` | Hit a runtime cap; see `status_details.reason`. |
| `failed` | LLM or TTS error; details in `status_details`. |

`status_details` is required when `status ∈ {incomplete, failed}`:

```
status_details ::= {
    reason: "drain_cap" | "token_limit" | "llm_error" | "tts_error",
    error?: { code: string, message: string }
}
```

### 8.5 audio_end_ms

`response.done` carries `audio_end_ms = played_ms` for **all** statuses,
including `completed` (§0.2). The §15.6 fixture set carries one fixture per
status value asserting the field is present and equals the pacer position at
termination.

`resp` advances `Streaming|Drain -> Finalized -> None` immediately before and
after `response.done` is emitted. `epoch` increments there, so post-terminal
stale events (late synthesis, late LLM tokens) are dropped at the dispatcher.

### 8.6 Output-audio buffer control

For WebRTC transports the server-side TTS pipeline maintains an output audio
buffer between the encoder and the transport write boundary; v3 exposes four
events for observing and controlling it. WebSocket transports SHOULD also
emit `started` / `stopped` for parity; `clear` / `cleared` are WebRTC-only
because WS clients control their own playback buffer.
`output_audio_buffer.*` events never change `resp` phase.

**Outbound: `output_audio_buffer.started { response_id }`** -- emitted
exactly once per response, in the same emit step as the first
`response.output_audio.delta` for that response and after that delta is on
the wire. A response producing no audio (text modality only, or cancelled
before any delta) MUST NOT emit `started`.

**Outbound: `output_audio_buffer.stopped { response_id, audio_end_ms }`** --
emitted exactly once per response that emitted `started`, triggered by
whichever happens first: `response.output_audio.done` was just emitted; the
response reached a terminal phase with `status ∈ {cancelled, incomplete,
failed}` (§8.4) and the pacer queue drained; or `output_audio_buffer.clear`
was received and the queue drained. `audio_end_ms` carries the same value as
`response.done.audio_end_ms` (§8.5) at the time `stopped` fires. The two MAY
be reported in either order as long as both reference the same `played_ms`
snapshot.

**Inbound: `output_audio_buffer.clear { event_id? }`** -- valid in `Active`
regardless of `resp` phase. It drops every pending frame in the pacer queue,
does NOT advance `played_ms` (only successful transport writes count, §7.3),
and does NOT cancel the response: LLM streaming continues but newly
synthesized audio is again dropped at the pacer. Clients wanting to stop
generation use `response.cancel` (§9.3). Once the drain completes the server
emits `output_audio_buffer.cleared { event_id? }`, plus `stopped`
immediately after if `started` has fired and `stopped` has not. If `clear`
arrives with no active output audio, `cleared` is an idempotent
acknowledgement and no second `stopped` is emitted.

## 9. Barge-in

Barge-in is the path from `vad.speech_started` while `resp != None`.

### 9.1 Atomicity

The handler runs under the session mutex and observes-and-acts on `resp`
atomically, returning a `BargeInEffect` record (cancel snapshot + buffered
events) that the caller emits without re-entering the lock. Without single
acquisition, a phase observed as `Streaming` can transition to `Drain`
between observation and cancel, leaking TTS frames past the barge-in point.

`BargeInEffect` carries `cancelled: bool`, `id`, `item_id`, `epoch`,
`played_ms_snapshot`, `transcript_at_cancel`, and `was_drain: bool`. The
snapshot is taken under the mutex (§7.3); the post-write guarantee on
`played_ms` ensures it reflects exactly what the user has heard.

### 9.2 Delay

`barge_in_delay_ms` (§4.2) defers commitment. At `0` barge-in fires
immediately. Above `0` a `barge_in_task` sleeps the delay and the cancel
proceeds on expiry; if `vad.speech_stopped` arrives during the delay the
barge-in is suppressed (§9.4). While `barge_in_task` sleeps the outbound
`speech_started` event is buffered, so the client does not observe the
barge-in until it commits.

### 9.3 Commitment

When the barge-in commits:

1. `played_ms` is snapshotted from the active response, under the mutex.
2. The response task is cancelled. Its cancellation handler emits the
   bracket-close events for the active item with status `incomplete`, then
   `response.done(status: "cancelled", audio_end_ms: played_ms_snapshot)`.
3. **If `played_ms_snapshot > 0`**, the server emits

   ```json
   {"type": "conversation.item.assistant_truncated",
    "item_id": "<assistant_item_id>",
    "audio_end_ms": <played_ms_snapshot>,
    "transcript": "<partial transcript heard>"}
   ```

   When `played_ms_snapshot == 0` (response created but the pacer has not
   advanced) the event is NOT emitted; nothing was on the wire to truncate.
   This event is the server fact; the client request stays
   `conversation.item.truncate` (§0.2).
4. The buffered `input_audio_buffer.speech_started` is published.
5. `vad` advances to `Speaking` and the partial-transcription task starts.

### 9.4 Suppression

If `vad.speech_stopped` arrives while `barge_in_task` sleeps: the task is
cancelled, no `speech_started` is published, `resp` is unchanged and the
active response continues unaffected, and the buffered audio for the aborted
speech segment is discarded (the buffer's `audio_start_ms` is cleared on the
next append). A suppressed barge-in is observable to operators via inspector
telemetry (`bargein.suppressed`) but produces no client-visible events.

### 9.5 Simultaneous barge-ins

If `vad.speech_started` fires while a `barge_in_task` from a *previous*
`vad.speech_started` is sleeping: the previous task is cancelled (no
`speech_started` was published, so nothing is retracted), its pending bargein
record is discarded, and a new task starts for the new event with a fresh
delay computed from the current `barge_in_delay_ms`. The pending bargein
record is single-slot per session.

### 9.6 Internal failure

If a state-machine invariant (§2.4) is violated mid-session, the session
emits `error { code: "internal_state_error", message }` and terminates the
transport. The violation is logged with the offending state snapshot.
Implementations do not attempt to recover; the property fuzzer (§15.5) is
where the violation class is ruled out, not the runtime.

## 10. Wire protocol

### 10.1 Inbound events

| Event | Valid in | Effect | Reject error code |
|---|---|---|---|
| `session.update` | Active | Merge fields per §11. | `session_update_invalid` |
| `input_audio_buffer.append` | Active | Append PCM to current buffer. | (silently ignored otherwise) |
| `input_audio_buffer.commit` | Active | Force commit (§7.1). | `input_audio_buffer_commit_empty` if below `min_speech_ms` |
| `input_audio_buffer.clear` | Active | Zero current buffer; do not rotate. | (silently ignored when Empty) |
| `conversation.item.create` | Active | Append item; emit `conversation.item.added` (alias `conversation.item.created`, §0.3) per I9. | `invalid_request_error` |
| `conversation.item.delete` | Active | Remove item by id. | `invalid_request_error` if id not found |
| `conversation.item.truncate` | Active | Adjust assistant item duration (client request). | `invalid_request_error` |
| `conversation.item.retrieve` | Active | Look up item by id; emit `conversation.item.retrieved` with full content (§7.5). | `item_not_found` |
| `response.create` | Active, `resp == None` | Create response (§8.1.1); honor body overrides. | `response_already_active` |
| `response.cancel` | Active, `resp != None` | Cancel as in §9.3 sans server-issued truncate. | `response_cancel_not_active` |
| `output_audio_buffer.clear` | Active | Drain pacer audio queue; emit `output_audio_buffer.cleared` (+ `stopped` if currently `started`). Does not cancel the response (§8.6). | (silently ignored if no audio in flight) |

The "Reject error code" column is normative: implementations emit exactly
this code when the precondition fails, with `event_id` set to the offending
inbound event id. Any other inbound event produces
`error { code: "unknown_event_type" }`; unknown events are never silently
dropped.

### 10.2 Outbound events

The canonical sequence for one clean turn (canonical names per §0.3):

```
session.created                                            (once per session)
session.updated                                            (per accepted update)
input_audio_buffer.speech_started      item_id=A
input_audio_buffer.partial_transcription                   (zero or more)
input_audio_buffer.speech_stopped      item_id=A
input_audio_buffer.committed           item_id=A
conversation.item.added                item_id=A           (user, in_progress)
conversation.item.input_audio_transcription.completed item_id=A
conversation.item.done                 item_id=A           (user, completed; optional, MAY be skipped on STT failure)
response.created                       id=R
response.output_item.added             item_id=B
response.content_part.added
output_audio_buffer.started            response_id=R              (emitted with first audio delta; §8.6)
response.output_audio_transcript.delta                      (zero or more)
response.output_audio.delta                                 (zero or more)
response.output_audio_transcript.done
response.output_audio.done
output_audio_buffer.stopped            response_id=R, audio_end_ms=played_ms  (§8.6)
response.content_part.done
response.output_item.done              item_id=B
response.done                          id=R, status=completed
                                       audio_end_ms=played_ms  (§8.5)
```

Item retrieval is out-of-band and does not appear in the canonical-turn
sequence: `conversation.item.retrieve(item_id=A)` MAY arrive at any point
during `Active`, and the matched `conversation.item.retrieved(item)` is the
only event the server emits in response (§7.5). Recognized aliases per §0.3
apply throughout: wherever an invariant (§10.3) names one spelling, it
applies to either.

Server-issued additions: `conversation.item.assistant_truncated` (§9.3),
emitted on barge-in commit or `response.cancel` while `played_ms > 0` and
distinct from the client-issued `conversation.item.truncate`; and
`session.done { reason }` at session termination.
`response.tool_progress` is RESERVED for future tool-call streaming.

### 10.3 Wire-level invariants

Machine-checkable from a captured trace (§15.2):

- **W1.** `response.done(id=R)` is emitted exactly once for each
  `response.created(id=R)`.
- **W2.** `response.*.delta` and `response.*.done` events for response R are
  emitted only between `response.created(R)` and `response.done(R)`.
- **W3.** `input_audio_buffer.committed(item_id=A)` is emitted after
  `input_audio_buffer.speech_stopped(item_id=A)` (or the triggering
  `input_audio_buffer.commit` event) and before
  `conversation.item.added(item_id=A)`.
- **W4.** `response.done(id=R)` carries `audio_end_ms` equal to `played_ms`
  at termination, **for all four statuses (`completed`, `cancelled`,
  `incomplete`, `failed`)** (§8.5).
- **W5.** *(guidance, not invariant)* The relative ordering of
  `input_audio_buffer.partial_transcription` and
  `input_audio_buffer.speech_stopped` is not guaranteed; clients tolerate
  either order. The invariant checker does not check W5; it documents the
  tolerance.
- **W6.** No `response.*` event with `response_id=R` follows
  `response.done(id=R)` on the wire. Late synthesis from cancelled responses
  is dropped at the dispatcher.
- **W7.** `conversation.item.assistant_truncated(item_id=A)` is emitted only
  when there exists a `response.done(id=R)` carrying
  `status ∈ {cancelled, incomplete}` that referenced `item_id=A`, AND the
  snapshotted `played_ms > 0`.
- **W8.** Every accepted `conversation.item.create(item_id=A)` from the
  client is followed by exactly one `conversation.item.added(item_id=A)` from
  the server, making I9 visible on the wire.
- **W9.** Every accepted `conversation.item.retrieve(item_id=A)` is followed
  by exactly one `conversation.item.retrieved(item.id=A)` (§7.5). Rejected
  retrievals (`item_not_found`) instead emit one `error` event referencing
  the inbound `event_id` and MUST NOT emit `conversation.item.retrieved`.
- **W10.** `output_audio_buffer.started(response_id=R)` is emitted at most
  once per response `R`, only after the first
  `response.output_audio.delta(response_id=R)`, and never after
  `response.done(id=R)`.
- **W11.** Every `output_audio_buffer.started(response_id=R)` is paired with
  exactly one `output_audio_buffer.stopped(response_id=R)` before
  `session.done`. `stopped` MAY appear before or after `response.done(id=R)`
  but MUST reference the same `played_ms` snapshot (§8.5 / §8.6).
- **W12 -- Deltas are flushed as produced (live-trace only).** This is *the*
  realtime-latency guarantee: ear-level latency is dominated by the producer
  (LLM tokens / TTS frames) plus transport, with the server adding at most
  `max_inter_delta_ms` of accumulation worst-case. Within a response `R`, the
  three delta-stream event types (`response.output_audio.delta`,
  `response.output_audio_transcript.delta`, `response.output_text.delta`, all
  keyed by `response_id=R`) carry payload the server produces incrementally.
  A v3 server MUST emit each chunk as soon as it has the chunk AND has the
  right to send it (`Created` phase or later, §2.3). It MUST NOT batch
  producer chunks beyond the predicted-flush burst below, and MUST NOT hold
  the final chunk(s) until the corresponding `.done` is ready.

  - **W12a -- Max inter-delta gap.** For each stream `S` within a response
    `R` with >= 2 delta events emitted **after** the predicted-flush window
    (§8.1.2), let `gaps[i] = delta[i+1]._t_ms - delta[i]._t_ms`.
    `max(gaps)` MUST NOT exceed `max_inter_delta_ms` (§17.6 default `1500`).
  - **W12b -- No terminal stall.** For each stream `S` within a response `R`
    with >= 1 delta event, `S.done._t_ms - S.delta[last]._t_ms` MUST NOT
    exceed `max_terminal_stall_ms` (§17.6 default `500`).

  **Predicted-flush exemption.** When a response leaves `Predicted` (§2.3,
  §8.1.2) the buffered pre-EOU tokens all become send-able simultaneously at
  `response.created` and flush in one burst bounded by
  `predicted_flush_grace_ms` (§17.6 default `200`). For deltas with
  `_t_ms <= response.created._t_ms + predicted_flush_grace_ms`, W12a's gap
  is measured from the first delta AFTER the window, not within it -- the
  burst is W12-conformant by construction. Servers without a `Predicted`
  phase have a zero-token flush window, and W12a applies to ALL deltas.

  W12 is live-trace only: canonicalized fixtures strip wall-clock timestamps
  (§15.4) and MUST set `_t_ms = null` on every event, at which point W12
  skips silently. The harness exposes the check with
  `--strict --live-timings`; CI gates against live captures only.

### 10.4 Data-channel framing

Each event is wrapped. Payloads <= `data_channel_fragment_max` bytes (default
900, §17.6):

```json
{"type":"full_message","id":"<event_id>","data":"<base64-json>"}
```

Otherwise split into N fragments, each <= `data_channel_fragment_max`:

```json
{"type":"partial_message","id":"<event_id>",
 "fragment_index":i,"total_fragments":N,"data":"<base64-fragment>"}
```

Fragments for a given `id` are emitted contiguously and in order;
implementations do not interleave fragments from different events on a single
data channel. WebSocket transports require no framing -- events are sent as
raw JSON text frames.

### 10.5 Error envelope

```json
{"type":"error","error":{
  "code":"<symbol>",
  "message":"<human readable>",
  "event_id":"<inbound-event-id-if-any>",
  "param":"<offending field, optional>"
}}
```

| Code | Class | Meaning |
|---|---|---|
| `invalid_request_error` | 4xx | Malformed inbound event. |
| `unknown_event_type` | 4xx | Inbound event type not in §10.1. |
| `session_not_active` | 4xx | Inbound event before `session.created`. |
| `session_update_invalid` | 4xx | `session.update` field validation failed. |
| `response_already_active` | 4xx | `response.create` while `resp != None`. |
| `response_cancel_not_active` | 4xx | `response.cancel` while `resp == None`. |
| `input_audio_buffer_commit_empty` | 4xx | Commit below `min_speech_ms`. |
| `client_too_slow` | 4xx | Outbound queue cap exceeded (§7.4). |
| `item_not_found` | 4xx | `conversation.item.retrieve` for an unknown id (§7.5). |
| `eou_kind_unsupported` | 4xx | `session.update` set `eou.kind` to an unsupported value (§6.2). |
| `eou_fusion_rule_unsupported` | 4xx | `session.update` set `eou.fusion_rule` to an unsupported value (§6.2.3 -- typically `gated` without trained gate weights). |
| `internal_state_error` | 5xx | Invariant violation (§9.6). |
| `vad_failed` | 5xx | VAD inference error (§4.4). |
| `stt_failed` | 5xx | STT inference error. |
| `model_load_failed` | 5xx | Required model failed to load. |

Client faults (4xx): the session continues. Server faults (5xx): the session
terminates after the error event is flushed. The §15.6 fixture set includes
one fixture per code; an implementation that declares a code but never emits
it fails its per-code fixture.

## 11. Session configuration

### 11.1 Schema

The Session object's full field set is defined by §17, which is authoritative
for names, types and defaults. On connection the server emits
`session.created` carrying a Session object populated from server defaults;
clients update fields via `session.update`.

### 11.2 Updates

`session.update` performs a deep merge. Every parameter in §17.1-§17.7 is
session-mutable; §17.8-§17.9 fields are process-scoped and rejected with
`session_update_invalid`. The server validates that field names exist on
Session, that values match the declared type and range from §17, and that
`instructions` is a non-null string.

Updates are atomic: **if any field fails validation, no field is applied.**
The implementation pattern is mandatory; see §11.2.1.

#### 11.2.1 Atomic apply pattern (mandatory)

**Parse-all -> validate-all -> commit-all.** Phase 1 parses and validates
every supplied field into a staging struct, never touching live session
state, and returns an error on the first invalid field. Phase 2 moves the
staged values into live state; no validation can fail there.

The anti-pattern is mutating state as fields are parsed, which leaves partial
writes behind when a later field fails validation. Conformance fixtures
`006-session-update-atomic` and `010-session-update-atomic-both-fields` pin
this: one valid field plus one invalid field, then a read-back asserting
neither was applied.

### 11.3 Hard timeout

A session terminates after `session_max_duration_s` (default 1800, §17.1).
Clients MAY shorten this via `session.update`; they MAY NOT extend it beyond
`session_max_duration_hard_cap_s` (process-scoped, §17.8). Termination emits
`session.done { reason: "max_duration" }` followed by transport close.
Clients reconnect to resume.

### 11.4 Reconciliation

**Default rule.** A parameter change applies to the next operation that reads
the field; in-flight operations keep the old value. Exceptions:

- **`turn_detection.type = "none"`**: an in-flight Speaking buffer collapses
  to Stopped at update time without arming `commit_timer` (commit fires on
  explicit `input_audio_buffer.commit`).
- **`turn_detection.silence_duration_ms`**: an armed `commit_timer` is
  rescheduled with elapsed time preserved; a new value placing the fire time
  in the past commits immediately.
- **`eou.silence_hard_cap_ms`**: rearmed; a deadline in the past commits
  immediately.
- **`session_max_duration_s`**: reschedules the hard-timeout timer with
  elapsed time preserved.
- **`sealed_buffer_retention_count`** lowered below the current count: oldest
  sealed buffers evict FIFO until count matches.

## 12. Transport

### 12.1 WebRTC

The server accepts `POST /v1/realtime` with
`Content-Type: application/sdp`; the body is the client offer, the response
the server answer.

The answer SDP is filtered to a single audio codec from the OPUS family.
Channel count is taken from the offer (mono or stereo); sample rate is 48000.
Non-OPUS codec entries (payload types, `rtpmap`, `fmtp`, `rtcp-fb`) are
removed before the answer is returned, admitting Twilio / Asterisk /
SIP-bridged clients offering `OPUS/48000/1` while still rejecting any
non-OPUS negotiation. The answer's bundled `m=` lines share `ice-ufrag` and
`ice-pwd` to match common WebRTC client assumptions (notably aiortc, which
emits distinct credentials per m-line).

OPUS codec parameters: `stereo=0|1` matches the negotiated channel count;
`useinbandfec=1` SHOULD be accepted (in-band FEC reduces packet-loss
artifacts on barge-in detection); `usedtx=0` is forced (DTX silence frames
complicate VAD); `cbr=0` (constant bitrate is not required); and
`maxaveragebitrate`, `maxplaybackrate`, `sprop-stereo` are accepted as
offered. `red` (RFC 2198 redundant audio) is rejected.

Audio ingress: opus -> s16 stereo -> polyphase resample to 16 kHz mono per
§3.0. Audio egress: TTS-native f32 mono per §12.4 -> 48 kHz {mono | stereo}
opus on a single `audio` track, channel count matching the negotiated SDP.

### 12.2 WebSocket

The server accepts `GET /v1/realtime` with WebSocket upgrade. Audio is
carried via `input_audio_buffer.append` (inbound) and
`response.output_audio.delta` (outbound; alias `response.audio.delta`,
§0.3), both base64-encoded at the session-configured `input_audio_format` /
`output_audio_format` (§3.3 and §12.4).

### 12.3 Transport-agnostic semantics

The state machine, event semantics and invariants in this document are
identical across WebSocket and WebRTC. Only framing (§10.4) and audio
carriage differ.

### 12.4 TTS egress pipeline

TTS adapters produce **mono f32 at the model's native rate** (Kokoro 24 kHz,
Piper varies per voice), and a **single resample-and-encode step at egress**
matches the session's `output_audio_format`. Implementations MUST NOT
downsample TTS audio to 16 kHz internally.

Accepted `output_audio_format` values:

| Value | Wire rate | Wire encoding |
|---|---|---|
| `pcm16` | 24000 | s16 LE mono |
| `pcm16_16k` | 16000 | s16 LE mono |
| `g711_ulaw` | 8000 | µ-law |
| `g711_alaw` | 8000 | A-law |

WebRTC always emits OPUS at 48 kHz on the audio track regardless of
`output_audio_format`; the data-channel `response.output_audio.delta` (alias
`response.audio.delta`, §0.3) carries the session-configured format in
parallel.

## 13. Identifiers

Event, item, response and session ids are server-generated. Default format:
24-character base32 with a type prefix -- `evt_` (data-channel and inspector
events), `item_` (conversation items), `resp_` (response objects), `sess_`
(sessions). The exact length and base are not load-bearing; clients treat ids
as opaque except for prefix-based type discrimination.

Implementations expose an `IdSource` abstraction so deterministic-replay
traces can substitute a counter-based generator. The default `IdSource` is
cryptographically random; the counter-based generator is the
production-non-default and tests inject it via dependency injection, never
via global mutable state.

## 14. Telemetry and observability

### 14.1 Inspector lane

Implementations expose an internal event stream parallel to the wire for
diagnostics. Inspector events do not reach the data channel; they live on a
separate transport mounted at `/v1/inspect` (WebSocket).

The lane is **normative**, not optional: the §15.5 property fuzzer drives
`check_state` through it, and §15.4 canonicalization applies uniformly to
wire and inspector events when both are captured into a unified trace.

#### 14.1.1 Event envelope

```
InspectorEvent {
    session_id:  string,
    seq:         u64,           // monotonic per-session, assigned by the relay
    ts_mono_ns:  u64,           // monotonic clock at emission
    ts_wall:     f64,           // wall-clock seconds since epoch
    lane:        LaneId,        // see 14.1.2
    kind:        string,        // lane-scoped discriminator
    corr: {                     // correlation handles current at emission time
        turn_id:     string?,
        item_id:     string?,
        response_id: string?,
        phrase_id:   string?,
    },
    span_id:     string?,       // OpenTelemetry span id (16 hex chars) if present
    payload:     object,        // kind-specific fields
}
```

The envelope is **normative**: anything publishing to `/v1/inspect` MUST emit
this exact shape.

#### 14.1.2 Lane vocabulary

`LaneId` is a closed enum:

| Lane | Purpose |
|---|---|
| `audio_level` | Per-window RMS samples for both `mic_in` and `tts_out` channels. |
| `vad` | VAD detection events: `pending_start`, `confirmed_start`, `rejected_pending`, `confirmed_stop`. |
| `stt` | Streaming STT progress: `partial`, `final`. |
| `turn` | Turn-level lifecycle: `turn_start`, `user_committed`, `bargein_context`, `turn_end`. |
| `bargein` | Barge-in lifecycle (§9): `bargein_pending`, `bargein_fired`, `bargein_cancelled`, `bargein_suppressed`. |
| `eou` | End-of-utterance classifier events (§6.7): `scored`, `hard_cap_fired`, `cancelled`, `fallback`. |
| `llm` | Upstream LLM call: `plan_start`, `first_token`, `done`. |
| `response` | Response lifecycle bracket: `plan_start`, `done`, `cancelled`. |
| `tool` | Tool-call dispatch and result. RESERVED until tool-call streaming ships. |
| `tts_req` | TTS synthesis requests (one per request to the TTS adapter). |
| `tts_chunk` | TTS audio chunks produced (one per encoded frame batch). |
| `tts_pacer` | Pacer state samples; `played_ms` (sampled at 10 Hz; §7.3). |
| `wire` | Outbound wire events not already on a dedicated lane (catch-all for control frames). |
| `state` | State-machine transitions (§14.2): `transition { phase, from, to }`. |
| `error` | Errors and invariant violations: `invariant_violation { violation, state_snapshot }`, `raised`, `failed`, `dropped`. |

Adding a lane is **non-breaking** (§19); removing or renaming one is
breaking.

#### 14.1.3 Required emissions

Every implementation MUST emit: `vad` -- `pending_start`, `confirmed_start`,
`confirmed_stop`, `rejected_pending`; `bargein` -- `bargein_pending`,
`bargein_fired`, `bargein_cancelled`, `bargein_suppressed`; `eou` -- per
§6.7; `tts_pacer` -- `played_ms` sampled at >= 10 Hz while
`resp ∈ {Streaming, Drain}`; `state` -- `transition` per §14.2; `error` --
`invariant_violation` on every §2.4 violation.

Other lane/kind pairs in §14.1.2 are RECOMMENDED but not required.

#### 14.1.4 Relay and transport

The lane is served as a per-session WebSocket under `/v1/inspect`. The relay
buffers events with a bounded queue (default `inspector_relay_cap = 1024`,
oldest-dropped on overflow with an `error.dropped` event injected).
Subscribers connect at any time and receive only events emitted after
subscribe; the lane is not a durable log. Implementations MAY persist events
to disk separately under `inspector_session_dir`.

The relay is keyed by `session_id`; correlation across the session comes from
the `corr` envelope fields, mutated as the session moves through turns and
items.

### 14.2 Transition observability

State-transition events are runtime-toggled via the `inspector.transitions`
config field, with a sampling rate in
`inspector.transitions_sample_rate` (default 1.0 in development, 0.0 in
release builds).

### 14.3 Tracing

OpenTelemetry spans are created at session lifetime, per turn (commit ->
terminal `response.done`), per LLM call, per STT call, and per TTS synthesis
call.

### 14.4 Capabilities

`GET /v1/realtime/capabilities` returns a JSON object describing feature
support, and is unauthenticated:

```json
{
  "rfc_version": "v3",
  "features": {
    "eou_kinds": ["vad", "heuristic", "text", "audio", "fusion", "integrated"],
    "input_audio_formats": ["pcm16", "pcm16_16k", "g711_ulaw", "g711_alaw"],
    "output_audio_formats": ["pcm16", "pcm16_16k", "g711_ulaw", "g711_alaw"]
  }
}
```

## 15. Testability

### 15.1 Differential traces

Implementations are testable against captured wire traces: replay an inbound
event trace and assert the outbound trace matches a golden file modulo
allowed divergence (timestamps; ids if random). The `IdSource` substitution
(§13) makes traces byte-identical once the random component is removed.

### 15.2 Wire-invariant assertions

`assert_trace_invariants(trace) -> Result<(), Vec<Violation>>` takes a
serialized trace and returns the set of violated invariants from W1-W4 and
W6-W12 (W5 is guidance, §10.3). It is the primary regression gate; CI runs it on
every fixture trace.

The reference implementation is `conformance/lib/trace_invariants.py`, one
`check_*` function per invariant. Other-language implementations MAY invoke
the reference module directly (Python FFI such as `pyo3`, or a subprocess) or
ship a parallel implementation. A parallel implementation MUST be
cross-checked against the reference on the shared fixture corpus in CI on
every PR; the linkage mechanism is not prescribed.

### 15.3 Synthetic audio fixtures

Each fixture ships expected `eou.score` ranges (per kind) and expected commit
timing, so a model regression surfaces loudly rather than silently degrading
UX. Required fixtures:

- **Clean utterance.** One sentence then silence; commit at
  `audio_end_ms + min_delay_ms`.
- **Mid-utterance pause.** A 200-300 ms internal pause straddling
  `silence_duration_ms`; commit MUST NOT fire on the pause.
- **Barge-in straddling drain.** User speech entering an assistant response's
  trailing drain window; exercises §9.1 atomicity.
- **EOU re-entry mid-`commit_timer`.** A long trailing pause that fires
  `commit_timer`, then resumed speech that cancels it (§6.6).
- **Silence-only input.** No voiced audio; no commits, no responses.
- **Short utterance below response threshold.** "uh-huh" alone then silence;
  commit fires for the conversation record but no response is auto-created
  because `audio_ms < min_speech_for_response_ms`.
- **Hard-cap firing during EOU stall.** An EOU mock that never returns;
  commit MUST fire at `silence_hard_cap_ms`. Catches the "clamp instead of
  parallel timer" bug class (§6.3.1).
- **Hard-cap firing with low EOU score.** EOU returns `p < threshold` with
  `delay_ms = max_delay_ms > silence_hard_cap_ms`; the hard cap fires first.
- **Per-status `audio_end_ms`.** Four fixtures, one per `response.status`,
  asserting `audio_end_ms` is present and equals `played_ms` at termination
  (§8.5).
- **Atomic `session.update`.** One valid field plus one invalid; neither is
  applied (§11.2.1).
- **Simultaneous barge-in.** Two `vad.speech_started` within
  `barge_in_delay_ms`; §9.5 single-slot replacement.

### 15.4 Trace canonicalization

Differential testing canonicalizes the trace before comparison:

1. **Wall-clock timestamps** (`ts_ms`, `created_at`): replaced with the event
   ordinal index in the trace.
2. **Random ids**: replaced with `<TYPE>_N` where TYPE is the prefix (`sess`,
   `evt`, `item`, `resp`) and N is the order of first appearance.
   Cross-event identity is preserved.
3. **Floating-point fields with stochastic origin** (`eou.score`,
   `vad.probability`, transcript token logprobs): rounded to 3 decimals.
4. **Audio payloads** (`audio` base64 fields): replaced with their length in
   bytes; byte-identical audio across runs is not a conformance requirement.
5. **Free-form transcript text**: structurally compared by default (presence
   and ordering of delta events); byte-equal comparison is opt-in via
   `--strict-text`.

`canonicalize_trace(trace) -> CanonicalTrace` and
`trace_diff(a, b) -> Option<Index>` are the named APIs; the trace-diff reference
implementation is `conformance/lib/trace_diff.py` and the id-canonicalization
reference is `CanonicalizeTrace` in the Go conformance suite. The §15.2 linkage
rule applies: invoke a reference directly, or ship a parallel implementation
cross-checked against it in CI.

### 15.5 Property fuzzer

Implementations expose a property fuzzer driving the state machine with a
random walk over the legal event space.

**Mandatory op set:** `vad.speech_started`, `vad.speech_stopped`,
`input_audio_buffer.commit`, `input_audio_buffer.clear`, `response.create`
(in any phase, to exercise rejection paths), `response.cancel`,
`session.update` (valid and invalid bodies, to exercise §11.2.1),
`transcription_complete` (synthetic STT verdict), `llm_complete`,
`tts_drained`, `barge_in_delay_expire`, `commit_timer_expire`,
`hard_cap_expire`.

**Schedule:** 5,000 steps x 1 fixed seed for the headline CI gate, plus
1,000 steps x 6 randomized seeds for the multi-seed extension. After every
step `check_state(state)` runs (§2.4); a failure aborts the run with the
offending state and the seed/step for replay.

**Emission capture:** the fuzzer's emitted events are captured into an
in-memory trace and run through `assert_trace_invariants` at the end of each
seed.
Because that trace is independent of the implementation's own test code, it
catches the class where an implementation bug is mirrored in its assertion.

### 15.6 Conformance fixtures

Fixtures live at `conformance/` at the repository root, **not** under any
per-implementation directory. Each is one directory under
`conformance/fixtures/` carrying `input.jsonl` (inbound events),
`expected.jsonl` (canonicalized expected trace), `README.md` (what it
exercises and its spec pins) and any input artifacts. Reference
invariant/diff modules live in `conformance/lib/`; the runner is
`conformance/runner/run_fixture.py`. `conformance/README.md` carries the
per-band inventory, the naming convention and the add-a-fixture procedure.

CI invokes the runner against every fixture. **A failing fixture is a release
blocker.** Adding a fixture needs no RFC revision; modifying an existing one
is an RFC change, because it implies a wire-protocol behavior change.

An implementation shipping a parallel (non-Python) trace-invariant or
canonicalization implementation MUST run a CI cross-check diffing its output
against the reference on the shared corpus.

### 15.7 Bug-postmortem fixtures

Every bug a v2 implementation exhibited that v3 closes has a regression
fixture in the corpus, and those fixtures run on every CI build.

## 16. Out of scope

Deferred to follow-up RFCs:

- Tool calling and `response.tool_progress` semantics.
- Audio-direct-to-LLM mode (raw audio parts forwarded to chat completion
  without intermediate transcription).
- Speaker diarization on the input track.
- Multi-track WebRTC inputs.
- Server-initiated reconnection / session resumption.
- VAP-style continuous turn-state prediction (Ekstedt & Skantze 2022;
  arxiv:2401.04868).
- Speaker-channel separation for backchannel detection on a separate channel
  (Moshi-style full-duplex): out of scope for the half-duplex pipeline this
  spec describes.
- Backchannel lexicon filtering. The duration backstop
  (`min_speech_for_response_ms`, §17.4) is the always-armed defense;
  domain-specific lexicons are deployment configuration.

## 18. Conformance

An implementation is v3-conformant when it passes every fixture under
`conformance/fixtures/`, links the canonical `assert_trace_invariants` (§15.2)
and `canonicalize_trace` (§15.4) references, and runs the §15.5 fuzzer for
>= 5,000 steps x 1 seed in CI on every PR.

There is no partial conformance. A failing fixture is a release blocker.

## 19. Versioning policy

This document is `v3`. The next version is `v4`, not `v3.1`.

A change is **breaking** (requires a version bump and fixture update) if it
adds a new outbound event type, removes or renames an existing outbound
event, changes the meaning of an existing field on an outbound event, changes
a wire invariant from W1-W8, or changes the §11.2 atomic-update guarantee.

A change is **non-breaking** (allowed within the same version line) if it
adds a new optional inbound field with a documented default, a new error code
(clients tolerate unknown codes), a new fixture, or a new inspector event.

Tightening a default value (e.g. lowering `silence_hard_cap_ms` from 5000 to
4000) is non-breaking *for the version*, but operators MUST review the change
in the changelog.

## Appendix C. Implementation guidance (non-normative)

- **C.2 Typed timestamps and durations.** `Millis` (session-relative
  timestamp) and `DurationMs` (span) SHOULD be distinct named types even
  though both wrap a 64-bit integer; conflating them produces the
  `audio_end_ms = duration_of_buffer` bug.
- **C.3 Sample-rate-carrying audio types.** Audio buffers SHOULD carry sample
  rate and channel count in their type, not as out-of-band annotations.
- **C.4 Wire-event alphabet as enum.** Event-type names SHOULD be a closed
  alphabet (enum, sum type, const set), not free strings.
- **C.5 Single canonical state store.** `SessionState` (§2) is the single
  canonical store of session phase. Do not duplicate fields onto a "session
  config" and a "runtime context" struct that drift; derived runtime data
  belongs on a separate struct that does not participate in invariant
  checking.
- **C.6 Emission gate.** All `response.*` emission SHOULD go through one
  helper that consults the `RespPhase` discriminator first -- the single
  chokepoint for fragmentation, queue accounting and inspector mirroring.

### C.7 played_ms snapshot

The `played_ms` snapshot consumed by §9.1's `BargeInEffect` is taken inside
the same critical section that decides to cancel; reading it outside the
mutex is a TOCTOU bug. Pass the cancel path a snapshot callable, not a
snapshot value.
