# CUDA serving architecture

Three parts: the paged KV cache, continuous batching with M=B batched decode,
and the graphed Eagle3 verify loop the spec-decode serving path uses. Validated
vs open is the private status ledger § "PRD phase-by-phase" (phase 2
Engine, phase 5 Spec-decode). No serving-knob reference page exists — grep `NV_`
under `rust/src/` for the live set.

## Qwen3.8 bounded parallel serving

Use an eight-lane pool for concurrent Qwen3.8 requests while retaining the
existing batch numerical route:

```sh
NV_QWEN35_DENSE_CUDA_SERVE=1
NV_Q38_BATCH=1
NV_Q38_BATCH_SIZES=1,2,4,8
NV_Q38_BATCH_GEMM=0
NV_Q38_BATCH_SOLO_ARMS=0
NV_KV_MAX_SEQ_LEN=8192
NV_DRAFTER=mtp
NV_Q38_BOOT_WARM_PREFILL=1
NV_Q38_BOOT_WARM_DRAFTER=1
NV_CHAT_CONCURRENCY=16
NV_CHAT_QUEUE_MS=3000
NV_SSE_SEND_TIMEOUT_MS=1000
```

These are process environment settings. Increasing the context limit multiplies
the private KV allocation across every lane; validate a larger context before
raising it. More than eight active lanes requires the numerically different
`NV_Q38_BATCH_GEMM` route. Sixteen simultaneous requests over eight lanes are
two cohorts, not a sixteen-row GPU batch. A lone request retains MTP; a cohort
uses batched decoding without MTP. Late arrivals wait for the active cohort to
drain because eager prefill invalidates its captured graphs. Cohort prompts
prefill sequentially; a wider decode pool does not ingest long prompts
simultaneously, and later members wait for earlier prefills.

Six- and eight-row decode use the grouped E4M3 GEMV through
`Qwen38BatchE4m3GroupScopeGuard`. The scope leaves prefill, solo, MTP, other
models, and other physical batch sizes on their existing default routes.
A partially occupied cohort uses the route selected by its padded bucket size.
`NV_Q38_E4M3_GROUP=0` restores the previous six- and eight-row routes; explicit values
retain their existing process-wide meaning. The kernel identity suite
(`gemv_e4m3_group_identity`) and the complete-logit hashes emitted by
`qwen38_batch_step_profile` certify the route change. Compare the batch hash
between configurations, and separately verify the solo reference hash is
unchanged; batch-versus-solo equality is not the contract. Performance evidence
lives in the private run ledger under the `q38-safe-parallel` and
`q38-168k-e4m3group-b6` ladders.
The published eight-lane figures in the private status ledger at lines 3401-3436 and
3456-3466 describe the `NV_Q38_E4M3_GROUP=0` route. Its four-lane and solo
figures retain their original interpretation. The unchanged escape also
reproduces the corresponding pre-scope rows in the performance store.

`QwenBatchScheduler` bounds pending jobs by the larger of the lane count and
`NV_CHAT_CONCURRENCY` (the latter is capped at 64). `NV_CHAT_QUEUE_MS` bounds
waiting for admission, including while another cohort occupies the GPU. Zero
means reserve an idle dispatcher immediately or reject; it disables the
formation delay. Solo requests also have bounded waiter count and lock wait.
Expired or disconnected requests are removed before prefill, and disconnected
active members are removed before another decode step.

Capacity rejection returns HTTP 503 with `Retry-After: 1` on chat completions
and Responses; Messages preserves Anthropic's 529 overload status. The error
says "try later". A recognized CUDA allocation failure is retryable too.
An interrupted generation cannot become a successful empty or truncated
completion. Once streaming headers have been sent, failure is an explicit
stream error; it cannot change the HTTP status. Invalid context length remains
a client error. Queue deadlines do not recover a wedged GPU or a dead process.

The suites covering overload and recovery are `qwen_overload_http` and the
real-weight `qwen38_capacity_e2e`. The latter exercises both solo and batch
engines separately. a private ladder record measures completed in-process
Axum HTTP/SSE waves, excluding network transport, with a deliberately long queue
budget and verifies actual cohort sizes;
it complements the short-queue rejection tests and is not an overload policy.

For a 168,000-token prompt, configure `NV_KV_MAX_SEQ_LEN_Q38` and, when using
batch lanes, `NV_Q38_BATCH_KV` to cover the prompt plus completion and any
speculative headroom. The default batch cache limit is 32,768 tokens.
Explicit `NV_Q38_PREFILL_CHUNK=4096` bounds batch lane prefill to the existing
chunked serving route. Unset, zero, invalid, and empty settings retain the
batch one-shot route; a prompt no longer than the explicit chunk also keeps
that route. The solo serving route continues to default to chunking.
Validate real prefill peak memory before increasing the lane count: synthetic
KV decode measures steady-state decoding and omits prompt ingestion work.
The `qwen38_batch_chunked_prefill` suite separately checks the chunked serving
reference and the old one-shot reference, including continuation and lane
reuse after graph capture. Chunked-reference equality alone does not qualify
a batch default change.

`NV_CHAT_QUEUE_MS` ends at admission. Qwen workers emit `Started` after
successful prefill or MTP initialization, so a caller's `timeout` or
`x-request-timeout-ms` covers that work before streaming headers. Prefill OOM
also returns a retryable response before headers. The worker retains its model
lock or scheduler reservation after a caller timeout until outstanding work
exits; another request cannot reuse it prematurely. An admitted prefill has
no cancellation checks between chunks, and callers without a deadline have
no first-event time limit. Chunking bounds temporary work but does not
interrupt running CUDA operations. MTP additionally retains the prompt's
trunk hidden rows for drafter initialization; its memory and latency exceed a trunk-only prefill measurement.

The actual-prefill instrument in `qwen38_prefill_depth` records the full CFX
context hint and reports zero generated tokens for prefill-only runs.
`NV_CTX_TOKENS=168000` uses an exact token count; the parser's `168k` shorthand
means 172,032. Optional `NV_PREFILL_DECODE_TOKENS=N` generates a fixed-length
greedy continuation from the real cache, counting the first token sampled
from prefill logits and timing the remaining N-1 eager forwards separately.
Those timings include host logits, argmax, and synchronization; they do not
measure HTTP or MTP serving, and deterministic-token input is not a quality
corpus.

For a 262,144-token total window, set both `NV_KV_MAX_SEQ_LEN_Q38=262144`
and `NV_Q38_BATCH_KV=262144`; the prompt must leave room for generation and
speculative verification. Every batch lane reserves the full configured
capacity. MTP also needs a solo cache while the lane pool remains allocated.
Include six in `NV_Q38_BATCH_SIZES=1,2,4,6,8` so the memory planner can select
it when eight does not fit. Read the actual lane count from the boot plan;
client concurrency can exceed resident lanes only through the bounded queue.
The default queue budget can expire while earlier cohort members prefill.
The default VRAM budget is 80% of device memory. `NV_VRAM_BUDGET_GIB` can
select a larger process-specific budget after real prefill and MTP peak-memory
validation; keep the planner and its separate solo-cache reserve enabled.
Use `NVK_SHELL=.#cuda-no-models` for Qwen-only instruments and inspect the
auxiliary items in the plan. The shell can still discover `rust/models` and
set `SPEACHES_PLUS_MODELS`; inherited or discovered model settings may reserve
engines that a chat-only test never loads.

`NV_Q38_BPROF_MAX_SEQ` separates allocated capacity from synthetic decode
start depth in `qwen38_batch_step_profile`. The real graphed MTP depth suite
uses `NV_Q38_MTP_MAX_SEQ` for the same distinction and requires at least 256
timed emitted tokens for its output fingerprint. Its effective decode rate
uses total emitted tokens divided by decode wall time, not a step median.

The long mode of `qwen38_throughput_e2e`, selected by
`NV_Q38_HTTP_PROMPT_TOKENS`, calibrates the official rendered prompt to an
exact token count and verifies returned usage. It reports actual lane capacity,
per-request terminal outcomes, queue-inclusive first-token latency, and
successful completion tokens over the whole wave. Rejections are reported
separately; an all-rejected wave has no successful decode rate. Its long queue
budget is a benchmark setting, not an interactive serving recommendation.
An early EOS may report fewer tokens, but a `length` finish must consume the
requested generation budget. Percentiles describe the observed wave, whose
sample count is reported; they do not estimate production tail latency.
MTP acceptance depends on the workload, so pair repeated-text and freeform
measurements before choosing a speculative configuration.

CUDA Qwen serving starts fresh prompt state on each request: solo engines reset
or allocate caches, batch prefill resets its lane, and MTP rebuilds trunk and
drafter state. The test-only primed-state dump/restore path is not an HTTP
prefix cache. Reusing a prefix requires both attention KV and GDN convolution
and recurrent state, plus compatible positions and immutable snapshots;
shortening attention KV alone cannot rewind GDN state.

`NV_Q38_SOLO_DEVICE_ARGMAX=1` opts eligible greedy solo graph decoding into
device-side winner selection. Prefill keeps checked host sampling, and a zero
device winner also uses that path so an all-nonfinite row cannot become a valid
token. Penalties and other sampling modes keep the host sampler. The real HTTP
suite `qwen38_device_greedy_http` compares host/device/host output and usage;
this option does not change the MTP route.

The attention experiment's `qwen38_tc_corpus` gate uses immutable prose and code
at both short and long depths with the full configured cache capacity. Baseline
and null processes must match every logit word before the tensor-core arm is
adjudicated. Perplexity and accuracy bounds are separate from its strict
one-BF16-ULP cross-winner rule; passing only the former does not qualify the
route. Reference artifacts bind the executable, checkpoint, corpora, settings
and captured kernel census. Changing any of those requires fresh references.

## Laguna bounded long-context serving

Laguna's configured KV limit is a hard request ceiling. A request cannot enlarge
its cache to accommodate an oversized prompt or completion. A shared admission
lock excludes eager execution while speculative or batch jobs own the model.
Worker jobs retain their reservation through cancellation cleanup, and eager
requests hold exclusive ownership through GPU completion. Waiter count and one
absolute admission deadline are bounded by `NV_CHAT_CONCURRENCY` and
`NV_CHAT_QUEUE_MS`. Persistent
speculative or batch caches can coexist with one eager cache; the memory plan
must reserve that headroom. Laguna does not automatically shrink its lane pool
to fit available VRAM.

The speculative worker uses a bounded job queue and checks client liveness
before prefill, between prefill chunks and during decoding. Admission ends the
queue deadline; a caller deadline continues to cover prefill. HTTP streaming
starts only after prefill produces a token. Worker errors do not trigger a
second eager allocation, and lost events or a missing backend completion cannot
become a successful truncated answer. The `laguna_loop::overload_tests` suite
covers queue limits, cancellation, all three HTTP surfaces and recovery.

Laguna spec and batch workers keep a preallocated device probe. After a
request error, a failed probe produces the exact worker-retirement marker;
`LagunaSpecReservation::observe` closes shared eager/spec admission before
releasing the failing reservation, even if its client has disconnected.
The worker delivers terminal errors to active and queued jobs and exits.
A successful probe preserves the request error and its cause. The serial
spec worker classifies failures inside a validated execution as retryable and
publishes the error before prefix cleanup and health probing. It retains the
callback reservation until cleanup finishes; a later failed probe still sends
the exact retirement marker. Input validation and cancellation keep their
existing behavior. The HTTP adapters return their overload response before
headers, or a terminal error event after headers. This early publication does
not cover a GPU call or destructor that never returns. Healthy requests
perform no additional probe readback. The probe, state destruction and worker
join can themselves wait on the driver; retirement is not a bounded CUDA
recovery mechanism. Initialization failures retain the builder's existing
required/optional engine policy.

`NV_LAGUNA_BATCH_GRAPH=1` selects two persistent M1 graph slots. It requires
`NV_LAGUNA_BATCH=2`, `NV_LAGUNA_BATCH_INTERLEAVE_PREFILL=1`, enabled spec-worker
serving, `NV_LAGUNA_SERVE_DRAFT=0`, packed DFlash disabled, and
`NV_LAGUNA_FP8_KV` unset. Each slot owns its BF16 cache and retained graph;
decode visits active slots sequentially, with GPU batch size one. Chunked
prefill and request admission share that loop. Both slots must capture and
replay before startup succeeds; explicit graph selection refuses initialization
failure instead of switching to per-request serving. Unset or zero preserves
the eager batch route. `BatchM1State` logs actual captured node counts and
lifetime replay counts, including warmup and prior requests. These counts do
not establish simultaneous GPU execution or per-request throughput.

Experimental `NV_LAGUNA_BATCH_GRAPH=m2` shares projections and fused routed
MoE across two active decode rows. It retains separate fixed-scale FP8 full
attention caches and BF16 sliding caches, with per-lane attention and positions.
The physical masks `01`, `10` and `11` each have a retained graph; an inactive
lane does not advance. Capture uses the model's explicit CUDA stream and a
Candle host-metadata cache spanning warmup and capture. The owner borrows this
stream and must not clear another graph owner's caches during teardown.

`validate_m2_graph_selection` enforces the two-lane, greedy, draft-disabled
configuration, direct FP8 prefill, prefix reuse disabled, FP8 XQA and fused
NVFP4 routed MoE. Startup must capture and replay every mask and refuses
per-request fallback. This mode is distinct from sequential M1 graph slots.
Qualify its exact source composition with the real-weight graph suite in
`laguna_batch_graph`, then measure HTTP completion, admission, cancellation and
the offered concurrency curve. Short-prefix graph identity does not establish
deep-context throughput, task quality or usable memory headroom.

The prepared `m2-spec` worker retains a draft context-commit graph per physical
lane and consumed length of one, two or three tokens. A full draft ring replays
the existing context arithmetic against fixed buffers; partial windows use the
existing eager append. Auxiliary inputs and positions are staged before replay.
Target rollback precedes the commit, and draft frontiers advance only after the
shared success synchronization, before token emission. Reset requires an idle,
healthy commit owner; failed GPU work retires the worker through the retryable
error path. The suite covering context capture and lifecycle
(`m6_context_commit_graph_preserves_real_auxiliary_window_and_proposer`) compares
initialized ring bytes and subsequent proposer logits with eager append. It does
not qualify changes to weight precision, verifier arithmetic or corpus quality.

`NV_LAGUNA_PREFILL_CHUNK` accepts 256, 512, 1024, 2048, 4096 or 8192 tokens
and defaults to 1024 (user sign-off 2026-09-12; `=256` restores the reference
width). Sliding storage reserves `window + chunk` rows, clipped to KV
capacity; full-attention capacity is independent of chunk size. The
interleaved worker yields between chunks. Select a production value using
corpus quality and resident-decode latency beside a competing prefill.

`NV_LAGUNA_PREFILL_FUSED_NORMROPE` combines multirow CUDA BF16 Q/K
normalization, partial RoPE, scaling and output conversion. It retains the
BF16 rounding boundary after normalization; reduction and RoPE arithmetic
use FP32. `NV_LAGUNA_PREFILL_FUSED_GATE` combines per-head softplus and
attention gating, with FP32 softplus followed by BF16 gate rounding and
multiplication. Both are on by default (user sign-off 2026-09-12; the ladder
final-row hash is identical with them on or off at 2048/32768/168000, so the
fusions are bitwise); `=0` restores the unfused chains and their launch order. The helpers retain
CUDA input read guards through enqueue. Weight formats, cache readers and
captured decode bodies are unchanged. Other eligible multirow eager calls
can also use these hooks. The suite covering the primitive chains
(`laguna_r3_prefill_fused_elementwise`) uses real configuration with synthetic
inputs and separately reports ordinary and signed-zero differences; actual
serving-route and task-quality evaluation remain separate requirements.

`NV_LAGUNA_PREFILL_FLASHINFER=1` selects the native pinned FlashInfer full
attention prefill kernel for concrete BF16 `LagunaKvCache` instances. It uses
the committed length after appending the chunk, splits KV work according to
kernel occupancy, and reuses cache-owned scratch on one CUDA stream. The
wrapper validates shapes and capacity and rejects stream migration or adapter
errors. Sliding attention and single-token decode retain their existing routes;
the FP8 cache does not select this BF16 implementation. Weight precision is
unchanged. The flag defaults off pending quality evaluation of the changed
attention reduction. Different generated output alone does not quantify task
quality loss; a routing parity test with the flag enabled in both arms does
not evaluate old-versus-new attention numerics.

`LagunaStepGraph` retains the selected BF16 or FP8 cache for its lifetime.
`NV_LAGUNA_FP8_KV` uses presence semantics; leave it unset to select BF16.
`NV_LAGUNA_FP8_UNIT_SCALE=1` selects the immutable `FixedOne` FP8 scale policy
for both eager and captured writes. Dynamic per-row scales and fixed-unit
bytes are different cache formats and cannot share a reader by relabeling
metadata. Selecting fixed-unit policy with a BF16 cache is an error.

The same prefill opt-in selects direct E4M3 KV reads for a `FixedOne` full
layer through `LagunaKvCacheFp8::try_prefill_attention_fp8`. Queries and output
remain BF16. The hook checks the initialized layer span and prepared query
tail, then retains one stream-bound split workspace without a BF16 KV shadow.
Dynamic-scale and sliding caches keep their existing paths. Selected-route
errors propagate instead of silently switching to a different cache reader.
`Gemma4Cache for Box<T>` forwards the optional prefill hook, including its
errors, so boxed HTTP caches reach the same concrete override. The suite
covering boxed dispatch (`boxed_prefill_dispatch_tests`) checks this trait
boundary; concrete-cache CUDA tests alone do not prove the HTTP route.

The target-scoring instrument `laguna_serving_quality` uses an immutable
chat-wrapped continuation after real chunked prefill at capacity262144.
It compares complete F32 logits from M1 or M3 graphs with an explicitly
selected BF16 or FixedOne FP8 cache. A separate bitwise reference/null pair
is required before candidate scoring. PPL, top-one accuracy and winner-gap
diagnostics record numerical differences; completing the measurement does
not adjudicate quality or qualify DFlash acceptance and HTTP recovery.

`NV_LAGUNA_XQA=1` and `NV_LAGUNA_XQA_FP8=1` select the external pinned native
XQA adapters for BF16 and fixed-unit FP8 full attention, respectively. Each
requires its matching adapter directory, row-specific cubins and a compatible
cache. Supported graphs have one, two, three or five query rows, and physical
capacity is a multiple of 128 up to 262144. Sliding layers retain their BF16 ring. Retain
the actual adapter, cubin and server identities with fired route evidence;
an environment variable alone does not establish successful graph selection.

HTTP speculative acceptance copies the active XQA span status into its existing
acceptance readback and rejects a nonzero status before returning the round's
tokens. A checked acceptance error cannot enter host acceptance fallback.
Earlier valid streamed tokens remain delivered; the failing round supplies an
error instead of a successful completion. This status covers invalid cache
spans, not nonfinite logits or recovery from a hung CUDA driver.

DFlash target acceptance separately rejects NaN, positive infinity and rows
without a finite candidate. Negative-infinity masks remain valid when the
row contains a finite candidate. The CUDA reduction checks every verifier
row before returning accepted tokens, including rows beyond the first draft
mismatch; its existing scratch and acceptance readback carry the failure.
The shared proposer argmax output remains a bounded token ID. Host fallback
also checks target logits, so it cannot turn a numeric rejection into a
successful round. This guard does not validate draft logits or plain decode
and does not recover a stalled CUDA driver.

The same checked target reduction validates the host-visible prefill anchor
in plain, speculative and batch serving. Eager batch decode validates every
target row before emitting any lane's tokens. Invalid rows return an explicit
retryable error; finite rows retain first-index tie behavior. These checks
reuse existing host readbacks. Captured M1 device argmax and draft proposal
logits remain outside this host-row guard.

`NV_LAGUNA_DFLASH_DEVICE_TRANSPORT=1` requests direct device draft IDs for
HTTP serving. Unset or `0` preserves host transport. Eligible rounds require
packed draft weights, fixed K, a relaxed context ring, no lookup proposal,
Vegas disabled and an existing verifier bucket. The proposer and verifier
own their buffers through the checked acceptance readback. Device-route
errors terminate the request before emission; length-only host placeholders
cannot enter host verification or acceptance fallback. The first verifier
creation and unsupported rounds keep host transport. Retain actual completed
device-round counters when measuring this optional path.

Verifier rows 2-8 project q/k/v/gate, norm+rope and the gated o_proj on the
m=1 decode kernels (`NV_LAGUNA_QKVO_ROWS`, `NV_LAGUNA_O_GATE_FUSE`; unset is
on, `=0` restores the M-row GEMMs), bit for bit per row with the plain step.
`NV_LAGUNA_VERIFY_SLIDING_ROWS` selects the optional sliding-attention rows
kernel. The sliding kernel receives compact length after append and
subtracts the query-row count to recover the committed prefix; using the
appended length directly as the prefix violates causality. Kernel primitive
equality and repeated output on one route do not qualify the complete
fixed-unit or changed-attention trajectory. These selectors do not change
the packed target or draft weight policy.

DFlash RoPE tables use the draft checkpoint's declared position capacity.
`append_context` checks nonnegative contiguous positions and the full span
before any CUDA access; proposals also validate their span. The capacity and
invalid-position recovery suites in `laguna_dflash` and `laguna_dflash_verify`
cover the old boundary and long-context positions. A successful HTTP response
alone does not prove speculation: retain the completed request's
`graph_propose_rounds` and `eager_propose_rounds` alongside acceptance evidence.

NVFP4 describes the checkpoint's quantized weight groups. Record the draft
weight format and KV-cache format separately; a BF16 KV comparison still uses
the NVFP4 target. `NV_LAGUNA_HOST_MOE` must be absent for GPU MoE execution;
setting it to `0` still selects the host path.

The publisher's `DFlash-NVFP4` source stores BF16 weights trained against an
NVFP4 target. Its name does not prove packed draft execution.
`NV_LAGUNA_DFLASH_NVFP4=1` packs supported large draft projections at load time
and requires an explicit existing `NV_LAGUNA_DFLASH_DIR`, enabled speculation
and a ready packed draft. Load or warmup failure rejects the model instead of
silently selecting plain serving. Retain `DflashQuantizationSummary` counts,
packed and scale bytes, and the small gate and normalization exclusions.
Activation and KV precision remain separate fields.

`NV_DFLASH_W4A16_ROWS` optionally keeps BF16 activations for small-row packed
draft projections. Unset or zero disables the policy; values one through eight
require packed DFlash. The draft loader installs the policy on its own packed
linear storage before sharing it, leaving target projections unchanged. Boot
fields `w4a16_rows` and `armed_linears` report installed policy; they do not
prove a particular request executed that kernel. The weight storage remains
four-bit, and larger prefill projections retain their existing activation path.

The FA2 parameter mirror in `laguna_fa2` follows the pinned Candle library ABI.
The suite covering both wrapper outputs and graph replay
(`laguna_fa2_contract`) compares real CUDA results with an independent CPU
attention reference. Draft graph capture equality uses the identical
uncaptured tree body; the alternate eager implementation has different
arithmetic. Neither storage proof nor graph equality replaces real target-only
versus speculative output checks and acceptance measurements.

## 1. Paged KV cache + prefix caching

Unpaged (`Gemma4::new_kv_cache_fp8`) is a private cache per request at
`kv_max_seq_len`, per layer `max_seq_len * n_kv * (2*head_dim + 8)` bytes (K/V
fp8 plus two f32 scale planes), no pooling, no prefix reuse.

**Layering.** `nv-models` must not depend on `nv-engine`: host allocator and
prefix-cache hash table in `nv-engine` (`BlockManager`), GPU fp8 pool and
`Gemma4Cache` adapter in `nv-models` (`paged_fp8.rs`, beside
`Gemma4KvCacheFp8`). They exchange values only — a `&[u32]` block table and
integer geometry.

**GPU paged fp8 pool** `nv-models::paged_fp8::PagedKvFp8Pool`, one for all
running sequences, per layer four slabs sized by *pool* block count:

    K_fp8   [num_blocks, block_size, n_kv, head_dim]  u8
    V_fp8   [num_blocks, block_size, n_kv, head_dim]  u8
    K_scale [num_blocks, block_size, n_kv]            f32
    V_scale [num_blocks, block_size, n_kv]            f32

Per-layer geometry differs (gemma4 sliding vs full layers differ in
`head_dim`/`n_kv`), so every layer owns its `(n_kv, head_dim)` and four slabs
over the *same* global block id space: a block id is a slot in
`[0, num_blocks)` valid for every layer. `block_size` is fixed (default 16,
matching `SchedulerConfig.block_size`); logical position `p` under block table
`T` maps to slot `T[p / block_size] * block_size + (p % block_size)`.
`pool_bytes` / `bytes_per_block` / `max_blocks_for_budget` size `num_blocks`
from a VRAM budget, not `max_seq_len * num_sequences`;
`build_gemma4_batch_engine` takes a fraction of free VRAM via
`cudarc::mem_get_info` — `NV_BATCH_KV_FRACTION` (default 0.25), overridden
outright by `NV_BATCH_KV_BLOCKS`.

**Host block tables + prefix caching** `nv-engine::BlockManager`: fixed-size
blocks, `VecDeque<u32>` free list, ref counts.
`compute_block_hash(tokens, prefix_hash)` chains the previous hash in, so
identical *prefixes* collide and not just identical blocks; `allocate_for`
shares a matching block (`share_or_pop`); `deallocate` frees only at
`ref_count == 0`; `commit_filled_block` hashes the *last filled* block during
decode, so prefix sharing is not limited to prefill; `extend_for` /
`extend_for_slots` add a block at the boundary; `PoolGeometry` mirrors pool
accounting dependency-free. `fork_tail_for_write` is copy-on-write: a write into
a shared (`ref_count > 1`) tail block allocates a private copy and returns
`(logical_block_idx, old_id, new_id)` to memcpy on GPU. Decode only ever writes
the tail block, so at most one COW per step.

**Paged cache adapter** `nv-models::PagedGemma4Cache` implements `Gemma4Cache`,
a drop-in for `Gemma4KvCacheFp8` in `Gemma4::forward_with_cache`, holding
`Arc<Mutex<PagedKvFp8Pool>>`, `block_table: Vec<u32>`, `current_len`, the step's
COW plan. `write_at(layer, k_new, v_new)` quantizes into block-table slots, not
a contiguous `start + token` slab; `view(layer, len)` gathers `len` logical
positions into contiguous `[1, len, n_kv, head_dim]` bf16, reusing the bf16
attention path unchanged; `try_decode_attention_fp8` is the
fused-paged-attention seam, `Ok(None)` falling back to gather + bf16 (correct,
slower). The engine pushes block table and `current_len` each step via
`set_block_table` / `prepare_for_decode`.

**CUDA kernels** take `const int* block_table` plus `int block_size` and resolve
the physical slot through it:

    nv_kernels_quantize_kv_fp8_paged     append
    nv_kernels_dequantize_kv_fp8_paged   gather len logical positions -> bf16
    nv_kernels_copy_kv_block_fp8         COW copy of one block: K, V, 2 scales

Under `cfg(not(feature = "cuda"))` the pool keeps a CPU reference image, so the
data structures stay unit-testable with no GPU.

**Pointer hazard (recurring class).** Raw-pointer call sites must honor candle's
`layout.start_offset()` on narrowed inputs: `narrow(1, i, 1).contiguous()`
returns an offset view instead of copying a size-1 batch row, so
`as_cuda_slice()` + `device_ptr()` dropping the offset makes batch slot N>0 read
and write slot 0's KV. Slice the cuda slice by `start_offset()`. This class
bites `append_one_kv`, `moe_grouped.rs`, `laguna_fp8.rs` and
`Gemma4KvCacheFp8::write_at` — **check it in any new raw-pointer path.**

## 2. Continuous batching + M=B batched decode

A per-model `tokio::Mutex` held across a whole prompt-to-EOS loop queues
concurrent `/v1/chat/completions` requests instead of interleaving them.
Replacement: orchestration admitting and evicting between steps, plus a decode
forward running B sequences in ONE pass so the dominant per-layer GEMMs run once
at M=B, not B times at M=1.

**Orchestration** (`nv-engine/src/batch_engine.rs`). `BatchEngine<S:
BatchStepper>` is the model-agnostic core over `Scheduler` / `BlockManager` /
`Sequence`; `GenRequest { prompt_tokens, max_new_tokens, eos_token_ids,
sampling, reply }` is one admission unit with its own
`mpsc::Sender<EngineEvent>`; `EngineEvent::{Started, Token, Done, Error}` is the
per-`seq_id` stream; `BatchStepper` is the GPU seam —
`on_admit(seq_id, &SamplingConfig)` (per-seq sampler state),
`prefill(&[PrefillInput]) -> Vec<StepResult>` (batched prompt pass),
`decode(&[SeqInput]) -> Vec<StepResult>` (batched single-token pass, each
`SeqInput` carrying `{seq_id, position, token, block_table}`),
`release(seq_id)` (frees per-seq KV and sampler state on finish or abort).
`BatchEngine::step()` drives one `ScheduledBatch` through the stepper and
`complete_step`, drains finished sequences, emits `Done`; `order_tokens`
re-aligns results to scheduler `seq_ids`, so a stepper may return out of order.

`nv-engine/src/batch_runtime.rs` provides the async front `BatchEngineHandle`,
which spawns the step loop on a **dedicated OS thread** — the model forward must
not block the tokio reactor and wants a single owner. A `Command` channel
carries `Submit` / `Abort` / `Shutdown`; the loop drains commands, calls
`engine.step()` when there is work, otherwise `blocking_recv`s; `submit()`
returns the `mpsc::Receiver<EngineEvent>` the HTTP handler streams from; `Drop`
sends `Shutdown` and joins. That thread is the sole model owner, so no global
per-model mutex remains and requests interleave at token granularity.

**Per-op batchability (the M=B insight).** Per layer, for B sequences: q/k/v/o
projections and gate/up/down MLP GEMMs dominate and are *position-independent*,
each row an independent `[hidden]` vector, so stacking B rows into
`[1, B, hidden]` makes every `Linear::forward` one M=B GEMM — the occupancy win.
RMSNorm is elementwise on the last dim and shape-agnostic, so `[1, B, ...]`
passes through. `Rope::apply` flattens leading dims to `tokens` and indexes
cos/sin by a per-token `positions` vector, so `[1, B, n, head_dim]` q/k with a
length-B `positions` (each row's OWN absolute position) rotates correctly per
row — that is why a batch of sequences at different lengths is fine. Attention
is the one genuinely per-row op, each row attending over its own KV at its own
length.

So `Gemma4::forward_decode_batched(tokens: &[u32], positions: &[usize],
caches: &mut [&mut PagedGemma4Cache]) -> Result<Tensor>` is **batched (M=B)
everything except attention, per-row attention**, returning `[B, vocab]`: embed
B tokens to `[1, B, hidden]` scaled by `embed_scale`,
`caches[i].prepare_for_decode(len_i, len_i + 1)`, push each block table, then
per layer `input_layernorm`, q/k/v + RMSNorms, RoPE over the length-B
`positions`, the per-row attention loop, o_proj, residuals, MLP, residual scale
— M=B but the loop — then `caches[i].advance(1)` per seq, final norm, lm_head.
The loop narrows row `i` of k_rot/v to `[1, 1, n_kv, head_dim]`, calls
`caches[i].write_at(layer, k_i, v_i)`, then
`caches[i].try_decode_attention_fp8(...)` or the fallback
`caches[i].view(layer, len_i + 1)` plus `flash_attention` at `seq_q = 1` —
identical math to single-seq decode — and stacks the B outputs to
`[1, B, n_q*head_dim]`. **Because it reuses the exact helpers the
single-sequence path uses, a B-sequence batch where every row was alone produces
the same tokens as running them one at a time**; that contract is
regression-tested by `paged_batched_decode_correctness.rs`. Prefill stays
per-seq (`forward_with_cache` on the seq's paged cache), correct and not the
bottleneck. The seam for a true batched paged-attention kernel is the loop body:
one call taking `[B]` block-table and `[B]` context-length arrays, mirroring
vLLM `paged_attention` v2; the staged `kv_fp8_paged.cu` gather already routes
through a block table, but that kernel is not in tree.

**Batch-composition determinism.** Batched decode is *not* bitwise deterministic
across batch composition (M=B vs M=1 bf16 reduction order — vLLM has the same
property), so exact-match tests such as
`concurrent_identical_greedy_is_deterministic` are gated to the non-batched
path.

**Stepper** (`rust/src/oapi/batch_chat.rs`). `Gemma4PagedBatchStepper` sits
alongside the serial `Gemma4BatchStepper` fallback, owning `Arc<Gemma4>`, one
shared `Arc<Mutex<PagedKvFp8Pool>>` sized from a block budget at construction,
and a per-seq `PagedGemma4Cache` and sampler state. `prefill` sets each seq's
block table, runs `forward_with_cache`, samples the first token; `decode`
assembles `(tokens, positions, &mut caches)`, makes ONE
`forward_decode_batched` call, samples per row through `nv_layers::sampler`
(same parity as `ChatSampler`). Block tables come from `SeqInput.block_table` /
`PrefillInput.block_table`. A decode batch of size 1 still goes through
`forward_decode_batched` with B=1, identical to single-seq decode.

**HTTP wiring.** `LoadedModel::Gemma4` keeps `Arc<Gemma4>` (shared, not behind a
`Mutex`) so the batch-engine thread owns batched access while the legacy locked
path serves the spec-decode and graph routes; one `BatchEngineHandle` per Gemma4
model at load time owns that `Arc<Gemma4>` and the paged pool. On the plain
greedy/sampling path `NvEngineChat::generate` tokenizes, calls
`handle.submit(...)`, forwards `EngineEvent::{Started, Token, Done, Error}` onto
the existing `mpsc::Sender<ChatEvent>`, and funnels Token through the same
incremental-detok helper `run_sampling_gemma4` uses, reusing detokenization,
stop-string matching and streaming verbatim.

The engine path is opt-in via `NV_BATCH_ENGINE`. Eagle3 spec-decode stays on the
direct `run_sampling_gemma4` path because `BatchEngine` does not drive `Verify`
batches (the scheduler supports the batch kind; `step()` returns an explicit
error for it), as do guided decoding, `logit_bias` and logprobs, whose
per-request sampler state the batch sampler does not thread.

## 3. Graphed Eagle3 verify in the serving spec loop

The serving loop is the override-CHAIN round in
`chat_engine/gemma4_loop.rs` over `nv-models/src/gemma4_graph.rs`, and it pays
ONE forward per round; two forwards — an ungraphed re-prefill of `context + tree` plus another
to recompute the aux accumulator — is a verify floor of ~2x a full prefill per
round growing O(context), which makes an ungraphed loop net-negative against
plain graphed decode. `Gemma4VerifyCache` (`new_verify_cache`) is a persistent
bf16 KV cache filled once at prefill and thereafter only *appended* to (O(k) per
round), never re-prefilled; its `compact_path` gather/scatter is what the *tree*
path needs, unused by the chain path because chain accepts are a contiguous
prefix already in the right slots. `GraphedGemma4Verify` captures ONE CUDA graph
of the k-token verify forward (`forward_verify_dev` over the verify cache) and
replays it per round at a cost independent of context length, returning the k
logit rows *and* the per-token aux hidden states for the next draft — which is
what eliminates the second forward.

**The override-chain round.** State across rounds: `context: Vec<u32>`
(committed tokens); `committed: usize`, both `context.len()` and the KV rows
resident in the verify cache; `seed: Vec<f32>`, the verifier's logits at the
LAST committed position; and the aux accumulator — the Eagle3 draft's input,
row-major `[committed, fc_in]`, growing by exactly `accepted` rows per round in
lockstep with `context`. `aux_accum` below is this chapter's name for it; the
loop carries it as `aux_proj` (the projected device tensor), `aux_pending` (the
host `Vec<f32>` used when aux is streamed) and `aux_base` (the row offset the two
are indexed from), and `NV_SPEC_DEFER_DRAFTER` moves when it is armed without
changing its end state (03-speculative-decoding.md).

1. **Draft.** `chain_draft(&context, aux_accum, k)` → k draft tokens conditioned
   on the last committed token's aux row.
2. **Build the batch.** `batch[0] = argmax(seed)` — the verifier's own greedy
   bonus token, accepted by construction — and `batch[1..k] = draft[1..k]`, at
   absolute positions `[committed, .., committed + k - 1]` under a
   lower-triangular mask. **The root is overridden with the bonus rather than
   `draft[0]` because the graphed forward writes KV for every batch slot at its
   absolute position**: slot 0 lands at `committed`, the next real position, so
   a guaranteed-accepted token there makes that KV correct and permanent the
   moment the round commits — no separate bonus forward, no compaction. This
   caps tokens/round slightly below a self-conditioned tree but pays only ONE
   forward per round.
3. **Verify.** `gv.run(&batch, &positions, &lower_tri(k), committed)` → `logits`
   (`k x vocab`) and `gaux` (`L x k x hidden`, one aux block per Eagle aux
   layer). The first call captures the graph; later calls replay.
4. **Accept walk.** Slot 0 is always accepted. For `i in 1..k`, accept
   `batch[i]` iff `argmax(logits[i-1]) == batch[i]` (the verifier at slot `i-1`
   predicts slot `i`); stop at the first mismatch, so `accepted ∈ [1, k]`.
5. **Commit.** Push `batch[0..accepted]` onto `context`; append their aux rows
   (`aux_row(gaux, j)` concatenates the per-layer hidden blocks for token `j`
   into one `fc_in` row) onto `aux_accum`; `committed += accepted`. Their KV is
   already resident at `[committed_old, committed_old + accepted)`.
6. **Carry the seed.** `seed = logits[accepted - 1]`.

Streaming and stop handling (EOS, stop strings, `max_new`) apply token-by-token
over the committed slice exactly as the non-spec loop does.

**KV-cache correctness invariants.** *Append-only*: `forward_verify_dev` writes
batch KV at `[committed, committed + k)`, the kernel reads context KV
`[0, committed)`, and rejected slots are never read after a reject since
`committed` advances only by `accepted` and the next round's batch overwrites
them. No invalidation, no compaction: accepts are the contiguous prefix
`batch[0..accepted]` at contiguous positions, so committed KV is already dense.
*`n_committed` device scalar*: re-uploaded inside the graph from
`host_committed` on each replay, so advancing `committed` on the host suffices —
no re-capture per round. *Seed↔aux lockstep*:
`aux_accum.len() == committed * fc_in` and `seed = logits[accepted - 1]` must
hold together (the draft conditions on the last aux row, the bonus comes from
the matching seed), which appending aux rows for exactly the committed tokens
preserves.

**Capture safety and fallback.** The first `gv.run` captures with k fixed for
the whole request; k never changes mid-request, so one capture serves the
generation. `device.synchronize()` is drained at loop entry to clear any sticky
CUDA error from a prior request's graph teardown. Prefill uses eager
`forward_verify`, not the graph, for the cache and the initial seed and aux
accumulator. If `GraphedGemma4Verify::new` or the prefill fails — cache
overflow, say, with `max_seq` sized `prompt + max_new + k + 16` — the error
propagates to `run_sampling_gemma4`, which already wraps spec in a `?`. **There
is no silent fallback to the ungraphed verifier**; ungraphed `Gemma4Verifier`
stays reachable behind `NV_EAGLE3_UNGRAPHED=1` for A/B and as the tree-mode path
(`NV_EAGLE3_TREE`), which needs the ungraphed masked forward.

**Env switches.** `NV_USE_EAGLE3` enables spec decode (gated on greedy plus no
guided/logit-bias/logprobs); `NV_EAGLE3_K` sets chain width k, serving default
ctx-gated (4 for prompts <8192 tokens, 3 above); `NV_EAGLE3_UNGRAPHED=1` forces
the ungraphed verifier loop for A/B; `NV_EAGLE3_TREE=1` selects tree mode,
routed to the ungraphed masked path because the graphed path is chain-only by
construction of the override trick; `NV_PROF_CHAT` prints per-round and summary
tok/s, tokens/round and accept rate. The full drafter/verify knob surface is
03-speculative-decoding.md § "The knobs".
