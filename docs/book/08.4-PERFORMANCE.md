# Quoting a performance number

Numbers go stale within hours, so this file records **how to quote one**, not
a scoreboard. The rule: a measured performance number may be quoted **only
from a row of `perf/runs.jsonl`, citing its `run_id`**. Prose — docs, code
rationale strings, commit messages — never carries raw figures; it states the
relationship the measurement evidenced ("the coop route outruns the m-row
arm", "fp8 KV wins at depth and holds ppl") and points at the store. For the
rules that decide what to optimise, read
`05.7-apple-silicon-inference-architecture.md`.

## A number without its basis is not a number

Always state, in the same breath:

- **The checkpoint.** `google/gemma-4-E4B-it` is bf16;
  `google/gemma-4-E4B-it-qat-w4a16-ct` is 4-bit QAT. They are different models
  and differ substantially on identical code. A "regression" between them is
  not a regression: quoting w4a16 throughput requires naming that snapshot in
  the row's checkpoint field.
- **The backend and the machine.** CUDA, wgpu-on-Vulkan and wgpu-on-Metal are
  three different numbers, and Apple parts differ from each other by more than
  most optimisations do.
- **Prompt and completion length.** Prefill amortises over the completion, so
  the same unchanged binary reads differently at `ct=64` and `ct=128`. This has
  already produced a phantom regression.
- **Decode vs end-to-end.** Server decode excludes prefill and HTTP; they are
  not interchangeable and the gap is large.
- **Load.** Record it. A busy box materially inflates absolutes, though
  in-process A/B ratios survive it.
- **The ceiling, when a number is quoted as a fraction of one.** A bandwidth
  ceiling is only a ceiling for the **traffic mix** and the **working-set size**
  it was measured at. Name both, in the cell.

## A ceiling is a curve, not a number

Three separate rounds published flattering ratios by dividing by the wrong
ceiling, and in each the error was invisible until a figure crossed the sanity
bar below.

**Traffic mix.** A read-only ceiling and a read+write ceiling are different
quantities on the same card: `cuda_stream_read` and BabelStream `Dot` reach
**1630 GB/s**, while `dtod_copy` -- 256 MiB each way, counting both directions --
reaches **1475 GB/s**. Read/write turnaround costs roughly 10%, so neither is
wrong. Divide a weight-streaming GEMV by the copy figure and it reads 100.1% of
ceiling; divide it by the read figure and it reads 90.6%.

**Working-set size.** The same `memcpy_dtod` reads **234 GB/s at 0.25 MB, 956 at
1 MB, 3013 at 3 MB, 4097 at 12 MB, 6120 at 48 MB and 4405 at 64 MB** -- an L2
knee, not a plateau. A 256 MiB calibration cell is a DRAM measurement, and
applying it to a 3 MB per-lane recurrent state understates that kernel's
inefficiency by roughly a factor of five.

Before quoting any kernel as a fraction of a ceiling, check that the ceiling
probe's working set is on the **same side of the L2 knee** as the kernel's, and
that its read/write mix matches. Where they cannot be matched, quote the kernel
in absolute GB/s and say no ceiling applies.

**Some kernels have no bandwidth ceiling at all.** A serial recurrence is
dependency-bound, not memory-bound: the GDN prefill scan runs at 50-64 GB/s
while its neighbours in the same bench reach 1132-2243, at a near-constant
3.7 TFLOP/s. Reading such a kernel against a bandwidth figure invents a deficit
that no byte-side change can close, and hides the reformulation that can -- a
shuffle-based rewrite of that scan is worth 1.46-1.62x, and the ceiling of the
scalar-recurrence class itself sits ~3.2-3.5x below FLA's chunked tensor-core
formulation of the same prefill on the same card (170-178 vs 520-594 ns/tok at
the qwen3.8 shape, T>=2048; measured same-day at 250 W, both serial under the
GPU flock). Quote the scan against that on-card chunked reference, never against
our own v1.

**The sanity bar: at or above ~95% of the relevant sustained ceiling, assume an
accounting defect rather than a triumph.** It has caught three published claims
-- a family row at 101% MBU, an exhibit pin at 96.1%, and a GEMV at 100.1% --
and in every case the fault was the denominator, not the kernel.

## Comparing two configurations

Measure them **interleaved in one process**, not across boots. Between-boot
comparison has repeatedly produced effects the same size as the change being
claimed — run the same configuration against itself as a null control and see
what it "wins" by before believing anything.

Verify the flag reached the builder. An unchanged pass count or boot-line
format string means the knob did nothing, however plausible the delta.

**A margin is resolved by its basis, not by its size.** Two identical graphs
read −28.0 µs apart, 0.32% of an 8.78 ms step; identically-routed *arms* have
been measured 5.5% apart, seventeen times wider, and a published +6.4% win
evaporated once cooldown gating was applied. So the floor a delta must clear
depends on how it was obtained:

- A **single ungated delta** carries the whole 5.5%. Under it, nothing is
  established — including a *negative*, so an arm rejected on −2.8% is
  unrefuted rather than refuted.
- **Same-HEAD pairing does not help here.** It removes code drift, but the
  5.5% was measured between arms that route identically, so it is exactly the
  residual pairing leaves behind. Treating a same-HEAD pair as a thermal
  control is the standing trap.
- **Cooldown gating** (`ladder.py --cooldown-below-watts`) removes most of it.
- **Paired-repeated with a p-value** removes it directly, and a small margin
  established this way beats a large one that was not: a +0.4% paired median
  at 10/10 and p=0.002 is a firmer verdict than an ungated +5%.

`load_spec` therefore refuses a multi-arm spec that names no `null_pair` — two
separately-run arms resolving to the same path — or set `null_pair_waived_because`
and say why not. Read the arm delta against that measured null, never against zero.

A same-day null pair floors only same-ladder comparisons. Across days the
effective floor is wider than the pair suggests — the q38 servenv instrument
repeats at 0.1 % within a ladder, yet the same two arms compared across two
days flipped sign at the 1.6-1.8 % scale (kvshare-in-stack, rows
"q38 servenv") — because clock, thermal and build state drift between
sessions in ways a same-session pair never samples. A cross-day margin under
~2 % on this class of instrument is unresolved regardless of how tight the
same-day null reads; re-run both arms in one ladder before claiming it.

## Flipping a default moves only what UNSET means

Every explicit env value keeps its pre-flip meaning — `=1` still forces the
arm, `=0` restores the prior default (a multi-env stack at all-`0` is the
full pre-flip arm), and suites measuring a non-default arm pin its envs
explicitly instead of relying on unset. Unset may resolve to a mode rather
than a boolean — a label filter (`NV_G4MOE_GEMV_SGLAT` unset = `at-oproj`)
or a depth gate (`NV_GOW_FLASH_LANEPOS` unset = the gated route at its
measured knee) — and non-qualifying shapes keep the prior path silently
while an explicit value still asserts. This is what keeps every pre-flip
row in the store interpretable: a row's flags read identically on both
sides of the flip, so no gate weakens and no published number goes orphan.

## Quality numbers on chat-tuned checkpoints

Teacher-forced perplexity on a raw, untemplated corpus is not a valid quality
metric for a chat-tuned checkpoint, and the failure mode is not "noisy" — it is
a number that looks like a code defect. Off its template the model is both
genuinely poor and numerically chaotic: independent causal code paths disagree
with each other at the argmax level, the score swings with block size and
batch shape, and nothing distinguishes this from a broken kernel except weeks
of exoneration. The same stack that scores astronomical raw-corpus perplexity
copies 512 templated tokens verbatim at perplexity near one.

The rule: quality numbers for gemma4-family (and any chat-tuned checkpoint)
come only from chat-wrapped scoring — the suite covering this is
`gemma4_chat_wrapped_continuation_teacher_forced_ppl_via_serving_decode` in
`nv-models/tests/ppl_gemma4.rs`, which also reports teacher-forced top-1
accuracy. Chat-wrapped and raw-corpus perplexities are different quantities;
never compare one to the other across model families. Qwen-family checkpoints
tolerate raw corpora, which is a property of those checkpoints, not evidence
the raw premise is generally valid. The causality gate for the masked forward
(`changing_only_the_last_token_must_not_move_any_earlier_row...`) and the
depth gate (`scoring_a_verbatim_copy_task_inside_the_chat_template...`) in the
same file are how to tell a real logits defect from this eval artifact before
opening an investigation.

## Where numbers live

`perf/runs.jsonl`, and nowhere else durable. Each row carries the basis tuple
above by construction (checkpoint with revision, backend, device, flags,
commit, log path) and a `run_id`; quoting a number means citing that row.
Instruments emit `NV-MEASURE` lines (`nv_config::measure`, format pinned in
`08.5-MEASUREMENT.md`) and the perf-room harness (`perf/run-harness.sh` +
`perf/parse_and_append.py`) turns them into rows — a number that never became
a row was never measured. Measurement rounds are deliberately not written up
in docs: the durable output of a round is a rule in the architecture doc, a
default in the code, or a row in the store — never a figure in prose.

**`build_name` is free text and does not identify a model.** It carries 247
distinct values over ~1600 rows, and one model wears several: Qwen3.8-27B
appears under both `q38 …` and `qwen3.8 …`, gemma4-26B-A4B under `g4moe …`,
`g4moe-26b …` and `gemma4-26b-a4b …`. Grouping a graph on it silently merges
eras and arms into one line. Group on the checkpoint id plus the resolved arm
and backend, and when a figure ships, name the exact `build_name` values behind
each line so a reader can see what was excluded.

**Rows are append-only and nothing marks one superseded**, so a true
measurement of a since-fixed path stays readable as current — and stays
invisible to any "latest per cell" rule when its era used a family label no
current row shares. `gemma4-26b-a4b moe wgpu kv-ring` reads 1.5 tok/s at
122880 while the same model reads 47.3 at that depth and 42.5 at the *deeper*
196608 under other labels. A deeper rung cannot be 28× faster; the 1.5 is an
honest reading of a broken arm and must be excluded by name, never deleted.
When a cell disagrees with a deeper cell in the impossible direction, suspect
the label before the kernel.

## Running an arm ladder

Arm ladders — {arm-name → env dict} × depths, each cell landed as a row —
run through `perf/ladder.py`, never as hand-rolled shell loops. A JSON spec
(worked example: `perf/ladders/gptoss-fuse-round1.json`) names the ladder,
the shared `run-harness.sh` arguments and env, the depth axis, and the arms;
the runner executes serially through the harness (it never appends rows
itself), tags every row's notes with `ladder=<id> arm=<name>`, and prints a
baseline-relative table from the store afterwards. `--dry-run` prints the
planned invocations. Arm ORDER thermally biases late arms on a heat-soaked
GPU, so `--cooldown-below-watts N` gates each invocation on `power.draw`
(with a loud timeout, not a silent proceed), and each row's notes carry the
start-of-run clocks/power/temperature sample; the end-of-run sample goes to
the ladder transcript because rows are append-only.

## Querying the store

Row queries go through `perf/rows.py`, not inline `python3 -c` one-liners:

- `filter` / `table` — `--build` regex, `--since`, `--note`, `--flag K[=V]`,
  and `-w 'field(=|!=|~|!~|>=|<=|>|<)value'` with dot paths
  (`flags.NV_CTX_TOKENS`, `ppl.value`); `table -c` picks columns.
- `compare --a EXPR --b EXPR` — joins two filtered sides on `--key` (default
  `prefill_tokens`, i.e. depth), latest row per cell, and prints the delta
  per key. A delta within `--epsilon-pct` of zero reads **SUSPECT-INERT**:
  identical medians mean the config never switched the pipeline — verify the
  flag reached the builder before reading the result as a kernel verdict.
  When the delta's sign flips along a numeric key axis it prints the
  crossover — this is how a depth knee is determined and quoted.
- `ledger --build REGEX` — the chronological adjudication story of a
  campaign family, grouped by arm (the `arm=<name>` notes convention, which
  `ladder.py` writes automatically), with first/last rows and the verdict
  words found in notes. STATUS updates start from this, not from re-grepping
  the store by hand.

## Merging concurrent appends

`perf/runs.jsonl` is append-only, so the true resolution of every textual
merge conflict on it is the union of both sides. `.gitattributes` assigns it
the `union-jsonl` merge driver, implemented by `perf/merge-runs-jsonl.py`
(validates every line, unions, drops exact duplicates, warns on diverged
`run_id`s). git config does not travel with the clone, and git runs the
driver from the repo root, so the enable command carries the script's
resolved path: running `python3 perf/merge-runs-jsonl.py` with no arguments
prints the exact `git config merge.union-jsonl.driver ...` line for the
current checkout; run it once per clone. A store already contaminated with conflict markers is repaired in place by
the 1-arg form, `python3 perf/merge-runs-jsonl.py perf/runs.jsonl`. Both
modes refuse — loudly, file untouched — on any line that is neither a valid
row nor a conflict marker; hand-editing the store stays a hand decision.
