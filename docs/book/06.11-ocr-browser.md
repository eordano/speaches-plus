# 6.11 dots.ocr in the browser

`nv-ocr-web` is the wasm32 carve of the dots.ocr serving arm. It compiles the
same code the native server runs — the wgpu vision tower and the affine-u4
graph decoder, dequant-in-kernel, GPU handoff splice, no candle decoder —
behind `DotsOcrPipeline::from_parts_wgpu_graph_w4`, which differs from the
dir-loaded metal arm only in taking its safetensors as owned bytes. The portal
page `/ocr-full-wgpu` drives it end to end: capability probe, model download,
read view with region overlay and corrections, train view, adapter store.

## Delivery and residency

The portal serves the checkpoint at `GET /ocr-model/index` (a sha256 manifest
of `PORTAL_OCR_MODEL_DIR`) and `/ocr-model/file/<name>` (immutable,
week-cached bytes). The browser lands each file in OPFS once, verifies it with
`crypto.subtle`, and never fetches it again: on init the glue streams
`config.json`, `tokenizer.json` and `*.safetensors` from OPFS into wasm
staging chunk by chunk (`weights_push`), and the engine builds the pipeline
from them. Adapters are PEFT pairs (`adapter_config.json` +
`adapter_model.safetensors`) under OPFS `ocr-adapters/<name>/`.

The page, glue, and wasm artifacts precache through
`static/ocr-web/sw.js` (served with `Service-Worker-Allowed: /` so a worker
under `/ocr-web/` controls the page navigation). After one full load the tab
works with the network cable pulled: code from the worker's cache, weights and
adapters from OPFS.

## The wasm surface

`nv-ocr-web/src/wasm.rs` exports the module `static/ocr-web/glue.js` adapts:
`weights_clear/push/staged` and `adapter_stage/clear/staged` feed staging;
`engine_init` consumes it and builds the pipeline (`kv_span` defaults to 4096
per `BROWSER_KV_SPAN_DEFAULT_..._CAPS_LOAD_TIME`); `engine_ocr_page` streams
region frames to a JS callback and returns the token report. Training has its
own staging: `train_weights_clear/push/staged` take the mlx dots.ocr-4bit
snapshot (the trainer's only accepted base, per
`TRAIN_ACCEPTS_ONLY_THE_MLX_AFFINE_U4_GS64_EXPORT...`),
`train_sample_stage_rows` takes precomputed dump-format samples, and
`train_sample_stage_page` takes a corrected page (image + text + optional
bbox) whose vision rows `engine_train` computes through the serving session's
tower at train time — sample assembly mirrors the `nvk-dots-vision-dump`
example (`SAMPLE_ASSEMBLY_MIRRORS_NVK_DOTS_VISION_DUMP...`).
`engine_train` streams `{type: "train_step", step, loss}` frames and leaves
the PEFT pair readable via `train_adapter_config_json` /
`train_adapter_safetensors`. Adapter activation is an engine rebuild — the
graph records LoRA slices at construction, the same rule as native
`reload_adapter` — through the bytes-based seam
`LoraAdapter::from_named_bytes` → `DgLora::from_adapter` →
`from_parts_wgpu_graph_w4_lora`.

## The readback pump

Every GPU→CPU readback the browser performs goes through
`dispatch::read_back_begin` + `PendingReadback` in nv-kernels: `map_async`
registers a waker-carrying callback, and the pumped future awaits it — on
wasm the browser resolves the map, on native the future drives
`device.poll(PollType::Poll)` and self-wakes
(`PUMP_SELF_WAKES_ON_NATIVE_BECAUSE_MAP_CALLBACKS_FIRE_ONLY_INSIDE_DEVICE_POLL`).
The proven native blocking arm is byte-for-byte the same submission sequence
resolved with `poll(Wait)`; async bodies shared by both arms take a
`ReadbackArm` and native entry points drive them with `drive_blocking`
(one noop-waker poll — the blocking arm never suspends). Serving rides
`recognize_pumped`, which serves exactly the graph decoder + resident-tower
arm (`PUMPED_SERVING_IS_THE_GRAPH_PLUS_RESIDENT_TOWER_ARM_ALONE...`) with a
serial decode loop (run-ahead stays a blocking-arm feature); the trainer's
kernel wrappers all carry `*_arm` twins ending in the same pump. Error scopes
whose pop would block are released on wasm without reading
(`POP_BLOCKS_ON_NATIVE_AND_DROPS_ON_WASM...`) — browser validation errors
surface on the console through the uncaptured-error handler. The pump arm is
re-provable natively: `NV_OCR_WEB_PUMP=1` re-runs the bytes-vs-dir parity
gate through `ocr_page_pumped`, and the train gate's pumped smoke
(`NV_OCR_WEB_TRAIN_PUMP_TEST=1`) asserts finite, rep-deterministic losses.

## W4 everywhere, and the gates that hold it

The LM trunk, embed and head quantize to affine-u4 gs64 at load; the trainer
(`nv-ocr-web/src/train/`) is an explicit backward schedule over the QLoRA WGSL
kernels with fp32 LoRA A/B on a top-8-layer window. What keeps the browser arm
honest:

- bytes-vs-dir parity (`tests/native_parity.rs`): the bytes-loaded session
  matches the dir-loaded serving graph on the labnotes fixture — 6 regions
  each, 0 text diffs, prompt 3615==3615, generated 419==419.
- the trainer gate (`tests/train_gate.rs`): 20 steps on dump-n25 track the
  canonical 0.212043 → 0.001704 trajectory, and the saved adapter round-trips
  into the serving graph.
- adapter seam equality (`tests/adapter_bytes.rs`): a bytes-loaded adapter is
  tensor-identical to the dir-loaded one.
- subgroup portability: the graph suite's tree-twin gates cover the fallback
  kernels a subgroup-less or width-unknown browser device selects.
- the E4B twin of this trainer (`train/e4b/`, [6.6](06.6-lora-training.md)):
  the same kernel set carries Gemma 4 E4B's three-branch layer; its native
  gate (`tests/e4b_train_gate.rs`) holds finite descending bit-repeatable
  losses and a serving-graph adapter load, the window gate
  (`tests/e4b_window_gate.rs`) holds that the dumped window replays the full
  schedule bitwise, and the harness's `e4b` arm holds `E4B-QLORA-TRAINS` in
  Chromium from 885 MB of prequantized window shards.
- the Kokoro voice-fitting surface (`src/kokoro_web.rs`, [7.2](07.2-voices.md)):
  synthesis, the style evolution and the AdaIN adapter fit on the wasm32 CPU
  backend; its native gate (`tests/kokoro_web_gate.rs`) and the harness's
  `kokoro` arm hold `KOKORO-FITS` in Chromium.
- the browser train arm (`Q38WEB_ARMS=train` below): six steps on the same
  dump-n25 basis, run by Chromium's own WebGPU on a hardware adapter,
  reproduce the native pumped smoke's losses to the six decimals both print;
  the verdict is `QLORA-TRAINS`.
- portal suites: the model route, the worker's scope grant, `application/wasm`,
  the precache/served coherence check, and the glue's pure logic under node.

## Limits

- **The bf16 checkpoint outsizes wasm32.** The engine quantizes at load from
  the rednote bf16 snapshot (~5.7 GB); wasm32 linear memory caps at 4 GiB, so
  a full-size serving init cannot stage in-tab. A graph constructor over the
  pre-quantized mlx 4-bit export (~3.3 GB) is the fix path — and until it
  lands, a live-browser serving run stays blocked on memory, not on dispatch
  (`ASYNC_READBACK_PUMP_LANDED = true` records that the readback refusals are
  gone).
- **One wasm32 allocation caps at 2 GiB** (`isize::MAX`): a `Vec` reserving
  the whole 3.3 GB mlx shard panics with `capacity overflow`. The train arm
  therefore rebuilds the shard in the tab with every `vision.*` tensor
  dropped (`pushSafetensorsFiltered` in the harness) — the trainer rides
  precomputed vision rows and never opens the tower — and reserves the
  resulting ~1.0 GB of `language_model.*` tensors exactly through
  `train_weights_reserve` before streaming. Training fits in-tab today;
  serving still waits on the graph constructor above.
- **GPU buffers die on drop, not on garbage collection.** Upstream wgpu 30's
  WebGPU backend leaves `WebBuffer`'s `Drop` a no-op, so a `GPUBuffer` lives
  until the JS collector reaches its wrapper; the vendored copy
  (`third-party/patches/wgpu-30.0.0.patch`) destroys it when the last clone
  drops, as the native backends do. Without that patch a training step leaks
  its activations and logits at ~5 GiB a step in Chromium and dies with
  `VK_ERROR_OUT_OF_DEVICE_MEMORY` by step 4; with it the six-step run holds
  ~680 MiB of device memory.
- **Browser support.** WebGPU is required. Subgroups are optional (the engine
  primes subgroup width as unknown in a browser and selects the tree twins);
  `shader-f16` is optional (bf16 is bit-ops either way); the default 128 MiB
  storage binding fits the ~117 MB W4 head and embed, and the engine requests
  only limits the adapter offers; a default 16384-byte workgroup budget
  auto-disables `NV_DOTS_ATTN_REG` (needs 16480).

## Verifying in a browser

`rust/scripts/q38-browser-parity.sh` drives a headless Chromium (or the Mac
Chrome) against `crates/nv-ocr-web/harness/q38_layer_parity.html` served from
`Q38WEB_WORK` (`web/` holds the wasm from `OCR_WEB_OUT=$Q38WEB_WORK/web
build-ocr-web.sh`). `Q38WEB_ARMS=tint` needs no checkpoint: the page loads
the module, `q38_tint_probe` builds every browser module and entry through
the browser's own WebGPU implementation (Dawn and Tint in Chromium), and the
result records the adapter summary, the device limits, the entries this
adapter cannot build because they exceed its limits (the engine routes around
those at runtime by the same caps) and the Tint rejections proper.
`ALL-MODULES-VALIDATE` means zero Tint rejections. The `sg`/`nosg` arms add
the native reference slice cut by `q38_layer_parity_native` from the mlx
Qwen3.8-27B-4bit export.

Which adapter the browser hands over is the browser's choice, and on a
server it is decided by the display, not by GPU flags. `Q38WEB_DISPLAY=xvfb`
re-executes the driver under `xvfb-run` with the GPU flag set that Chromium
needs for hardware WebGPU on Linux (`--enable-features=Vulkan,DefaultANGLEVulkan,VulkanFromANGLE
--use-gl=angle --use-angle=vulkan --ozone-platform=x11`, sandbox off,
blocklist ignored); on a Linux NVIDIA host that yields the RTX PRO 6000 as a WebGPU
adapter (`architecture: blackwell`, subgroups of 32, 1024 invocations, 48 KiB
of workgroup storage, 16 storage buffers per stage) and every browser module
validates with nothing over a limit. `Q38WEB_ARMS=probe` is the pure
JavaScript control: `requestAdapter`, `requestDevice`, one compute dispatch
and a readback, no wasm; `Q38WEB_GPU_INFO=1` prints the GPU process's
devices and feature status over DevTools (`harness/gpu_info.py`, a
dependency-free CDP client), which is how the two headless outcomes below
were told apart.

`Q38WEB_ARMS=train` is the in-browser QLoRA gate. `Q38WEB_WORK/train-model/`
holds (or symlinks) the mlx dots.ocr-4bit `config.json` and
`model.safetensors`, and `Q38WEB_WORK/dump/` is an `nvk-dots-vision-dump`
output (`index.jsonl` plus per-sample safetensors). The page stages
`config.json`, streams the shard through `pushSafetensorsFiltered` keeping
only `language_model.*`, stages the first `?samples=` dump rows (default 6,
the native pumped smoke's count) and runs `engine_train` for `?steps=`
(default 6) at rank 16 over the top 8 layers, seed 7; `QLORA-TRAINS` means
every loss and gradient came back finite. On an RTX PRO 6000 under
`Q38WEB_DISPLAY=xvfb` the losses are 0.030129, 0.014393, 0.007357,
0.004209, 0.002568, 0.001614 — the native `NV_OCR_WEB_TRAIN_PUMP_TEST=1`
smoke on the same dump prints the same six — in 67 s with a 10.6 MB adapter.

`Q38WEB_ARMS=e4b` is the Gemma 4 E4B twin of that gate. `Q38WEB_WORK/e4b-dump/`
is an `nvk-e4b-window-dump` output (or the `e4b_window_gate` suite's
`NV_E4B_WINDOW_OUT`): `config.json`, the two prequantized window shards,
`e4b-window.json`, `index.jsonl` and per-sample safetensors. The page pushes
the config and shards through `train_weights_push`, hands the first
`?samples=` files to `e4b_sample_stage` and runs `e4b_train` for `?steps=`
at rank 16 over the dump's window; `E4B-QLORA-TRAINS` is the verdict, and
[6.6](06.6-lora-training.md) carries the numbers.

`--headless=new` cannot reach the discrete adapter on this box. With ANGLE's
Vulkan the GPU process runs on the NVIDIA device and reports WebGPU
`enabled`, but the first `requestAdapter` kills it: SIGSEGV through a null
function pointer with `libnvidia-eglcore.so.590.48.01` on the stack, three
times, then the page gets `null`. Chromium's headless ozone platform uses a
surfaceless EGL display and NVIDIA's EGL core hands back an unresolved entry
point on that path; with a real X display the same flags work. The
`--use-vulkan=native --disable-vulkan-surface` set does not crash but does
not reach hardware either: DevTools shows the GPU process on SwANGLE with
`hardwareSupportsVulkan: false`, so WebGPU is `unavailable_software` and the
page gets SwiftShader (`[BrowserWebGpu Cpu]`, subgroups of 4, 256
invocations, 32 KiB, 10 storage buffers). SwiftShader still runs Dawn and
Tint in full, so it remains a valid validation gate when no display is
possible; the eleven over-limit entries it reports (the 1024- and 512-wide
entries, the 13- and 11-storage-buffer attention entries, the three
`q3w_delta_scan_wy` variants) are the ones the engine routes around by the
same device caps at runtime.

## Building

```sh
rust/scripts/build-ocr-web.sh   # OCR_WEB_OUT overrides the portal output dir
```

The script sources the cached devenv (its rustc carries wasm32 std), applies
the `getrandom wasm_js` RUSTFLAGS, puts a nix `lld` on PATH, builds
`nv-ocr-web --no-default-features --features browser` for
`wasm32-unknown-unknown`, and runs a `wasm-bindgen` CLI pinned to the exact
`Cargo.lock` version (cargo-installed once when nixpkgs' differs). It writes
`nv_ocr_web.js` + `nv_ocr_web_bg.wasm` into `portal/static/ocr-web/`; both are
committed, so a checkout serves the page without a rust toolchain.
