# Running LLMs on Apple silicon: the rules, and why

Read this before any performance, quantization, or kernel work. It records
**why** things are the way they are and what has already been falsified, and
deliberately carries no measurement narrative, per-box conditions, or scoreboard
— those go stale in hours and were never what made a decision. The one exception
is §1's ceiling table: a target that cannot exist is a decision, not a score.

## 1. What is possible, and what is faster

### The ceiling is arithmetic — price it before targeting a tok/s

Decode streams the whole resident graph once per token, so

```
floor_ms/token = bytes_read_per_token / measured_roofline
```

is a hard bound no kernel goes under. Take the numerator from the engine's own
sum over the buffers it binds (`weight_bytes_per_token()`), never from a
parameter count or a checkpoint size: the graph transcodes formats at load and
the shipping format is routinely not the checkpoint's, so a hand sum from
safetensors headers is trustworthy only after it reproduces that accessor on a
model where both exist.

Per decode token, on the shipping wgpu default (the measured stream-read roofline
and each model's realized fraction of its floor: `perf/runs.jsonl`):

| model, as it actually runs | GB/tok |
|---|---|
| Gemma-4-31B-IT-NVFP4 — int8/128 attn+FFN, bf16 tied head | 33.02 |
| gemma-4-E4B-it-qat-w4a16-ct — w4a16 `sg_pk`, bf16 head | 3.58 |
| Qwen3.6-35B-A3B-NVFP4 — nvfp4 experts, bf16 DeltaNet, int8 head | 3.38 |

**100 tok/s single-stream on the dense 31B is impossible; the target is
retired.** A 10 ms token buys fewer bytes at the roofline than **2 bits/weight**
over the 30.7e9 weights in its decode path; even an all-4-bit checkpoint's byte
budget lands the floor at well under half the target, and the best measured
4-bit arms sit below their floors. Nothing on the bytes axis closes a multi-fold
gap — only amortizing one weight read over several tokens does, which means
batching or speculative decoding's verify batch.

The other two are **not** byte-bound and their floors clear 100 tok/s with room,
yet both sit far under those floors, so their gap is kernels and per-dispatch
overhead: the MoE spends most of its token somewhere other than streaming
weights. Spend rounds there. KV traffic is second-order and flips no verdict: at
32k context it adds a small share of the 31B's token and a modest share of the
MoE's.

### Fewer bits is not faster

Realized GEMV rates differ enough that bit width alone predicts nothing: the
per-format rate ladder (bf16 and both int8 forms at the top, fp8 below them,
then w4a16 `sg_pk`, nvfp4 `fmlut`, mxfp4, and nvfp4 `tree` far below, a
multi-fold spread at overlapping bytes/weight) lives in `perf/runs.jsonl`. int8
runs at essentially bf16's efficiency while halving bytes; most 4-bit kernels
lose to bf16 outright, because 4-bit decode arithmetic costs more than the
bandwidth it saves.

**The only operative quantity is `bytes / rate`, never bit width:**

```
replacing format B with A pays  ⟺  R_A / R_B  >  B_A / B_B
```

Back-tested repeatedly and never wrong. It predicted the 31B's int8 flip — that
model got roughly twice as fast while reading substantially *more* bytes per
token.

**Corollary:** quote the kernel variant, never just the format. The same format
spans a multi-fold rate range depending on which variant runs. A format is not
fast; a kernel is.

### Why nvfp4 specifically cannot win

Two causes, both read off the generated MSL rather than inferred:

- `dot4I8Packed` has no native lowering on Metal — it becomes `packed_char4`
  casts plus a scalar chain.
- e2m1 is a **non-uniform** code. Its value set {0,½,1,1½,2,3,4,6} is not an
  arithmetic progression, so no cheap SWAR unpack exists. One was searched for
  and does not exist.

The memory path is fine; the decode ALU is the wall. The scale-swizzle layout was
suspected and cleared — removing the scale load buys only a few percent.
**Kernel structure rescues nvfp4 severalfold and it still loses:** `fmlut`
(packed nibble LUT, 4 rows per subgroup) more than doubles 31B `gate_up` and the
inequality still picks int8 group(16) at that shape, because int8 group sits at
the roofline and no 4-bit kernel comes close (rates: `perf/runs.jsonl`).

### Why 4-bit PTQ cannot ship on a non-QAT checkpoint

Salience-aware PTQ genuinely works and is still not enough. AWQ channel scaling
on captured activations wins severalfold over RTN and GPTQ error compensation
wins too; they do not compose; and the dense 31B FFN still lands **orders of
magnitude past the flip bar on perplexity**. Scale policy is not the missing
piece — a dense sweep and an oracle scale land within noise of a cheap ladder —
so counting levels bounds nothing and a better ladder buys nothing. On the 31B it
would not be worth having even if it passed: the byte ceiling above prices a
4-bit FFN there far below the retired target. Mixed precision is real and small
(attention is measurably more damaging per GB of weight than the FFN, `down_proj`
more per weight than `gate_up`), transcoding costs materially on top, and e2m1 is
not the better code. **4-bit is a checkpoint property, not a serving decision.**
Numbers: `perf/runs.jsonl`.

**Weight rms is a screen, never a verdict.** Across architectures it does not
predict KL — a conversion with *better* weight rms than an accepted one
rejected far past the bar — and within one it points the **wrong way**:
AWQ+GPTQ is markedly worse on weight rms than a plain MSE ladder and clearly
better on the logits.

## 2. Things that measured worse

Every row is a real negative result. A negative result is a result.

| change | why it was expected to win | why it lost |
|---|---|---|
| int8 lm_head | fewer bytes, quality passes by orders | the bf16 head is the fastest term per byte in the graph; the int8 kernel collapses severalfold in rate. Slower, with byte-identical output |
| grouped scales on a native source | grouping cuts PTQ error | grouping does not rescue quantizing from native precision; it measured worse than per-row |
| int8 MoE experts | same conversion accepted on a dense model | MoE routers amplify perturbation into discrete expert-selection flips |
| `var<workgroup>` staging | classic tiling win | wgpu zero-initializes workgroup memory per launch — a severe regression |
| naive GEMM for M>1 | a GEMM must beat M GEMVs eventually | still multiples worse at M=256; saturates at a tiny fraction of peak |
| larger M-row prefill chunks | 4× rows should be ~4× cheaper | M-row GEMV does not reuse weights across rows; scaling saturates early |
| uniforms derived on-GPU | removes the CPU from the loop | the writes it removes cost a sub-noise slice of the token. Also blocked: a compute shader cannot write a uniform buffer |
| extra dispatch fusion on an already-fused graph | fewer launches | the removable passes were already gone; the published census was stale |
| persistent readback staging, spin-polling | remove allocation / wake latency | both null. The host cost is the device drain itself |
| lane-splitting a low-occupancy kernel | most of the GPU looks idle | it was bytes-in-flight bound, not occupancy bound. Splitting hurt |
| aspect-ratio kernel routing | tall shapes want a different variant | a capability test beats a shape heuristic; the rule mis-routed a real shape by a double-digit percentage |
| relaxing the too-strict subgroup gate on the fp8/int8 *epilogue* | the identical fix on the nvfp4 GEMV was worth a real margin | zero. The control landed between two runs of the same arm. An epilogue is a reduction, not the weight stream, and the model is bandwidth-bound — fixing a gate only pays when it changes the whole kernel |
| interleaving gate/up rows so a fused epilogue reads one stream | the pairing makes a workgroup read two regions half a matrix apart | under the null control at 43008×5376; the permutation buys nothing |
| GPU token chaining as a default | amortizes the per-token sync | small mean gain for multiples-worse worst-case inter-token latency |
| constant trip count on the loop that indexes an accumulator array | the compiler can then unroll it into registers | 0.86–0.99×. It never beat the array it was removing; shrink the live set instead |

Two of these are one failure: **replacing a fast kernel with a byte-cheaper slow
one.** Never quantize a tensor until the replacement kernel is measured above
crossover *on the shape it will actually run*.

## 3. Kernel rules (WGSL → naga → MSL)

**The accumulator spill is the dominant kernel bug here.** `var acc:
array<f32,N>` indexed under a runtime-bounded loop or a runtime guard spills to
thread-local memory; unrolling it, or recomputing the value instead of caching
it, has paid from a modest win to multi-fold. It is mechanically detectable —
the generated MSL
declares `type_N <name> = {};` at function scope. Grep the MSL, never the WGSL.

**Shrink the live set; do not unroll harder** (the table above prices the
unroll). Which fix applies depends on what the array is: a *cache* of something
cheap goes away by recomputing it, while a real accumulator indexed by two nested
loops goes away by moving the outer loop *inside*, so one iteration's accumulators
are live and stay scalars — worth a real multiple on the M-row flash stage 1,
bit-exact, because a row's arithmetic never depended on the other rows.

`enable subgroups;` is rejected by this naga — subgroup builtins compile bare.

**Audit every capability gate against a runtime probe.** Gates that test
reported ranges rather than actual behaviour have twice hidden working
hardware — a strict subgroup predicate, and cooperative matrix — so a "this
hardware can't" note is a claim to re-test, not a fact. A gate that is too
*loose* is worse, and looseness is usually a magnitude test standing in for a
divisibility one: `gs >= 32u` folded 32 weights under one scale at gs=40/48/56/
72, where only `gs % 32 == 0` is legal. Assert at the call site.

**e4m3fn biased exponent 0 is `mant · 2⁻⁹`, not `(1 + mant/8) · 2⁻⁷`.** Three
shipped WGSL functions read it the normal-band way, and a real NVFP4 checkpoint
emits exactly those codes — scale bytes 0x01–0x07 — for any block whose scale
falls below 2⁻⁶. Measured: 7 of 7 wrong codes, three of them encoding to 0x00,
which loses the block outright, and a many-ulp error through the GEMV. Both
backends had it, identically, which is why no cross-backend parity test could
ever see it. Encode and decode must move together or the mismatch reopens.

## 4. Execution

A token is a strict dependency chain — layers of norm→proj→attn→proj→FFN, then
lm_head→argmax — so **there is no intra-token parallelism to harvest.** Only four
things can be removed, and they are small relative to weight streaming:

1. **Host syncs.** The per-token blocking readback plus device drain is the only
   measurable host cost. Everything else in the host path is unmeasurable.
2. **Uniform writes.** Priced and retired — see the table above.
3. **Dispatch count, and it is serial cost — not launch cost and not grid.** An
   empty 256-thread dispatch costs the same whether it runs 1 workgroup or
   1024: the cost is **flat in grid**. So "widen the grid" cannot fix a small
   pass, and has now failed at it three times (split width on flash stage 1,
   twice; a wg.z-chunked flash stage 2; the MoE quantize passes, where a 72×
   work increase moved nothing). What *does* pay is merging: D
   dispatches of grid G against ONE dispatch of grid D·G wins essentially
   linearly in D (measured across D = 2/4/8/16; numbers: `perf/runs.jsonl`).
   Fusion is worth roughly linear in how many
   dispatches it removes; widening is worth nothing.
   The constant does **not** transfer between graphs or machines — re-fit it
   before planning against it. On a MoE with many small passes this is the
   largest overhead term. An
   elementwise pass folded into a GEMV epilogue is free only while that GEMV is
   *at* roofline, where its ALU hides under the weight stream; below it the ALU
   shows up almost in full — the same gelu fold is free on int8 group(16) and
   gives back most of the pass it deletes on e4m3. It still nets a win; size it,
   don't assume it. Fold *into* the big kernel; don't fuse two small ones.
4. **Bytes**, but only above crossover.

**There is no CUDA-graph equivalent in wgpu.** `Queue::submit` consumes the
command buffer by value, so command buffers cannot be replayed; encode-ahead
(build token N+1's buffer while N runs) is the ceiling the API allows, and
encode is a fraction of a percent of a token anyway.

**Prefill is a different problem from decode.** It has M rows at once, so it is
a real GEMM and matrix units apply where decode's dependency chain forbids them.
Chunked M-row prefill is worth multiples over one decode graph per prompt token;
a cooperative-matrix GEMM is worth multiples again, because unlike the M-row
GEMV it actually reuses weights across rows.

## 5. Serving

### Speculative decoding, in closed form

```
 t_spec/token = (v(k+1) + c(k)) / τ     pays ⟺ τ > τ* = (v(k+1)+c(k)) / d
 v(m) = W/B_eff + m·A + H
```

Two limits are the whole story:

- **Bandwidth-bound** (`A → 0`): `τ* → 1`. Any acceptance above 1.0 wins.
- **Compute-bound** (`W/B_eff → 0`): `τ* → m = k+1`. But `τ ≤ k+1` by
  construction, so **speculative decoding can never pay on a compute-bound
  model, at any acceptance rate.** It is not a tuning problem.

So it pays only where weight traffic dominates and is m-independent. Sizing the
verify batch to what actually runs — rather than to the prefill chunk width —
drops τ\* substantially and is what moves a losing model into the paying range.
Verification **is** a batch of size k+1, which is why this inequality and the
batching one are identical: batching amortizes the same weight read across more
tokens, is the largest available lever, and needs a GEMM that reuses weights
across rows to deliver anything at all.

### Wiring

**A kernel win reaches serving only through the constructor serving uses.** These
graphs build once from a weight source, and serving builds from a *loader*, not
from host weights — so anything specialized at codegen has to be decided from
tensor headers, before the first weight is read. Wired into the host-weights
constructor alone it compiles, type-checks, and is a silent no-op in production.
Pipelines are shared across tensors, so bake a specialization only when the whole
checkpoint agrees on it, and fall back — never fail — when it does not. The same
trap one level up: a kernel the graph never *names* is unreachable however fast
it is, so check who dispatches an entry before optimising it.

### Memory

```
device_GiB ≈ 0.983 × weight_GiB + 3.612
```

The marginal cost of a model is ~1.0× its checkpoint bytes; the rest is a
per-process fixed cost paid once. Residency is effectively free, so multi-model
serving costs what the weights cost.

**Admission must budget the load transient, not the steady state.** Loaders that
expand weights on the host peak far above where they settle, and there is no
recoverable error to catch — the platform hands out memory until the process is
killed, so proactive refusal is the only defence.

## 6. Measurement

- **A green test may have run nothing.** `cfg`'d-out suites, env-gated early
  returns, missing adapters and dependency guards, and fixtures the shader
  compiler folds to a constant all print success. Prefer tests that **panic**.
- **A gate is only as sharp as its reference distribution.** On 2–3-token control
  *answers* the reference is near one-hot and KL is tiny whatever the weights do:
  a 4-bit FFN read as a rounding error there and **orders of magnitude worse on
  the same prompts' own text**.
- **Build with `--release` for anything timed.** `cargo test` defaults to the
  dev profile here, which has manufactured double-digit-percent "wins" that
  reverse in release.
- **One kernel-rate suite per process.** Several heavy suites in one process
  depress every arm by tens of percent.
- **Run a null control.** Comparing a configuration against *itself* across
  boots has repeatedly produced effects the same size as the ones being claimed.
  Build it through the same path as the arms: a pipeline cache keyed on
  (source, entry) hands two labels the *same* object, and a control that is
  literally the arm cannot bound anything.
- **A new shader entry inherits none of its neighbour's build options.**
  Workgroup memory is zero-initialized per launch unless the entry is on an
  exemption list, so an A/B against an established entry prices the memset, not
  the kernel: it inverted a real win into a stable, shape-independent
  multi-fold
  loss. Equalize build options in the harness; exempt only the routed default.
- **Do not use the per-dispatch profiler for totals.** It overstates small
  passes by an order of magnitude and once invented an overhead that did not
  exist.
- **Attribute a change to its own phase.** Prefill amortizes over the
  completion, so the same unchanged binary reads differently at different
  completion lengths. Always report prompt and completion counts.
- **Verify the flag reached the builder.** An unchanged pass count or boot-line
  format string means the knob did nothing, however plausible the timing delta.
