# The wgpu fp8 epilogue: what the two accumulators actually differ by

**The accumulator hypothesis is falsified. The epilogue swap is accepted
empirically, and it is backed by per-element coverage of the epilogues themselves
rather than by a kernel gate that could not see them.** Lane `iv-fp8`. Every
number here comes from `rust/crates/nv-models/tests/wgpu_fp8_epilogue.rs` on an
an NVIDIA Blackwell workstation GPU (Vulkan, subgroup 32); the
raw logs are not archived in this repository, and the per-element coverage
argument does not depend on them.

## 1. The two epilogues

`gemma4_wgpu.rs::build_fp8_pipelines` picks one of two entry-point pairs:

| mode | entries | accumulator |
| --- | --- | --- |
| shipped (`legacy_epilogue: 0`, the default) | `g4w_gemv_fp8_pk`, `g4w_gemv_fp8_pk3` | `qg_group_acc_e4m3`: fresh 16-element partial `d`, then `acc = fma(scale, d, acc)` |
| legacy (`legacy_epilogue: 1` via `set_attn_variant`) | `g4w_gemv_legacy_pk`, `g4w_gemv_legacy_pk3` | `qg_row_acc_e4m3`: one flat accumulator over the whole row, `total * qg_row_scale[row]` in the epilogue |

**Structurally they are one expression with the constant distributed
differently.** With the shipping configuration (`AttnQuant::default()` ->
`group = 0`), `quant_gemv::group_shift(0)` is `ROW_GROUP_SHIFT = 31`, so
`qg_row_scale[sbase + (v >> sh)]` is `qg_row_scale[row]` for **every** `v` -- the
same scalar the legacy epilogue multiplies by at the end. `s * Σ_v Σ_i w_i x_i`
versus `Σ_v (s * Σ_i w_i x_i)`, and f32 arithmetic is essentially equivariant
under multiplication by a constant. The only real difference is summation order:
one flat 336-term-per-lane chain versus a two-level 16-inner / 10.5-outer chain,
both far below bf16 output resolution.

## 2. The measurement, and the verdict

`the_legacy_row_scale_epilogue_lands_on_the_same_bits_as_the_shipped_one` runs
both entry points over the same buffers at the real Gemma4-31B shapes and diffs
the bf16 outputs bit-for-bit. On the o projection (sliding and full-attention,
tree and subgroup paths) **0 of 21504 elements differ**. On the fused qkv
projection at `k = 5376` -- the shape where the fix was supposed to matter most --
**7 of 16384 outputs (0.043%) differ, by at most 3 bf16 ulp**, and both arms are
within one bf16 ulp of an f64 reference.

A projection that is bit-identical on 21504 of 21504 o-proj elements and differs
on 7 of 16384 qkv elements by <=3 ulp **cannot flip a generation trajectory
except through the ordinary chaos of greedy decoding** -- which is exactly the
effect the reproducibility work measured (three runs of a byte-identical
configuration gave 66 ended / 78 ended / 96 not-ended). So the swap is recorded
as **empirically accepted, not explained**, and two honest possibilities remain
undistinguished: the original failure was never in the accumulator (the
entry-point swap landed together with other changes), or it was real but
data-dependent in a way random e4m3 codes and random row scales do not reproduce
-- the bit-identity argument in §1 is structural and holds for any data, while
the <=3 ulp qkv deltas are cancellation effects and real Gemma4 rows could cancel
harder than synthetic ones.

## 3. Why the old kernel gate could not have seen any of this

The gate credited with proving the fix reported `1.5145e-3` versus `1.5145e-3`.
**A bf16 output has a relative half-ulp of `2^-9 = 1.953e-3`, so that aggregate
was pinned at the output quantisation floor and structurally incapable of
resolving an epilogue defect.** `wgpu_fp8_epilogue.rs` replaces it with a
per-element bf16-ulp comparison against an f64 reference, plus an f32
accumulation noise floor (`16 * f32::EPSILON * Σ|w_i x_i|`) for rows whose true
dot product is buried under their own cancellation. On the real shapes that floor
is ~1.9e-5 against ~5.4e-4 for one bf16 ulp of a typical row, so it never relaxes
a typical element -- it only excuses catastrophic cancellation, and the harness
prints how many elements it excused.

## 4. Coverage that now exists

`wgpu_fp8_epilogue.rs` covers both the subgroup and the tree code paths, at both
`group = 0` and `group = 128`, on four real shapes: o-proj sliding
(n=5376, k=8192, `g4w_gemv_fp8_pk`), o-proj full-attention (n=5376, k=16384, same
entry with `dst_word_off = 24`), fused qkv sliding (n=16384, k=5376,
`g4w_gemv_fp8_pk3` split 8192/4096/4096) and fused qkv full-attention
(n=20480, k=5376, split 16384/2048/2048).

Every run also compiles four to five **mutated copies of the shipped shader
string** and requires each to fail. The mutants and their worst observed error:
`row-scale-index-collapsed-to-row-0` (190 ulp at group=0, 31720 at group=128),
`tree-pair-word-halves-swapped` / `sg-pair-word-halves-swapped` (32443),
`tree-hi-row-reads-its-own-lane-instead-of-the-next-warp` (32520),
`q-scatter-word-index-xor-1` (32359 on Q, 16379/16384 elements wrong),
`k-scatter-stride-halved` (40415 on K), `v-scatter-row-offset-plus-one-pair`
(32390 on V). **The mutants are applied to the string returned by
`gemma4_wgpu::fp8_pk_shader_source`, which is the same expression
`build_fp8_pipelines` uses to build the shipped pipelines**, so the probe and the
product cannot drift apart.

## 5. The default rests on this evidence

`ATTN_FP8_DEFAULT_ON = true` in `gemma4_wgpu`; build with an off attn variant
(`set_attn_variant`) to get bf16 attention back. The widened A/B behind it --
Gemma4-31B-IT-NVFP4 @ `e5ef03af`, every prompt through the shipped
`chat_template.jinja`, EOS-aware against `[1, 106, 50]`, reported per prompt and
never pooled -- returned worst per-prompt agreement 100.0%, no termination
mismatch on any prompt, no repetition loop, no stop-token leak, worst-perplexity
prompt `control-water` at ratio 1.000427 against an allowed 1.05, and ALLOW.
16 CONTROL prompts, all at 100.0% free-running argmax agreement with
`first divergence None` and `shape IDENTICAL`; median top-2 margins 15.1 to 20.1;
reference-token rank median/p95/max = 1 on every prompt; both arms producing the
same text on all 16. **The table was produced twice in two independent processes
and came out byte-identical** -- the opposite of the low-margin open-ended
prompts, which gave 66/78/96 across three runs of a byte-identical configuration.
Only controls carry the A/B.

Two mechanisms make that verdict reachable at all, and both stay in the harness.
**Pack widening:** `fp8_contract_freerun.rs` derives the template's
single-user-turn affix pair from the renders already in the pack (LCP/LCS over
the minimal-turn-shape prompts, suffix trimmed forward to the first markup
character), *proves* the derivation by re-encoding all 6 source renders and
requiring byte-identical ids, and only then emits 13 more controls through the
same tokenizer; it refuses to widen a pack it cannot reproduce
(`NV_FP8_WIDE_PACK=0` measures the narrow pack). **Real reference quality:**
`evaluate_default_flip_suite` used to be handed `reference_quality: None`, so it
always appended "no teacher-forced perplexity / rank evidence supplied" and could
never return ALLOW; the reference arm's own NLL on its own greedy trajectory is
now recomputed from bf16 logits already captured during the free run, so the
ratio the gate checks is a real number.

**Not measured by this lane: a fresh speed number.** The `-11.6%` handed to
`evaluate_default_flip_suite` is a previously recorded value and the GPU was
sharing a ~58 GB co-tenant throughout. The only performance facts measured here
are the weight traffic (31.479 GB -> 23.007 GB per token, a 26.91% cut) and the
dispatch count (728 -> 728, unchanged).

## 6. The chunked-prefill / batch-decode mk twins

Chunked prefill and batch decode additionally need an M-row multi-K ("mk") GEMV
variant that reproduces the M=1 decode path bit-for-bit, because a graph can
switch between the two within one run. It holds because the mk twins reproduce
the TREE reduction *and* the subgroup epilogue's `qg_butterfly` evaluates the same
f32 association tree as `qg_reduce` at lane 0 (same per-lane accumulator, same
pairwise order) -- so the tree mk twin is bitwise-identical to the *sg* decode
path too, not only the tree one.
`wgpu_fp8_epilogue::mk_tree_twin_is_bitwise_identical_to_both_decode_epilogues`
asserts exactly this. Only the *legacy* epilogue has a genuinely different
summation order and no mk twin.

**That assertion was vacuous on Metal until its sg arm stopped gating on the
strict `subgroup_ok` predicate**, which requires the adapter to report
`min == max == 32`; Metal reports `4..64` and fails it, so the sg comparison was
skipped and the test still printed ok. The lesson generalises: a comparison
guarded by a capability predicate reports success when the predicate is false.

`gemma4_wgpu::fp8_sg` still gates on that same strict predicate, so on any adapter
that fails it -- Metal, and this repo's own Vulkan probe alike -- the sg family
stays unreachable and chunked prefill / batch decode always take the tree
epilogue. **That predicate is deliberately not relaxed:** switching it to the
looser `sg32_ok` was tried and measured a null on this box (two runs of the same
tree arm bracketing the sg arm, well inside noise), unlike the real win the same
relaxation bought `gemv_nvfp4::select_variant`, where it changed the whole GEMV
rather than a reduction tail. Bit-exactness for a hypothetical tree->sg swap here
is genuinely verified; its speed is not, so the flip is not made.
