# The wgpu fp8 epilogue: what the two accumulators actually differ by

**The accumulator hypothesis is falsified. The epilogue swap is accepted
empirically, not explained.** The figures below came from a per-element suite
on an NVIDIA RTX PRO 6000 Blackwell Max-Q (driver 590.48.01, Vulkan, subgroup
32) that is no longer in the tree; the raw logs are not archived in this
repository, and the structural argument in §1 does not depend on them.

## 1. The two epilogues

`gemma4_wgpu.rs::build_fp8_pipelines` builds the e4m3 pair from one of two
entry-point pairs (the int8 pair `g4w_gemv_int8_pk` / `_pk3` sits beside them;
`ATTN_VARIANT_DEFAULT` selects int8, and an e4m3 variant is built through
`set_attn_variant`):

| mode | entries | accumulator |
| --- | --- | --- |
| shipped (`legacy_epilogue: 0`, the default) | `g4w_gemv_fp8_pk`, `g4w_gemv_fp8_pk3` | `qg_group_acc_e4m3`: fresh 16-element partial `d`, then `acc = fma(scale, d, acc)` |
| legacy (`legacy_epilogue: 1` via `set_attn_variant`) | `g4w_gemv_legacy_pk`, `g4w_gemv_legacy_pk3` | `qg_row_acc_e4m3`: one flat accumulator over the whole row, `total * qg_row_scale[row]` in the epilogue |

**Structurally they are one expression with the constant distributed
differently.** At `group = 0` (per-row, `AttnQuant::default()`),
`quant_gemv::group_shift(0)` is `ROW_GROUP_SHIFT = 31`, so
`qg_row_scale[sbase + (v >> sh)]` is `qg_row_scale[row]` for every `v` -- the
same scalar the legacy epilogue multiplies by at the end. `s * Σ_v Σ_i w_i x_i`
versus `Σ_v (s * Σ_i w_i x_i)`, and f32 arithmetic is essentially equivariant
under multiplication by a constant. The only real difference is summation order:
one flat 336-term-per-lane chain versus a two-level 16-inner / 10.5-outer chain,
both far below bf16 output resolution.

## 2. The measurement, and the verdict

Both entry points, run over the same buffers at the real Gemma4-31B shapes and
diffed bit-for-bit on the bf16 outputs: on the o projection (sliding and
full-attention, tree and subgroup paths) 0 of 21504 elements differ. On the fused
qkv projection at `k = 5376` -- the shape where the fix was supposed to matter
most -- 7 of 16384 outputs (0.043%) differ, by at most 3 bf16 ulp, and both arms
are within one bf16 ulp of an f64 reference.

A projection that is bit-identical on 21504 of 21504 o-proj elements and differs
on 7 of 16384 qkv elements by <=3 ulp **cannot flip a generation trajectory
except through the ordinary chaos of greedy decoding** (three runs of a
byte-identical configuration gave 66 ended / 78 ended / 96 not-ended). Two
possibilities remain undistinguished: the original failure was never in the
accumulator (the entry-point swap landed together with other changes), or it was
real but data-dependent in a way random e4m3 codes and random row scales do not
reproduce -- the bit-identity argument in §1 is structural and holds for any
data, while the <=3 ulp qkv deltas are cancellation effects and real Gemma4 rows
could cancel harder than synthetic ones.

## 3. An aggregate error cannot see an epilogue defect

**A bf16 output has a relative half-ulp of `2^-9 = 1.953e-3`, so an aggregate
relative error near that value is pinned at the output quantisation floor and
structurally incapable of resolving an epilogue defect.** The instrument that can
is a per-element bf16-ulp comparison against an f64 reference, plus an f32
accumulation noise floor (`16 * f32::EPSILON * Σ|w_i x_i|`) for rows whose true
dot product is buried under their own cancellation. On the real shapes that floor
is ~1.9e-5 against ~5.4e-4 for one bf16 ulp of a typical row, so it never relaxes
a typical element -- it only excuses catastrophic cancellation, and the
instrument must print how many elements it excused.

## 4. Coverage

No suite in the tree compares the two e4m3 epilogues, runs mutated copies of the
`gemma4_wgpu::fp8_pk_shader_source` string, or diffs the mk twins of §5 against
the decode path. `nv-models/tests/wgpu_fp8_formats.rs` covers variant
construction, format ranking and which projections the quantized path sweeps --
not epilogue bits. Mutation coverage of this shader belongs on
`fp8_pk_shader_source`, the same string `build_fp8_pipelines` compiles, so the
probe and the product cannot drift apart.

## 5. The chunked-prefill / batch-decode mk twins

Chunked prefill and batch decode additionally need an M-row multi-K ("mk") GEMM
variant (`g4w_gemm_fp8_mk_pk` / `_pk3`, `build_mk_pipelines`) that reproduces
the M=1 decode path bit-for-bit, because a graph can switch between the two
within one run. It holds by construction: the mk twins reproduce the TREE
reduction, and the subgroup epilogue's `qg_butterfly` evaluates the same f32
association tree as `qg_reduce` at lane 0 (same per-lane accumulator, same
pairwise order), so the tree mk twin is bitwise-identical to the sg decode path
too, not only the tree one. Only the legacy epilogue has a genuinely different
summation order and no mk twin.

`gemma4_wgpu::fp8_sg` gates on `gemv_nvfp4::subgroup_ok`, the probed-width
predicate (`subgroup_width_known() == Some(32)`), so the sg family is reachable
on any adapter whose dispatched probe reports 32 -- Metal included -- and chunked
prefill / batch decode take the sg epilogue there. A strict
`min == max == 32` predicate would fail on Metal (which reports `4..64`) and turn
any sg comparison gated on it into a silent skip: a comparison guarded by a
capability predicate reports success when the predicate is false. Speed is not
why the gate routes by capability: the sg-vs-tree epilogue choice measured a
null on this box, unlike `gemv_nvfp4::select_variant`, where the same
probed-width gate changed the whole GEMV. What licenses it is the bit-exactness
above: tree and sg epilogues are bitwise-identical, so the gate can never change
an answer, only a (measured-null) latency.
