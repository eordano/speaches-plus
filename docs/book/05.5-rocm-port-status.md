# nv-kernels on ROCm/HIP

`nv-kernels` carries a HIP backend behind the `rocm` cargo feature, alongside the
CUDA and wgpu backends rather than replacing either. **No ROCm box exists in this
fleet**, so nothing here has ever been timed; treat every performance statement
as reasoning about hardware, never as a result. What has been compiled is device
codegen for real AMD targets; what has been executed ran on an RDNA2 iGPU.
Companion: `rust/crates/nv-kernels/hip/pending/PORTING-NOTES.md` carries the
group-specific detail for the quarantined sources.

## 1. The build

Devshell: default `nix develop`. ROCm comes from nixpkgs `clr` with
`rocm-device-libs` as a **separate store path**, so `ROCM_DEVICE_LIB_PATH` is
mandatory alongside `ROCM_PATH` -- without it `cargo check -p nv-kernels
--features rocm` fails with *"cannot find ROCm device library"* and `build.rs`
panics with a remediation message. `ROCM_ARCH_LIST` selects targets (e.g.
`'gfx942;gfx1100'`).

**`cargo check` never links**, so the undefined symbols of §4 cost nothing until
a binary is built. That is the intended, loud failure mode -- and it means a
green `cargo check --features rocm` proves the sources compile, not that anything
links.

## 2. Hipified sources are checked in

Ported sources live in `nv-kernels/hip/`; unported ones are quarantined in
`hip/pending/` and excluded by a **shallow** `hip/*.cpp` glob, so promotion is a
plain `git mv` one level up with no `build.rs` change. The rocm build emits a
`cargo:warning` naming every quarantined file and stating that Rust callers of
the corresponding `nv_kernels_*` symbols will fail to link. Regenerate only when
the corresponding `.cu` changes, and diff the result against the repaired file.

Hipify is **not** run at build time. Most kernels need manual repair that
regeneration would silently discard -- the wave-width re-derivations are
structural rewrites of the warp/lane decomposition, not token swaps, and hipify
does not touch one of them -- and `hipify-perl` is reachable only from the
nixpkgs `rocmPackages.hipify` store path, so hipify-at-build-time would add a hard
ROCm build-time dependency for something that changes only when a `.cu` does.

**`hipify-perl` emits invalid C++ for templated `__global__` launches** and
reports exit 0, because perl does not parse C++: it splits
`cudaFuncSetAttribute`'s argument list on the comma *inside a template argument
list*, yielding `gdn_recurrent_kernel_f32<128), 128>`. `hipify-clang` -- given
`--cuda-path`, `--clang-resource-directory` and host libstdc++ `-isystem` paths,
none of which it finds on its own -- emits the correct form. **Rule: any file
that launches or references a templated `__global__` goes through hipify-clang,
or has its `hipFuncSetAttribute` call hand-checked.**

`cuda_sm120/gemv_blockscaled_probe.cu` is **deliberately not ported**: its only
symbol appears once in the whole tree, at its own definition, and it is absent
from `include/nv_kernels.h`, so bindgen never sees it and no Rust caller can
exist. Its body is a link-time canary for a CUTLASS type with no AMD analogue;
the `rocm` build should simply lack the symbol.

## 3. Wave width is the whole porting hazard

`hip/nv_hip_wave.h` carries the primitives:

- `NV_HIP_WAVE` / `nv_hip::kWave` -- compile-time wave width from an explicit
  target-family table (`__GFX9__` = 64; `__GFX10__`/`11`/`12` = 32) with a hard
  `#error` for an unrecognised AMDGCN target. **`__AMDGCN_WAVEFRONT_SIZE__` no
  longer exists** in current ROCm/LLVM, and `warpSize` is a non-constexpr object
  with `operator int()`, so the usual internet recipe silently falls into its
  `#else` and yields 32 on CDNA. The family table is the only correct source.
- `lane_mask_t` = `unsigned long long` with a correctly-sized `kFullMask`. HIP's
  `__shfl_*_sync` **static-asserts** the mask is 64-bit; a bare `0xffffffffu` is
  a hard compile error, not a silent wrong answer.
- `wave_sum<WAVE>` / `wave_max<WAVE>` -- width passed explicitly;
  `lane_group_sum<N>` -- the cross-wave fan-in stage; `host_wave_size()` /
  `host_max_lds_bytes()` -- runtime `hipDeviceGetAttribute` queries.
- `wave_aligned_block(desired, max_block)` rounds a block size up to a whole
  number of runtime-queried wavefronts. **This is the single place the 32/64
  launch decision lives**; every launch config goes through it rather than a fixed
  tier ladder, which would launch half-empty wave64s.

**Three classes of surviving `32` are correct and must not be "fixed":**
`kRowLanes = 32` in the gemv family is lanes per output row, not wavefront width
(reductions pass the width explicitly to `__shfl_xor`; on wave64 one physical
wave spans two output rows and the width-32 clamp keeps them independent --
correct, and untuned, since true wave64 with `kRowsPerBlock` halved has never
been benchmarked); the NVFP4 swizzled scale-factor layout (`/128`, `&3`, `&31`,
`*32`, `*16`) is a **checkpoint format contract**, not lane arithmetic, and is
preserved byte-for-byte; and the 4-bit packing arithmetic (32 nibbles per
`uint4`, `GS == 32`, `K & 31` alignment, the `(k0>>5)*33 + (k0&31)` LDS
bank-conflict pad) stays because AMD LDS also has 32 banks of 4 bytes.

**LDS tree reductions in `attn_decode`, `rmsnorm_residual` and `sampler` call
`__syncthreads()` on every iteration** rather than taking a warp-lockstep
shortcut, so they are wave-agnostic by construction. That is the classic CUDA
porting trap and it is deliberately absent; do not optimise the barrier away
because it is a no-op at wave64, since the same 64 threads are two waves on RDNA.

Two latent traps, recorded because they are not present bugs.
`lane_group_sum<N>` passes the *compile-time* `kWave` as its shuffle width while
`wave_sum`/`wave_max` take `WAVE` explicitly and `kFullMask` derives from `kWave`,
so compiling an RDNA arch with `-mwavefrontsize64` would make `kWave` 32 while
the runtime `warpSize` is 64 and the runtime-dispatched `wave_sum<64>` would run
with a 32-bit-valued mask -- `build.rs` passes no `-mwavefrontsize` flag, so
family macro and runtime width always agree today. And `flash_decode`'s
double-buffered fast path gates on `(HD >> 3) == WAVE`, i.e. `HD == 8*WAVE`, so on
wave64 that is HD=512 only and the common HD=128/256 falls to the generic loop;
correctness is unaffected, and the fix is a `uint2`/`u32` variant for
`HD == 4*WAVE` and `HD == 2*WAVE`.

## 4. CUDA-isms that must stay absent

A grep for `__ldg`, `__ldcs`, `__byte_perm`, `asm volatile`, `__nv_*`,
`cuda[A-Z]*`, `__hip_fp8_e4m3_fnuz`, `__HIP_E4M3_FNUZ` across `hip/` must return
zero hits.

- **The FNUZ trap.** `hipify` silently rewrites `__nv_fp8_e4m3` to
  `__hip_fp8_e4m3_fnuz`, which has exponent bias 8 and saturates at 240 --
  encoding toward a `kFp8Max` of 448 would clip in the container and the stored
  scale would stop inverting, producing **wrong numbers with no error**. Every fp8
  site therefore uses a hand-written software OCP E4M3 codec, because
  `HIP_FP8_TYPE_OCP` is 0 on gfx942 and HIP's own OCP path is host-only on CDNA3.
  On-device KV bytes stay bit-compatible with the CUDA build on every gfx target.
- **Inline PTX** does not survive hipcc and there is none left.
- **`__ldg`** has no matching ROCm overload for these pointer types and `__ldcs`
  is undeclared entirely; both are plain loads now, since `const __restrict__`
  already conveys the aliasing information and AMD has no separate read-only
  texture path. *Consequence:* the `gemv_w4a16_m1_proto` variant sweep is
  **degenerate** -- with `__ldcs` gone, `kStream=true`/`false` compile to identical
  code, so variants 0 and 1 are duplicates and the variant table needs a fresh
  benchmark to pick a default.

## 5. C ABI coverage: measure it, do not read it off a page

The method is symbol-level: extract every `nv_kernels_*` identifier from
`include/nv_kernels.h`, compile every `.hip.cpp` for a target, take
`nm -g --defined-only` over the objects, and diff the two sets. **The header
grows faster than the HIP tree does**, so any coverage count written into a
document is stale on arrival -- re-derive it. What the diff has always shown, and
what will not change without work:

- **The five Marlin symbols have no AMD story at all.**
  `nv_kernels_marlin_gemm_w4a16{,_ex,_prezeroed}`, `_repack_w4a16` and
  `_workspace_elems` come from vendored upstream Marlin (`cuda/marlin/`, in
  `SKIP_SUBPATHS`), which is hand-written `mma.sync` PTX for NVIDIA tensor cores.
  Not portable by hipify; it needs a from-scratch MFMA/WMMA rewrite or replacement
  by a hipBLASLt / Composable Kernel w4a16 path.
- **`nv_kernels_device_info(int* wave_size, char* arch_name, int len)` is defined
  but undeclared.** It reads `prop.warpSize` and `prop.gcnArchName` and is
  callable over the C ABI, but it is not in `include/nv_kernels.h`, so bindgen
  does not see it and **nothing in Rust can see the wave size or gcnArchName**.
  Declaring it plus a safe wrapper next to `cuda::capability()` is a three-line
  change and unblocks any arch-aware dispatch.
- **`nv_kernels_capability` deliberately fails on AMD.** It used to return
  `hipDeviceProp_t.major/.minor`, which is `(9,4)` on gfx942 -- Rust would have
  reported "SM 9.4" and any sm90/sm100 feature gate would have silently mis-fired.
  It now zeroes both out-params and returns `-1000`, so callers get an error
  rather than a plausible lie.
- `cutlass_fp4_gemm` and `moe_grouped_fp4_gemm` are **ABI stubs returning
  -1001**, with signatures and argument-validation returns preserved.

## 6. NVFP4 versus MXFP4

**Decode NVFP4 to bf16/fp16 in-kernel and feed the standard bf16 matrix-core
path. Offline MXFP4 transcode is a lossy, gfx950-only option that needs
measurement before any accuracy claim.**

This is implemented, not merely recommended: `gemv_nvfp4.hip.cpp` keeps the
16-entry E2M1 lookup table and `decode_ue4m3` into fp32 exactly as the CUDA source
had it, and `cutlass_fp4_gemm.hip.cpp` carries a working
`nvfp4_decode_to_bf16_prologue` whose decode tables are lifted verbatim from
`cuda/gemv_nvfp4.cu` so the two paths cannot drift. Decode-to-bf16 is the right
default for a correctness-first port because it is **lossless** with respect to
the checkpoints pinned in `flake.nix`, it still gets full matrix-core throughput
(the operand fetch keeps the 4-bit bandwidth advantage; only the
register-resident tile widens), and it requires no offline conversion, so a ROCm
user runs the same files an NVIDIA user runs.

MXFP4 transcode is lossy and must not be presented as free. Both formats use
4-bit E2M1 elements, but NVFP4 blocks 16 elements under an **FP8 E4M3** scale
while OCP MXFP4 blocks 32 under an **E8M0 power-of-two** scale, so two errors
compound: the scale loses all mantissa bits, and the block doubles so one scale
covers twice the dynamic range. E4M3-over-16 is precisely the precision NVFP4
exists to add. Native CDNA4 MFMA on MXFP4 is genuinely faster, so it is worth
measuring -- but only measuring.

The encoder side is format-preserving either way: `quantize_nvfp4_bf16.hip.cpp`
produces packed E2M1 plus UE4M3 scales, with the swizzled scale layout and
128-row SF tile padding preserved byte-for-byte; its only numeric deltas from the
CUDA source are `log2f`/`floorf`/`exp2f` -> `frexpf` and `exp2f` -> `ldexpf`,
both proven bit-identical across an exhaustive float sweep.

**One caveat stated plainly:** the `cutlass_fp4_gemm.hip.cpp` prologue indexes
scales **linearly** (`scales[i/16]`) while real checkpoints use the 128x4 swizzle
of `swizzled_scale_dst()`. The decode *arithmetic* is correct; the *addressing*
is a placeholder, and whoever wires it into a CK or hipBLASLt mainloop must apply
the swizzle on the read side or de-swizzle at load.

## 7. The backend must branch on architecture

There is no single AMD matrix-core intrinsic. Each arm below was verified by
compiling it, not read off a table:

| Target | Family | Wave | Matrix core |
| --- | --- | --- | --- |
| gfx90a | CDNA2 | 64 | `__builtin_amdgcn_mfma_f32_32x32x8bf16_1k` |
| gfx942 | CDNA3 | 64 | `__builtin_amdgcn_mfma_f32_32x32x8bf16_1k` |
| gfx950 | CDNA4 | 64 | `__builtin_amdgcn_mfma_f32_32x32x16_bf16`; **adds native MXFP8/MXFP6/MXFP4** via `__builtin_amdgcn_mfma_scale_f32_32x16x128_f8f6f4` |
| gfx1100/1200 | RDNA3/4 | 32 | **WMMA, not MFMA**: `__builtin_amdgcn_wmma_f32_16x16x16_bf16_w32` |
| gfx1036 | RDNA2 | 32 | **Neither.** Needs a scalar `#else` fallback, not an `#error`. |

Two traps found only by compiling: **the RDNA WMMA builtin bakes the wave width
into its name** (the unsuffixed `__builtin_amdgcn_wmma_f32_16x16x16_bf16` does
not exist and fails with "use of undeclared identifier"; it must be `_w32` or
`_w64`), and **the accumulator fragment size differs with wave width** --
`f32x8` on wave32 versus `f32x4` on wave64 for the same logical 16x16x16 tile, so
a fragment type hardcoded to 8 floats silently corrupts on wave64.

**CUTLASS tile shapes and stream-K do not carry over.** MFMA wants K in multiples
of 16 (gfx942 bf16) or 32 (gfx950 bf16) with a different LDS double-buffer
schedule, so the SM120 variant matrix must be **re-swept on real hardware, not
translated**. Stream-K has no AMD analogue -- CK split-K and hipBLASLt algorithm
search are the closest -- so collapse the `_streamk` entry point into the base one
on ROCm, keeping the symbol for ABI stability. The consequence for the NVFP4
decision: on gfx942 there is **no** native FP4 matrix path at all, so
decode-to-bf16 is not merely the safe choice, it is the only choice; MXFP4 becomes
interesting on gfx950, and only after measurement. Toolchain note: rocWMMA,
Composable Kernel and hipBLASLt are packaged in this nixpkgs but exist **only as
unrealised `.drv` paths**, so depending on any of them is a flake change, not a
code change.

## 8. What is unverified, and what would settle it

**Every wave64 code path is compiled and unexecuted.** The only AMD device in the
fleet is a gfx1036 RDNA2 iGPU (wave32, 4 CUs). A forced `-mwavefrontsize64` build
on it genuinely exercises 64-lane semantics, but that is RDNA-in-wave64-mode, not
CDNA; CDNA codegen, LDS behaviour and MFMA-adjacent scheduling are unverified at
runtime. So is `flash_decode`'s cross-block fan-in (`__threadfence` + agent-scope
atomic + reading another block's scratch), which passed on a 4-CU part where L2
coherence is nearly free -- the CUDA memory model does not transfer, and this
specifically wants a multi-XCD MI300 run.

**A CUDA-golden byte-diff has never been run, and it does not need AMD
hardware.** An sm_120 NVIDIA part is available in this fleet -- precisely the
target `cuda_sm120/` is written for -- so an A/B of CUDA output against HIP output
on the same inputs is the highest-value verification available and it is cheap.

Ordered by what unblocks the most: promote `hip/pending/` in dependency order
(`kv_fp8` must land before or with `flash_decode`, since the latter's fp8 path
decodes a cache the former writes; promotion is `mv`); declare
`nv_kernels_device_info` in the header and add a Rust wrapper (§5); run everything
on real CDNA, priority the `rmsnorm` reduction tree at `kWarps = BLOCK/64`,
`flash_decode`'s cross-block fan-in, and `tree_verify_attn`'s cross-warp merge at
`kWarps=4`; evaluate hipBLASLt or Composable Kernel w4a16 before writing MFMA by
hand; implement the two FP4 GEMM stubs (§7); and re-tune the `flash_decode`
fast-path gate, the gemv 32-lane row tiling and `gdn_recurrent`'s occupancy
question before measuring.

**A carried-over bug still needs fixing in the CUDA tree.**
`cuda_sm120/moe_grouped_fp4_gemm.cu` has a vacuous bounds check --
`int e = threadIdx.x; if (e >= gridDim.x * blockDim.x) return;` can never fire.
It is safe today only because the launch is `<<<1, num_experts>>>`; it becomes an
out-of-bounds read the moment the launch goes multi-block. The HIP copy is fixed;
the CUDA one is not.

## 9. Why both ROCm and wgpu exist

`05-backends.md` states the split; the ROCm side of it is that this backend
targets CDNA specifically -- MFMA matrix cores, wave64 reductions, `hipGraph`,
AMD-native FP8 -- so it is the right answer for a datacenter AMD deployment, buys
nothing on Apple, Intel or a browser, and requires a full ROCm toolchain to
build. The cargo features are independent (`cuda`, `rocm`, `wgpu`) and
`src/lib.rs` gates them separately: `pub mod sys` and `pub mod cuda` are gated
`any(feature = "cuda", feature = "rocm")`, so **the `cuda` module name now means
"native C-ABI backend"**; `pub mod graph` stays CUDA-only because it imports
`cudarc::driver` directly and `hipGraph` is a separate port; and `rocm = []`
deliberately pulls no `cudarc`.

Both ports share one lesson, arrived at independently: **the default build is
silently green in ways that mean nothing.** For wgpu it was a missing Vulkan
loader, which made every suite take its skip path. For ROCm it is that
`cargo check` never links, so undefined symbols cost nothing until someone builds
a binary. State, per claim, whether a machine actually ran it.
