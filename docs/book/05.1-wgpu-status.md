# wgpu / Vulkan -- port status, kernel parity, serving, and performance

Canonical wgpu document: what works, how correct it is, and what remains. Speed
numbers live in the basis-tuple quoting rule (numbers live in the private run ledger), the single place
both backends are compared. Companions:
[`05.2-kernel-parity-matrix.md`](05.2-kernel-parity-matrix.md) (what gates each
kernel -- authoritative where it disagrees with §2 here),
[`05.6-macos-port-status.md`](05.6-macos-port-status.md) (the Metal adapter --
everything below is Vulkan-only), [`04.1-fp8.md`](04.1-fp8.md),
[`08.1-quality-harness.md`](08.1-quality-harness.md),
[`05.5-rocm-port-status.md`](05.5-rocm-port-status.md),
the private status ledger.

**Every number below is Vulkan on the CUDA box and its raw logs are not in the
repo**; nothing here has a live gate except where a suite is named. §11 is the
one section measured elsewhere -- an AMD Strix Halo box with no CUDA in it.

Three claim strengths are used throughout and are not interchangeable:
COMPILES (`cargo check` succeeds), RUNS-SYNTHETIC (a test drives it on
tiny/random shapes), SERVES (a real HTTP request, real weights, coherent
output). SERVES is reached from the HTTP binary: `NV_SERVE_BACKEND=wgpu` plus
`NV_WGPU_CHAT_MODEL_DIRS=<snapshot>` loads the decoder and completes a chat
request with `sampling="in-shader-argmax"`.

## 1. Verdict

| Model | wgpu decoder | decodes real weights | serves a real chat request | output |
|---|---|---|---|---|
| `google/gemma-4-E4B-it` (bf16) | `nv-models::gemma4_e4b_wgpu` | yes (42 layers) | yes | coherent, correct, ends its turn |
| `nvidia/Gemma-4-31B-IT-NVFP4` | `nv-models::gemma4_wgpu` | yes | yes | coherent, correct, ends its turn |
| `RedHatAI/Qwen3.6-35B-A3B-NVFP4` | `nv-models::qwen3_5_moe_wgpu` | yes | yes | coherent, correct; reasoning trace split into `reasoning_content` (§4.4 item 2) |

**Every wgpu decoder graphs decode identically: chunked submission of a prebuilt
pass list -- one `queue.submit` per `NV_WGPU_SUBMIT_CHUNK` passes (unset
resolves to 32, so a token costs ceil(passes/32) submits and encode of chunk
N+1 overlaps execution of chunk N; `=0` restores the single end-of-step
submit; explicit values keep their meaning) -- with in-shader two-stage argmax
and a 4-byte token readback.** This holds for all seven -- `gemma4_wgpu`,
`gemma4_e4b_wgpu`, `gemma4_moe_wgpu`, `qwen3_5_moe_wgpu`, `qwen3_5_dense_wgpu`,
`gpt_oss_wgpu`, `laguna_wgpu` -- and chunked prefill (one submit per M-row
chunk, default M=8..16) is on by default in every one of them. The per-token
profiling arms (`submit_profiled_slices`, `NV_WGPU_PROFILE=1`) submit per-pass
timed slices instead and are off by default; profiling mode disables submit
chunking so profiled shares stay undistorted.

The graph-dispatch layer is fully shared; the decode kernels are not. Only
`wk::residual_scale` (7/7), `wk::rmsnorm` and `wk::rmsnorm_residual` (6/7) are
broadly shared. Five trivial glue ops -- argmax stage1/2, the bf16-GEMV core,
nvfp4 `quant_rows`, gather-embed, contiguous kv-write -- are reimplemented under
a per-model prefix (`q3w_`/`g4w_`/`g4m_`/`gow_`/`lgw_`/`e4b_`) 5-7 times with
byte-for-byte identical cores, though shared versions exist in
`graph_decode.wgsl` and `wk::gemv_bf16`; promoting them to `wk::` is pure
subtraction with no numeric or perf change. What is justifiably per-model:
weight-format GEMVs, the fused `*_attn_norm_rope` kernels (qk-norm placement,
softcap, GQA grouping, gpt-oss attention sinks), and `e4b`'s
LoRA/verify/matformer kernels.

**4-bit is the served default wherever the checkpoint ships it, but the default
weight format is per-decoder.** `qwen3_5_moe_wgpu`, `qwen3_5_dense_wgpu` and
`laguna_wgpu` serve nvfp4 (v2 subgroup GEMV default-on where a 32-wide subgroup
exists); `gemma4_moe_wgpu` serves w4/group-32 experts with a bf16 dense trunk;
`gpt_oss_wgpu` serves mxfp4 with dequant-in-shader. Two are NOT 4-bit by default:
`gemma4_wgpu` always requantizes its nvfp4 checkpoint's FFN to int8 (group 128
unless `NV_G4_WGPU_W8_FFN_GROUP` says otherwise; no env var keeps it nvfp4), and
`gemma4_e4b_wgpu`'s default checkpoint is bf16. The nvfp4-v2 shape router (`gemv_nvfp4_v2::select_pk`) covers
both served 31B FFN shapes with bit-exact goldens, so the 31B int8 default is a
deliberate quality choice, not a missing 4-bit kernel.

No dispatch count in this chapter is gated. `pass_count()` is the quantity the
server logs as `passes_per_token` on the engine-ready line. **Every pass count
here and in `05.6-macos-port-status.md` is ungated prose and rots on the next
fusion**; read a count off the boot line.

Against CUDA on identical prompts, template and weights: **three of five prompts
byte-identical**, the other two equivalent in quality (§4.3).

There is no CUDA-vs-WGSL parity suite in the tree, by decision: *two
implementations agreeing is not an oracle* -- the wgpu w4a16 family and its own
oracle once carried the same group-16 scale-indexing bug, which no amount of
agreement could have caught. What cross-backend checking remains lives in
`#[cfg(feature = "cuda")]` modules inside three wgpu suites (`wgpu_moe_grouped`,
`wgpu_lora`, `fp8_contract_e4m3`; `05-backends.md`, "Keeping the twins
honest"). **Every "bit-exact against CUDA" claim in §2.2 therefore has no live
gate.** The standing rule: a cross-backend agreement test is deleted wherever the
shipping backend has an independent host oracle for that entry.

## 2. Kernel-level parity with CUDA

### 2.1 Coverage

No kernel constructs `WgpuError::Unimplemented`; its only two occurrences are the
variant and its `Display` arm in `wgpu_backend/mod.rs`.

A zero stub count is not a coverage metric. A CUDA kernel that lands with no
wgpu counterpart is invisible to it -- nothing was stubbed, so nothing reports
missing. The way to see the real gap is to count `cuda/*.cu` against
`wgsl/*.wgsl` fresh; the count moves every time either backend gains a kernel.
What that count does not cover: `flash_decode`'s model-called `_mk` variants, and
a wgpu Marlin. The honest fix is to declare `Unimplemented` stubs for anything
CUDA-only, exactly as the original port did, so the metric can see it.

**The spec-decode verify trio has WGSL twins; what is CUDA-only there is the
serving wiring, not the kernels.** `wgsl/verify_fused_norms.wgsl`,
`wgsl/tree_verify_attn.wgsl` and `wgsl/tree_verify_fp8.wgsl` each ship with a
`nv_kernels::wgpu_backend::kernels::*` wrapper that includes them. Do not read
the WGSL trio's existence as tree-spec serving on wgpu (§9 item 14). At kernel level the CUDA-only residue
is Marlin (`cuda/marlin/`; `KernelId::MarlinGemmW4a16` is the one entry of
`KernelId::ALL` with no WGSL module, and `kind_supports` reports exactly that one
missing on wgpu -- §6) and the two SM120 CUTLASS files (§2.4).

### 2.2 Cross-backend agreement, as rules

None of this has a live gate (§1), so it is carried as three transferable
rules rather than as a results table. What was once observed in one process, real
CUDA FFI against WGSL on this adapter pair: every decode-path kernel exercised
(`attn_decode_f32`, `gemv_bf16`, `gemv_w4a16`, `kv_fp8`, `moe_unpermute_scatter`,
`residual_scale`, `rmsnorm_residual`, `sampler_topk_topp`, `rope_f32`,
`rope_bf16`, `depthwise_conv1d_silu_bf16`) was bit-exact; `gemm_nvfp4` was
not, and a probe of eight K-loop reassociations proved bit-exactness against
CUTLASS is unreachable, not unachieved (wgpu is asserted never further from
the exact f64 product than CUDA).

1. Write `fma(a, b, c)`, not `a * b + c`. WGSL `fma()` lowers to SPIR-V
   `Fma`, reproducing nvcc's `-fmad=true` contraction exactly;
   `moe_unpermute_scatter` became bit-exact on that substitution alone.
2. `ex2.approx.f32` and WGSL `exp2` agree on this stack -- an NVIDIA-Vulkan
   observation, not a spec guarantee: on AMD/Intel/Apple a 2-3 ULP `exp2`
   difference can flip a sampled token near a bucket boundary (§11).
3. Bit-exactness here is single-adapter (NVIDIA 590.48.01 Vulkan).

Two deliberate behavioural divergences, both pinned by tests: WGSL wrappers
return `WgpuError::Shape` where CUDA kernels would read out of bounds (clamped
OOB reads produce different but plausible numbers), and `moe_permute` is
deterministic on wgpu -- bit-exact against a sequential-cursor CPU oracle -- where
CUDA assigns slots with `atomicAdd` and is not. The wgpu side is the stronger
claim in both cases.

### 2.3 Signature divergences, and the one that silently costs bit-exactness

The two wgpu entries differ in signature from their CUDA twins in ways a porter
must know: `attn_decode` takes a `scaling: f32` CUDA does not (CUDA callers
pre-scale `q`), so parity is bit-exact only because the tests pass
`scaling == 1.0`; `gemv_bf16_normed` takes `eps: f32` where CUDA takes a
precomputed `rstd` device pointer; and `flash_decode`'s stubs omit CUDA's
`fan_in: *mut u32`, with the `_mk` variants having no wgpu stub at all.

The one that bites numerically: `wgsl/dequant.wgsl`'s
`int4_decode_u4b8(word, elem, group_scale)` folds the group scale into **every
element**, changing the association versus every CUDA w4a16 kernel, which hoists
the scale out of a 32-element block. A scale-free `int4_dequant_u4b8_raw` would
stop the next porter silently losing bit-exactness.

### 2.4 What is genuinely not portable, and why it is not the dtypes

WGSL has no trouble with any packed format in this crate.
`wgsl/dequant.wgsl` decodes E2M1, UE4M3, signed E4M3, E5M2, bf16 and
4-bit-int-with-zero-point-8 as integer bit manipulation on `u32` words, and
`wgpu_dequant.rs` verifies each against `nv_quant` exactly. **No future
document should claim a dtype blocker.** Nor is it warp intrinsics:
`grep -ln 'wmma|mma_sync|ldmatrix|cp.async' cuda/*.cu` returns nothing, and what
the hand-written `.cu` files do use -- `__shfl_*` warp reductions -- maps to WGSL
subgroup ops or a shared-memory halving tree.

What does not port is the schedule, in exactly two files.
`cuda_sm120/cutlass_fp4_gemm.cu` is three macro expansions of FlashInfer's SM120a
block-scaled tensor-core mainloop (TMA/`cp.async` multistage pipelining,
warp-specialized producer/consumer, swizzled shared-memory atoms, stream-K tile
scheduling with a device workspace), and `cuda_sm120/moe_grouped_fp4_gemm.cu` is
a grouped `OpClassBlockScaledTensorOp` whose prologue kernel materializes
per-expert pointers, strides and CuTe `LayoutSFA`/`LayoutSFB` objects into
scratch. **WGSL has no device pointers and no way to reconstruct CuTe layout
descriptors.** The answer is not to port them but to replace the schedule:
`gemm_nvfp4` has a scalar path and a real `coop_mat` path, both bit-exact
against the CPU reference.

NVFP4 is NVIDIA-only as a hardware format, and no vendor exposes 4-bit matrix
silicon through WGSL (`coop_mat` in wgpu 30 gives f16/f32 element types, not
FP4), so **in-shader dequantization to f16 is the portable path by necessity,
not by preference** -- correct even though it spends bandwidth the native FP4
path would not. `05-backends.md` carries the NVFP4-vs-MXFP4 format contrast.
`wgpu_backend/device.rs` requests only `SHADER_F16 | SUBGROUP` in
`required_features`; `EXPERIMENTAL_COOPERATIVE_MATRIX` must be enabled on the
`wgpu::Device` for a coop_mat shader to validate even though the adapter reports
`coop_mat=true`. At M=1 a 16x16x16 tile wastes 15/16 of the A-operand lanes
and the op is bandwidth-bound anyway -- no published implementation reports
coop_mat wins for GEMV. Keep it for prefill/batch GEMM.

## 4. Serving

### 4.1 What was proven, and how

The live wgpu serving suites are `wgpu_serving_unit.rs`, `http_wgpu_wiring.rs`,
`wgpu_guided_e2e.rs` and the `wgpu_spec_*`/`wgpu_*_routes` suites under
`rust/tests/`. Proven through the real `axum::Router` +
`handle_chat_completions` on an idle-gated GPU, for E4B, the 31B and Qwen3.6:
each decoder reports kind, pass count, EOS set and `max_seq` on the engine-ready
line, answers a greedy prompt correctly, honours `max_tokens`, finishes with
`finish_reason=stop`; SSE deltas reassemble byte-identically into the
non-streaming completion and end with `data: [DONE]`; greedy output is
reproducible across two successive requests to the same resident model (which is
what proves the KV cache is reset per request); a fixed `seed` reproduces a
sampled completion.

Two harness traps: a stop-string test that picks a >=4-char word from the model's
own output fails when the model answers in digits; and Qwen3.6 emits ~340 tokens
of chain of thought before its answer (its template ends with an open `<think>`
block), so a 96-token budget is not enough to see the answer -- a small
`max_tokens` reads as a failure that is not one.

### 4.2 Templating and EOS are right

`WgpuChatEngine::load` calls `ChatTemplate::load_reason(model_dir)` and **refuses
to construct** if the model ships no template, and `official_template()` returns
`Some` unconditionally: **there is no code path in this engine that can produce a
ChatML prompt.** Token arithmetic cross-checks the served prompts exactly
(Gemma4's fixed overhead is 9 ids, so E4B reported `prompt_tokens=14` for a 5-id
user turn and the 31B, whose template adds a 4-id thought-channel suffix,
reported 18). `eos_ids_from_dir` loads the sorted `eos_token_id` set from
`generation_config.json` and refuses to serve without one, and the harness
asserts no raw control marker appears in any served content -- on both the body
and the reassembled SSE stream.


### 4.3 wgpu vs CUDA on identical prompts

On quality, wgpu is the same as CUDA. Holding everything identical (same
`nvidia/Gemma-4-31B-IT-NVFP4` checkpoint, same official `chat_template.jinja`,
byte-identical prompt token ids, greedy free-running, same stop set, 96-step
budget, verified-idle GPU), three of five prompts came back byte-identical and
the other two shared their opening tokens, diverged at a near-tie and then
cascaded -- the expected consequence of different kernels breaking a tie
differently, not evidence of a defect. Do not read a non-terminating CUDA
completion as CUDA nondeterminism; a sibling run reproduced it on both arms.
Genuine CUDA nondeterminism does exist and is characterised in
[`08.1-quality-harness.md`](08.1-quality-harness.md) and
[`04.1-fp8.md`](04.1-fp8.md) §5.3. For the other two models no cross-backend run
on identical prompts exists.

Do not assume the CUDA arm is the coherent one. Measured:
`google/gemma-4-E4B-it` on CUDA through the HTTP binary at temperature 0,
`NV_NO_SPEC=1`, returns 300 tokens of multilingual garbage with
`finish_reason: "length"`, while the same binary and prompt on wgpu returns
`"Paris"` / `stop`.

### 4.4 What does not work

1. wgpu serving from the HTTP binary works. `main.rs` builds the chat router
   from `oapi::chat_engine_wgpu::registry_from_env_with_wgpu()` under
   `#[cfg(feature = "wgpu")]`, via `WgpuRegistryPlan::{Delegate,Extend,Replace}`;
   Delegate is the default, so compiling the feature in cannot change a
   deployment that never asked for wgpu. An explicitly requested wgpu backend
   that loads nothing REFUSES TO START, symmetric with the cuda path.
2. The reasoning-trace split lives in the shared `oapi::chat` handler, so
   both backends get it: `ThinkPostProcess { active:
   engine.thinking_split_supported(), opened:
   prompt.trim_end().ends_with("<think>") }`, then `split_thinking` on the
   non-streaming path and `ThinkingStream` on the streaming one. Neither backend
   overrides the gate (the trait default
   `official_template().declares_thinking_switch()`). Live gate: the
   `thinking_splits_*` tests in `oapi::chat`, which put the trace in
   `reasoning_content` and leave `content` as the answer alone, with no stray
   `</think>`; no suite renders the cached real templates. Qwen3.6, Qwen3.5-9B
   and Laguna-XS render `opened=true` (their templates open the block themselves, so the model only
   emits the closer) and the Gemma-4 family `opened=false` -- the case that would
   leak the whole trace if `opened` were computed wrong.
3. The prompt head derives from a `BosDeclaration` read out of the tokenizer
   (`add_bos_token`, `bos_token`), with `generation_config.json` as a fallback
   rather than the authority, and `Suppressed` as an explicit state: a checkpoint
   that declares no `bos_token` does not get one invented for it, least of all a
   token that is also in its EOS set. `rust/tests/http_wgpu_bos_guard.rs` holds
   it and refuses to report success with no snapshot to assert against.
4. **Prefill falls back to one token per command-buffer replay whenever the
   chunked path is not live.** The engine takes the chunk path whenever
   `WgpuDecoderHandle::prefill_chunk_len` is non-zero, and the M=1 loop serves
   only the tail; each of the seven kinds returns 0 only when its own prefill
   pass list did not build. A zero
   costs a P-token prompt P full replays, so read `prefill_chunk_len` off the
   engine before attributing a slow first token to the GPU.
5. Detokenization is incremental (`VisibleStream::step_incremental`) on every
   kind but `GptOss`, which decodes the whole `generated` vector every step --
   O(n²), harmless at 15 tokens, quadratic at 4096.
6. Guided/JSON-constrained decoding works: the wgpu engine builds the same
   `chat_engine::build_guided` the CUDA loops use, installs it on `HostSampler`
   via `set_guided`, and applies the mask in `pick`, forcing the logits-readback
   path. `rust/tests/wgpu_guided_e2e.rs` and `wgpu_guided_unit.rs` cover it.
7. Tools are wired but not GPU-tested. The engine passes the real tool list
   into the official template instead of copying `chat.rs`'s known-broken path;
   CPU-verified that Gemma4's template consumes `tools`, but no tool-calling
   request has been run against wgpu weights.

### 5.1 Eagle3 + LoRA is CUDA-only, and that matters more than it looks

`nv-specdecode/src/lora_spec.rs` is `#![cfg(feature = "cuda")]` and its `mod`
declaration is cuda-gated. The CUDA-side measurement that makes this
load-bearing: on a 64-vocab synthetic LM, base-drafter / adapted-verifier
acceptance is 0.281 vs 1.000 when drafter and verifier both carry the
adapter. The adapter must be applied to the drafter too, so a future wgpu
spec-decode path without the LoRA kernels cannot serve adapted models even once
attention runs.

### 5.3 Asymmetries that are the design, not a gap

Each is a rule to apply. Closing one reverses the rule, and needs the rule's
reason answered first.

1. wgpu is gpt-oss's default slot, and the cuda arm is deliberately expensive.
   `NV_GPTOSS_CUDA_SERVE=1` builds `nv_models::gpt_oss_cuda`, which **dequantizes
   every mxfp4 expert tensor to bf16 at load** and runs attention through
   `nv_layers::attn::sdpa_with_sinks` (the eager path, because the cuda flash
   kernel takes no sink argument). There is still no cuda mxfp4 GEMM or GEMV --
   `gpt_oss_wgpu` is the only gpt-oss path with one -- so the cuda arm costs
   ~41.8 GB resident against ~13.7 GB, plus `heads*rows*context` f32 of eager
   scratch per prefill chunk. `GPTOSS_NO_CUDA_WITHOUT_THE_OPT_IN` states this in
   the binary. Do not build a cuda mxfp4 kernel path to close a cost decision.
2. No WGSL Marlin and no WGSL CUTLASS-class batched 4-bit GEMM (§9 items
   12-13). wgpu covers w4a16 and nvfp4 through its own gemv/gemm shaders; the
   batched-throughput class is a cuda-architecture asset, not a port debt.
3. **The tree-verify WGSL kernels exist and the tree-spec serving wiring stays
   cuda-only** (§2.1); §9 item 14 is a verdict about CUDA-graph-captured serving,
   and a kernel existing does not reopen it.
4. STT stays on CPU in a wgpu-only build. GPU STT is third-party C++
   (`whisper-rs`, `ct2rs`) with its own CUDA feature; §9 item 16 says do not build
   a WGSL Whisper, so CPU is the designed outcome.
5. Laguna's cuda internals have no wgpu twins on purpose. `laguna_fa2.rs`,
   `laguna_graph.rs` and `laguna_serve.rs` are `#![cfg(feature = "cuda")]`; wgpu
   serves the same checkpoint through the separate `laguna_wgpu` module. Two
   per-architecture serving engines, not two halves of one port.
6. Per-architecture performance variants are never culled across backends. A
   CUDA kernel never removes a wgpu kernel, and the reverse: wgpu's coop-matrix
   decode GEMV paths and cuda's PDL / shared-memory kernels are each the only
   path their hardware has.
7. cuda-first precedence when both features compile is policy. `AUTO_POLICY`
   states it in the binary, `main.rs` prefers a `Delegate` default plan, and
   `nv_layers::lora_slots` re-exports the wgpu `LoraDispatch`/`LoraHook` under the
   unprefixed names only when cuda is absent. Compiling wgpu in cannot change a
   deployment that never asked for it.
8. Gate counts are not a parity metric. `grep -rn 'feature = "cuda"'` over
   `rust/crates rust/src` outnumbers `"wgpu"` by roughly 4.5 to 1, and the ratio
   measures construction style: cuda is gated in place inside shared model files,
   wgpu lives in parallel `*_wgpu` modules carrying one gate at the top. Count
   decoders, kernels and served classes instead.
9. wgpu reaches models through exactly four crates -- `nv-kernels`,
   `nv-layers`, `nv-models`, `nv-specdecode`. A wgpu path added elsewhere is a new
   dependency edge, not a fix.
10. **Parakeet, the nv-tts talker, Silero VAD and the EOU heads run on CPU on
    both backends.** Only `src/tts/mod.rs` builds an ONNX execution-provider
    ladder; `stt/parakeet.rs`, `vad/mod.rs`, `eou/onnx.rs`, `eou/audio.rs` and
    `pii/classifier.rs` build sessions with none. A symmetric absence, not a
    cuda/wgpu gap.
11. **qwen3.5-dense cuda serving stays opt-in, and the registry does not know
    it.** `QWEN35_DENSE_CUDA_OPT_IN_MATCHES_THE_WGPU_ORACLE_AND_STAYS_OPT_IN`
    (`chat_engine/build.rs`) records that the cuda arm returns the same tokens as
    the wgpu oracle and holds more VRAM for the same weights, and gates it on
    `NV_QWEN35_DENSE_CUDA_SERVE=1`. `backend_select::cuda_model_unservable_reason`
    does **not** read that variable, so `/v1/backends` reports the class as
    unconditionally cuda-refused. Reconcile the two before quoting either; the
    same env admits qwen3.8-27B to cuda, where the registry *does* read it.

### 5.4 Open gaps, stated as the degradation a selection produces

The matrix's `no` cells already say which side lacks what. What they cannot say is
what a selection costs, and that is the form to reason in: a cuda selection
degrades to full re-prefill on every reconnect (no `persist`, no
`plan_prefix_reuse`) and to a `QWEN38_DENSE_NO_CUDA` refusal on qwen3.8-27B, whose
`detect_family` `starts_with("qwen3")` catch-all routes the config to
`qwen3::Qwen3Config` where `qwen3.rs` has no linear-attention mixer for the 3-of-4
`linear_attention` layers -- the same holds for qwen3.5-dense 9B by default (§5.3
item 11). A wgpu selection degrades to one contiguous KV buffer capped at the
load-time `max_seq` with batching on `Gemma4Dense` alone under `NV_WGPU_BATCH`
(`BATCH_GRAPH_SEAM` names the missing seam for the other six graphs); to text-only
on the Gemma-4 family, with an explicit `bail!` per graph rather than a silent
drop, because image rows reach two wgpu graphs (`Qwen3_5DenseWgpu` and
`Qwen3MoeWgpu`) and audio reaches none; to plain decode on everything but
Gemma4E4b unless an opt-in admits the kind (§5); and **on Linux,
to no memory guard at all**, because `mem_fit::available_memory_gib` returns
`None` there and `plan()` short-circuits.

qwen3.8's wgpu lm_head streams the checkpoint's `F8_E4M3` bytes with per-row
scales and never widens them to bf16
(`FP8_LMHEAD_DEFAULT_ON_FOR_THE_SAME_REASON_AS_FP8_PROJ`). That is a memory
choice, not a speed one: decode at 27B batch=1 is not lm_head-bandwidth-bound, so
profile where the step time goes before touching the lm_head for latency. Kernel
gate: the suite covering the fp8 rowscale entry (`wgpu_q3d_fp8_lmhead`).

### 5.5 Where the evidence is thinner than the matrix

A matrix row is a claim about the code. These are the rules for what a run
proves -- each one a way a lane comes back green having tested nothing.

- **The default-serving backend of a model is not always the one its gates
  cover.** Most of the `gemma4_moe_*` battery is `#![cfg(feature = "wgpu")]`
  while cuda is Gemma4-MoE's default backend (whose only real-weights decode test
  is the `NV_GGUF_PATH`-gated `gguf_gemma26b_gpu`), and no `ppl_*` suite exists in
  `crates/nv-models/tests/` for any family. Before quoting a quality gate, check
  its `#![cfg]` header names the backend the model actually serves on.
- **`laguna_wgpu` serves from the binary but its suites need a feature no default
  lane sets.** All six `laguna_wgpu_*` suites are
  `#![cfg(feature = "laguna-wip")]` while `nvk.sh` defaults to `cuda,wgpu` for
  nv-kernels and `cuda` elsewhere. Run them as
  `NVK_PKG=nv-models NVK_FEATURES=cuda,wgpu,laguna-wip`.
- **Cross-backend agreement is established for three kernel families and
  transitively everywhere else.** The only tests compiled under
  `cfg(all(feature = "cuda", feature = "wgpu"))` are the CUDA modules of
  `wgpu_moe_grouped` (grouped MoE GEMM against the CUTLASS path), `wgpu_lora`
  and `fp8_contract_e4m3` (E4M3 encoding). Attention, rope, rmsnorm, the GEMVs
  and the sampler agree only through each side's own CPU oracle -- the standing rule (§1), but it
  makes "wgpu matches cuda" for those an inference.
- wgpu skip polarity is inverted between crates. `nv-kernels` and `nv-layers`
  wgpu suites are loud by default; the nv-models real-model suites
  using `common::ctx_or_skip` (`gemma4_e4b_wgpu_verify`,
  `deepseek_ocr_decoder_wgpu` among them) print `skipping: no wgpu adapter`
  and pass unless `NV_KERNELS_WGPU_REQUIRE=1` is set.
- A gated `mod` disappears without a sentinel unless the file plants one.
  `tests/qwen38_multimodal_e2e.rs` and `tests/wgpu_serving_unit.rs` are the
  pattern to copy: a `#[cfg(not(feature = "wgpu"))]` marker test printing
  "compiled OUT ... this is a SKIP, not a pass". `tests/responses_http.rs` has no
  such marker, so its warm-resume coverage vanishes from a cuda-only run while
  the file's other nine tests still report green.
- A self-recorded baseline is a regression gate, not an oracle.
  `qwen38_multimodal_e2e` compares against a transcript it recorded itself
  (`NV_QWEN38_MM_TEXT_BASELINE`), and the qwen3.8 vision tower has no independent
  reference -- contrast `deepseek_ocr_oracle`, which has a CPU one. And
  `tests/qwen38_routing.rs`, the routing contract for a model that serves only on
  wgpu, is `#![cfg(feature = "cuda")]` and compiles out of a wgpu run.
- Two rows rest on nothing checkpoint-specific. gpt-oss is a parked family
  with no real-weights wgpu suite in the tree, although the
  `ModelClass::GptOss` registry row still names one; `Qwen35Moe`'s wgpu row is
  `ArchitectureFamily` against qwen3.6 with no checkpoint-specific suite on
  either side.

### 5.6 The Voxtral Realtime STT twin

`nv_models::voxtral_wgpu::VoxtralWgpu` is the Vulkan twin of the CUDA realtime
STT decoder (`07-speech-stack.md`). `rust/src/stt/voxtral.rs` serves it under
`NV_SERVE_BACKEND=wgpu`, or whenever the box has no CUDA device, with the same
checkpoint, Tekken vocab, streaming prefix and merged LoRA adapters as the CUDA
path. It follows the chat decoders' shape -- prebuilt pass lists replayed from
device-resident token and position buffers, in-shader argmax, one ring readback
per replay batch -- but owns its kernels (`VX_WGSL`, `VX_GEMV_NV4_WGSL`,
`VX_ATTN_PREFILL_WGSL` in `voxtral_wgpu.rs`), so nothing here is covered by the
chat decoders' gates.

Weight format is `NV_VOXTRAL_QUANT`, read by `wgpu_quant_from_env`: `nvfp4`
(the default, by `WGPU_NVFP4_IS_THE_DEFAULT_BY_THE_LIBRISPEECH_73_CLIP_CORPUS_TEST`:
the 73-clip corpus test scores the same word errors as bf16 at under half the
time per token) or `bf16`. `nvfp4` quantizes exactly what the CUDA path does
(`DECODER_WEIGHTS_SET_THE_STEP_FLOOR_SO_ONLY_THEY_ARE_QUANTIZED`: the 26 decoder
layers' qkv, o, gate/up, down and the tied lm_head's own copy; encoder and
embedding stay bf16) with the CUDA quantization (per-tensor global 448*6/amax,
block-16 ue4m3 scales, `nv_quant::nvfp4::quantize_rows_with_global`, the same
scale swizzle), and keeps bf16 activations the way CUDA does at every M <= 64:
W4A16, dequantized in the GEMM tile loader for the seed and in `vx_gemv_nv4`
for the step. It deliberately does not take the chat decoders' `q3w_gemv_nvfp4`
route, which quantizes activations to e2m1 per block and would add an error
term the CUDA Voxtral path never has. The instrument that blessed the CUDA flip
(`voxtral-tune eval`, 73 LibriSpeech dummy clips) drives `VoxtralRealtime`
only, so the wgpu engine runs the same corpus through the suite covering corpus
word errors (`wgpu_corpus_word_errors_reproduce_the_cuda_flip_instrument`,
`NV_VOXTRAL_CORPUS=<rows.jsonl>`); any change that reassociates a sum on this
path reruns it before it ships, and the commit names it.

**The prefix is seeded once.** Prefix row r adds audio row r (BOS included),
and an audio row whose mel frames all end before the first STFT window that
reaches past the zero left pad is the same across clips through the causal
encoder (`THE_PREFIX_ROWS_THAT_SEE_ONLY_THE_LEFT_PAD_ARE_SEEDED_ONCE_PER_MODEL`).
`VoxtralWgpu::seed_rows` derives that count from the pad, hop and window
constants (31 of the 39 prefix rows for the shipped tokenizer); `seed_passes`
computes their K/V through the GEMM path on the first clip and keeps it, and
`prefill` runs only the remaining rows per clip. The suite covering the prefix
seed (`wgpu_prefix_seed_rows_are_bitwise_the_same_across_clips`) asserts the
seeded audio rows bitwise across two clips; the row after them differs by a
real signal, not rounding, so the count is tight.

**The nvfp4 step drafts pads like the CUDA graph**
(`THE_NVFP4_STEP_DRAFTS_PADS_LIKE_THE_CUDA_GRAPH_AND_STAYS_BITWISE_PER_ROW`,
`PAD_DRAFT_SPECULATION_COMMITS_EVERY_LEADING_PAD_OF_AN_M_ROW_STEP` in
`voxtral_graph.rs`). A replay is an M-row block: row 0 carries the committed
token and rows 1..M the streaming pad; `vx_rope_kv` writes M consecutive
positions, `vx_attn_decode1`/`2` take a row index and run each row's own
prefix in the one-row order, `vx_argmax1` reduces per row and `vx_argmax2`
commits rows while the previous row's argmax is the pad, advances the device
position by the count and mirrors it into the ring's extra slot
(`RING_POS_SLOT`), so a batch of replays still needs one readback.
`decode_stream` batches replays by remaining/M exactly as `GraphState`
does. `PAD_DRAFT_ROWS_DEFAULT_FOR_NVFP4` is four by measured ms/token on the
fixture (two and eight are close, one is well behind); `NV_VOXTRAL_SPEC_ROWS`
mirrors the CUDA knob for the ladder, and bf16 stays one row. The same block
is the per-clip prefix prefill, with the lm_head on its last row only.

Every row of the M-row product is bitwise the one-row product, which is what
makes greedy acceptance exact: `vx_gemv_nv4` is generated per M
(`gemv_nv4_source`) with the lane-to-block-pair mapping, the per-row fma chain,
`subgroupAdd` and the `sg_per_pair` merge unchanged, and the lib suite asserts
row 1 of a three-row product against the one-row product bitwise, for the
plain, accumulating and normed inputs, and the same for the decode attention
and the accept pass. The input row is not staged in workgroup memory: it was,
with the rmsnorm fused into the prologue, and at M rows every workgroup
re-normalized M rows for its two to sixteen weight rows, which is why the
first M-row GEMV cost M times the one-row read. Now `vx_norm_rows` writes each
row's rmsnorm once (attn_norm before qkv, the delay-folded ffn_norm before
gate/up, the final norm before the lm_head) in the GEMV's permuted layout
(`NV4_ROWS_ARE_PERMUTED_SO_A_SUBGROUP_READS_ITS_32_BLOCK_PAIRS_CONTIGUOUSLY`,
`nv_perm`: within each 1024-element group a subgroup's 32 block pairs are
contiguous per vec4 column, so the 32 lanes read 512 contiguous bytes per
load), the decode attention and silu passes write the same layout for o and
down, and the GEMV reads x straight from L1 with no prologue at all: e2m1
decodes arithmetically (`E2M1_DECODES_THROUGH_THE_F16_SUBNORMAL_LADDER`, two
nibbles per `unpack2x16float`) rather than through a byte LUT in workgroup
memory, which costs less than the LUT's gathers at every M. Staging the
permuted rows as f32 to save the bf16 unpack is a measured loss at M >= 2:
the doubled L1 traffic outweighs it. The permutation needs k to be a multiple
of 1024 and a 32-wide subgroup, which `gemv_nv4` asserts. A layer is ten passes
(`THE_NVFP4_STEP_FUSES_RMSNORM_AND_RESIDUAL_ADDS_INTO_ITS_GEMVS`) and the
one-row GEMVs run closer to the memory rate than the staged version did. Read
the live count off `VoxtralWgpu::step_pass_count`, and the replay count off
`VoxtralWgpu::replays`; the acceptance suite prints both.

**The encoder prefill** runs `vx_gemm` as an 8x8 register tile on 64 threads
over a 64x64 output tile with a 32-wide K step: the loader has four threads
per row fetch one vec4 each, so a warp's load covers eight rows' contiguous
64-byte segments (the one-thread-per-row loader read half of every sector it
touched and ran at two thirds of this speed), prefetches the next K tile into
registers during the multiply, dequantizes nvfp4 in place for the seed, and
the bf16 encoder linears share it. `Kit::split_k_for` splits K whenever the
output tile count falls short of `GEMM_SPLIT_K_TARGETS_THIS_MANY_WORKGROUPS`,
so the encoder's o and down (twenty column tiles) fill the card like gate/up,
with `vx_gemm_reduce` summing the partials and owning the epilogue (bias,
GELU, f32, accumulate); `split_part` sizes the partial buffer per clip.
`vx_attn_prefill_hd64`/`hd128` put four threads on each query row, one per
head-dim quarter, sharing the score through two `subgroupShuffleXor` steps
and keeping a quarter of the accumulator each; one thread per row left two
warps per SM on a 376-frame clip and was the encoder's largest pass.

Loading flushes upload staging per layer
(`UPLOAD_STAGING_IS_FREED_ONLY_AT_A_DEVICE_POLL_SO_THE_LOADER_FLUSHES_PER_LAYER`):
`create_buffer_init` parks each upload's staging copy until a device poll, and
on a resizable-BAR adapter that staging is device memory, so without the flush
the loader's peak is twice the checkpoint.

`NV_WGPU_PROFILE=1` routes the encoder and every replay through
`submit_profiled_slices`; `encode` prints `dispatch::profile::table` for its
passes and `decode_stream` for the replay, keyed by `entry:linear`
(`vx_gemv_nv4:vx-dec-gu`, `vx_attn_prefill_hd64`, ...). The per-pass sum is
close to the GPU timeline; the inter-dispatch gap is not a lever and
`NV_WGPU_SUBMIT_CHUNK` makes no difference. The acceptance suite's `warm
phases ... best of N` line times mel+encoder, the per-clip prefix prefill and
the decoder separately, the decoder both per token and per replay; it is the
best of several repeats because the SM clock needs longer than one short
decode to leave idle, and it is only a number on an idle card: three agents
share this GPU and a contended run reads two to three times slower across
every phase, encoder included. The `--ignored` lib probes
`gemv_nv4_row_ladder_probe` and `gemm_encoder_shapes_probe` time the GEMV at
one to eight rows and the GEMM at the encoder's shapes without a model, which
is the edit loop for either kernel.

Gates: the unit suite covering each kernel against a host oracle (`--lib
voxtral_wgpu`, synthetic shapes, including the nvfp4 GEMM/GEMV with the norm
pass and accumulate against `dequantize_nvfp4_host`, the M-row bitwise
assertions and the accept chain), and the real-weight suite
`tests/voxtral_wgpu.rs` (`NV_VOXTRAL_TEST=1 NV_SERVE_BACKEND=wgpu`): audio
embeddings against the transformers oracle, the LibriSpeech fixture at zero
token diffs, the prefix seed, and the corpus instrument above. Run the fixture
under both `NV_VOXTRAL_QUANT` values before touching a kernel; the phase times
it prints and the profile tables are the speed numbers for this twin and live
in the run ledger and the commit messages.

A segfault at test-process exit after a green run, with the kernel log naming
`libnvidia-gpucomp.so` or `libnvidia-glvkspirv.so` (`segfault at 11` or `at
18`), is NVIDIA's shader compiler crashing at teardown on a particular shader
source, not the test: cargo then reports the binary as failed after every test
passed. Read `journalctl -k` for that frame before treating such an exit as a
bug here.

On wgpu's Metal backend (Apple silicon) the twin runs the same kernels: the
adapter grants subgroups, the runtime width probe sets the GEMV's lane count,
and the workgroup storage budget is the one the native gate enforces. The lib
suite comparing the ungranted attention twins against the subgroup kernels is
bitwise on Vulkan and a relative band on Metal
(`METAL_COMPILES_EACH_KERNELS_REDUCTION_IN_ITS_OWN_ORDER_SO_THE_TWINS_ARE_A_BAND_THERE`):
Metal compiles each kernel's reduction in its own order under fast math (the
`simd_sum` law in `05.7`, section 7), so two kernels agree to a band there,
never to the bit, and a Metal run of any cross-kernel bitwise gate is a band
gate or a void one.

### 5.7 The Voxtral TTS codec twin

`nv_models::voxtral_tts_codec_wgpu::VoxtralTtsCodecWgpu` is the Vulkan twin of
the candle codec decoder in `voxtral_tts_codec.rs` (`07.1-voxtral-tts.md`,
"Codec port status"): the same contract (`decode(codes)` over `[T, 37]` cut at
the first end-of-audio frame, `decode_frames(&mut CodecState, frames)` for a
stream, f32 at 24 kHz clamped to `[-1, 1]`), the same weight-norm fold,
transposed-conv-as-causal-conv rewrite, semantic table, ALiBi slopes `0.5^h`,
windows 2/4/8/16, QK and block RMSNorm epsilons and LayerScale, with every
weight bf16 and f32 accumulation. Its rules:

- **The state is device resident**
  (`THE_STATE_IS_DEVICE_RESIDENT_SO_A_FRAME_REPLAYS_A_PREBUILT_PASS_LIST`). A
  `CodecState` holds a frame counter, the `k - 1` trailing input columns of
  each of the five convolutions, and per attention layer a `window`-slot K/V
  ring addressed by absolute position modulo the window. `cx_im2col` reads the
  counter to choose between the carried history and the first-call pad
  (replicate, reflect or zeros), `cx_attn` derives the valid ring span and the
  ALiBi distances from it, `cx_kv_commit` scatters the newest keys into their
  slots, and `cx_advance` bumps it; the carried columns are copied out of the
  im2col buffer by `cx_carry`. So the pass list for a given frame count is
  built once per state, cached by frame count, and replayed; a call does no
  host work beyond uploading the codes and reading back the samples.
  `decode` runs on a model-owned state that `reset` returns to frame zero.
- **Every convolution is an im2col GEMM.** The im2col row is tap-major over
  the channel vector; the input conv pads K from 876 to 896 so the 32-wide K
  step tiles it; the three upsamplers are the causal `[x[i-1], x[i]]` conv
  whose `[2C]` output row is already the `[2, C]` time-interleaved layout, so
  no permute follows; `output_proj` emits `[8T, 240]` patches that are the
  sample stream in memory order.
- **Kernels.** `cx_gemm`/`cx_gemm_reduce` are the STT twin's bf16 register-tile
  GEMM with split-K (`Kit::split_k_for`, same workgroup target), kept in this
  file because the twin's source is private to it; its one epilogue flag
  (`GEMM_SCALE_ACCUM`) rounds the product to bf16, multiplies by the LayerScale
  column, rounds again and accumulates into the residual, which is the
  reference's bf16 op order. `q`, `k`, `v` are one GEMM, `w1`/`w3` one GEMM.
  The pre-norms reuse the shared `rmsnorm_bf16`; `cx_norm_rows` is the same
  norm with a row stride and offset so the QK norm reads the fused `qkv` rows.
  `cx_attn` is a 64-thread workgroup per query row and head, one word of the
  head per thread, over at most `window + 1` keys: the partial dots meet in
  workgroup memory, scores and softmax are f32, the output bf16 (one thread
  per row and head was the largest pass of a frame); `cx_silu_mul_rows` is the gated
  product over the fused gate/up row; `cx_latent` builds the `[T, 292]` latent
  from the codes and the semantic table on the device.
- Activation scratch grows to the largest call
  (`SCRATCH_GROWS_TO_THE_LARGEST_CALL_AND_STARTS_AT_THIS_MANY_FRAMES`); growing
  drops the cached pass lists and keeps the carried state.

The suite covering the twin (`tests/voxtral_tts_codec_wgpu.rs`, `#[ignore]`,
`NV_SERVE_BACKEND=wgpu`, `VOXTRAL_TTS_MODEL_DIR` or the snapshot path in the
suite) decodes both fixtures, asserts the waveform within the bf16 band of the
fixture's clamped `waveform`, reports the fraction within 1e-2, asserts the
per-frame stateful decode against the full decode, prints the best-of-N full
decode and the per-frame cost, prints the `NV_WGPU_PROFILE=1` table for one
stateful frame, and with the `cuda` feature closes the loop through the CUDA
`VoxtralRealtime` on the decoded wav resampled to 16 kHz. The suite prints the
adapter summary (`WgpuContext::summary`) so a run names its backend, device
and subgroup grant.

The twin is the codec's Metal route: `VoxtralTtsCodec::load` refuses a Metal
device by design, and this suite runs unchanged on wgpu's Metal backend, where
the waveform holds the same bands and the per-frame stateful decode matches
the full decode. Its STT closed loop stays behind the `cuda` feature, so on a
Mac the codec's closed loop is the TTS suite's (5.8).

### 5.8 The Voxtral TTS twin

`nv_models::voxtral_tts_wgpu::VoxtralTtsWgpu` is the Vulkan twin of the
candle TTS port in `voxtral_tts.rs` (`07.1-voxtral-tts.md`): the same
`synthesize(text, voice, noise, max_frames, trace, teacher)` contract and the
same `Synthesis`, `FrameTrace` and `StageMs` results, the same prompt (BOS,
begin-audio, the voice's `[AUDIO]` run spliced with the preset tensor read
from its `.pt`, the Tekken text, repeat and begin-audio), the same neox row
permutation and folded softmax scale on `wq`/`wk`, the same masked semantic
argmax, three-layer bidirectional flow head over the two-by-three CFG token
batch, Euler and FSQ rounding, and the 37-row embedding sum. It shares the STT
twin's kernels: `voxtral_wgpu.rs` exposes its `Kit` (GEMM with split-K, bf16
and nvfp4 GEMVs, `vx_norm_rows`, `vx_rope_kv`, the prefill and decode
attention, silu, residual add) `pub(crate)`, and the TTS twin adds only what
the TTS graph needs (`VT_WGSL`: `vt_prompt_rows`, `vt_frame_embed`,
`vt_semantic_argmax`, `vt_flow_tokens`, `vt_flow_attn`, `vt_euler`). Its rules:

- **The prompt prefills through the split-K GEMM path** with the STT
  decoder's shape: one `vt_prompt_rows` gather builds the `[m, 3072]` input on
  the device, then per layer rmsnorm, qkv GEMM, `vx_rope_kv` from position
  zero, `vx_attn_prefill_hd128`, o, residual norm, gate/up, silu, down; the
  final norm runs over the prompt rows and the two heads (semantic head,
  `llm_projection`) read the last row by offset. The pass list is built per
  call because its shapes are the prompt's; the step and flow lists are built
  once at load.
- **A frame is two submits and one readback.** The flow list is the nfe Euler
  steps back to back: per step `vt_flow_tokens`, which applies
  `input_projection` to the bf16 state (K padded from 36 to 64) in the same
  pass that assembles the six rows (noise token, time token i, conditioning;
  the unconditional triple with a zero conditioning row), three layers at M=6,
  the final norm, the velocity head over all six rows, and `vt_euler`. The
  step list is `vt_frame_embed` over the 37 ids, the backbone step (the STT
  twin's nvfp4 layer, or the bf16 layer below), the final norm, both heads and
  `vt_semantic_argmax`, which also advances the device position. A free run
  submits the flow and the next step together and reads the 37-word frame
  once; teacher forcing reads the frame, writes the teacher's ids and then
  submits the step; `trace` splits the lists where the fixtures look (per
  Euler step on frame 0, around the embedding sum). wgpu cannot replay a
  command buffer, so each submit re-encodes its prebuilt pass list; the pipelines,
  bind groups and parameter uniforms are built once at load, and nothing is
  written per dispatch.
- **Every bf16 linear of a frame is `vt_gemv`**
  (`THE_M_ROW_GEMV_READS_VEC4_WEIGHTS_PER_SUBGROUP_LANE_AND_FUSES_SILU_AND_THE_RESIDUAL`),
  generated per (M, R) from one template: a unit of `sg_per_unit` subgroups
  owns R weight rows and every lane reads one 16-byte `vec4` of each row per
  step, so a 32-lane subgroup reads 512 contiguous bytes per load and the M
  input rows come from L1; lanes meet in `subgroupAdd`, the parts of a unit in
  workgroup memory. `vx_gemm` at six rows runs compute-bound on its 64-row
  tile at several times the one-row GEMV's time for the same bytes, and a
  scalar-word GEMV at six rows runs at half the one-row rate, which is why the
  flow sweeps the six CFG rows per weight `vec4`; a unit of four plain rows
  (halving the input loads per weight byte) is a measured loss at six rows,
  so a plain unit is two rows and only the gate/up unit holds four. The
  epilogue is
  the fusion point: `VG_OUT_F32` writes the f32 qkv row the rope reads,
  `VG_ACCUM` rounds the product to bf16 and adds it into the residual (the
  reference's two roundings), and `VG_GATE_UP_SILU` owns the gate and up rows
  of two columns and writes `silu(gate) * up`, so a layer has no silu pass and
  no residual-add pass. At M=1 the prologue is the fusion point too:
  `VG_NORM_PROLOGUE` reduces the row's sum of squares in the workgroup and
  normalizes the input on the fly with `nv_norm4` (the arithmetic of
  `rmsnorm_bf16`), so the backbone layer is qkv, rope, the two decode
  attention passes, o accumulated into the residual, gate/up with silu, and
  down accumulated into the residual; at M=6 the prologue would re-normalize
  six rows per workgroup, so the flow keeps the shared norm passes. An
  ungranted device gets the same kernel with eight 32-lane virtual warps
  summing in workgroup memory. Read the live counts off `step_pass_count` and
  `flow_pass_count`; the suite prints both.
- **The flow head has its own weight format.** `NV_VOXTRAL_TTS_FLOW_QUANT`
  (`VoxtralTtsWgpu::flow_quant_from_env`, bf16 when unset) selects the flow
  layers' format apart from the backbone's: `q8_0` quantizes qkv, o, gate/up
  and down as ggml does (blocks of 32 along K, an f16 absmax/127 scale, int8
  codes; `q8_rows`) and `vt_gemv` is generated with the int8 arm, where a lane
  reads sixteen codes per `vec4`, two input `vec4`s per weight `vec4`, and
  scales each block's f32 dot before accumulating. The flow never prefills, so
  the format needs no GEMM; the backbone keeps bf16 because its prefill runs
  through the shared `vx_gemm`, which has no int8 tile loader. The arm is an
  opt-in
  (`THE_Q8_0_FLOW_HEAD_STAYS_AN_OPT_IN_BECAUSE_THE_ES_FIXTURE_LEAVES_ITS_LAST_EULER_STEP_OUTSIDE_THE_FLOW_BAND`):
  it scores inside the paired noise of bf16 on the corpus instrument below and
  holds every band on the `en` fixture, but on `es` the unconditional velocity
  of the last Euler step lands just outside the flow band, which is the
  knife edge 7.1 describes, so the default flow rows stay bf16.
- **A change to this path reruns the corpus instrument.** Every kernel above
  reassociates the f32 sums against the previous kernel, so the frame-loop
  bands are necessary and not sufficient: the suite covering corpus word
  errors (`wgpu_corpus_word_errors_reproduce_the_cuda_eager_instrument`,
  `NV_VOXTRAL_TTS_CORPUS`, `NV_VOXTRAL_TTS_SEED`) synthesizes the 73
  LibriSpeech rows with `SeededNoise` at the CUDA instrument's seed and
  voice, decodes through the codec twin, transcribes with the STT twin,
  writes the per-row record to `/tmp/voxtral-tts-corpus-wgpu-<label>.jsonl`
  (`NV_VOXTRAL_TTS_CORPUS_LABEL`) and, given `NV_VOXTRAL_TTS_CORPUS_PAIR`,
  reports the paired per-row difference against an earlier record with its
  standard error; the aggregate is read against the CUDA eager bf16 arm's
  count at the same seed (`corpus_word_errors_per_configuration` in
  `tests/voxtral_tts.rs`). A kernel ships when the frame-loop suite is green
  and the paired difference sits inside the seed-to-seed spread; its commit
  names both.
- **Euler and FSQ round on the device exactly as the host does**
  (`EULER_AND_FSQ_RUN_ON_THE_DEVICE_WITH_ONE_BF16_ROUNDING_PER_OPERATION`):
  `vt_euler` rounds `alpha * v_cond`, `(1 - alpha) * v_uncond`, their sum, the
  product with `dt` and the sum with `x_t` to bf16 in that order, then the
  FSQ's `(c + 1)`, `* 0.5`, `* levels` before `round` (ties to even), which is
  the `half::bf16` arithmetic of `voxtral_tts.rs` step for step; the lib suite
  asserts the trajectory and the codes bitwise against that host arithmetic.
  The semantic head writes bf16 logits and the argmax takes the lowest index
  among equal values over ids `1..8194`, the reference's first-index rule
  (`THE_SEMANTIC_ARGMAX_READS_BF16_LOGITS_SO_TIES_BREAK_AS_THE_REFERENCE_BREAKS_THEM`);
  it writes only `ids[0]`, and the FSQ pass copies the id into the frame, so
  the frame buffer is intact when the host reads it after the next step was
  already submitted.
- **Weights are bf16 by default, and nvfp4 is an opt-in the gate rejects**
  (`THE_TTS_TWIN_SERVES_BF16_BECAUSE_NVFP4_FAILS_THE_FRAME_LOOP_GATE`).
  `VoxtralTtsWgpu::quant_from_env` reads `NV_VOXTRAL_QUANT` with bf16 as the
  unset value, unlike the STT twin whose unset value is nvfp4, and
  `NV_VOXTRAL_TTS_FLOW_QUANT=nvfp4` selects the flow head's arm apart. `nvfp4`
  quantizes the backbone and flow layers' qkv, o, gate/up and down (the same
  tensors `DecoderLinearBuilder` quantizes on CUDA, with the same per-tensor
  global and block-16 scales) and keeps the embeddings, the semantic head,
  `llm_projection`, `input_projection`, `time_projection` and the velocity
  head bf16; the step is then the STT twin's fused layer (`vx_norm_rows`,
  `vx_gemv_nv4` with the residual accumulated in the GEMV, permuted attention
  and silu outputs), the flow the same GEMV at M=6 with `vt_flow_attn` writing
  the permuted layout, and the prefill dequantizes in the GEMM tile loader.
  On both fixtures that path leaves teacher-forced hidden states outside the
  relative band, flips semantic ids at margins far above two bf16 ulps and
  moves acoustic codes by more than one level, and one free run's transcript
  changes casing: the TTS frame loop is a knife edge the STT corpus instrument
  never sees, so the nvfp4 default does not carry over from the STT twin.
- **State.** The KV cache holds `KV_CAPACITY_ROWS` positions per layer; the
  device position, the 37 ids, the frame, the Euler state, the heads' outputs
  and the flow activations are allocated once. Voice tensors upload on first
  use and stay cached per preset.

`NV_WGPU_PROFILE=1` routes the prefill, flow and step lists through the
profiler and `synthesize` prints `dispatch::profile::table` per call, keyed by
`entry:linear` as in the STT twin (the per-step gate in that table is
informational here: a call's dispatch count is the prefill plus frames times
the step and flow lists); `step_pass_count` and `flow_pass_count` are the live
counts, and the suite prints both with the per-stage milliseconds (`StageMs`,
measured with a device poll per stage under `trace`, where the free run's
step is submitted apart from the flow so the split is honest) and the
best-of-N end-to-end time of an untraced free run, which submits the flow and
the next step together.

Gates: the lib suite covering each new pass against a host oracle (`--lib
voxtral_tts_wgpu`: Euler/FSQ bitwise against `half::bf16`, the masked argmax
tie rule and position increment, the three-token attention, the embedding
sum, and `vt_gemv` in every epilogue and both subgroup arms against the host
product), and the real-weight suite `tests/voxtral_tts_wgpu.rs`
(`NV_VOXTRAL_TTS_TEST=1 NV_SERVE_BACKEND=wgpu`), which mirrors
`tests/voxtral_tts.rs` assertion for assertion over both fixtures: prompt ids
and timesteps equal, teacher-forced hidden states within the relative band,
the frame-0 velocities and trajectory per step, the fed-back embedding,
semantic flips only at sub-two-ulp ties with the oracle's id second, acoustic
codes never worse than one level off and the off-by-one fraction under the
bound, a free run reaching `[END_AUDIO]` deterministically, and the closed
loop through `VoxtralTtsCodecWgpu` and `VoxtralStt` (the wgpu STT twin under
`NV_SERVE_BACKEND=wgpu`) transcribing the fixture text verbatim for the free
run and for the oracle's own frames. The loaded line names the adapter
(`WgpuContext::summary`), so a log states which backend and subgroup grant the
numbers below it belong to.

On Apple silicon the twin runs on wgpu's Metal backend from the `no-models`
dev shell (`NVK_SHELL=.#no-models NVK_FEATURES=wgpu` through `nvk.sh`, with
`LIBRARY_PATH` at the SDK's `usr/lib` so build scripts link libiconv, the
`speaches-test` wrapper's rule; `ccache` is a Linux-only shell package because
its elfutils dependency has no darwin platform). Every band and the closed loop
hold there with subgroups granted, through the codec twin and the wgpu STT
twin, with the same pass counts per frame as on Vulkan. The frame there is the
bf16 GEMVs at a fraction of the Metal stream rate, the large ones nearer it than
the small ones, and the prompt prefill runs the scalar `vx_gemm` because no
cooperative-matrix configuration matches the GEMM tile (`gemm_tile=None` in
the summary); the per-dispatch drain is a small share of the frame. The candle
eager path (`voxtral_tts.rs`) also loads on a Metal device and holds the
teacher-forced bands, but runs an order of magnitude behind the twin per frame
and has no closed loop there: `tests/voxtral_tts.rs` pairs it with the candle
codec, which refuses Metal, so the twin is the Metal arm and the eager path is
not a Metal route.

### 5.9 The Voxtral TTS twins in a browser

`nv-ocr-web`'s `voxtral_tts_web` carries both twins to wasm32 behind the
crate's `browser` feature ([6.11](06.11-ocr-browser.md) for the crate, its
build and its harness): the same `VoxtralTtsCodecWgpu` and `VoxtralTtsWgpu`
the Vulkan path runs, with no kernel of their own. What the browser arm adds
is wiring, and each piece is a rule the native twins now follow too:

- **Every readback has a pumped arm.** `decode_arm`, `decode_frames_arm`,
  `synthesize_arm` and `frame_from_hidden_arm` take a `ReadbackArm`; the
  native entry points (`decode`, `decode_frames`, `synthesize`,
  `frame_from_hidden`) are `drive_blocking` over the same bodies. The web
  backend's device poll is a no-op, so a blocking readback there never
  returns; the browser awaits the pumped arm and the pump parks on the map
  callback alone.
- **A pass owns the buffers it binds**
  (`A_PASS_HOLDS_ITS_BOUND_BUFFERS_BECAUSE_THE_WEBGPU_BACKEND_DESTROYS_A_BUFFER_WHEN_ITS_LAST_HANDLE_DROPS`).
  The param uniforms and scratch the pass builders create would otherwise be
  destroyed the moment the builder returns, and Chromium rejects the whole
  submit; natively the bind group kept them alive and the leak of the rule
  was invisible.
- **The checkpoint is a few virtual shards read by Range**
  (`THE_CHECKPOINT_IS_A_FEW_VIRTUAL_EXTERN_SHARDS_READ_BY_RANGE_SO_NEITHER_HEAP_HOLDS_THE_8_GB_FILE`).
  `nv-weights` addresses a shard in `usize`, so the 8 GB consolidated file is
  presented as five extern shards whose rebuilt headers each stay under
  4 GiB (codec, heads, embedding, two halves of the backbone); a tensor
  crosses wasm memory once, at its own size, on its way to the device, and
  the wasm heap's peak is a few tensor-sized transients, never the model.
- **Three tiers, one model.** The codec tier is the codec twin alone
  (`audio_tokenizer.*`). The heads tier is `from_parts` with
  `with_backbone` false
  (`HEADS_ONLY_LOADS_NO_BACKBONE_LAYER_AND_NO_TEXT_EMBEDDING_SO_A_BROWSER_CAN_RUN_THE_FLOW_FROM_SERVED_HIDDEN_STATES`):
  the final norm, both heads, the codebook embedding and the flow head, and
  `frame_from_hidden` as its frame contract -- a server-side backbone ships
  the normed hidden state of each frame (one row of the model width in
  bf16) and the browser returns the 37 codes and feeds the codec. The full
  tier loads the 26 layers and the text embedding and runs `synthesize`; it
  needs an adapter whose storage binding holds the embedding (`Kit::lin`
  refuses otherwise) and a 64-bit host with room for the GPU process's
  copy, and it is the tier a weight-streaming or quantized backbone would
  shrink. Voices reach the browser model through `stage_voice` (the harness
  parses the preset's `.pt` in wasm); `synthesize` refuses a heads-only model.
- **Subgroups are optional.** Chromium grants `subgroups` and the module
  choke point injects the directive, so the subgroup kernels run as on
  Vulkan with the runtime width unprobed (the STT width ladder treats a
  browser as width-unknown; the TTS kernels only need lanes of four and
  thirty-two). An ungranted device selects the workgroup-memory twins
  (`UNGRANTED_SUBGROUPS_SELECT_WORKGROUP_MEMORY_TWINS_OF_THE_TWO_ATTENTION_REDUCTIONS`):
  `vx_attn_decode1_nosg` over eight 32-lane virtual warps and the prefill
  `_nosg` twins in the butterfly's own association, which the lib suite holds
  bitwise against the subgroup prefill; the native proof of the whole twin on
  that path is the frame-loop suite under `NV_WGPU_SUBGROUPS_UNGRANTED=1
  NV_VOXTRAL_QUANT=bf16` (bf16 keeps the closed loop's STT twin off nvfp4,
  whose GEMV needs subgroups). Both twins stay under the default of eight
  storage buffers per stage; the GEMM tiles and the prefill attention need
  more than the 16 KiB default of workgroup storage, which the engine takes
  from the adapter's own offer.

Gates: the suite covering the browser surface natively
(`nv-ocr-web/tests/voxtral_tts_web_gate.rs`, `NV_VOXTRAL_TTS_WEB_TEST=1
NV_SERVE_BACKEND=wgpu`) opens the file on disk as one extern shard and drives
the pumped arm: both fixtures decode within the codec twin's band of the
clamped reference, the per-frame stream matches the full decode, and the
heads tier reproduces the oracle's frames 0, 1, 2 and last from the recorded
hidden states with the semantic logits and flow trajectory in band. The
browser gate is the harness's `tts` arm ([6.11](06.11-ocr-browser.md)), whose
`CODEC-DECODES+HEADS-MATCH` verdict on Chromium's own WebGPU (Dawn and Tint on
the NVIDIA adapter under Xvfb) holds the same bounds, and whose `full` tier
holds the teacher-forced run over the oracle's frames to the frame-loop
suite's acoustic bound (`FULL-RUNS-TEACHER-FORCED-IN-BAND`) while reporting
the free run (frame count, agreement with the oracle's frames, the per-frame
cost) without claiming parity: a free run's semantic argmax is the knife edge
7.1 describes, and Tint's codegen is a third accumulation order.

## 6. Decoder residency

`gemma4_wgpu.rs`, `qwen3_5_moe_wgpu.rs` and `gemma4_e4b_wgpu.rs` are native
`GpuTensor`-resident decoders: weights uploaded once, a list of
`wgpu::ComputePipeline` passes built at construction, that list replayed per
token inside one command encoder, four bytes (`token_out`) read back per step.
`candle_nn`, `candle_core::Device` and `Device::` have zero occurrences in all
three; the only `candle_core` references are host weight-staging helpers on
`Device::Cpu`. That is unpinned -- the suite that asserted it went with the
cull of source-text assertions, so re-grep before quoting it.

Everything that is not one of those three is still a candle module and would
run on CPU under a wgpu-only build: `nv_models::gemma4::Gemma4`,
`qwen3_5_moe::Qwen3Moe`, the vision and audio towers, the Qwen3 embedding model
and both spec-decode verifiers. `nv-kernels`' generic API is host-slice-only
(`dispatch.rs` exposes `storage_from_slice` / `storage_zeroed` / `uniform_from` /
`run` / `read_back`) and `nv-layers`/`nv-models` still hand raw `CUdeviceptr`s to
`nv_kernels::cuda::*`; the three resident decoders route around that layer
entirely. A general-purpose device-resident tensor is worth building and is not
what blocks serving.

`ModelClass::required_kernels()` demands `marlin_gemm_w4a16` for the dense/E4B
set even though the wgpu E4B decoder never calls it. `wgpu_required_kernels()`
routes around it for the serving path; every other consumer of the registry gets
a wrong answer for that class. `kind_supports` itself is honest about the grouped
MoE GEMM -- `MoeGroupedGemmNvfp4` counts as present on wgpu, and
`MarlinGemmW4a16` is the only kernel it reports missing there.

## 7. Where the wgpu time goes

Speed tables are in the basis-tuple quoting rule (numbers live in the private run ledger). The
structural findings are here.

### 7.1 Three regimes, not one bottleneck

Anyone aiming a round at "the bottleneck" will not find one. The token's cost
is flat across three classes -- nvfp4-gemv (below DRAM peak, headroom remains),
the tiny-kernel glue (moves almost no bytes), and the bf16 qkv+o / lm_head classes
(near or at DRAM peak, no code fix available) -- where before the GEMV rewrite it
was a single peak dominated by the NVFP4 GEMV. Per-class shares and rates:
the private run ledger.

> The wgpu path sits well below DRAM peak not because the memory system, the
> driver or the dispatch model is the limit -- bf16 kernels on this exact stack
> run near peak, matching CUDA's whole serving path -- but because a large share
> of the token is spent in an NVFP4 GEMV shader running below peak, and a further
> share in a swarm of kernels that move no bytes at all.

Caveat: the stage-profile reconstruction executes more dispatches per token than
the real fused model, so its "other" bucket is over-counted; treat the
tiny-kernel bucket as a range bounded below by the dispatch-count rescale, and do
not quote a point value.

### 7.2 Bytes are the currency, not launches

Measured repeatedly in both directions (numbers: the private run ledger): fusion
removed a large share of all dispatches (exactly 9 x 60 layers' worth) and bought
only a small share of the token; the raw launch floor is a small share of the
token at the fused dispatch count; and most byte-cutting experiments were
neutral-to-negative. **A byte cut converts to a time cut at a fraction well under
one, and only when the format it replaces was actually DRAM-saturated** --
halving the bytes of the near-peak qkv+o bf16 class bought a real win while int8
on the already-saturated lm_head class cost time.

There are two launch floors and neither corrects the other. GPU timestamp
queries bookending each `ComputePass` inside `submit_profiled_chunk`
(`nv-kernels/src/wgpu_backend/dispatch.rs`) give an on-device execution window;
a trivial kernel dispatched N times into one command buffer with a single final
host sync gives a linear fit whose slope is the host-observed marginal cost, a
multiple of the timestamp floor because it includes compute-pass-boundary driver
overhead the timestamp window does not capture. A per-op host sync folds hundreds
of microseconds into a per-dispatch number; never time dispatches that way.

Two items left open rather than smoothed over: **`NV_WGPU_O_NVFP4=1` needs a
retest** -- the `o_proj -> nvfp4` verdict was measured against an NVFP4 kernel
that has since nearly doubled its streaming rate and the arithmetic says it
should flip, so do not quote "don't take it" as current (**DERIVED, NOT
MEASURED**); and int8-lm_head VRAM is inconsistent between harnesses, one
reading above the bf16 baseline and one below, NOT EXPLAINED -- probably one
path keeping both a bf16 and an int8 copy resident.

### 7.3 Conversion dispatches

Two audits returned negative results worth keeping. Storage width: the feared
"1 bf16 per u32 weight tensor" pattern does not exist on the decode path
(every weight upload goes through `pack_pairs` or `bytes_to_words`), and `vec4`
loads buy almost nothing over scalar `u32` on a pure stream, so a GEMV's deficit
is kernel structure, not load width. Dtype conversion: swapping the whole
`rmsnorm -> gemv -> pack -> gelu` bf16 interchange for an f32 one moves the chain
by noise, and by zero in the fused single-compute-pass regime -- **the bf16
round-trips at stage boundaries cost nothing measurable**, and taking that swap
breaks parity gates for no payoff.

What conversions do cost is dispatches: `pack_lo16` (the `g4w-pack16` pipeline
over `nv-kernels/wgsl/g4w_glue.wgsl`, the only pack entry point there is)
7/layer x 60 + 2 = 422, and `cast_bf16_to_f32` 1/layer = 60 -- a large
share of all passes, every one launch-bound (a `pack16` over 131072 elems costs
the same as over 2048). Split one-pass-per-dispatch they cost a multiple of their
fused cost, **worth knowing before anyone splits the decode pass for timestamps
or debugging.**

Three of them are removable bit-identically, because each relocates existing
bit patterns rather than touching a rounding site: have the gemv/flash producers
store packed (`ROWS_PER_GROUP=8` already co-schedules rows 2r and 2r+1 in one
workgroup, so lane 0 can emit the packed word); have `quantize_row_nvfp4_bf16`
own blocks 4t..4t+3 and OR four scale bytes into one u32 (no write race); and add
a `fd_q_bf16` load path to flash stage 1, since bf16->f32 widening is exact. The
exact-rounding emulations that make that guarantee meaningful are `rms_div_rn`,
`kv_div_rn`, `q_div_small`/`q_finish`, `fd_recip`/`fd_round`, and the manual RNE
in `bf16_encode` and `kv_encode_e4m3`. **The logits bf16 round-trip is not in
that class** -- removing it drops the f32->bf16 rounding of every logit before
softcap and argmax, so every bit-exact logit/argmax gate must be re-baselined;
keep it last. The activation NVFP4 quantize is not removable at all: its fp4
rounding is exactly what CUDA's tensor-core path does, so it is parity-defining.

### 7.4 Ceiling, and the kill list

From the published record (no GPU work by us; numbers: the private run ledger): mature
native Vulkan on NVIDIA reaches decode parity-class rates against CUDA with no
known hard floor materially above parity; prefill keeps a real CUDA advantage
even with coopmat2; and cooperative matrix is prefill-only (tg128 essentially
unchanged -- do not retrofit it into decode GEMV). **A realistic ceiling for this
codebase is modestly behind CUDA on decode**, with exact-gate constraints rather
than API limits deciding the last part.

Killed, recorded so it is not repeated: shape-gated NVFP4 variant selection.
`select_variant_for_shape` (`gemv_nvfp4.rs`) has exactly one caller in the tree,
a host helper used only by tests, while the model calls the shape-blind
`select_variant` once. Wiring it is DERIVED at a percent-class win, an order
of magnitude below the shader-efficiency problem, and NOT MEASURED end to end
because no code path can produce it. The same lane's parameterised `SgwConfig`
shader is likewise unreachable from `GemvVariant` (still just `Tree | Sg`).

## 8. Would a different quantized checkpoint help?

Switching checkpoints is a simplicity lever, not a bandwidth lever. At
group-of-32 4-bit every serious candidate moves the same ~4.5 bits/element as
NVFP4 (4 + 8/16) except MXFP4 (4.25). Stay on NVFP4 for the headline number (it
is the CUDA-parity reference). If a switch is wanted, take
`google/gemma-4-31B-it-qat-w4a16-ct`: `weight_packed I32 [out, in/8]` plus
plain row-major `weight_scale BF16 [out, in/32]` -- no swizzle, no global scale,
no FP8 -- unpacking to exactly `w4a16_q` in the shader with bf16 scales read
natively by `gemv_w4a16.wgsl` (`wgpu_gemv_w4a16` 6/6, `max_ulp=0` across group
sizes 8..3072). Same bytes/token as NVFP4, so it doubles as the clean A/B
separating dequant-layout cost from dispatch overhead at equal bandwidth.
`amd/gemma-4-31B-it-MXFP4` is the only candidate that strictly reduces bytes
moved, but it needs an MXFP4 GEMV lane and an eval pass first (the kernel work
needs no download -- `openai/gpt-oss-20b` is the fleet's pinned mxfp4
checkpoint). Skip
AWQ-4bit (asymmetric zero-points `gemv_w4a16.wgsl` lacks), Intel AutoRound (GPTQ
column-interleaved qweight needs repack) and GGUF (no container loader in-repo).

## 9. Ranked remaining work

The one durable Tier-1 asset is not a gate at all: the entire host-side
generation stack in `chat_engine.rs` is already ungated and backend-neutral
(sampling params, the whole `ChatSampler`, `stream_text_delta`, `StreamEmitter`,
`IncrementalDetok`, `build_logprob_entry`, `build_guided`, `kv_window`,
`ChatRegistry`) because it consumes `&[f32]` logits and nothing else. All three
wgpu decoders expose exactly that via `decode_step_logits()`.

Two registry items stay open and are cheap: `ModelClass::required_kernels()`
still demands `MarlinGemmW4a16` for the dense/E4B set the wgpu decoder never
calls (§6), and ~12 pure-CPU helpers plus 13 tests in `chat_engine.rs` sit behind
`#[cfg(feature = "cuda")]` while touching no GPU API (`detect_family`,
`resolve_qwen3_5_moe_eos_ids`, `parse_bos_id`, the three `render_*_prompt`s,
`det_hash_f32`, `effective_max_new`, the chat semaphore), so those 13 tests have
never executed in a non-CUDA run.

The one Tier-2 item worth naming as a rule rather than a wish: **an M>1 wgpu
forward unlocks batching, paged KV and fast prefill simultaneously**, and it is
the only thing standing between wgpu and a server rather than a demo. Everything
else in that class (an embedding-row entry point beside the existing
`decode_step` / `decode_step_logits` so multimodal rows can enter, splicing LoRA deltas into
resident pass lists, the NVFP4 GEMV x-side decode) is integration work whose
kernels already exist -- the x-side decode is blocked by ownership, not
technique: the kernel bodies live in `gemma4_wgpu.rs` / `qwen3_5_moe_wgpu.rs`
rather than `nv-kernels`.

### Do not pursue parity, and say so out loud

Beyond the two already stated as design rules (no WGSL Marlin and no WGSL
CUTLASS-class batched 4-bit GEMM, §5.3 item 2; no WGSL Whisper, §5.3 item 4):

CUDA-graph-captured speculative decoding (Eagle3 / DFlash) serving. The
design is built on cudarc stream capture plus graphed verify; wgpu's pre-recorded
command buffers cover the replay half but not the dynamic-shape tree-verify
half. The WGSL verify kernels existing (§2.1) does not reopen it -- the kernels
were never the hard half. Consequence: wgpu decode stays at ~1x where CUDA gets
~2x at bs=1, except on Gemma4E4b where the suffix-automaton / learned-drafter
route runs (§5). Given wgpu's baseline is already slower per token, this is the
worst effort-to-benefit ratio in this document.

The consequences of the Marlin and grouped-GEMM verdicts, stated once: batched
W4A16 prefill on wgpu stays materially slower than CUDA (bs=1 E4B decode is
unaffected -- the CUDA path itself falls back to GEMV under
`NV_E4B_FORCE_GEMV`), and MoE models decode on wgpu at a throughput gap that
widens with batch size. Accept both. The gap worth closing on Laguna is not a
kernel port but that its suites need `laguna-wip` on the lane (§5.5).


## 10. Reproduction

`08-build-and-testing.md` owns `nvk.sh` and lane discipline; what is
wgpu-specific is the loader and the skip polarity.

```sh
NVK_LANE=<lane> NVK_PKG=nv-kernels NVK_FEATURES=wgpu \
  rust/scripts/nvk.sh test -- --test-threads=1

# serving: build --no-run, then run the binary directly under a VERIFIED 64-BIT loader
export LD_LIBRARY_PATH=<64-bit vulkan-loader>/lib:/run/opengl-driver/lib:$LD_LIBRARY_PATH
export VK_ICD_FILENAMES=/run/opengl-driver/share/vulkan/icd.d/nvidia_icd.json
export TMPDIR=$HOME/.cache/cargo-tmp
export NV_WGPU_SERVE_TEST=1 NV_WGPU_SERVE_MAXSEQ=1024
export NV_WGPU_SERVE_DIR=<checkpoint snapshot dir>
# real-weight E4B decodes are 20-25 GB: NV_E4B_WGPU_TEST=1
```

Name a suite from the tree and check it is still there first -- the corpus is
culled on the rule that a file which cannot go red on a wrong number gets
deleted, so a recipe quoting a suite by name outlives the suite.

The whole workspace under the wgpu feature is one command,
`NVK_SWEEP_BACKEND=wgpu rust/scripts/sweep-workspace.sh` (`05.12` §6.2): the
crates that declare the feature get it, the rest run featureless, and the
wgpu-only `nv-models` suites that refuse to skip get their synthetic gates
(`NV_G4BD`, `NV_G4D_CHUNKED_PREFILL`, `NV_G4PFW`) from the script. A suite that
needs a checkpoint the box does not hold stays red by design rather than
skipping: `http_wgpu_bos_guard` wants a Qwen snapshot under `NV_TEMPLATE_HUB` or
`HF_HUB_CACHE`, and the Qwen3.6 hub is the `qwen36` devshell's `HF_HUB_CACHE`
(`nix build .#devShells.<system>.qwen36` realizes it).

The browser side of the same stack is gated in 6.11: `Q38WEB_DISPLAY=xvfb
rust/scripts/q38-browser-parity.sh` validates every browser module through
Chromium's own Dawn and Tint on the discrete adapter.

Two rules a hang taught. A device poll waits at most
`WGPU_POLL_TIMEOUT_SO_A_HUNG_DISPATCH_IS_AN_ERROR_NOT_A_WEDGED_THREAD` (five
minutes) and then fails the readback naming the cause; a submission that has
not signalled by then is a hung dispatch, never a slow one. And a kernel that
takes a loop bound from a storage-read position clamps it to the capacity its
params carry (`q3w_attn_decode`: `min(pos + 1, max_seq)`): a corrupt or
random position is a wrong answer, not hours of GPU time -- the poison-parity
harness hands every storage buffer random words and sat 52 minutes on that
kernel before the clamp.

Two traps, both of which have produced false greens here. A suite gated on a
feature the lane lacks (`#![cfg(feature = "wgpu")]` under nv-models' default
`cuda`) compiles to nothing and prints `0 passed; 0 ignored` in `0.00s` -- that is a
SKIP, and a genuine `#[ignore]` skip shows a non-zero ignored count. And a
wgpu suite with no Vulkan loader prints `1 passed` in `0.00s` having executed
zero GPU work: most `vulkan-loader` store paths on this box are 32-bit, and a
32-bit loader fails silently with no `VK_LOADER_DEBUG` output at all. Every real
wgpu run prints an adapter banner naming the device, driver, `shader_f16`,
subgroup range and `coop_mat` config; **a wgpu run without that banner is a skip,
whatever the result line says.**

## 11. AMD / Strix Halo (RADV) -- the second adapter

Rules from the strix lane (AMD Strix Halo APU, Mesa RADV, no CUDA on the box) --
the first partial answer to §2.2 finding 3. Two scope guards: this is
kernel-suite state, not a parity verdict, and the real-weight result is
decode, not serving.

- RADV enumerates the APU without root, and **host RAM headroom is a hard
  precondition**: the APU has no dedicated VRAM, so GPU allocations come out of
  the same pool as everything else. A ~15 GiB need against ~6 GiB `MemAvailable`
  produced a global OOM with database processes as eligible victims. Check
  headroom before any load.
- AMD is safe-by-fallback -- a perf cost, not a correctness one. Kernel
  suites run 568 passed / 20 failed / 1 SIGSEGV; all 20 failures share one cause,
  subgroup width 64 where the code assumed 32 (compare §10's NVIDIA banner
  `subgroup=true(32..32)`). The shipped decode path guards on subgroup width and
  falls back to the Tree variant, and `gemv_nvfp4_v2::subgroup32_ok` guards every
  v2 model call site.
- The in-shader NVFP4 dequant path is vendor-neutral at kernel level -- eight
  NVFP4/quant suites pass on RADV including the exact-dequant and
  bit-exact-decode cases -- but no NVFP4 checkpoint has been decoded on AMD,
  and host-RAM headroom is why.
- E4B bf16 real-weight decode works on AMD at a bandwidth-plausible rate.
  That is the engine-level decode path; **no HTTP request has been served from
  AMD**, so it is not a SERVES claim.
- The Mesa cooperative-matrix compiler SIGSEGVs on valid input. That is the
  1 SIGSEGV -- a driver bug, upstream-worthy, not a defect in these shaders.
- The exp2/sampler tripwire cannot be tripped there. The CUDA-vs-WGSL
  comparison that would catch it needs CUDA, which the box does not have, so it
  must become a token-divergence watch: compare AMD-decoded token streams
  against recorded NVIDIA/CUDA streams on identical prompts.

Resume rules for that lane: run `--no-fail-fast` so the 20 known subgroup-width
failures do not mask anything new; pin the ICD to RADV rather than relying on
loader enumeration order; never trust green without the adapter banner (§10 --
it bites harder here because a silently-missing adapter and a wrong-adapter pick
are both live on an APU box); and **never system-switch that host as a side
effect of GPU work** -- its running system is far behind the tree, so a rebuild
deploys the whole fleet delta to a box serving live services, and a Vulkan ICD is
pure userspace and needs no switch.
