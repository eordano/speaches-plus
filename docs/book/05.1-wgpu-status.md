# wgpu / Vulkan -- port status, kernel parity, serving, and performance

Canonical wgpu document: *what works, how correct it is, and what remains*. Speed
numbers live in [`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md), the single place
both backends are compared. Companions:
[`05.2-kernel-parity-matrix.md`](05.2-kernel-parity-matrix.md) (what gates each
kernel -- authoritative where it disagrees with §2 here),
[`05.6-macos-port-status.md`](05.6-macos-port-status.md) (the Metal adapter --
everything below is Vulkan-only), [`04.1-fp8.md`](04.1-fp8.md),
[`08.1-quality-harness.md`](08.1-quality-harness.md),
[`05.5-rocm-port-status.md`](05.5-rocm-port-status.md),
[`01.4-STATUS.md`](01.4-STATUS.md).

**Every number below is Vulkan on the CUDA box and its raw logs are not in the
repo**; nothing here has a live gate except where a suite is named. §11 is the
one section measured elsewhere -- an AMD Strix Halo box with no CUDA in it.

Three claim strengths are used throughout and are not interchangeable:
**COMPILES** (`cargo check` succeeds), **RUNS-SYNTHETIC** (a test drives it on
tiny/random shapes), **SERVES** (a real HTTP request, real weights, coherent
output). SERVES is reached from the HTTP binary: `NV_SERVE_BACKEND=wgpu` plus
`NV_WGPU_CHAT_MODEL_DIRS=<snapshot>` loads the decoder and completes a chat
request with `sampling="in-shader-argmax"`.

## 1. Verdict

| Model | wgpu decoder | decodes real weights | serves a real chat request | output |
|---|---|---|---|---|
| `google/gemma-4-E4B-it` (bf16) | `nv-models::gemma4_e4b_wgpu` | yes (42 layers) | yes | coherent, correct, ends its turn |
| `nvidia/Gemma-4-31B-IT-NVFP4` | `nv-models::gemma4_wgpu` | yes | yes | coherent, correct, ends its turn |
| `RedHatAI/Qwen3.6-35B-A3B-NVFP4` | `nv-models::qwen3_5_moe_wgpu` | yes | yes | coherent, correct; reasoning trace split into `reasoning_content` (§4.4 item 2) |

**Every wgpu decoder graphs decode identically: one `queue.submit` per token over
a prebuilt pass list, with in-shader two-stage argmax and a 4-byte token
readback.** This holds for all seven -- `gemma4_wgpu`, `gemma4_e4b_wgpu`,
`gemma4_moe_wgpu`, `qwen3_5_moe_wgpu`, `qwen3_5_dense_wgpu`, `gpt_oss_wgpu`,
`laguna_wgpu` -- and chunked prefill (one submit per M-row chunk, default
M=8..16) is on by default in every one of them. The per-token profiling arms
(`submit_profiled_slices`, `NV_WGPU_PROFILE=1`) are the only paths that submit
more than once per token, and they are off by default.

**The graph-dispatch layer is fully shared; the decode *kernels* are not.** Only
`wk::residual_scale` (7/7), `wk::rmsnorm` and `wk::rmsnorm_residual` (6/7) are
broadly shared. Five trivial glue ops -- argmax stage1/2, the bf16-GEMV core,
nvfp4 `quant_rows`, gather-embed, contiguous kv-write -- are reimplemented under
a per-model prefix (`q3w_`/`g4w_`/`g4m_`/`gow_`/`lgw_`/`e4b_`) 5-7 times with
byte-for-byte identical cores, though shared versions exist in
`graph_decode.wgsl` and `wk::gemv_bf16`; promoting them to `wk::` is pure
subtraction with no numeric or perf change. What is *justifiably* per-model:
weight-format GEMVs, the fused `*_attn_norm_rope` kernels (qk-norm placement,
softcap, GQA grouping, gpt-oss attention sinks), and `e4b`'s
LoRA/verify/matformer kernels.

**4-bit is the served default wherever the checkpoint ships it, but the default
weight format is per-decoder.** `qwen3_5_moe_wgpu`, `qwen3_5_dense_wgpu` and
`laguna_wgpu` serve nvfp4 (v2 subgroup GEMV default-on where a 32-wide subgroup
exists); `gemma4_moe_wgpu` serves w4/group-32 experts with a bf16 dense trunk;
`gpt_oss_wgpu` serves mxfp4 with dequant-in-shader. Two are NOT 4-bit by default:
`gemma4_wgpu` requantizes its nvfp4 checkpoint to int8/group-128 under `W8_FFN`
(`NV_G4_WGPU_W8_FFN=off` restores pure nvfp4), and `gemma4_e4b_wgpu`'s default
checkpoint is bf16. The nvfp4-v2 shape router (`gemv_nvfp4_v2::select_pk`) covers
both served 31B FFN shapes with bit-exact goldens, so the 31B int8 default is a
deliberate quality choice, not a missing 4-bit kernel.

**Only one dispatch count in this chapter is gated: the dense graph's.**
`gemma4_dense_host_shape_real_weights` (`NV_G4D_HOST_SHAPE=1` plus
`NV_GEMMA4_DIR`) asserts **548 passes/token** for `Gemma-4-31B-IT-NVFP4`
(2 prologue + 10 for layer 0 + 59 x 9 + 5 head, with the gelu fold on) and
asserts both fold arms, so a fusion change cannot move it silently.
`pass_count()` is the same quantity the server logs as `passes_per_token`.
**Every other pass count here and in `05.6-macos-port-status.md` is ungated prose
and rots on the next fusion** -- the dense count alone has run
1268 -> 728 -> 608 -> 548, so any 728 or 608 you find is history. Read a count
off the boot line or the census gate.

Against CUDA on identical prompts, template and weights: **three of five prompts
byte-identical**, the other two equivalent in quality (§4.3).

**There is no CUDA-vs-WGSL parity suite in the tree, by decision.** All 25
`parity_*` suites were deleted on the rule that *two implementations agreeing is
not an oracle* -- the receipt being the round where the wgpu w4a16 family and its
own oracle carried the same group-16 scale-indexing bug, so no amount of
agreement could have caught it. They were also gated on
`NV_KERNELS_PARITY_REQUIRE=1` and returned early otherwise, and fed synthetic LCG
data at magnitudes no checkpoint produces. **Every "bit-exact against CUDA" claim
in §2.2 therefore has no live gate**; the four surviving `parity_*` files
(`parity_gemv_bf16_i8`, `parity_gdn`, `parity_kv_fp8_paged`,
`parity_verify_fused` -- the last CUDA-vs-CPU-oracle, not WGSL) are what remains.
The standing rule: a cross-backend agreement test is deleted wherever the
shipping backend has an independent host oracle for that entry.

## 2. Kernel-level parity with CUDA

### 2.1 Coverage

No kernel constructs `WgpuError::Unimplemented`; its only two occurrences are the
variant and its `Display` arm in `wgpu_backend/mod.rs`.

**A zero stub count is not a coverage metric.** A CUDA kernel that lands with no
wgpu counterpart is invisible to it -- nothing was stubbed, so nothing reports
missing. The way to see the real gap is to count `cuda/*.cu` against
`wgsl/*.wgsl` fresh; the count moves every time either backend gains a kernel.
What that count does not cover: `flash_decode`'s model-called `_mk` variants, and
a wgpu Marlin. The honest fix is to declare `Unimplemented` stubs for anything
CUDA-only, exactly as the original port did, so the metric can see it.

**The spec-decode verify trio has WGSL twins; what is CUDA-only there is the
serving wiring, not the kernels.** `wgsl/verify_fused_norms.wgsl`,
`wgsl/tree_verify_attn.wgsl` and `wgsl/tree_verify_fp8.wgsl` each ship with a
`nv_kernels::wgpu_backend::kernels::*` wrapper that includes them. Read
`parity_verify_fused.rs` for what it is -- `#![cfg(feature = "cuda")]`, CUDA
against a CPU oracle, no WGSL side -- and do not read the WGSL trio's existence
as tree-spec serving on wgpu (§9 item 14). At kernel level the CUDA-only residue
is Marlin (`cuda/marlin/`; `KernelId::MarlinGemmW4a16` is the one entry of
`KernelId::ALL` with no WGSL module, and `kind_supports` reports exactly that one
missing on wgpu -- §6) and the two SM120 CUTLASS files (§2.4).

### 2.2 What cross-backend agreement established, before the suites were culled

**None of this has a live gate** (§1), so it is carried as three transferable
rules rather than as a results table. What was once observed in one process, real
CUDA FFI against WGSL on this adapter pair: every decode-path kernel exercised
(`attn_decode_f32`, `gemv_bf16`, `gemv_w4a16`, `kv_fp8`, `moe_unpermute_scatter`,
`residual_scale`, `rmsnorm_residual`, `sampler_topk_topp`, `rope_f32`,
`rope_bf16`, `depthwise_conv1d_silu_bf16`) was **bit-exact**; `gemm_nvfp4` was
not, and a probe of eight K-loop reassociations proved bit-exactness against
CUTLASS is **unreachable, not unachieved** (wgpu is asserted never further from
the exact f64 product than CUDA).

1. **Write `fma(a, b, c)`, not `a * b + c`.** WGSL `fma()` lowers to SPIR-V
   `Fma`, reproducing nvcc's `-fmad=true` contraction exactly;
   `moe_unpermute_scatter` became bit-exact on that substitution alone.
2. **`ex2.approx.f32` and WGSL `exp2` agree on this stack** -- an NVIDIA-Vulkan
   observation, not a spec guarantee: on AMD/Intel/Apple a 2-3 ULP `exp2`
   difference can flip a sampled token near a bucket boundary (§11).
3. **Bit-exactness here is single-adapter** (NVIDIA 590.48.01 Vulkan).

Two deliberate behavioural divergences, both pinned by tests: WGSL wrappers
return `WgpuError::Shape` where CUDA kernels would read out of bounds (clamped
OOB reads produce *different but plausible* numbers), and `moe_permute` is
deterministic on wgpu -- bit-exact against a sequential-cursor CPU oracle -- where
CUDA assigns slots with `atomicAdd` and is not. The wgpu side is the stronger
claim in both cases.

### 2.3 Signature divergences, and the one that silently costs bit-exactness

The two wgpu entries differ in signature from their CUDA twins in ways a porter
must know: `attn_decode` takes a `scaling: f32` CUDA does not (CUDA callers
pre-scale `q`), so parity is bit-exact only because the tests pass
`scaling == 1.0`; `gemv_bf16_normed` takes `eps: f32` where CUDA takes a
precomputed `rstd` device pointer; and `flash_decode`'s stubs omit CUDA's
`fan_in: *mut u32`, with the `_mk` variants having no wgpu stub at all.

The one that bites numerically: `wgsl/dequant.wgsl`'s
`int4_decode_u4b8(word, elem, group_scale)` folds the group scale into **every
element**, changing the association versus every CUDA w4a16 kernel, which hoists
the scale out of a 32-element block. A scale-free `int4_dequant_u4b8_raw` would
stop the next porter silently losing bit-exactness.

### 2.4 What is genuinely not portable, and why it is not the dtypes

**WGSL has no trouble with any packed format in this crate.**
`wgsl/dequant.wgsl` decodes E2M1, UE4M3, signed E4M3, E5M2, bf16 and
4-bit-int-with-zero-point-8 as integer bit manipulation on `u32` words, and
`wgpu_dequant.rs` verifies each against `nv_quant` **exactly**. **No future
document should claim a dtype blocker.** Nor is it warp intrinsics:
`grep -ln 'wmma|mma_sync|ldmatrix|cp.async' cuda/*.cu` returns nothing, and what
the hand-written `.cu` files do use -- `__shfl_*` warp reductions -- maps to WGSL
subgroup ops or a shared-memory halving tree.

What does not port is the **schedule**, in exactly two files.
`cuda_sm120/cutlass_fp4_gemm.cu` is three macro expansions of FlashInfer's SM120a
block-scaled tensor-core mainloop (TMA/`cp.async` multistage pipelining,
warp-specialized producer/consumer, swizzled shared-memory atoms, stream-K tile
scheduling with a device workspace), and `cuda_sm120/moe_grouped_fp4_gemm.cu` is
a grouped `OpClassBlockScaledTensorOp` whose prologue kernel materializes
per-expert pointers, strides and CuTe `LayoutSFA`/`LayoutSFB` objects into
scratch. **WGSL has no device pointers and no way to reconstruct CuTe layout
descriptors.** The answer is not to port them but to **replace the schedule**:
`gemm_nvfp4` has a scalar path *and* a real `coop_mat` path, both bit-exact
against the CPU reference.

**NVFP4 is NVIDIA-only as a hardware format**, and no vendor exposes 4-bit matrix
silicon through WGSL (`coop_mat` in wgpu 30 gives f16/f32 element types, not
FP4), so **in-shader dequantization to f16 is the portable path by necessity,
not by preference** -- correct even though it spends bandwidth the native FP4
path would not. `05-backends.md` carries the NVFP4-vs-MXFP4 format contrast.
`wgpu_backend/device.rs` requests only `SHADER_F16 | SUBGROUP` in
`required_features`; `EXPERIMENTAL_COOPERATIVE_MATRIX` must be enabled on the
`wgpu::Device` for a coop_mat shader to validate even though the adapter reports
`coop_mat=true`. At **M=1 a 16x16x16 tile wastes 15/16 of the A-operand lanes**
and the op is bandwidth-bound anyway -- no published implementation reports
coop_mat wins for GEMV. Keep it for prefill/batch GEMM.

## 4. Serving

### 4.1 What was proven, and how

The live wgpu serving suites are `wgpu_serving_unit.rs`, `http_wgpu_wiring.rs`
and the `wgpu_*_serving_ab.rs` family. Proven through the real `axum::Router` +
`handle_chat_completions` on an idle-gated GPU, for E4B, the 31B and Qwen3.6:
each decoder reports kind, pass count, EOS set and `max_seq` on the engine-ready
line, answers a greedy prompt correctly, honours `max_tokens`, finishes with
`finish_reason=stop`; SSE deltas reassemble byte-identically into the
non-streaming completion and end with `data: [DONE]`; greedy output is
reproducible across two successive requests to the same resident model (which is
what proves the KV cache is reset per request); a fixed `seed` reproduces a
sampled completion.

Two harness traps: a stop-string test that picks a >=4-char word from the model's
own output fails when the model answers in digits; and Qwen3.6 emits ~340 tokens
of chain of thought before its answer (its template ends with an open `<think>`
block), so **a 96-token budget is not enough to see the answer** -- a small
`max_tokens` reads as a failure that is not one.

### 4.2 Templating and EOS are right

`WgpuChatEngine::load` calls `ChatTemplate::load_reason(model_dir)` and **refuses
to construct** if the model ships no template, and `official_template()` returns
`Some` unconditionally: **there is no code path in this engine that can produce a
ChatML prompt.** Token arithmetic cross-checks the served prompts exactly
(Gemma4's fixed overhead is 9 ids, so E4B reported `prompt_tokens=14` for a 5-id
user turn and the 31B, whose template adds a 4-id thought-channel suffix,
reported 18). `eos_ids_from_dir` loads the sorted `eos_token_id` set from
`generation_config.json` and refuses to serve without one, and the harness
asserts no raw control marker appears in any served content -- on both the body
and the reassembled SSE stream.


### 4.3 wgpu vs CUDA on identical prompts

**On quality, wgpu is the same as CUDA.** Holding everything identical (same
`nvidia/Gemma-4-31B-IT-NVFP4` checkpoint, same official `chat_template.jinja`,
byte-identical prompt token ids, greedy free-running, same stop set, 96-step
budget, verified-idle GPU), three of five prompts came back byte-identical and
the other two shared their opening tokens, diverged at a near-tie and then
cascaded -- the expected consequence of different kernels breaking a tie
differently, not evidence of a defect. Do not read a non-terminating CUDA
completion as CUDA nondeterminism; a sibling run reproduced it on both arms.
Genuine CUDA nondeterminism does exist and is characterised in
[`08.1-quality-harness.md`](08.1-quality-harness.md) and
[`04.1-fp8.md`](04.1-fp8.md) §5.3. For the other two models no cross-backend run
on identical prompts exists.

**Do not assume the CUDA arm is the coherent one.** Measured:
`google/gemma-4-E4B-it` on CUDA through the HTTP binary at temperature 0,
`NV_NO_SPEC=1`, returns 300 tokens of multilingual garbage with
`finish_reason: "length"`, while the same binary and prompt on wgpu returns
`"Paris"` / `stop`.

### 4.4 What does not work

1. **wgpu serving from the HTTP binary works.** `main.rs` builds the chat router
   from `oapi::chat_engine_wgpu::registry_from_env_with_wgpu()` under
   `#[cfg(feature = "wgpu")]`, via `WgpuRegistryPlan::{Delegate,Extend,Replace}`;
   Delegate is the default, so compiling the feature in cannot change a
   deployment that never asked for wgpu. An explicitly requested wgpu backend
   that loads nothing REFUSES TO START, symmetric with the cuda path.
2. **The reasoning-trace split lives in the shared `oapi::chat` handler**, so
   both backends get it: `ThinkPostProcess { active:
   engine.thinking_split_supported(), opened:
   prompt.trim_end().ends_with("<think>") }`, then `split_thinking` on the
   non-streaming path and `ThinkingStream` on the streaming one. Neither backend
   overrides the gate (the trait default
   `official_template().declares_thinking_switch()`). Live gate:
   `tests/thinking_close_marker_real.rs`. All 8 cached thinking-capable templates
   put the trace in `reasoning_content` and leave `content` as the answer alone,
   with no stray `</think>`. Qwen3.6, Qwen3.5-9B and Laguna-XS render
   `opened=true` (their templates open the block themselves, so the model only
   emits the closer) and the Gemma-4 family `opened=false` -- the case that would
   leak the whole trace if `opened` were computed wrong.
3. **The prompt head derives from a `BosDeclaration` read out of the tokenizer**
   (`add_bos_token`, `bos_token`), with `generation_config.json` as a fallback
   rather than the authority, and `Suppressed` as an explicit state: a checkpoint
   that declares no `bos_token` does not get one invented for it, least of all a
   token that is also in its EOS set. `rust/tests/http_wgpu_bos_guard.rs` holds
   it and refuses to report success with no snapshot to assert against.
4. **Prefill falls back to one token per command-buffer replay whenever the
   chunked path is not live.** The engine takes the chunk path when
   `chunked_prefill_enabled()` (`NV_WGPU_CHAT_CHUNKED_PREFILL`, on unless `0`)
   and `WgpuDecoderHandle::prefill_chunk_len` is non-zero; each of the seven
   kinds returns 0 only when its own prefill pass list did not build. A zero
   costs a P-token prompt P full replays, so read `prefill_chunk_len` off the
   engine before attributing a slow first token to the GPU.
5. **Detokenization is O(n²)** -- the whole `generated` vector is decoded every
   step. Harmless at 15 tokens, quadratic at 4096.
6. **Guided/JSON-constrained decoding works**: the wgpu engine builds the same
   `chat_engine::build_guided` the CUDA loops use, installs it on `HostSampler`
   via `set_guided`, and applies the mask in `pick`, forcing the logits-readback
   path. `rust/tests/wgpu_guided_e2e.rs` and `wgpu_guided_unit.rs` cover it.
7. **Tools are wired but not GPU-tested.** The engine passes the real tool list
   into the official template instead of copying `chat.rs`'s known-broken path;
   CPU-verified that Gemma4's template consumes `tools`, but no tool-calling
   request has been run against wgpu weights.

## 5. The capability matrix vs CUDA

**cuda** = works in the CUDA serving path today. **wgpu** = works in the wgpu
serving path.

### 5.1 Eagle3 + LoRA is CUDA-only, and that matters more than it looks

`nv-specdecode/src/lora_spec.rs` is `#![cfg(feature = "cuda")]` and its `mod`
declaration is cuda-gated. The CUDA-side measurement that makes this
load-bearing: on a 64-vocab synthetic LM, base-drafter / adapted-verifier
acceptance is **0.281 vs 1.000** when drafter *and* verifier both carry the
adapter. **The adapter must be applied to the drafter too**, so a future wgpu
spec-decode path without the LoRA kernels cannot serve adapted models even once
attention runs.

### 5.3 Asymmetries that are the design, not a gap

Each is a rule to apply. Closing one reverses the rule, and needs the rule's
reason answered first.

1. **wgpu is gpt-oss's default slot, and the cuda arm is deliberately expensive.**
   `NV_GPTOSS_CUDA_SERVE=1` builds `nv_models::gpt_oss_cuda`, which **dequantizes
   every mxfp4 expert tensor to bf16 at load** and runs attention through
   `nv_layers::attn::sdpa_with_sinks` (the eager path, because the cuda flash
   kernel takes no sink argument). There is still **no cuda mxfp4 GEMM or GEMV** --
   `gpt_oss_wgpu` is the only gpt-oss path with one -- so the cuda arm costs
   ~41.8 GB resident against ~13.7 GB, plus `heads*rows*context` f32 of eager
   scratch per prefill chunk. `GPTOSS_NO_CUDA_WITHOUT_THE_OPT_IN` states this in
   the binary. Do not build a cuda mxfp4 kernel path to close a cost decision.
2. **No WGSL Marlin and no WGSL CUTLASS-class batched 4-bit GEMM** (§9 items
   12-13). wgpu covers w4a16 and nvfp4 through its own gemv/gemm shaders; the
   batched-throughput class is a cuda-architecture asset, not a port debt.
3. **The tree-verify WGSL kernels exist and the tree-spec serving wiring stays
   cuda-only** (§2.1); §9 item 14 is a verdict about CUDA-graph-captured serving,
   and a kernel existing does not reopen it.
4. **STT stays on CPU in a wgpu-only build.** GPU STT is third-party C++
   (`whisper-rs`, `ct2rs`) with its own CUDA feature; §9 item 16 says do not build
   a WGSL Whisper, so CPU is the designed outcome.
5. **Laguna's cuda internals have no wgpu twins on purpose.** `laguna_fa2.rs`,
   `laguna_graph.rs` and `laguna_serve.rs` are `#![cfg(feature = "cuda")]`; wgpu
   serves the same checkpoint through the separate `laguna_wgpu` module. Two
   per-architecture serving engines, not two halves of one port.
6. **Per-architecture performance variants are never culled across backends.** A
   CUDA kernel never removes a wgpu kernel, and the reverse: wgpu's coop-matrix
   decode GEMV paths and cuda's PDL / shared-memory kernels are each the only
   path their hardware has.
7. **cuda-first precedence when both features compile is policy.** `AUTO_POLICY`
   states it in the binary, `main.rs` prefers a `Delegate` default plan, and
   `nv_layers::lora_slots` re-exports the wgpu `LoraDispatch`/`LoraHook` under the
   unprefixed names only when cuda is absent. Compiling wgpu in cannot change a
   deployment that never asked for it.
8. **Gate counts are not a parity metric.** `grep -rn 'feature = "cuda"'` over
   `rust/crates rust/src` outnumbers `"wgpu"` by roughly 4.5 to 1, and the ratio
   measures construction style: cuda is gated in place inside shared model files,
   wgpu lives in parallel `*_wgpu` modules carrying one gate at the top. Count
   decoders, kernels and served classes instead.
9. **wgpu reaches models through exactly four crates** -- `nv-kernels`,
   `nv-layers`, `nv-models`, `nv-specdecode`. A wgpu path added elsewhere is a new
   dependency edge, not a fix.
10. **Parakeet, the nv-tts talker, Silero VAD and the EOU heads run on CPU on
    both backends.** Only `src/tts/mod.rs` builds an ONNX execution-provider
    ladder; `stt/parakeet.rs`, `vad/mod.rs`, `eou/onnx.rs`, `eou/audio.rs` and
    `pii/classifier.rs` build sessions with none. A symmetric absence, not a
    cuda/wgpu gap.
11. **qwen3.5-dense cuda serving stays opt-in, and the registry does not know
    it.** `QWEN35_DENSE_CUDA_OPT_IN_MATCHES_THE_WGPU_ORACLE_AND_STAYS_OPT_IN`
    (`chat_engine/build.rs`) records that the cuda arm returns the same tokens as
    the wgpu oracle and holds more VRAM for the same weights, and gates it on
    `NV_QWEN35_DENSE_CUDA_SERVE=1`. `backend_select::cuda_model_unservable_reason`
    does **not** read that variable, so `/v1/backends` reports the class as
    unconditionally cuda-refused. Reconcile the two before quoting either; the
    same env admits qwen3.8-27B to cuda, where the registry *does* read it.

### 5.4 Open gaps, stated as the degradation a selection produces

The matrix's `no` cells already say which side lacks what. What they cannot say is
what a *selection* costs, and that is the form to reason in: a **cuda** selection
degrades to full re-prefill on every reconnect (no `persist`, no
`plan_prefix_reuse`) and to a `QWEN38_DENSE_NO_CUDA` refusal on qwen3.8-27B, whose
`detect_family` `starts_with("qwen3")` catch-all routes the config to
`qwen3::Qwen3Config` where `qwen3.rs` has no linear-attention mixer for the 3-of-4
`linear_attention` layers -- the same holds for qwen3.5-dense 9B by default (§5.3
item 11). A **wgpu** selection degrades to one contiguous KV buffer capped at the
load-time `max_seq` with batching on `Gemma4Dense` alone under `NV_WGPU_BATCH`
(`BATCH_GRAPH_SEAM` names the missing seam for the other six graphs); to text-only
on the Gemma-4 family, with an explicit `bail!` per graph rather than a silent
drop, because image rows reach exactly one wgpu graph (`Qwen3_5DenseWgpu`) and
audio reaches none; to plain decode on everything but Gemma4E4b; and **on Linux,
to no memory guard at all**, because `mem_fit::available_memory_gib` returns
`None` there and `plan()` short-circuits.

One arm is worth naming so it is not re-tried for the wrong reason:
**`NV_Q3D_WGPU_FP8_LMHEAD=1` on qwen3.8 is a memory lever, not a speed lever.** It
frees 1.27 GiB of resident weights at exact greedy parity (99/99 identical tokens,
unsloth 27B @16b6615a) while ms/tok does not move (34.58 widened vs 35.03 fp8,
batch=1, 26-token prompt, 99 generated, a Blackwell workstation GPU, release). Decode
at 27B batch=1 is not lm_head-bandwidth-bound; profile where the step time goes
before re-trying it for latency. Kernel gate: the suite covering the fp8 rowscale
entry (`wgpu_q3d_fp8_lmhead`).

### 5.5 Where the evidence is thinner than the matrix

A matrix row is a claim about the code. These are the rules for what a run
proves -- each one a way a lane comes back green having tested nothing.

- **The default-serving backend of a model is not always the one its gates
  cover.** `ppl_gemma4_moe.rs` and the whole `gemma4_moe_*` battery are
  `#![cfg(feature = "wgpu")]` while cuda is Gemma4-MoE's default backend (whose
  only real-weights decode test is the `NV_GGUF_PATH`-gated `gguf_gemma26b_gpu`);
  `ppl_qwen35_dense.rs` is `#![cfg(feature = "cuda")]` against the arm that only
  serves opt-in; and qwen3.8-27B has no perplexity gate on either backend
  (`crates/nv-models/tests/ppl_*.rs` is the whole set). Before quoting a quality
  gate, check its `#![cfg]` header names the backend the model actually serves on.
- **`laguna_wgpu` serves from the binary but its suites need a feature no default
  lane sets.** All eight `laguna_wgpu_*` suites are
  `#![cfg(feature = "laguna-wip")]` while `nvk.sh` defaults to `cuda,wgpu` for
  nv-kernels and `cuda` elsewhere. Run them as
  `NVK_PKG=nv-models NVK_FEATURES=cuda,wgpu,laguna-wip`.
- **Cross-backend agreement is established for four kernels and transitively
  everywhere else.** The only suites under
  `#![cfg(all(feature = "cuda", feature = "wgpu"))]` are `parity_gdn`,
  `parity_gemv_bf16_i8`, `parity_kv_fp8_paged` and
  `wgpu_correct_moe_cuda_shape_sweep`. Attention, rope, rmsnorm and the sampler
  agree only through each side's own CPU oracle -- the standing rule (§1), but it
  makes "wgpu matches cuda" for those an inference.
- **wgpu skip polarity is inverted between crates.** `nv-kernels` and `nv-layers`
  wgpu suites are loud by default; the nv-models real-model suites
  (`gemma4_e4b_wgpu`, `gemma4_e4b_wgpu_verify`, `gemma4_wgpu_quant`,
  `lora_e4b_wgpu`, `deepseek_ocr_decoder_wgpu`) print `skipping: no wgpu adapter`
  and pass unless `NV_KERNELS_WGPU_REQUIRE=1` is set.
- **A gated `mod` disappears without a sentinel unless the file plants one.**
  `tests/qwen38_multimodal_e2e.rs` and `tests/wgpu_serving_unit.rs` are the
  pattern to copy: a `#[cfg(not(feature = "wgpu"))]` marker test printing
  "compiled OUT ... this is a SKIP, not a pass". `tests/responses_http.rs` has no
  such marker, so its warm-resume coverage vanishes from a cuda-only run while
  the file's other nine tests still report green.
- **A self-recorded baseline is a regression gate, not an oracle.**
  `qwen38_multimodal_e2e` compares against a transcript it recorded itself
  (`NV_QWEN38_MM_TEXT_BASELINE`), and the qwen3.8 vision tower has no independent
  reference -- contrast `deepseek_ocr_oracle`, which has a CPU one. And
  `tests/qwen38_routing.rs`, the routing contract for a model that serves only on
  wgpu, is `#![cfg(feature = "cuda")]` and compiles out of a wgpu run.
- **Two rows rest on nothing checkpoint-specific.**
  `gptoss_wgpu_real_weights_decode` is doubly gated (`#[ignore]` plus
  `NV_GPTOSS_WGPU_TEST`) so it never runs in a sweep, and the
  `ModelClass::GptOss` registry row says as much; `Qwen35Moe`'s wgpu row is
  `ArchitectureFamily` against qwen3.6 with no checkpoint-specific suite on
  either side.

## 6. Decoder residency

`gemma4_wgpu.rs`, `qwen3_5_moe_wgpu.rs` and `gemma4_e4b_wgpu.rs` are native
`GpuTensor`-resident decoders: weights uploaded once, a list of
`wgpu::ComputePipeline` passes built at construction, that list replayed per
token inside one command encoder, four bytes (`token_out`) read back per step.
`candle_nn`, `candle_core::Device` and `Device::` have zero occurrences in all
three; the only `candle_core` references are host weight-staging helpers on
`Device::Cpu`. That is **unpinned** -- the suite that asserted it went with the
cull of source-text assertions, so re-grep before quoting it.

Everything that is **not** one of those three is still a candle module and would
run on CPU under a wgpu-only build: `nv_models::gemma4::Gemma4`,
`qwen3_5_moe::Qwen3Moe`, the vision and audio towers, the Qwen3 embedding model
and both spec-decode verifiers. `nv-kernels`' generic API is host-slice-only
(`dispatch.rs` exposes `storage_from_slice` / `storage_zeroed` / `uniform_from` /
`run` / `read_back`) and `nv-layers`/`nv-models` still hand raw `CUdeviceptr`s to
`nv_kernels::cuda::*`; the three resident decoders route around that layer
entirely. A general-purpose device-resident tensor is worth building and is not
what blocks serving.

`ModelClass::required_kernels()` demands `marlin_gemm_w4a16` for the dense/E4B
set even though the wgpu E4B decoder never calls it. `wgpu_required_kernels()`
routes around it for the serving path; every other consumer of the registry gets
a wrong answer for that class. `kind_supports` itself is honest about the grouped
MoE GEMM -- `MoeGroupedGemmNvfp4` counts as present on wgpu, and
`MarlinGemmW4a16` is the only kernel it reports missing there.

## 7. Where the wgpu time goes

Speed tables are in [`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md). The
structural findings are here.

### 7.1 Three regimes, not one bottleneck

**Anyone aiming a round at "the bottleneck" will not find one.** The token's cost
is flat across three classes -- nvfp4-gemv (below DRAM peak, headroom remains),
the tiny-kernel glue (moves almost no bytes), and the bf16 qkv+o / lm_head classes
(near or at DRAM peak, no code fix available) -- where before the GEMV rewrite it
was a single peak dominated by the NVFP4 GEMV. Per-class shares and rates:
`perf/runs.jsonl`.

> The wgpu path sits well below DRAM peak not because the memory system, the
> driver or the dispatch model is the limit -- bf16 kernels on this exact stack
> run near peak, matching CUDA's whole serving path -- but because a large share
> of the token is spent in an NVFP4 GEMV shader running below peak, and a further
> share in a swarm of kernels that move no bytes at all.

Caveat: the stage-profile reconstruction executes more dispatches per token than
the real fused model, so its "other" bucket is over-counted; treat the
tiny-kernel bucket as a range bounded below by the dispatch-count rescale, and do
not quote a point value.

### 7.2 Bytes are the currency, not launches

Measured repeatedly in both directions (measured on the development box): fusion
removed a large share of all dispatches (exactly 9 x 60 layers' worth) and bought
only a small share of the token; the raw launch floor is a small share of the
token at the fused dispatch count; and most byte-cutting experiments were
neutral-to-negative. **A byte cut converts to a time cut at a fraction well under
one, and only when the format it replaces was actually DRAM-saturated** --
halving the bytes of the near-peak qkv+o bf16 class bought a real win while int8
on the already-saturated lm_head class *cost* time.

**There are two launch floors and neither corrects the other.**
`nv-kernels/tests/wgpu_dispatch_timing_audit.rs` (`NV_DISPATCH_AUDIT=1`) is the
cross-check: GPU timestamp queries bookending each `ComputePass` inside
`submit_profiled_chunk` (`nv-kernels/src/wgpu_backend/dispatch.rs`) give an
**on-device execution window**, while a trivial atomic-increment kernel
dispatched N times into one command buffer with a single final host sync gives a
linear fit whose slope is the **host-observed** marginal cost. The fit's
intercept is noise-level, which rules out the failure mode the cross-check exists
to catch (a naive per-op sync folding hundreds of microseconds into a
per-dispatch number); its slope runs a multiple of the timestamp floor because
host-observed cost includes compute-pass-boundary driver overhead the timestamp
window does not capture. Both floors: `perf/runs.jsonl`.

Two items left open rather than smoothed over: **`NV_WGPU_O_NVFP4=1` needs a
retest** -- the `o_proj -> nvfp4` verdict was measured against an NVFP4 kernel
that has since nearly doubled its streaming rate and the arithmetic says it
should flip, so do not quote "don't take it" as current (**DERIVED, NOT
MEASURED**); and **int8-lm_head VRAM is inconsistent between harnesses**, one
reading above the bf16 baseline and one below, **NOT EXPLAINED** -- probably one
path keeping both a bf16 and an int8 copy resident.

### 7.3 Conversion dispatches

Two audits returned negative results worth keeping. **Storage width**: the feared
"1 bf16 per u32 weight tensor" pattern does **not** exist on the decode path
(every weight upload goes through `pack_pairs` or `bytes_to_words`), and `vec4`
loads buy almost nothing over scalar `u32` on a pure stream, so a GEMV's deficit
is kernel *structure*, not load width. **Dtype conversion**: swapping the whole
`rmsnorm -> gemv -> pack -> gelu` bf16 interchange for an f32 one moves the chain
by noise, and by zero in the fused single-compute-pass regime -- **the bf16
round-trips at stage boundaries cost nothing measurable**, and taking that swap
breaks parity gates for no payoff.

What conversions *do* cost is dispatches: `pack_lo16` 7/layer x 60 + 2 = **422**,
`pack_lo8` 2/layer = **120**, `cast_bf16_to_f32` 1/layer = **60** -- roughly a
third of all passes, every one launch-bound (a `pack16` over 131072 elems costs
the same as over 2048). Split one-pass-per-dispatch they cost a multiple of their
fused cost, **worth knowing before anyone splits the decode pass for timestamps
or debugging.**

Three of them are removable **bit-identically**, because each relocates existing
bit patterns rather than touching a rounding site: have the gemv/flash producers
store packed (`ROWS_PER_GROUP=8` already co-schedules rows 2r and 2r+1 in one
workgroup, so lane 0 can emit the packed word); have `quantize_row_nvfp4_bf16`
own blocks 4t..4t+3 and OR four scale bytes into one u32 (no write race); and add
a `fd_q_bf16` load path to flash stage 1, since bf16->f32 widening is exact. The
exact-rounding emulations that make that guarantee meaningful are `rms_div_rn`,
`kv_div_rn`, `q_div_small`/`q_finish`, `fd_recip`/`fd_round`, and the manual RNE
in `bf16_encode` and `kv_encode_e4m3`. **The logits bf16 round-trip is not in
that class** -- removing it drops the f32->bf16 rounding of every logit before
softcap and argmax, so every bit-exact logit/argmax gate must be re-baselined;
keep it last. The activation NVFP4 quantize is not removable at all: its fp4
rounding is exactly what CUDA's tensor-core path does, so it is parity-defining.

### 7.4 Ceiling, and the kill list

From the published record (no GPU work by us; numbers: `perf/runs.jsonl`): mature
native Vulkan on NVIDIA reaches decode parity-class rates against CUDA with no
known hard floor materially above parity; prefill keeps a real CUDA advantage
even with coopmat2; and cooperative matrix is **prefill-only** (tg128 essentially
unchanged -- do not retrofit it into decode GEMV). **A realistic ceiling for this
codebase is modestly behind CUDA on decode**, with exact-gate constraints rather
than API limits deciding the last part.

Killed, recorded so it is not repeated: **shape-gated NVFP4 variant selection.**
`select_variant_for_shape` (`gemv_nvfp4.rs`) has exactly one caller in the tree,
a host helper used only by tests, while the model calls the shape-blind
`select_variant` once. Wiring it is **DERIVED** at a percent-class win, an order
of magnitude below the shader-efficiency problem, and **NOT MEASURED** end to end
because no code path can produce it. The same lane's parameterised `SgwConfig`
shader is likewise unreachable from `GemvVariant` (still just `Tree | Sg`).

## 8. Would a different quantized checkpoint help?

**Switching checkpoints is a simplicity lever, not a bandwidth lever.** At
group-of-32 4-bit every serious candidate moves the same ~4.5 bits/element as
NVFP4 (4 + 8/16) except MXFP4 (4.25). Stay on NVFP4 for the headline number (it
is the CUDA-parity reference). If a switch is wanted, take
**`google/gemma-4-31B-it-qat-w4a16-ct`**: `weight_packed I32 [out, in/8]` plus
plain row-major `weight_scale BF16 [out, in/32]` -- no swizzle, no global scale,
no FP8 -- unpacking to exactly `w4a16_q` in the shader with bf16 scales read
natively by `gemv_w4a16.wgsl` (`wgpu_gemv_w4a16` 6/6, `max_ulp=0` across group
sizes 8..3072). Same bytes/token as NVFP4, so it doubles as the clean A/B
separating dequant-layout cost from dispatch overhead at equal bandwidth.
**`amd/gemma-4-31B-it-MXFP4`** is the only candidate that strictly reduces bytes
moved, but it needs an MXFP4 GEMV lane and an eval pass first (the kernel work
needs no download -- `openai/gpt-oss-20b` is on disk and
`gpt_oss_20b_checkpoint_layout_is_mxfp4_row_major` passes against it). **Skip**
AWQ-4bit (asymmetric zero-points `gemv_w4a16.wgsl` lacks), Intel AutoRound (GPTQ
column-interleaved qweight needs repack) and GGUF (no container loader in-repo).

## 9. Ranked remaining work

The one durable Tier-1 asset is **not a gate at all**: the entire host-side
generation stack in `chat_engine.rs` is already ungated and backend-neutral
(sampling params, the whole `ChatSampler`, `stream_text_delta`, `StreamEmitter`,
`IncrementalDetok`, `build_logprob_entry`, `build_guided`, `kv_window`,
`ChatRegistry`) because it consumes `&[f32]` logits and nothing else. All three
wgpu decoders expose exactly that via `decode_step_logits()`.

Two registry items stay open and are cheap: `ModelClass::required_kernels()`
still demands `MarlinGemmW4a16` for the dense/E4B set the wgpu decoder never
calls (§6), and ~12 pure-CPU helpers plus 13 tests in `chat_engine.rs` sit behind
`#[cfg(feature = "cuda")]` while touching no GPU API (`detect_family`,
`resolve_qwen3_5_moe_eos_ids`, `parse_bos_id`, the three `render_*_prompt`s,
`det_hash_f32`, `effective_max_new`, the chat semaphore), so those 13 tests have
never executed in a non-CUDA run.

The one Tier-2 item worth naming as a rule rather than a wish: **an M>1 wgpu
forward unlocks batching, paged KV and fast prefill simultaneously**, and it is
the only thing standing between wgpu and a server rather than a demo. Everything
else in that class (`decode_step_embed` for multimodal, splicing LoRA deltas into
resident pass lists, the NVFP4 GEMV x-side decode) is integration work whose
kernels already exist -- the x-side decode is blocked by ownership, not
technique: the kernel bodies live in `gemma4_wgpu.rs` / `qwen3_5_moe_wgpu.rs`
rather than `nv-kernels`.

### Do not pursue parity, and say so out loud

Beyond the two already stated as design rules (no WGSL Marlin and no WGSL
CUTLASS-class batched 4-bit GEMM, §5.3 item 2; no WGSL Whisper, §5.3 item 4):

**CUDA-graph-captured speculative decoding (Eagle3 / DFlash) *serving*.** The
design is built on cudarc stream capture plus graphed verify; wgpu's pre-recorded
command buffers cover the *replay* half but not the dynamic-shape tree-verify
half. The WGSL verify kernels existing (§2.1) does not reopen it -- the kernels
were never the hard half. *Consequence:* wgpu decode stays at ~1x where CUDA gets
~2x at bs=1, except on Gemma4E4b where the suffix-automaton / learned-drafter
route runs (§5). Given wgpu's baseline is already slower per token, this is the
**worst effort-to-benefit ratio in this document.**

The consequences of the Marlin and grouped-GEMM verdicts, stated once: batched
W4A16 prefill on wgpu stays materially slower than CUDA (bs=1 E4B decode is
unaffected -- the CUDA path itself falls back to GEMV under
`NV_E4B_FORCE_GEMV`), and MoE models decode on wgpu at a throughput gap that
widens with batch size. Accept both. The gap worth closing on Laguna is not a
kernel port but that its suites need `laguna-wip` on the lane (§5.5).


## 10. Reproduction

`08-build-and-testing.md` owns `nvk.sh` and lane discipline; what is
wgpu-specific is the loader and the skip polarity.

```sh
NV_KERNELS_WGPU_REQUIRE=1 NVK_LANE=<lane> NVK_PKG=nv-kernels NVK_FEATURES=wgpu \
  rust/scripts/nvk.sh test -- --test-threads=1

# serving: build --no-run, then run the binary directly under a VERIFIED 64-BIT loader
export LD_LIBRARY_PATH=<64-bit vulkan-loader>/lib:/run/opengl-driver/lib:$LD_LIBRARY_PATH
export VK_ICD_FILENAMES=/run/opengl-driver/share/vulkan/icd.d/nvidia_icd.json
export TMPDIR=$HOME/.cache/cargo-tmp
export NV_WGPU_SERVE_TEST=1 NV_WGPU_SERVE_MAXSEQ=1024 NV_WGPU_SERVE_TOKENS=64
export NV_WGPU_SERVE_DIR=<checkpoint snapshot dir>
# Qwen3.6 needs NV_WGPU_SERVE_TOKENS=96+; at 96 the harness escalates to 384 itself
# real-weight decodes are 20-25 GB each: NV_E4B_WGPU_TEST=1, NV_QWEN36_WGPU_TEST=1
```

Name a suite from the tree and check it is still there first -- the corpus is
culled on the rule that a file which cannot go red on a wrong number gets
deleted, so a recipe quoting a suite by name outlives the suite.

**Two traps, both of which have produced false greens here.** A suite gated
`cfg(all(feature="cuda", feature="wgpu"))` compiles to nothing under
`NVK_FEATURES=wgpu` and prints `0 passed; 0 ignored` in `0.00s` -- that is a
SKIP, and a genuine `#[ignore]` skip shows a **non-zero ignored** count. And a
wgpu suite with no Vulkan loader prints `1 passed` in `0.00s` having executed
zero GPU work: **most `vulkan-loader` store paths on this box are 32-bit**, and a
32-bit loader fails silently with no `VK_LOADER_DEBUG` output at all. Every real
wgpu run prints an adapter banner naming the device, driver, `shader_f16`,
subgroup range and `coop_mat` config; **a wgpu run without that banner is a skip,
whatever the result line says.**

## 11. AMD / Strix Halo (RADV) -- the second adapter

Rules from the strix lane (AMD Strix Halo APU, Mesa RADV, no CUDA on the box) --
the first partial answer to §2.2 finding 3. Two scope guards: this is
**kernel-suite state, not a parity verdict**, and the real-weight result is
**decode, not serving**.

- **RADV enumerates the APU without root**, and **host RAM headroom is a hard
  precondition**: the APU has no dedicated VRAM, so GPU allocations come out of
  the same pool as everything else. A ~15 GiB need against ~6 GiB `MemAvailable`
  produced a global OOM with database processes as eligible victims. Check
  headroom before any load.
- **AMD is safe-by-fallback -- a perf cost, not a correctness one.** Kernel
  suites run 568 passed / 20 failed / 1 SIGSEGV; all 20 failures share one cause,
  **subgroup width 64 where the code assumed 32** (compare §10's NVIDIA banner
  `subgroup=true(32..32)`). The shipped decode path guards on subgroup width and
  falls back to the Tree variant, and `gemv_nvfp4_v2::subgroup32_ok` guards every
  v2 model call site.
- **The in-shader NVFP4 dequant path is vendor-neutral at kernel level** -- eight
  NVFP4/quant suites pass on RADV including the exact-dequant and
  bit-exact-decode cases -- but **no NVFP4 checkpoint has been decoded on AMD**,
  and host-RAM headroom is why.
- **E4B bf16 real-weight decode works on AMD** at a bandwidth-plausible rate.
  That is the engine-level decode path; **no HTTP request has been served from
  AMD**, so it is not a SERVES claim.
- **The Mesa cooperative-matrix compiler SIGSEGVs on valid input.** That is the
  1 SIGSEGV -- a driver bug, upstream-worthy, not a defect in these shaders.
- **The exp2/sampler tripwire cannot be tripped there.** The CUDA-vs-WGSL
  comparison that would catch it needs CUDA, which the box does not have, so it
  must become a **token-divergence watch**: compare AMD-decoded token streams
  against recorded NVIDIA/CUDA streams on identical prompts.

Resume rules for that lane: run `--no-fail-fast` so the 20 known subgroup-width
failures do not mask anything new; **pin the ICD to RADV** rather than relying on
loader enumeration order; **never trust green without the adapter banner** (§10 --
it bites harder here because a silently-missing adapter and a wrong-adapter pick
are both live on an APU box); and **never system-switch that host as a side
effect of GPU work** -- its running system is far behind the tree, so a rebuild
deploys the whole fleet delta to a box serving live services, and a Vulkan ICD is
pure userspace and needs no switch.
