# Concurrency and ordering contract -- realtime lane

Read this before you parallelize anything in `rust/src/realtime/`, or before you
turn on batching in the chat lane. Several invariants below are the only thing
standing between a plausible-looking optimization and a client that silently
receives a `response.done` for a response it never saw created.

## 1. The invariant table

Scope key: per-session, per-item (per response_id or item_id), cross-lane (two
independent task graphs), global (whole process / all transports).

| ID | Invariant | Scope | Holds today | Tested | Enforced |
|----|-----------|-------|-------------|--------|----------|
| I1 | `session.created` is the first event on the wire for a session | per-session | **NO** | yes (tier2, red) | no |
| I2 | Every outbound event carries a monotone `event_id` | per-session | yes | yes (3 tier1 + 5 wire tests) | yes (`EventSeq` on the single sink call site) |
| I3 | speech_started < speech_stopped < committed < item.added < transcription.completed | per-item | yes (incidentally) | yes (checker + selftest) | no |
| I4 | No event references an item_id not yet announced | cross-lane | yes | yes (tier1 + env-gated session probe) | partially |
| I5 | No `partial_transcription{X}` after `transcription.completed{X}` | per-item | unknown | checker only | no |
| I6 | `response.created{R}` first, `response.done{R}` last, for that R | per-item | unknown | checker only | no |
| I7 | No event of R after `response.done{R}` | per-item | **NO** (but detectable) | yes (tier1, green) | no |
| I8 | At most one response streams into a session sink at a time | per-session | **NO** (TOCTOU) | checker only | no |
| I9 | Cancel stops synthesis and pacing, not just bookkeeping | per-item | yes | yes (4 cancel_energy tests) | yes (`TtsAbort`) |
| I9b | Session teardown/disconnect stops the lanes that outlive a response | per-session | yes | yes (2 cancel_energy + 3 `cancel` unit tests) | yes (`SessionCancel`) |
| I10 | Exactly one AudioPacer writes to a session's audio sink | per-session | **almost** (250 ms quiesce window) | indirectly, via I9 | partially |
| I11 | `audio_end_ms` / `played_ms` non-decreasing | per-session | unknown | checker only | no |
| I12 | Emit order equals wire order | global | **NO** | yes (tier2, red) | no |
| I13 | `conversation.item.diarization{X}` after `item.added{X}` and `completed{X}` | cross-lane | **NO** (deterministic inversion) | checker only | no |

| I15 | Backpressure blocks or errors, never silently drops | global | **NO** (two drop sites) | checker only | no |
| I16 | Backpressure is bounded and diagnosable on every transport | global | **NO** (WS lane unbounded) | yes (tier1: pins the stall) | no |

"Tested" means a test exists that would go red if the invariant were violated in
the code path the test drives. "Enforced" means production code structurally
prevents the violation. **Note the gap: most of these are *observable* and
almost none are *enforced*.**

I2, I4, I7, I9, I9b and I17 are closed structurally — `EventSeq` stamping in
`deliver_to_sink`, announced-item gating on the diarization lane, a
response-scoped WS `response.output_audio.delta`, `TtsAbort` and `SessionCancel`
energy cutoff, and one pinned Topic-classifier table. Their characterization
tests remain as tripwires.

### `deliver_to_sink` atomicity, and the I12 harness's own false positive

`Session::deliver_to_sink` stamps `event_id`, writes the inspector "out" record
and writes the wire as **one critical section** under an `outbound_send` mutex.
Without it, two tasks emitting concurrently on one session could take `event_id`
N and N+1 and land on the wire as N+1, N — the server's own sequence observably
out of order, with the inspector trace disagreeing with what the client received
(1-4 inversions per 256 concurrent emits). Nothing inside that section takes
`self.state`, and every caller releases `self.state` first, so it cannot
deadlock.

`order_harness.rs`'s two `tier2_i12_*` tests pin different halves of the same
claim and are easy to conflate.
`tier2_i12_concurrent_emitters_preserve_order` serialises its own stamp-and-emit
behind a harness-owned mutex, so it proves only the happens-before case — and
that serialisation is **required**, because `harness_seq` is taken by the
harness itself and overlapping emits have no happens-before edge, so
`harness_seq` order was never a property the server promised. Removing the
harness mutex yields ~120 `harness_seq` "inversions" per 256 emits and always
did: a harness artifact, and the load-sensitive failure this family kept getting
reported as. `tier2_i12_event_id_monotonic_under_unserialized_emitters` is the
real check — it does not serialise the emitters and asserts on `event_id` only,
from the server's own counter inside `deliver_to_sink`; before the
`outbound_send` lock this measured 1-4 inversions per run, and it is 0 now.

## 2. I1 and I12 -- the outbound path has no sequencer

This is the load-bearing open defect and the precondition for every batching or
mutex-removal change in this repo. `Session::attach_websocket` installs
`state.event_sink` inside the state lock, releases the lock, and only then sends
`session.created`, so any `emit_event` that resolves the sink in that window
wins the race; and `Session::emit_event`, `Session::emit` and
`Session::send_to_client` all clone the sink out of the state lock and then
`await` the send with **no lock held**, so N concurrent emitters interleave.

WebSocket is accidentally saved from *payload* corruption by the single mpsc
plus single writer task, so what you observe is reordering, not interleaved
bytes. WebRTC has neither protection: `transport.rs` loops
`for frame in frames { self.send_text(frame).await }` with no lock, so an event
above `DATA_CHANNEL_FRAGMENT_MAX` (900 bytes) can have its fragments interleaved
with another producer's, and payload integrity survives only because
`framing.rs` stamps a per-event uuid envelope. `event_id` (I2) makes the
reordering detectable client-side; it does not prevent it.

**Consequence for batching:** batched decode produces tokens for N requests in
one step, and fanning those out from N tasks into one per-session socket
reintroduces exactly this race. **The single outbound sequencer must land BEFORE
batching is turned on by default.** The same precondition blocks removing the
`Arc<Mutex<ort::Session>>` wrappers — those mutexes impose an accidental FIFO
that several lanes are implicitly ordered by.

## 3. I14 -- audio/transcript interleaving is a non-guarantee, on purpose

Transcript deltas come from the `run_response` parent at LLM token rate; audio
deltas come from the `tts_worker` child at 20 ms wall-clock pace. On WebRTC they
are on two different transports entirely (RTP track vs SCTP data channel) and no
server-side mechanism can order them. Enforcing an interleaving would either
stall the LLM or add audio jitter.

**Clients MUST NOT infer caption/audio alignment from wire order.** If a client
needs alignment, the fix is a timestamp / `played_ms` field on the events, not
wire ordering. A harness test asserts the checkers do *not* flag this pattern,
so nobody "fixes" it by accident later.

## 4. Priority order for the next person

1. **Single outbound sequencer.** Fixes I1 and I12 structurally, and is the
   precondition for batching and for mutex removal. Direction: send
   `session.created` while still holding the state lock (or stage events until
   it has gone out), and hold a dedicated send mutex across the `await` in
   `emit`/`emit_event`/`send_to_client` — or route all three through one owned
   outbound task.
2. **Close I10 properly.** `cancel` gives up after a 250 ms quiesce timeout and
   `run_response` still builds a fresh pacer per response over a shared sink.
   Give the pacer a response generation/epoch it checks before each write, so a
   straggler cannot write at all rather than merely being unlikely to.
3. **Close the I8 TOCTOU** by registering the response under the same lock
   acquisition that checks for one, and make the collision path abort the loser
   rather than warn. Today the loser's `run_response` is left streaming and
   unregistered, hence permanently unabortable — an I8 violation that
   manufactures an I9 violation.
4. **WS backpressure gate (I16)** — give `WsAudioPacer` the
   `outbound_queue_cap_ms` the WebRTC pacer already gets, and emit
   `client_too_slow`. Today a non-draining `ws_rx` blocks the emitter, blocks
   the VAD supervisor, backs up `audio_in`, and stops the WS reader from reading
   the client's microphone, with no error emitted.
5. **Stop silently dropping (I15)** — emit a client-visible error at both drop
   sites (the outbound-queue-cap drop and the I7 Predicted gate), and account
   `emit()` and the WS pacer in `outbound_inflight` so the cap measures actual
   outbound volume. The chat lane has the same failure mode: `batch_engine.rs`
   uses `let _ = ....try_send(...)` for `Token` and `Done`, so a slow SSE
   consumer causes silent token loss with a mismatched `completion_tokens`.
6. **Order diarization behind the transcript lane (I13)**, or accept the
   inversion and document it as an I14-style explicit non-guarantee. Either is
   defensible; the current silence is not. Also add
   `conversation.item.diarization` to `KNOWN_EVENT_TYPES` in
   `conformance/lib/trace_invariants.py`.

## 4b. Serving-surface concurrency

| surface | bound (N) | shed deadline (M) | concurrent test |
|---|---|---|---|
| `/v1/chat/completions`, `/v1/completions` | `NV_CHAT_CONCURRENCY` semaphore + VRAM admission capacity | `NV_ADMIT_QUEUE_MS` (3000) and `NV_CHAT_QUEUE_MS` -> 503 | `concurrency_real.rs`, `load_soak_real.rs` |
| `/v1/ocr` generative (deepseek, dots, got) | `NV_OCR_CONCURRENCY` (1) | `NV_OCR_QUEUE_MS` (3000) -> 503 `surface_busy` | `concurrency_surfaces.rs`, `concurrency_shed.rs` |
| `/v1/ocr` classical (tesseract) | **ungated by default**; `NV_OCR_CLASSICAL_CONCURRENCY` opts in | shares `NV_OCR_QUEUE_MS` | `concurrency_shed.rs` |
| `/v1/embeddings` | `NV_EMBED_CONCURRENCY` (1) | `NV_EMBED_QUEUE_MS` (3000) -> 503 | `concurrency_surfaces.rs`, `concurrency_shed.rs` |
| `/v1/audio/transcriptions` | **no lock, unbounded** -- correct by design, see below | none | harness only |
| `/v1/audio/speech` | `Arc<Mutex<Session>>` (ONNX), poison-recovering | none | none yet |

**The permit is acquired BEFORE `spawn_blocking`, never inside it.** That is the
load-bearing detail, not the semaphore: every model lock is taken inside the
blocking closure, so a waiter that queues *there* holds a blocking-pool thread
while it waits, and at tokio's default of 512 one hammered endpoint starves
every other surface. `concurrency_shed.rs` asserts this structurally rather than
by timing — the stub backend is entered exactly as many times as there were
200s (a shed request never reaches the model, which can only hold if the permit
is taken first), and with `max_blocking_threads(2)` and 16 requests hammering
one surface an unrelated `spawn_blocking` still answers in 1 ms.

**Why classical OCR is ungated.** A uniform permits=1 gate over all OCR backends
turned `concurrency_surfaces` red (0 passed / 4 failed) with a `surface_busy`
503 on request 0 of 8 — structural, not tuning, because the classical path takes
no lock (`OcrEngine::recognize_mode` is `&self`) and already fans each page over
`available_parallelism()` threads, so 8-way classical concurrency is an existing
tested contract and serialising it blows the 3 s window. A correct non-default
bound needs a measurement nobody has taken: classical page latency against the
per-request thread fan-out.

clippy `await_holding_lock` / `await_holding_refcell_ref` over the server crate
is **zero hits** — every lock is acquired inside `spawn_blocking`, never held
across an `.await`. Checked, not assumed; re-run after any change that moves a
lock. **Poison policy**: `/v1/ocr` and `/v1/embeddings` recover from
`PoisonError` via `into_inner()` with a WARN rather than bricking the endpoint
for the process lifetime, which is sound because neither guards a mutable
invariant — `DotsOcrPipeline` has no interior mutability and
`Qwen3::forward_hidden` reaches nothing mutable through `self`.

**FALSIFIED: making `/v1/embeddings` concurrent.** Since `Qwen3` proved `Sync`,
the `Mutex` could be dropped and requests run in parallel behind a permit gate.
Built, measured, reverted: sixteen concurrent single-input requests get
monotonically **worse** as permits rise from 1 to 4 to 8, both reps agreeing,
and intra-request batching shows the same shape. One small model on one GPU
serialises at the driver regardless, so added concurrency buys nothing and costs
task-spawn, semaphore and context-switch overhead — the `Mutex` was never the
bottleneck. Do not re-attempt without changing the premise, e.g. genuine request
batching (one forward over N padded sequences) rather than N concurrent
forwards.

**STT is the one surface with no lock at all, and that is correct.**
`WhisperHandle::WhisperCpp` holds `Arc<CppContext>` and calls
`ctx.create_state()` per request — the documented whisper.cpp pattern, weights
shared read-only and decode state per call — while `WhisperHandle::Ct2` holds
`Arc<Ct2State>` and calls `model.generate(&self, ...)`, CTranslate2 being
internally thread-safe. Verified on the real server, ct2 backend: 8 simultaneous
transcriptions of one clip, all byte-identical to a serial reference, zero panic
or poison lines.

**Harness rule learned here:** the 040/030 fixtures are synthetic
alignment-structure audio (030's is a 440 Hz tone) and transcribe to `"."`, so
an equality assertion built on them cannot fail. Cross-talk tests need real
speech (`e2e-drive/w_speech.wav`). **Check what your reference value actually
*is* before trusting an equality assertion built on it.**

## 4c. The CUDA default stream is the legacy null stream

Measured against the live device: candle's `CudaDevice::cuda_stream()` returns
`0x0`, the legacy null stream, while a forked stream returns a real handle.
`nv_layers::cuda_stream::current_stream()` falls back to `dev.cuda_stream()`
whenever no `with_stream` scope is active, so **every code path without an
explicit override launches on the legacy null stream**, which implicitly
synchronises with all blocking streams in the context. DSOCR's
`prefill_detached` / `prefill_slot` are in exactly that position — they reach
`embed_tokens_with_vision` -> `forward_embeds_hidden` -> `last_logits` with no
scope, so prefill serialises against the decode graph's forked streams and
against other concurrent requests.

**This is not a one-line fix**: the implicit synchronisation is load-bearing for
read-back correctness, so moving prefill onto a forked stream means every
read-back needs an explicit sync and a missed one is a silent data race, not a
visible failure. The decode-graph constructor shows the shape of the care
required — it synchronises the default stream and calls
`disable_event_tracking()` *before* forking. Land any change behind a
concurrency harness that can observe overlap, not on a code reading.

**Verdict: documented, harness-pinned limitation — not a fixable knob.** The
landed opt-in (`NV_DSOCR_PREFILL_STREAM=fork|perthread|1`, default off,
byte-identical when off) moves nv-layers segments to a per-thread **blocking**
stream (`CU_STREAM_PER_THREAD`); a `CU_STREAM_NON_BLOCKING` fork would silently
remove the load-bearing implicit ordering at every nv-layers/candle boundary,
because candle-native launches (routing matmul, `softmax_last_dim`,
`candle_flash_attn`, embedding gather, `last_logits`) are hardwired to the
legacy null stream. On real weights concurrent-2 scaling is a null either way,
confirming the serialization, and the knob buys nothing outside noise; safety
holds with it on (`deepseek_ocr_graph_batch` tokens EXACT on all 4 slots), but
keep it off. A real fix needs candle's own launches off the null stream. Three
durable findings: **busy-window overlap is the wrong signal** (legacy mode shows
`overlap_frac=1.000` while the device serializes underneath, so the harness
`nv-models/tests/dsocr_prefill_overlap.rs` — `LOAD_DSOCR=1`, `--ignored` — pins
the broken state on throughput scaling instead); **per-stream caches keyed on
raw `cu_stream` are a data race under per-thread streams**, since the per-thread
handle is the sentinel `0x2` on every thread, so `nv_quant::stream_cache_key()`
mixes a per-thread id into the key for `0x2` only; and `with_stream` must
restore its thread-local on panic as well as on normal return, or a pooled
request thread stays pinned to the failed request's stream — a contamination
with no symptom at the call site, because `current_stream()` silently returns
whatever the thread-local holds.

## 5. Running the harness

```sh
# default: tier1 + selftests + driver. Tier 2 SKIPS SILENTLY without models.
cd rust && cargo test -p speaches-plus --lib realtime::order_harness

# the known-red invariants. EMPTY as of the I2 fix: this selects 0 tests.
# A non-zero count here means someone re-ignored a tier1 test.
cd rust && cargo test -p speaches-plus --lib realtime::order_harness::tier1 -- --ignored

# tier 2 against a real Session -- THIS IS RED TODAY (I1, I12)
cd rust && SPEACHES_PLUS_MODELS=<repo>/rust/models \
  cargo test -p speaches-plus --lib realtime::order_harness::tier2 -- --test-threads=1

# the env-gated I4 diarization probes
cd rust && SPEACHES_PLUS_MODELS=<repo>/rust/models REALTIME_DIARIZATION=1 \
  cargo test -p speaches-plus --lib realtime::session::tests -- --ignored
```

Tier-2 tests **skip silently when `SPEACHES_PLUS_MODELS` is unset** — `models()`
returns `None` and the test returns `ok`. A plain `cargo test` therefore reports
green for tier 2 while testing nothing. Do not read a green tier 2 as evidence.

Convention: when you fix one of these bugs, the paired characterization test
that pins the *broken* surface is designed to go red. Update its expectation
rather than deleting it — the tripwire is the point.
