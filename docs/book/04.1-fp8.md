# FP8 -- cross-backend contract, defaults, and known issues

Canonical fp8 document; it subsumes every earlier fp8 status, measurement and
re-validation note. Owner lane: `fp8-contract`. Machine-enforced by
`rust/crates/nv-kernels/tests/fp8_contract_e4m3.rs` (which `include_str!`s this
file) and `rust/crates/nv-models/tests/fp8_contract_freerun.rs`. Companions:
[`08.1-quality-harness.md`](08.1-quality-harness.md) for how any of this is
measured, [`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md) for speed numbers,
[`05.1-wgpu-status.md`](05.1-wgpu-status.md) for the wgpu backend, and
[`04.2-fp8-epilogue-mechanism.md`](04.2-fp8-epilogue-mechanism.md) for the
per-element teardown of the two wgpu fp8 epilogues.

**Provenance.** Every measured cell behind this page -- CONTROL rows, mutant
counts, top-2 margins, decode-rate and VRAM figures -- was produced on the CUDA
box and its raw logs are not archived in this repository. The *contract* in §7 is
machine-enforced by the two suites named above and does not depend on any of
them.

## 0. The answer

| Question | Answer |
|---|---|
| Does wgpu fp8 attention corrupt output? | **No.** On chat-templated, EOS-aware prompts every fp8 arm produces coherent, correctly-terminating text and is token-exact on every high-margin control. |
| Is fp8 attention the wgpu default? | **Yes, hardcoded.** `gemma4_wgpu::ATTN_VARIANT_DEFAULT` (int8/128, all layers); tests select arms via `gemma4_wgpu::set_attn_variant`. §6. |
| Is there a real fp8 defect anywhere? | **Yes, one: the CUDA fp8 KV cache at long, low-margin context** -- forced-context logit `rms_rel` ~1.0, reproduced three times. §5.2. |
| Does fp8 exist for attention projections on CUDA? | Only through Laguna's opt-in `NV_LAGUNA_ATTN_FP8`. The generic CUDA attn-proj quantizer is NVFP4-only. §5.1. |
| What does fp8 attention cost/buy on wgpu? | -12.1% best-batch / -7.7% median-of-medians ms/tok, and **-13312 MiB (13.0 GiB)** VRAM at max_seq 4096, at an identical 728 dispatches and 26.91% fewer weight bytes/token. |

## 1. The measurement lesson

**Only free-running, EOS-aware, chat-templated measurement describes serving, and
a reference arm must be health-checked before it certifies anything.** Argmax
agreement failed in both directions on the same day: a **forced-context** number
(re-seed the candidate with the reference's token after every step) read 39/40 and
hid a real cascade, because serving never re-seeds; the free-running number on the
same configuration read 3/33 -- and that was itself refuted, because it came from
a raw un-templated prompt whose bf16 reference is a 96-token repetition loop
decoded past the stop set, so both halves of the "collapse" signature were later
reproduced from the *unquantized* model. The harness enforces the rule in its
types: `free_running_greedy()` returns a `FreeRunningTrajectory` whose `Display`
begins `FREE-RUNNING (serving metric)`; `forced_context_upper_bound()` returns a
`ForcedContextUpperBound` whose only accessor is
`upper_bound_agreement_is_not_serving_evidence()`; no method yields a bare ratio.

## 2. Quality evidence

Gemma4-31B-IT-NVFP4 @ `e5ef03af`, every prompt through the
shipped `chat_template.jinja`, EOS-aware against `[1, 106, 50]`, reported per
prompt and never pooled: **16 CONTROL prompts reach 100.0% free-running argmax
agreement**, `first divergence None`, `shape IDENTICAL`, reference-token rank
median/p95/max = 1 everywhere, median top-2 margins 15.1-20.1, both arms producing
the same text on all 16; worst-perplexity prompt `control-water` at ratio
**1.000427 against an allowed 1.05**; `evaluate_default_flip_suite` returns
**ALLOW** (§8). That table was produced twice in two independent processes,
byte-identical.

**Open-ended, low-margin prompts are descriptive only and are excluded from A/B
evidence**: a byte-identical configuration gave 66 ended / 78 ended / 96 not-ended
across three runs. Divergence-point margins across five chat-templated prompts are
**0.59-2.26** against reference medians 6.04-17.89, so no arm ever flipped a
decisive step first, and a one-token nudge of the *unquantized* bf16 model
produces the same or worse divergence on the same prompts. "The completion changes
on ambiguous prompts" is a property of greedy decoding on this model, not of fp8.

## 3. The epilogue "fix"

`gemma4_wgpu::build_fp8_pipelines` picks between a per-16-element accumulator
(shipped) and a whole-row accumulator (the legacy epilogue, selectable only via
`set_attn_variant { legacy_epilogue: 1, .. }`). **The accumulator hypothesis for
why the swap mattered is falsified**: at the real Gemma4-31B shapes the two are
bit-identical on 21504 of 21504 o-proj outputs and differ on 7 of 16384 qkv
outputs by at most 3 bf16 ulp, both within one bf16 ulp of an f64 reference --
see [`04.2-fp8-epilogue-mechanism.md`](04.2-fp8-epilogue-mechanism.md) for the
method and the mutation coverage that guards it. The swap is kept (it costs
nothing and removes the raw-prompt pathology) but is recorded as empirically
accepted, not explained.

## 4. Speed and memory

Method: `gemma4_wgpu_profile::real_e2e_clean_baseline`, `--release`,
`NVK_FEATURES=wgpu`, max_seq 4096, 15 warm-up decode steps then 5 batches x 16
tokens, `wait_idle` plus an `nvidia-smi` sample around every batch, GPU idle at
`0 %, 8564 MiB` before each run; three arms (bf16 attention, shipped fp8 epilogue,
legacy fp8 epilogue) on best batch, median-of-medians, VRAM during run and
passes/step. Numbers: `perf/runs.jsonl`.

fp8 vs bf16 wins a real percentage on both timing bases and saves a large VRAM
block at an identical **728** dispatches; the shipped epilogue is inside noise of
the legacy one, as it must be -- same passes, same bytes. **Median-of-medians is
the reliable comparison**: the bf16 run had four batches each containing a single
long stall that a mean-per-batch metric absorbs. The fp8 path has **no stage
decomposition** -- the profiling replica's qkv/o stages are `gemv_bf16` and there
is no `gemv_fp8` line.

## 5. CUDA

### 5.1 Generic fp8 attention projections do not exist on CUDA

The code refuses it and an executed test asserts the refusal: the
`NV_ATTN_PROJ_QUANT` parser accepts
`off|0|bf16, qkv, o|oproj, 1|on|true|yes|all|nvfp4|fp4|qkv+o` -- no fp8 spelling
at all. On CUDA, fp8 means the KV cache plus Laguna's opt-in per-row
attention-projection path (§5.4). **Every CUDA reference number in
[`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md) is therefore a bf16-attention
number.**

### 5.2 Known defect: the CUDA fp8 KV cache at length

`cuda_fp8_freerun::fp8_kv_free_running_matches_bf16_on_real_gemma4`, run three
times back to back, idle-gated, on the templated pack, arms bf16 KV vs fp8 KV:
`openended-system` fails at forced-context `logit rms_rel` 9.317e-1 / 1.454e0 /
1.061e0 against a 0.5 bar. `logit_rms_rel = ||bf16 - fp8|| / ||bf16||` over the
whole 262k logit vector, measured under **forced context**, so this is not
cascade amplification -- the fp8-KV logit vector differs from bf16's by about the
size of the vector itself. It is invisible on everything short and decisive:
controls are 2/2, 2/2, 3/3 byte-identical across all three runs at max `rms_rel`
0.087-0.149, `openended-list` 27/27 at 0.285. **Length- versus prompt-triggered
is confounded** -- the one failing prompt is both the longest and the
lowest-margin.

### 5.3 The CUDA bf16 reference is not reproducible

Three back-to-back runs of a byte-identical configuration give three different
bf16-KV transcripts (`openended-system`: 96 not-terminated / 96 not-terminated /
70 ended-turn) while the fp8-KV arm is byte-identical across all three; even a
2-token control's median top-2 margin moves (17.229 / 17.108 / 16.289) though its
argmax never does. Consequences: any CUDA A/B against a bf16 free-running
trajectory longer than ~30 tokens measures reference noise as well as arm
difference; §5.2's defect is real (three reproductions) but its *magnitude*
carries that jitter and must not be quoted to two significant figures; and
**whoever owns the CUDA attention/KV kernels should root-cause the
nondeterminism first.** The wgpu bf16 arm is byte-identical across four
independent invocations at up to 79 generated tokens, so this is a CUDA-path
problem, not a property of the model.

### 5.4 Laguna fp8 on CUDA

`rowquant_e4m3_kernel` (`nv-kernels/cuda/gemv_bf16.cu`) is contract-compliant
(§7.2), and making it so was **real but latent**: three of twelve unit `rel`
figures move and the first code divergence moves 20 steps later while greedy
output does not move at all -- the 32-token generation and the 65548-token needle
answer are byte-identical across arms. All four Laguna fp8 suites run and pass
(`laguna_quant_eval`: `agree=2033/2048 ties=15 gray=0 real=0`,
`needle8k=PASS needle65k=PASS`). **Caveat:** three of the four build their prompt
framing by hand (22 ids where the shipped template renders 55, no system persona,
thinking off), which is why `</assistant>` leaks into their reported answers --
treat their agreement ratios and their `accepted 24/24` spec-phase number as
plumbing checks, not acceptance results. Laguna fp8 attention projections have
never been run free-running through the templated harness.

## 6. Defaults

fp8 attention on wgpu is opt-**out**, flipped on the §2 evidence: 16 controls at
100.0% agreement, perplexity ratio 1.000427, and an ALLOW from
`evaluate_default_flip_suite` (which could not return ALLOW at all until the
harness stopped passing `reference_quality: None` --
[`04.2-fp8-epilogue-mechanism.md`](04.2-fp8-epilogue-mechanism.md) §5). The
default is hardcoded in `ATTN_VARIANT_DEFAULT` (`gemma4_wgpu.rs`); changing it is
a source edit to that const, reviewed against the evidence recorded here.

| surface | backend | current default | note |
|---|---|---|---|
| attention projections (q/k/v/o) fp8 | wgpu | **on, hardcoded** (`ATTN_VARIANT_DEFAULT`: int8/128, all layers) | §2 evidence; other variants constructible via `set_attn_variant` |
| attention projections fp8 | cuda | **does not exist** outside Laguna (§5.1) | n/a |
| attention projections nvfp4 | cuda | opt-in, `NV_ATTN_PROJ_QUANT`, `ATTN_PROJ_QUANT_DEFAULT_ON = false` | a *different format*; the backends do not quantize attention projections the same way. Worth 6.4% on 31B serving ([`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md)) |
| KV cache fp8 | wgpu | **always on, not switchable** | `gemma4_wgpu.rs` composes `kv_fp8` unconditionally, so there is no bf16-KV arm on wgpu. It is present in *both* arms of every experiment above, so it is not implicated -- but "not implicated" is not "measured" |
| KV cache fp8 | cuda | opt-in, `NV_LAGUNA_FP8_KV` | **§5.2 is a real defect at long, low-margin context.** Encoding and granularity are byte-exact with wgpu (`parity_kv_fp8`, `parity_kv_fp8_paged`). Fix §5.3's nondeterminism first |
| attention projections fp8 | cuda (Laguna, `NV_LAGUNA_ATTN_FP8`) | opt-in | contract-compliant (§5.4); never measured free-running through the templated harness |

## 7. The cross-backend fp8 contract

### 7.1 Encoding -- identical on both backends, enforced

- Format is OCP **E4M3**: 1 sign, 4 exponent, 3 mantissa bits, exponent bias 7,
  subnormals present, **no infinities**, one NaN pattern per sign (`0x7f`,
  `0xff`).
- **Max finite magnitude is 448.0**, not 240.0. `240` is the E5M2-ish figure and
  must never appear in an E4M3 path.
- **Rounding is round-to-nearest-even** on the mantissa.
- **Overflow saturates** to `+/-448` (`0x7e` / `0xfe`). `+/-inf` saturates; it
  does **not** become NaN. NaN in maps to NaN out. `-0.0` keeps its sign
  (`0x80`). This is CUDA's
  `__nv_cvt_float_to_fp8(x, __NV_SATFINITE, __NV_E4M3)`.

Enforced in `fp8_contract_e4m3.rs` by
`e4m3_encoder_matches_an_independent_nearest_code_reference` (brute-force over
all 127 finite codes with ties to even, plus exact halfway points, +/-1 ulp
either side, subnormals, saturation and 20000 pseudo-random values),
`e4m3_saturation_and_nonfinite_contract` (the 11 boundary cases by name),
`wgsl_encoder_agrees_with_the_host_encoder_on_device` (WGSL on a real adapter,
amax pinned to 448 so only the encoder is under test),
`cuda_e4m3_cast_agrees_with_the_wgpu_host_encoder_byte_for_byte`, and
`weight_and_kv_fp8_paths_share_one_encoder_and_one_scale_convention`.

### 7.2 Scale convention -- one division, `448/amax`

```
scale     = amax / 448.0
inv_scale = 448.0 / amax        // NOT 1.0 / scale
```

`1.0f / (amax / 448.0f)` is two roundings and is **not** byte-equivalent;
`inverse_scale_must_be_448_over_amax_not_one_over_scale` measures how many
encoded bytes differ and asserts the count stays non-zero.

**All producers at HEAD comply** -- wgpu `kv_fp8` (host and WGSL), wgpu
`quant_gemv::quantize_rows_fp8`, CUDA `kv_fp8.cu`, and CUDA
`rowquant_e4m3_kernel` (`cuda/gemv_bf16.cu`, with an `isfinite` guard in the amax
reduction matching wgpu `row_amax`). `laguna_fp8_contract.rs` keeps it fixed
twice over: a static scan
(`cuda_quantizers_must_not_compute_inverse_scale_by_round_trip`) that fails if
any `.cu`/`.cuh` source reciprocates a rounded fp8 scale, and
`cuda_rowquant_e4m3_encodes_against_448_over_amax`, which distinguishes the two
forms byte-wise on device (`cuda_rowquant_e4m3_amax_ignores_non_finite` covers
the guard).

The `at HEAD` column above is prose and `present_at_head` inside
`fp8_scaling_granularity_matrix_across_backends` is a hand-written `bool` --
which is precisely how `rowquant_e4m3_kernel` stayed documented as "absent at

FP8_PRODUCER_AT_HEAD rowquant_e4m3_kernel = yes

**The contract:** attention-projection weight fp8 is **per-row** -- one fp32
scale per output row, amax over finite elements, `scale = amax/448`,
`inv = 448/amax`, shared E4M3 encoder semantics -- on both backends.
`cuda_rowquant_e4m3_matches_wgpu_quantize_rows_fp8_byte_for_byte` pins the two
paths **byte-for-byte on codes and bit-for-bit on scales** (12 binades of row
amax, an all-zero row, +/-inf poison, an exact-448 amax, `-0.0`), alongside the
KV-cache pins (`parity_kv_fp8`, `parity_kv_fp8_paged`).
`fp8_scaling_granularity_matrix_across_backends` fails if either side's
granularity drifts from the other, or if this section stops recording the
contract.

`nv_layers::linear::quantize_fp8_per_tensor` is **not** part of this contract: it
is the generic CUDA `Linear` surface, not an attention-projection path. It keeps
the §7.1/§7.2 encoding contract but its granularity is deliberately out of scope;
if it is ever used for attention projections it must first move onto the per-row
contract and into the parity test.

A per-group path exists on wgpu (`group` in `AttnQuant`, shipped default 128)
selecting `quant_gemv::gemv_fp8_group` / `_sg`, with `scales_per_row(k, group)`,
`group_shift(group)` and `GROUP_ALIGN = 16`. `quantize_rows_fp8` is unchanged and
`group == 0` still means per-row, so the markers above describe the default.
**Changing the wgpu granularity requires changing the
`WGPU_WEIGHT_FP8_GRANULARITY` line in the same commit** -- and, because the
contract is granularity-matched, a matching CUDA per-group path or an explicit
re-negotiation of the `ATTN_PROJ_WEIGHT_FP8_GRANULARITY` line and the parity test.

### 7.4 Granularity is not the lever

`granularity_is_measured_not_assumed_and_e4m3_is_nearly_scale_invariant` measures
per-group against per-row at the real Gemma4-31B `k` values, over four weight-row
distributions, group sizes 128/64/32/16 and a from-spec NVFP4 reference.
**Per-group fp8 buys little on rms_rel, usually near nothing** -- e4m3's relative
precision is scale-invariant across ~17 binades, so a row-wide amax costs almost
nothing unless elements underflow the subnormal floor (`amax·2^-9/448`), and on
real weights per-row e4m3 pushes only a tiny fraction of values into subnormal
codes. And **fp8 per-row is severalfold more accurate than NVFP4-gs16 in 12/12
cases**, so a format with severalfold lower weight-quantization error than the one
that *works* cannot be breaking this model through weight-quantization error. On
real weights (layer 30 `o_proj` [5376 x 8192], 256 sampled rows) finer grouping
moves rms(dW)/rms(W) only marginally from per-row to group=16 for more bytes, and
under templating per-row, group-32, group-128 and int8/row are behaviourally
indistinguishable. **Do not spend a round on per-group fp8 scaling.**

### 7.5 Where the error is, in logit terms

Both epilogues perturb logits by roughly the same amount -- mean logit `rms_rel`
0.3236 (shipped) vs 0.3697 (legacy), a 12% improvement, not a qualitative one.

> **fp8 attention projections on wgpu flip any decision whose bf16 top-2 margin
> is below roughly 2 logits.** Prompts whose steps are all decisive (median
> margin 15-18) come out token-exact. Prompts with genuine token-level
> uncertainty (median margin ~6) diverge within ~10 tokens and then write a
> different, equally valid answer.

Measured divergence-point margins across five independent chat-templated prompts:
**0.59-2.26**. That is the number to carry forward, not any single agreement
ratio.

## 8. The acceptance bar for a default flip

Encoded in `evaluate_default_flip()`. A change may become a default only if
**all** of the following hold, per backend and per model:

| requirement | constant | value | why this number |
|---|---|---|---|
| free-running window | `MIN_FREE_RUNNING_WINDOW` | 64 tokens | at 33 tokens a single late divergence leaves too few post-divergence samples to distinguish "cascaded" from "recovered"; 64 gives ~50 samples for a divergence in the first quarter and is short enough to run five model builds in one test |
| free-running argmax agreement | `MIN_FREE_RUNNING_AGREEMENT` | 90% | the bar the repo already applies to NVFP4 o_proj (`assert!(agree * 10 >= n_replay * 9)` in `gemma4_wgpu_quant.rs`), so a new format is held to the standard a shipped one meets |
| divergence shape | -- | not `CASCADED` | an arm that never re-aligns has no restoring force |
| perplexity ratio | `MAX_PERPLEXITY_RATIO` | 1.05 | roughly the noise floor between adjacent well-behaved quantization schemes; tighter than the argmax bar so distribution damage is caught before token damage |
| reference-token rank | `MAX_MEDIAN_REFERENCE_RANK` / `MAX_P95_REFERENCE_RANK` | median <= 2, p95 <= 8 | median 2 permits losing a genuine coin flip half the time; p95 8 permits occasional near-ties but rejects an arm where the reference token left the plausible set |
| measured speed | -- | must be an improvement | a quantization change that is not faster has no case |
| evidence completeness | -- | perplexity + rank must be supplied | `evaluate_default_flip` **DENIES** when only argmax agreement is provided |

Shape classification: `IDENTICAL`; `RECOVERED` (there is an index after the first
divergence where the next `RESYNC_RUN = 4` tokens all match and post-divergence
agreement is >= `RECOVERY_RATE = 50%`); `CASCADED` otherwise
(`harness_distinguishes_a_benign_near_tie_from_a_cascade` pins it).
Free-running agreement plus divergence shape is the load-bearing clause;
perplexity and rank catch a *different* failure mode -- distribution damage with
no token damage (`default_flip_gate_denies_on_perplexity_even_when_argmax_agrees`
proves the gate rejects 100% argmax agreement at a 1.49x perplexity ratio). **A
metric evaluated only on the reference trajectory cannot see anything off it**,
so it must not substitute for the free-running clause. The gate must run **on
real weights**, on the backend whose default is changing;
`harness_binds_to_gemma4_wgpu_and_separates_the_two_metrics` says so in its own
output.

## 9. What is still not measured

- Context beyond ~130 tokens total (max_seq 256, 96-step window, ~30-token
  prompts) -- **the regime fp8 exists for is unmeasured.**
- Tool-message and `enable_thinking=true` framings.
- The CUDA bf16-KV nondeterminism mechanism: characterised (§5.3), not
  root-caused.
- Whether the CUDA fp8-KV blow-up is length- or prompt-triggered (§5.2).
- A stage decomposition of the shipped fp8 path (§4).
- Batch > 1, spec-decode, and multimodal with fp8 attention.
- A wgpu bf16-KV arm: wgpu KV fp8 is unconditional, so it has never been A/B'd.
- CUDA-side free-running quality for `NV_LAGUNA_ATTN_FP8` (§5.4).
