# Continual LoRA: trajectories in, adapters out

The serving loop can feed its own fine-tuning: every completed chat generation
is capturable as a training row, `/v1/fine_tuning/jobs` turns rows into a PEFT
adapter with an optional held-out eval, and a trained adapter becomes servable
without a restart. Adapter serving stays one full engine
per adapter ([`06.5-lora-design.md`](06.5-lora-design.md) §12) on two wgpu
graphs: `gemma4_e4b_wgpu` (full coverage) and `qwen3_5_dense_wgpu` (decode and
chunked-prefill sites; an adapter-bearing qwen engine verifies by m=1 stepping
because the verify and mtp graphs carry no lora sites).

## Trajectory capture

`NV_TRAJECTORY_DIR` arms it; unset means zero capture and zero cost. Every
generation on `/v1/chat/completions` and `/v1/messages` (streaming and not)
that reached its terminal `Done` event appends one JSON line to
`$NV_TRAJECTORY_DIR/trajectories.jsonl`:

```json
{"ts": 0, "endpoint": "chat|messages", "id": "...", "model": "...",
 "prompt": "...", "completion": "...", "reasoning": null,
 "finish_reason": "...", "stopped_by": null, "multimodal": false,
 "label": null, "prompt_tokens": 0, "completion_tokens": 0,
 "seed": 0, "temperature": null}
```

- `prompt` is the rendered template output the engine consumed and
  `completion` is the accumulated `TextDelta` stream, captured before
  thinking-split and tool-call parsing. For engines whose thinking survives in
  the text stream (gemma think markers, split server-side after capture) the
  pair is the model's own continuation; engines that emit reasoning as a
  separate `ReasoningDelta` stream (harmony-channel models) get it captured in
  `reasoning`, and such rows are not a faithful prompt→completion
  continuation — the consolidation script drops them unless told otherwise.
  Special tokens are stripped by serving on every engine, so `completion`
  never carries the terminal end-of-turn token.
- `finish_reason` is the raw engine value at every capture site, streaming
  or not — tool-call parsing happens after capture, so a tool-call generation
  logs its engine finish, with the wire markup intact in `completion`.
- A generation whose event stream ends without `Done` (engine death, dropped
  channel) appends nothing, and a stream the client abandons mid-delivery
  appends nothing: partial generations are not training data. `stopped_by`
  records a matched custom stop sequence; `multimodal` marks prompts whose
  media was extracted and is absent from the text.
- `label` echoes the request header `x-trajectory-label` (trimmed, empty means
  absent) so clients can tag conversations as training material —
  `label: bad` rows never train. `tag` echoes `x-trajectory-tag`, a
  client-chosen correlation id: proxies (LiteLLM) rewrite response ids but
  forward `x-*` headers for allowlisted model groups
  (`litellm_settings.model_group_settings.forward_client_headers_to_llm_api`;
  the bare `litellm_settings` flag is a no-op in LiteLLM 1.89.0 and the
  `general_settings` form forwards to every upstream, external routes
  included), so the tag is the join key that survives the proxy chain.
- Retro-labeling: `POST /v1/trajectory/label` `{"id"? , "tag"?, "label"}`
  (at least one of id/tag) appends to a daily `labels-YYYYMMDD.jsonl` beside
  the trajectory files — same dir, same retention. The reply reports both
  facts a relayer needs: `recorded` (the label row landed) and `matched`
  (some retained trajectory record actually carries that id or tag —
  `label_target_exists_in_retained_trajectories` streams the daily files
  line by line — exact field equality, never a substring hit in prompt text,
  never a whole-file read into memory). A label that joins
  nothing still records — the thumb never fails — but `matched: false` lets
  the caller report honestly instead of claiming a join that never happened;
  garden's feedback route surfaces it as `relayed: false`. Consolidation
  joins the patches by id or tag, last write wins over the request-time
  header. This is what the portal's 👍/👎 thumbs feed: the portal stamps
  every upstream call with a fresh tag, surfaces it on the final bubble and
  again on history replays (the tag persists with the room's `final`
  trajectory event), and a thumb posts the label here. Spoken turns join the
  same way: the realtime server stamps every conversation LLM call with the
  `resp_*` id it emits on the wire (the eager-predicted call included — a
  promoted response keeps its predicted id as the wire id, per
  `promoted_turn_wire_id` in `realtime/pipeline.rs`), so any realtime
  consumer can
  label a turn by the response id it already saw in frames. A rolled-back
  speculation leaves its eager record unlabeled: the fallback re-calls the
  LLM under a fresh wire id and tags that call with it, so the label still
  joins the record of the text actually spoken. The eager call's prompt is
  real user text — the speculative LLM opens only after the speculative STT
  transcript lands (`spawn_predicted_llm_after_stt`), never on a
  placeholder. A voice handler
  sitting behind a LiteLLM external route (garden's) adopts the forwarded
  tag instead of minting its own — but only for callers that prove
  themselves, since the route is otherwise open and an adopted tag is a
  join onto someone's trajectory. Two proofs work: the relay bearer LiteLLM
  presents as the route's configured api key (LiteLLM forwards only `x-*`
  client headers and replaces `Authorization`, so this is the only proof
  that survives the production hop; the fleet wires the intranet bearer on
  both sides), or a gateway device token for direct callers. Adoption
  carries the join through that hop and onto the trajectory records the
  handler's own LLM calls produce; the handler's host also needs the voice
  model group on LiteLLM's forward allowlist, or the tag dies before
  arriving.
  400 when capture is disabled; the fleet nginx routes
  `/v1/trajectory/` straight to speaches so the POST never hits LiteLLM.
- Appends run on the blocking pool, serialized in-process; a failed append
  warns and drops the record — generation never fails over logging. Rotation
  is the deployment's tmpfiles age rule; the file only grows otherwise.
- Writer: `oapi::trajectory` (`TrajectoryRecord`, `append`,
  `label_from_headers`). Capture points: `oapi::chat::{run_non_streaming,
  run_streaming}` and `oapi::messages::{run_non_streaming, run_streaming}`.

## Runtime adapter load/unload

`NV_ALLOW_RUNTIME_LORA_UPDATING` (truthy) mounts two routes on the chat
router, mirroring vLLM's `VLLM_ALLOW_RUNTIME_LORA_UPDATING` gate and the §8
interface quirks:

- `POST /v1/load_lora_adapter` `{"lora_name", "lora_path", "load_inplace"?}` —
  probes the PEFT dir, resolves the base via `base_model_name_or_path` against
  the boot-loaded wgpu bases (`wgpu_base_dirs`), builds a full
  `WgpuChatEngine::load_with_lora` engine off the request thread, and inserts
  it into the live `ChatRegistry`. Success is vLLM's bare string, not JSON:
  `Success: LoRA adapter '<name>' added successfully.` A name that matches a
  loaded base model is refused with 400 under every flag — `load_inplace`
  replaces only an existing adapter. Bad name, bad path, unresolvable base,
  and a body missing `lora_name`/`lora_path` are 400s (the handlers parse the
  body themselves for vLLM's 400, where axum's extractor would 422); an engine
  build failure is a 500 (vLLM routes its rank-cap `ValueError` the same way).
- `POST /v1/unload_lora_adapter` `{"lora_name"}` — removes the engine and
  tombstones the catalog row. Unknown name 404s, a base-model name or the
  default engine 400s, success is the bare `removed successfully.` string.
  Unloading frees the engine when the last in-flight request drops its `Arc`.
- `GET /v1/adapters` — mounts unconditionally, because the flag gates
  updating, not reading: one row per catalog adapter with `id`, `base_model`,
  `path`, `rank`/`alpha`/`scaling`/`target_modules`, a `status` of `loaded`
  (an engine is resident under the id) or `available`, and `loaded_at` (unix
  seconds for runtime loads; boot-discovered adapters report null).

Reloading after a new fine-tune round is `load_lora_adapter` with the same
`lora_name` and `load_inplace: true`: the handler rebuilds a fresh engine from
the bytes on disk and the registry insert swaps it atomically under the
`RwLock` — a request that resolved before the swap finishes on the engine it
started with, a request after sees only the new one, never a mix, and the
rotated KV tag (below) keeps a stale snapshot from resuming onto the new
weights. Lifecycle coverage is the two wgpu graphs with LoRA sites,
gemma4-e4b and qwen3.8-dense (`check_lora_target_kind` refuses the rest), and
on CUDA the Flash-Next engine (next section); other CUDA families load a
whole engine per adapter (`CudaLoraAdapterEngine`). No suite in the tree covers
restoration, swap coherence, tag rotation, loader freshness or wrong-shape
refusal on the wgpu graphs.

### Flash-Next on CUDA: hot-swap through pinned host RAM

With a qwen4_exp engine resident, `load_lora_adapter` does not build an
engine: it hands the directory to the engine's
`Qwen4ExpAdapterRegistry` (`nv-specdecode/src/qwen4_exp_adapters.rs`,
`HOT_SWAP_STAGES_IN_PINNED_HOST_RAM_VALIDATES_THERE_UPLOADS_ON_A_COPY_STREAM_THEN_SWAPS_ONE_POINTER`),
which keeps one live version per adapter id on the resident weights. A load:

1. reads `adapter_config.json`, `adapter_model.safetensors` and, for an
   expert adapter, `expert_lora.{json,safetensors}` into pinned host buffers;
   the version is a content hash of those bytes;
2. validates there, before the device is touched: every module is a
   qwen4_exp target with the linear's shapes at the config's rank, the
   declared `expert_lora` form matches `expert_lora.json`, the expert tensors
   match the form, rank and model shape, and the adapter's `base_identity`
   equals the engine's (`expert::base_identity_for_dir` of the served
   checkpoint);
3. checks free VRAM for about three times the adapter's bf16 bytes above the
   engine's floor (`NV_COLD_TIER_CHAT_MIN_FREE_GIB`);
4. uploads on a copy stream and builds the serving hooks;
5. swaps the id's live version in one map insert.

Any failure before the swap leaves the live version serving and answers 400.
A request resolves the id's version once, at its start, and holds its `Arc`
until it ends: a swap mid-stream never changes a running request, the next
request runs the new version, and the old version's device memory frees when
its last request drops. Requests to one engine run under its permit, so only
one version is attached at a time. The replaced or unloaded version's host
copy stays parked in pinned host RAM up to `NV_Q4EXP_LORA_HOST_PARK_GIB`
(default 1 GiB, oldest evicted first); loading the same directory again
restores it from there without reading the disk — the rollback path. Pinned
allocations never fall back to pageable memory: a load that cannot pin is
refused, and a boot adapter that cannot pin stops the server.

Caches: an adapter request takes a k=0 session tagged `id@version`
(`Qwen4Exp::take_adapter_session`). `put_session` drops any tagged session
(`ADAPTER_SESSIONS_NEVER_ENTER_THE_BASE_SESSION_CACHE_OR_ITS_RESIDENCY_TIERS`),
so the base's session cache, disk snapshots and MTP speculation never see
adapter KV. With `NV_Q4EXP_LORA_SESSION_CACHE=1` the engine keeps one adapter
session for prefix reuse, and reuses it only under the identical tag, so KV
made under version N never serves N+1.

`/metrics` reports `speaches_q4exp_lora_adapter_device_bytes` and
`speaches_q4exp_lora_adapter_in_flight_requests` per live `adapter`/`version`,
`speaches_q4exp_lora_host_parked_bytes`, and
`speaches_pinned_host_bytes_live`. `unload_lora_adapter` removes the id from
the chat registry and the adapter registry; its VRAM returns when in-flight
requests finish.

The NixOS option `modules.services.ai-llm-voice.cudaLora.adapters` is the
boot-time set and `cudaLora.hostParkGiB` the park budget. Runtime loads change
only the live process; a restart serves the option's set again.

The nightly loop's adapter reaches users in three steps, none of which is a
`colmena apply`:

1. the review gate approves the night's adapter (a store path written by
   `nv-train-nvfp4 lora --store-gcroot`);
2. `nix copy --to ssh://<serving host> <adapter store path>`;
3. `POST /v1/load_lora_adapter {"lora_name": "<id>", "lora_path": "<store
   path>", "load_inplace": true}` on the serving host swaps it in; a bad
   version is rolled back by loading the previous store path, still parked.

Updating `cudaLora.adapters` later makes the approved version the boot
default; until then a restart serves the previous boot set.

`ChatRegistry` carries interior mutability for this: every clone shares one
`RwLock`'d map, so an insert is visible to the router state cloned at boot.
`remove` refuses the default engine, and the `NV_CHAT_ALLOW_UNKNOWN_MODEL`
single-engine fallback reads the boot engine count, so loading and
unloading adapters never flips that behavior. `/v1/internal/chat-engines`
reads the live registry. Adapter residency is still invisible to the admission
gate (§11), so each loaded adapter costs a full base-weight copy of headroom
the KV budget cannot see.

Persistence across restarts: a fine-tuning job stamps its `fine_tuned_model`
id into the adapter's `adapter_config.json` as `nv_adapter_id`, and
`probe_adapter` prefers that stamp over the directory name — so a bare adapter
dir listed in `NV_LORA_ADAPTER_DIRS` reboots under the same `ft:` id clients
already pin (`name=path` specs cannot carry the id: the spec list splits on
`:`). KV disk snapshots key the adapter by a tag that folds in the weights
file's length and an xxh3 digest of its bytes
(`persist::adapter_tag_that_changes_when_the_weights_change`), so overwriting
adapter weights in place can never resume a stale snapshot, while identical
bytes keep their tag and a bare restart keeps its warm snapshot. The tag
hashes bytes rather than trusting mtime because consecutive fine-tune rounds
rewrite the same byte length within one mtime second.

`POST /v1/fine_tuning/jobs` composes with the gate: when runtime updating is
enabled, a succeeded job hot-loads its own adapter before registering it, and
reports `metrics.hot_loaded`. The request also takes `validation_data` /
`validation_file`; the job then reports `metrics.eval_loss_adapter` and
`metrics.eval_loss_base` — held-out cross-entropy with the adapter attached
and detached — which is the roll-over gate's input.

The job dispatches on the base checkpoint's `config.json`
(`fine_tuning::trainer_family_for_base`, which shares one
architectures/model_type tag walk — `oapi::model_family_tags` — with
`classify_wgpu_model`, so the trainer router and the wgpu serving classifier
cannot drift apart): a qwen3_5-dense config — qwen3.5-dense and
qwen3.8-dense share it — trains through `nv_train::qwen38::run_jsonl`, the
windowed trainer over the top `grad_layers` layers with the frozen prefix
streamed once (quantized-resident when the base holds a quantized linear on
CUDA, host-dequantizing otherwise); every other base trains through
`nv_models::train_runner::run` unchanged. Both arms consume the same jsonl
rows (`nv_train::load_jsonl_token_dataset`), honor `validation_data` /
`validation_file`, report the two eval losses under the same metric keys —
`metrics.trainer` names the arm — and share the whole job lifecycle: the
non-finite-gradient gate (both trainers surface `all_grads_finite` from a
device-side per-gradient sum, and a false fails the job before registration or
hot-load), the dead-module check, the `nv_adapter_id` stamp, catalog
registration and hot-load. On a qwen base the default `hyperparameters.target` is the qwen
trainer's own set (`Q38TrainArgs::default_targets`: q/k/v/o, gate/up/down,
`in_proj_qkv`, `in_proj_z`, `out_proj`), every one of which
`qwen3_5_dense_wgpu` serves through its decode and prefill LoRA sites. The
only servable leaves outside the defaults are the fused ab gemv halves
(`in_proj_a`, `in_proj_b`) — the trainer's projection table has no attach
point for them, so an adapter carrying them serves but cannot be produced by
this endpoint.

## The loop

`scripts/consolidate_trajectories.py` drives one consolidation round:

1. Filter: teacher pin (`--model`, required — rows from other models,
   `ft:*` adapters included, never train), raw-finish `stop` only, no
   stop-sequence truncation, no multimodal, no reasoning-split rows, no
   `label: bad` (with `--require-label`, only `label: good`), min length,
   sha-dedupe, newest-N cap.
2. Judge (optional, `--judge-model`): a served model scores each row 1–10;
   rows under `--judge-threshold` drop.
3. Train: `/v1/fine_tuning/jobs?wait=true` with a `--holdout-frac` split
   sent as `validation_data`.
4. Gate: the roll-over is refused (exit 2) unless held-out adapter loss
   beats base loss by `--gate-margin`; a refused adapter stays loaded for
   inspection and nothing is unloaded.
5. Roll: on a passed gate, every older `ft:*:<suffix>:*` adapter is
   unloaded, leaving exactly one rolling adapter; ids stay versioned, so KV
   caches never see the same name with different weights. Adapter dirs on disk
   are the rollback artifacts — reload one with `/v1/load_lora_adapter`.

Serving the adapter is opt-in per request by `model` id, so a bad round is a
no-op for every client that keeps naming the base model.

**An adapter distills whatever the log contains, including behavior nobody
wants locked in.** Consolidating trajectories moves failure modes from context
into weights, where a bad habit survives every new conversation. The teacher
pin, the judge, the label channel, and the held-out gate are the defenses;
never weaken all four at once, and never train on trajectories a client could
have poisoned unfiltered.

## Continue a Laguna adapter with new SFT

`POST /v1/fine_tuning/jobs` accepts `input_adapter`, a local PEFT adapter
folder containing `adapter_config.json` and `adapter_model.safetensors`.
This field is supported only for Laguna. Omit it to initialize a fresh adapter.

Keep `model` pointed at the original frozen base checkpoint. Supply the new SFT
through `training_file` or `training_data`, and use a separate `output_dir`.
Set `hyperparameters.rank`, `alpha` and `target` to match the input adapter;
ordinary fresh-job defaults still apply when these values are omitted.
The trainer rejects incompatible base identity, rank, scaling, tensor shapes,
module sets, non-finite weights and unsupported PEFT variants.

Continuation loads the existing A/B weights and creates a fresh AdamW optimizer.
It does not restore optimizer moments or an interrupted job's step position.
The input adapter remains unchanged. Mix retained good examples into the new SFT
and evaluate on untouched held-out work orders before promoting the output.

```json
{
  "model": "/models/laguna-base",
  "input_adapter": "/adapters/laguna-round-1",
  "training_file": "/data/round-2.jsonl",
  "validation_file": "/data/held-out.jsonl",
  "output_dir": "/adapters/laguna-round-2",
  "hyperparameters": {
    "rank": 8,
    "alpha": 16,
    "target": ["q", "k", "v", "o", "g"],
    "steps": 12,
    "learning_rate": 0.0001
  }
}
```
