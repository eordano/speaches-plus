# 08.5 Measurement lines

Every performance instrument emits one canonical machine-parseable line per
measurement, built with `nv_config::measure::Measurement` and read back with
`Measurement::parse`. The format is `NV-MEASURE v1` followed by `key=value`
fields (values with spaces are double-quoted, `\"` `\\` `\n` escaped). The
exact shape is pinned by `golden_line_is_stable_because_downstream_greps_pin_it`
in `nv-config/src/measure.rs`.

```
NV-MEASURE v1 instrument=ctx-scaling model=unsloth/Qwen3.8-27B-NVFP4@e850c69 backend=wgpu device="NVIDIA GeForce RTX 5090 (Vulkan)" batch=1 tokens=8192 steps=64 warmup=200 value=21.7 unit=ms/tok basis=eager_dense_wgpu_decode_step_synthetic_state_fill fill_s=3.1
```

## Required basis fields

`instrument model backend device batch tokens steps warmup value unit` are
mandatory; `parse` rejects a line missing any of them. Each exists because a
published comparison has failed on exactly that axis: slab-vs-slotshared KV
(`basis` extra), end-to-end-vs-per-gemm timing (`instrument` + `unit`), and
max_seq-vs-depth knee confusion (`tokens` is always the primed KV depth /
token count of THIS run, never a capacity). `model` is `owner/repo@rev`; derive it from the hub snapshot dir the
instrument already resolves (the checkpoint label helpers each real-weight
test uses). Anything else —
`prime=chunked`, `ring=`, `tok_s=` — goes in `extras`; extras cannot shadow a
basis key.

Perplexity lines additionally require `corpus=` in extras, and the pinned
corpus for the qwen3.8 scoreboard is `pg1342`: a ppl on `wiki.txt` reads far
above the same checkpoint on `pg1342` (current numbers: the private run ledger),
so a corpus-less ppl comparison manufactures a regression out of nothing. Cross-corpus deltas are never
comparable; a ppl claim is same-corpus, same-process A/B or it is not a claim.

## An arm names the effective configuration, not the environment

The arm is the set of knobs a measurement ran under, and it is named by the
**resolved value of every gate**, never by enumerating which environment
variables happen to be set. Building the label from `std::env::var` is correct
only while every gate defaults off, and it silently becomes a lie the moment one
defaults on: a run with no environment then prints `arm=zero-env` while
executing a fully armed path. Read the gate accessors — the same functions the
kernel launcher reads — and label from those.

This matters beyond tidiness, because the failure is **retroactive**. Two lines
carrying the identical `arm=` string, taken either side of a default flip, name
two different computations, and nothing in either line distinguishes them. So a
label built from environment presence makes every historical cell ambiguous the
first time a default moves. Where a stored line predates a flip, it is
interpretable only against the commit it was measured at; that is a reason to
name arms by effective configuration from the start, not a workflow to adopt
afterwards.

The same rule applies to a constant that encodes a tuned value in its name. A
number appearing in two constants is not one fact — `SPLITS` 47 in a shared
array's bound and 47 in a family's depth-gate rung are unrelated, and reading
them as the same value invents a defect or, worse, dismisses a real one.

## When to measure

- Release profile under the exclusive GPU flock: `nvk.sh probe`, never `test`,
  never two probes at once, never with a serving process on the card.
- A/B arms run interleaved in the same process, same warmed state; a number
  from two separate runs is a load-order measurement, not an A/B.
- **A gate latched in a `OnceLock` cannot be A/B'd this way at all**, because
  the first read fixes it for the life of the process. Interleaving is not
  merely inconvenient there, it is unsatisfiable, and a cross-process pair is
  then forced rather than sloppy. The substitute that carries the same weight
  is ABBA ordering within one lock session plus a **true null** — an arm
  spelled explicitly but resolving to the same code path as the default, which
  bounds the cross-process spread directly. Report that spread: a pair whose
  arms differ by less than it has measured nothing. Prefer a gate shape that
  can be A/B'd over one that cannot.
- Run the null control first: A-vs-A paired delta bounds the noise floor, and
  a claimed win smaller than that floor is noise.
- Warm to plateau, then report the median of the timed steps; `steps` and
  `warmup` in the line are the counts actually used.

## What a reader owes the line

A number quoted anywhere without its canonical line (or the full basis tuple
it encodes) is not a number — the basis-tuple quoting rule (numbers live in the private run ledger) governs quoting. Compare
two lines only when every basis field except the one under test matches.

## Legacy lines

Converted instruments emit the canonical line alongside their legacy line
(`CTX-SCALING ...`, `PP ...`) for one release, because existing greps and logs
pin the legacy shape; the legacy line goes away after that release. New
instruments emit only the canonical line.
