# KV disk persistence: warm tokens that survive a restart (wgpu)

The wgpu chat engine's single-entry prefix cache (`PrefixCache` in
`rust/src/oapi/chat_engine_wgpu.rs`, opt-in via `NV_WGPU_PREFIX_REUSE=1`) dies
with the process. This layer writes it — token stream, KV frontier, and the
decoder's full mutable device state — to disk and restores it at engine startup.
`05.9-prefix-cache-scope.md` states when reuse is legal at all; **nothing here
widens it.**

## Scope

Every wgpu decoder, through the `KvDisk` trait
(`rust/src/oapi/chat_engine_wgpu/persist.rs`), in one of two shapes: **KV-quad**
(gemma4-e4b, gemma4-dense) does per-layer download and upload of
`k_fp8`/`v_fp8`/`k_scales`/`v_scales` (`kv_cache_snapshot`, `kv_cache_restore`,
`restore_pos` in `nv-models`); **state-registry** (gemma4-moe, qwen3.5-moe,
qwen3.5-dense, gpt-oss, laguna) relies on each decoder's `reset()` being exactly
`pos = 0` plus zeroing its `state_buffers` list, so that registry is the complete
mutable state and `impl_wgpu_state_snapshot`
(`nv-models/src/wgpu_state_snapshot.rs`) moves it blob-for-blob. **A reset that
clears state outside the registry breaks this layer's completeness assumption
along with its own reset.**

A restored `RewindLimits::NONE` decoder serves exact extensions only: a prompt
whose tokens run through the saved frontier continues from it; any divergence
starts cold. That is what saving them is for — a pre-cached conversation state is
a known point a client builds on top of.

Snapshots cover the FULL buffer set but store only each buffer's **nonzero
prefix** (`nonzero_prefix_words`): a fresh engine's buffers are zeroed, so
uploading the prefix into them reproduces the state byte-for-byte, and disk cost
scales with live context instead of `max_seq`. This needs no slot or ring
arithmetic — whatever bytes are nonzero get stored, including stale bytes a rewind
left beyond the frontier (a size cost, never a correctness one). Fold-state
buffers are fixed-size regardless of context. Restore is unconditional;
consumption still passes the `NV_WGPU_PREFIX_REUSE` gate and the admission logic,
so with reuse off the restored frontier is reset away by the first request.

## Knobs and constants (`chat_engine_wgpu/persist.rs`)

- `NV_KV_CACHE_DIR` (`KV_CACHE_DIR_ENV`) — snapshot directory; unset (the
  default) disables the subsystem. One file per model id:
  `<sanitized-model-id>.nvkv`.
- `SAVE_DEBOUNCE` (5 s) — a snapshot is written after a request only if the last
  write is older than this and the prefix fingerprint changed; engine drop writes
  synchronously. The GPU download runs on the worker thread; serialization and the
  disk write run on a writer thread joined before the next save. **A failed async
  write is not retried until the fingerprint changes.**
- `HEADER_MAX` (4 MiB) — cap on the header a restore will buffer. The payload is
  read only after its declared length matches the live model's geometry, so a
  hostile file cannot make the server allocate more than one true state set.
- `SNAPSHOT_MAGIC` (`NVKVSNP2`) — bump when the format changes; older files are
  rejected and the engine starts cold.

## Validation: every mismatch starts cold, nothing crashes

File layout: magic, u32 header length, JSON header, raw little-endian payload. The
header carries model id, decoder kind label, LoRA adapter path, `max_seq`,
`prefill_chunk`, `sliding_window` (state-registry decoders stamp the last two 0 —
their geometry check is the per-blob length list), frontier, the token stream
(prompt plus emitted ids; a spec/chain run that commits past the emitted stream
saves a frontier restore rejects), per-chunk `(total, stored)` word counts, and
xxh3 hashes of the token stream and the payload. **Every field — including the
exact file length — is checked against the live engine before any GPU write, and
the payload hash is verified before any byte is uploaded.** Restore reads through
an `mmap`, so a warm file restores from page cache and no payload-sized allocation
ever exists — host memory peaks at one layer. Writes stream through a `BufWriter`
(one snapshot copy in memory, `fsync` before rename) into an `O_EXCL`-created,
pid+nonce-named `.tmp`, so a crash mid-save leaves the previous snapshot intact
and a planted symlink cannot redirect the write. Any rejection is a `warn` log and
a cold start.

**The xxh3 hashes detect corruption, not tampering — they are not a MAC.**
`NV_KV_CACHE_DIR` must be private to the server user: anyone who can write it can
forge a snapshot and poison the state later requests decode against.

The gate is the suite covering restore byte-identity and corrupt-file rejection
(`rust/tests/wgpu_prefix_reuse_ab.rs`,
`a_restored_kv_snapshot_serves_the_completion_a_cold_prefill_serves`):
`#[ignore]`, run by name with `NVK_FEATURES=cuda,wgpu`, `NV_WGPU_SERVE_TEST=1` and
a cached checkpoint. `01.4-STATUS.md` carries its run record.

## Stored responses: what `previous_response_id` does to this layer

`06-serving-surface.md` owns `/v1/responses`. What it adds here: with
`NV_KV_CACHE_DIR` set, `store` (default on) writes `<id>.nvkv` beside the
conversation sidecar via `ChatGenerateRequest.kv_store`, and
`previous_response_id` re-renders the stored conversation plus the new input and
passes `kv_resume`. The wgpu worker skips the restore when its live state already
sits at the stored frontier, otherwise it `reset()`s and uploads the snapshot --
**reset first, because a truncated snapshot is only byte-identical landing in
zeroed buffers.** Divergence, missing files, or a mismatched model serve cold (or
400/404 at the API edge), the store keeps the newest
`RESPONSE_STORE_KEEPS_NEWEST` snapshots, sidecars without snapshots still resume
just cold, and **instructions are per-request, not inherited** -- resending
identical instructions is what keeps a resume warm.
`usage.input_tokens_details.cached_tokens` is the honest hit signal.

The CPU gate is `rust/tests/responses_http.rs` (7 tests: shape, store→resume
re-render, GET/DELETE, unknown-id 404, streaming event sequence, tools 400, no-dir
404). The warm-resume gate is the same suite's
`a_resumed_response_serves_warm_after_the_live_state_diverged` (`#[ignore]`,
`NV_WGPU_SERVE_TEST=1` + `NV_WGPU_SERVE_DIR`): it stores, diverges the live state,
resumes by id, and requires warm cached tokens plus byte-identity with the
sequential continuation.

## Reporting

When a request is served off a reused prefix (restored or in-memory), the engine
emits `ChatEvent::PromptCached { cached_tokens }` immediately before `Started` —
**the order is a contract**: `/v1/messages` streaming reads both before emitting
`message_start`. `/v1/chat/completions` surfaces it as
`usage.prompt_tokens_details.cached_tokens`, `/v1/messages` as
`usage.cache_read_input_tokens` (`cache_creation_input_tokens` stays 0 —
maintaining the cache costs nothing extra). Both are absent or zero when nothing
was reused.
