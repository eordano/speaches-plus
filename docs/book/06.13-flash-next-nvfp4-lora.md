# Flash-Next NVFP4-native LoRA — train against the served forward, serve unmerged

Qwen3.8-Flash-Next (`qwen4_exp`) fine-tunes as LoRA over its served
weights: the routed experts stay in their checkpoint NVFP4 bytes (e2m1 values,
stored E4M3 block scales, `weight_scale_2`), the side projections in the fp8
rows the engine quantizes at load, and nothing is ever merged or requantized.
The adapter is served by the same CUDA engine as hooks on the resident
weights, so the served base stays byte-identical and the adapter applies the
way it was trained.

## What trains

Linear targets are the projections every serving path runs through
`nv_layers::Linear::forward`: full-attention `self_attn.{q,k,v,o}_proj` and
`mlp.shared_expert.{gate,up,down}_proj`
(`DEFAULT_TARGETS` in `nv-models/src/qwen4_exp_lora.rs`,
`LINEAR_TARGETS_ARE_THE_BF16_CHECKPOINT_PROJECTIONS_AND_THE_ROUTED_EXPERTS_ADAPT_THROUGH_THE_MOE_LAYER_EXPERT_HOOK`).

- Routed experts adapt through the MoE layer's expert hook, not a Linear
  (see *Routed-expert LoRA* below).
- GDN projections are not targets
  (`GDN_PROJECTIONS_ARE_NOT_TARGETS_BECAUSE_THE_FUSED_DECODE_KERNELS_READ_THEIR_WEIGHTS_DIRECTLY`).
- MoE routing is frozen: the router is a frozen Linear whose gradient still
  flows to its input.
- Only the top `window` layers train. The window may not reach a PLE layer;
  it is clamped to the deepest layers above it.

## Routed-expert LoRA

The routed experts run as one grouped NVFP4 GEMM with no per-expert Linear,
so they carry their own adapter: `expert::ExpertLoraLayer`
(`nv-models/src/qwen4_exp_expert_lora.rs`), attached to `MoeLayer` and
selected with `--expert-lora`. It adapts each routed expert's down projection
on its bf16 activation
(`EXPERT_LORA_ADAPTS_THE_ROUTED_DOWN_PROJECTION_ON_THE_BF16_ACTIVATION_SO_THE_NVFP4_GROUPED_GEMMS_STAY_BIT_IDENTICAL`):

    y_t = grouped_nvfp4(x_t) + shared(x_t) + s * sum_k w_tk B_e A_e act_e(x_t)

where `act_e = silu(gate_e x) * (up_e x)` comes from the served W4A4 grouped
gate/up GEMM before its NVFP4 requantization, `w_tk` are the router's
normalized top-k weights, and the delta is accumulated in f32 beside the
untouched grouped output. A zero adapter therefore reproduces the served
forward bitwise, at every row count. The routed slots are sorted by expert
into 16-row tiles, so the batched matmuls see one A or B per tile.

Forms (A is `[E_A, r, 640]`, B is `[E_B, 2560, r]`):

| form | A | B | params per layer at rank r (Flash-Next: E = 512) |
|---|---|---|---|
| `per-expert` | per expert | per expert | r(512·640 + 512·2560) = 1,638,400·r |
| `expert-a` | per expert | shared | r(512·640 + 2560) = 330,240·r |
| `hydra` | shared | per expert | r(640 + 512·2560) = 1,311,360·r |
| `shared` | shared | shared | r(640 + 2560) = 3,200·r |
| `none` | | | 0 |

The default is `expert-a` at rank 16 over the 6-layer window
(`EXPERT_LORA_DEFAULT_FORM_EXPERT_A_RANK_16_OVER_THE_WINDOW_COSTS_0_47_GIB_OF_FP32_ADAM_STATE_ON_REAL_FLASH_NEXT`):
31.7M parameters, 16 bytes each with fp32 Adam state, 0.47 GiB, plus a
transient per-layer twin graph of a few hundred MiB at 2048 tokens. Each
expert keeps its own A over its 640-wide activation (the expressive, cheap
side) and the layer shares the 2560-wide B. `per-expert` costs five times as
much (2.34 GiB at rank 16, 1.17 GiB at rank 8) plus per-tile B gathers of
about 1.5 GB at 2048 tokens; it fits the reference GPU host beside six resident expert stacks
only at rank 8, and at rank 16 only with the stacks handed over through
pinned host RAM (below). `shared` is a single low-rank map applied to the
router-weighted sum of activations and serves as the cheap control.

The trainer recomputes the activation twice in the twin: through the served
W4A4 grouped gate/up for its value and through Marlin W4A16
(`MoeExpertsMarlinActRowsOp`) for its gradient
(`THE_TWIN_EXPERT_ACTIVATION_TAKES_THE_SERVED_W4A4_VALUES_AND_THE_MARLIN_W4A16_GRADIENT`).
dX flows through both the base Marlin path and the LoRA path, and through the
router softmax via the LoRA delta's dependence on `w_tk`. The router itself is
frozen.

Decode with an expert adapter attached runs eagerly
(`EXPERT_LORA_DECODE_RUNS_EAGER_BECAUSE_ITS_ROUTED_ROWS_ARE_PLANNED_ON_THE_HOST`):
the delta plans its tiles on the host and recomputes the gate/up rows through
the prefill dispatch, which a CUDA graph cannot capture.
Requests without an adapter, and adapters with linear targets only, keep the
captured graph; base requests keep MTP speculation.

## How a step runs

`Qwen4ExpLoraTrainer::step`
(`THE_LOSS_IS_THE_ENGINE_FORWARD_AND_THE_GRADIENT_IS_A_PER_LAYER_TWIN_EVALUATED_AT_THE_ENGINE_ACTIVATIONS`):

1. **Frozen prefix.** `Qwen4Exp::hc_after_prefix` runs layers below the window
   with the engine's own `layers_forward`, once per row; the hyper-connection
   streams are cached on the host up to `prefix_cache_gib`.
2. **Exact window.** `Qwen4Exp::exact_layers_from` runs the window layers with
   the engine's layer code (fused HC mix, GDN prefill, flash attention, grouped
   W4A4 experts, fp8 side GEMMs) and records the streams entering each layer.
   The adapter applies through `ExactOrTwinLoraHook`, a detached delta on
   untracked inputs. The reported loss is this forward's CE.
3. **Head.** Only completion rows reach the final mix and the 248k-vocab head
   (`ONLY_COMPLETION_ROWS_REACH_THE_LM_HEAD_BECAUSE_HARNESS_PROMPTS_ARE_TEN_THOUSAND_TOKENS_AND_TARGETS_A_FEW_HUNDRED`).
4. **Per-layer twin backward.** From the top down, each window layer is re-run
   as an autograd twin started from the exact stream recorded for it: candle
   ops for the HC glue (`HcGate::mix_eager`, `hc_combine_eager`), the serving
   fp8 GEMM with a dX kernel (`QuantLinearOp`), the GDN twin sharing the
   engine's fp8 projections
   (`LinearAttention::train_twin_parts_sharing_the_resident_projections`),
   dense SDPA for attention below the QSA budget, and Marlin W4A16 over the same
   expert bytes (`MarlinMoeTrainStacks::build_from_checkpoint_rows`, whose
   backward multiplies by a requantized transpose). The surrogate
   `sum(y * g_out)` gives the layer's LoRA gradients and the gradient for the
   layer below.
5. Adam on fp32 A/B with a global-norm clip.

Activation rounding (W4A4 expert inputs, fp8 side inputs) is straight-through:
each twin's Jacobian is taken at the activations the engine produced, so its
rounding differs from the engine's but the error does not compound with depth.

Expert stacks cost about twice the layer's expert bytes (2.64 GiB per
Flash-Next layer); the trainer keeps as many window layers resident as free
memory above `vram_reserve_gib` allows and rebuilds the rest per use.

## Memory: what lives where

The trainer loads the base through the same `Qwen4Exp` loader the engine uses:
the token table stays in pinned host RAM and gathers one row per token over
PCIe (the CLI clears `NV_Q4EXP_EMBED_DEVICE` and refuses a device-resident
table), the PLE n-gram table is gathered on the CPU from the mmap
(`PLE_TABLE_STAYS_IN_THE_MMAP_BECAUSE_PINNING_48_GB_OF_HOST_RAM_DOES_NOT_FIT_BESIDE_TRAINING`;
its layer sits below the window, so it runs once per row inside the cached
frozen prefix), and the MTP head is not loaded. The device holds the NVFP4
experts, the fp8 side projections and the hyper-connection weights: the
engine's footprint less the 2 GiB MTP head. `metrics.json` records the table
placement under `tables`.

Pinned host RAM is the handover tier for training state, off by default:

- `--host-stacks-gib G` builds each window layer's Marlin train stacks once,
  parks them in pinned host RAM and drops them from the device; each backward
  uploads the next lower layer's stacks on a copy stream while the current
  layer's twin runs
  (`FROZEN_EXPERT_STACKS_HAND_OVER_THROUGH_PINNED_HOST_RAM_ONE_LAYER_AHEAD_OF_THE_TWIN_BACKWARD`),
  so the device holds two layers' stacks (5.3 GiB) instead of the window's six
  (15.8 GiB), and the host holds the window's 15.8 GiB. Stacks beyond `G`
  fall back to the device cache.
- `--host-optimizer` keeps the fp32 Adam moments in pinned host buffers and
  streams them one variable ahead of the update
  (`HOST_OPTIMIZER_STREAMS_EACH_VARIABLES_ADAM_MOMENTS_THROUGH_PINNED_HOST_RAM_ONE_VARIABLE_AHEAD_OF_THE_UPDATE`).

Both tiers produce the same adapter bit for bit as the device tiers (the
suite covering the handover tier). A pinned allocation that fails refuses the
run rather than fall back to pageable memory
(`PINNED_HOST_ALLOCATIONS_REFUSE_RATHER_THAN_FALL_BACK_TO_PAGEABLE_MEMORY_BECAUSE_A_PAGEABLE_COPY_SERIALIZES_THE_STREAM_AND_SWAPS_UNDER_PRESSURE`,
`nv-layers/src/pinned_host.rs`).

A separate trainer process cannot train beside a live engine on one 96 GB
card: each process holds its own copy of the experts. Training next to the
live engine would mean training inside the serving process on its resident
weights, with the stacks handed over through host RAM; that path is not
built.

## Export and serving

`Qwen4ExpLoraTrainer::export_for_base` writes PEFT `adapter_config.json` +
`adapter_model.safetensors` under the checkpoint's module names, A in bf16 and
B pre-multiplied by `alpha/r` in bf16 with exported `lora_alpha = r`, so the
loader's scaling fold is the identity. `adapter_config.json` also records
`expert_lora` (the form, `none` without one) and `base_identity`
(`expert::base_identity_for_dir`: a hash of `config.json` and the safetensors
headers, independent of the path). An expert adapter adds
`expert_lora.safetensors` (`model.language_model.layers.{i}.mlp.experts.lora_{A,B}`,
bf16, B pre-scaled) and `expert_lora.json` (format, form, rank, layers and the
model shape it was trained for). The loader refuses an adapter whose declared
form, rank, shapes or base identity disagree with the files or the resident
model.

`nv_specdecode::lora_spec::Qwen4ExpServingAdapter` prepares one
`ServingLoraHook` per module (the capture-safe m=1 kernel plus the fp32 candle
delta for prefill rows) and one `ExpertLoraLayer` per expert layer, attaches
them to the resident model and detaches them without reloading the base; an
adapter naming any non-target module is refused. Adapters load through
`nv_specdecode::qwen4_exp_adapters::Qwen4ExpAdapterRegistry`, which stages
them in pinned host RAM, validates them there and keeps one live version per
id; the hot-swap rules are in 06.7 (*Flash-Next on CUDA*). The server exposes
each `id=dir` in `NV_Q4EXP_LORA_ADAPTER_DIRS` as a chat model on the resident
weights (`Qwen4ExpAdapterEngine`); a request attaches the version it resolved
at its start under the qwen4_exp permit, runs a k=0 session tagged
`id@version` and detaches
(`QWEN4_EXP_ADAPTER_REQUESTS_TAKE_A_FRESH_NON_SPECULATIVE_SESSION_BECAUSE_THE_SESSION_CACHE_AND_THE_MTP_HEAD_BELONG_TO_THE_BASE`).
NixOS: `modules.services.ai-llm-voice.cudaLora`.

## The CLI

`nv-train-nvfp4` ships in the speaches-plus package:

- `lora --base B --data D --out RUN [--steps --seed --metrics --rank --alpha
  --targets --window --lr --max-seq --store-gcroot --expert-lora --expert-rank
  --expert-alpha --expert-layers --host-stacks-gib --host-optimizer]` —
  `--expert-lora` is `none | per-expert | expert-a | hydra | shared` (default
  `expert-a`, rank 16, alpha 32, over the 6 window layers); `--targets none`
  trains the experts alone. The nightly passes none of these, so the defaults
  are the night's configuration.
- `eval --base B --adapter RUN --data V --out E` — per-row held-out CE, base
  vs adapter, through `Qwen4ExpServingAdapter`
- `generate --base B [--adapter RUN] --data V --out G [--limit N]`
- `fixture --out DIR` — the decode-capable tiny qwen4_exp checkpoint
- `bench-layer --base B` — one real layer's engine and twin costs

Exit 4 with `{"error": "no_trainer"}` means the base is not qwen4_exp or the
build has no cuda feature. Rows are `prompt`/`completion`, `text`, or
`messages` + `completion` rendered with the checkpoint's chat template.

## Gates

- The suite covering trainer/engine identity (`nv-models/tests/qwen4_exp_lora.rs`):
  trainer streams equal `forward_rows` bitwise with the zero adapter attached
  (fused-row, staged and grouped MoE row counts), for linear and for every
  expert form; per-component twin error; directional derivatives of the
  served loss against finite differences, with bf16 and fp8 side GEMMs and
  for each expert form's A and B per layer; a bigram task where the loss falls
  and a shuffled-label control stops at the label-marginal floor, for linear
  targets and for expert-only adapters; the handover tier training the same
  adapter bitwise as the device tier; the pinned-host copy bandwidth and its
  overlap with compute.
- The suite covering hot-swap (`nv-specdecode/tests/qwen4_exp_lora_hotswap.rs`):
  every expert form served through the registry equals the trainer's export
  bitwise; a swap mid-stream leaves the running request bitwise on its
  version and the next request on the new one; corrupt, truncated, wrong-rank,
  wrong-form, wrong-base and missing-file adapters are refused with the live
  version still serving; adapter sessions are reused only under the same
  id@version and never enter the base cache; unload returns the VRAM; decode
  throughput per adapter kind.
- The suite covering serving parity (`nv-specdecode/tests/qwen4_exp_lora_serving.rs`):
  prefill logits through the serving hook equal the trainer's exported adapter
  bitwise, CUDA-graph decode equals eager decode, and the m=1 kernel stays
  within tolerance of the trainer's fp32 delta.
- The night's LoRA stage end to end (`apiary/nightly/tests/test_nvfp4_cli.py`,
  opt-in via `NV_TRAIN_NVFP4_CLI`).

## Not built

True FP4 compute for the trainable path (stochastic-rounded gradients,
Hadamard-rotated activations) — the trainable parameters are rank-r and
fp32, so the backward cost is the frozen base's dX, which already runs in
4-bit weights. Expert LoRA on gate/up (inside the activation) needs a
grouped-GEMM epilogue hook. A captured decode graph for expert adapters needs
a device-side tile plan. Router-bias training. MTP heads are not co-trained,
so adapter requests do not speculate.
