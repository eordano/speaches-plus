# Model compatibility matrix -- what this server can actually serve

Per-checkpoint blocker detail, complementing the model x backend matrix in
the private status ledger, which is the authority on which classes
serve on which backend. This page answers the different question: given a
checkpoint in the cache, what stops it, and is the blocker code or bytes.
Machine: RTX PRO 6000 Blackwell, 97887 MiB VRAM (95.6 GB).

## What "supported" means

Support is a property of the (family loader × on-disk naming convention × cached
bytes) triple, not of a format name. The dispatch surface is
`chat_engine/build.rs`'s `detect_family` -> `ModelFamily` -> `LoadedModel`
(02-model-loading.md); anything with no arm bails at `detect_family` with the
list of prefixes it accepts. Two standing traps:

- **Unknown `quant_method` falls through silently to `QuantScheme::None`.**
  `QuantizationConfig::from_hf_value` matches only the modelopt / NVFP4 / FP8 /
  compressed-tensors shapes and otherwise returns `Ok(Self::none())`, so a
  checkpoint declaring AWQ or GPTQ is treated as unquantized bf16 and fails
  later on a missing tensor, one layer from its cause.
- **`QuantScheme::{AwqInt4, GptqInt4, Marlin}` are declared and constructed
  nowhere** — a workspace grep finds only the enum definition. The live runtime
  set is `LinearKind::{Bf16, Fp8E4m3, Nvfp4, Mxfp4}`, and Marlin kernels reach
  the GPU through the `gemma4_e4b` w4a16 path, not through `QuantScheme::Marlin`.
  Delete the three dead variants or leave them until a checkpoint needs them.

Weights are safetensors on the CUDA path; GGUF loads through `GgufLoader` and
serves only on wgpu.

**Qwen3.5-397B-A17B is a multi-GPU project, not a support gap.** Its
architecture is `Qwen3_5MoeForConditionalGeneration`, the already-supported
family, so nothing architectural blocks it; it is unservable here on three
independent grounds — only `config.json` is cached; 397B params is ~794 GB bf16
and ~211+ GB even at NVFP4's 4.25 bits/value, against 95.6 GB VRAM; and no
tensor parallelism exists to split it (`NcclComm` / `all_reduce` / `world_size`
grep to nothing). No code change on this machine makes it servable.

## Dense-hybrid layer mixing

Qwen3.5/3.6 checkpoints interleave `full_attention` and `linear_attention`
layers. `nv-layers/src/layer_mixer.rs` is the model-independent extraction and
the place to build against: `MixerKind` parses HF `layer_types` strings and
rejects anything but `full_attention` / `linear_attention`; `LayerMixPlan` is
built from explicit `layer_types`, from `full_attention_interval` (index `i` is
full iff `(i+1) % interval == 0`), or uniform, and carries
`full_slot_for_layer` / `linear_slot_for_layer` maps, counts, index lists and a
`matches_full_attention_interval` validator; `Mixed<F, L>` replaces a hand-rolled
per-model mixer generically and `LayerMixPlan::build(make_full, make_linear)`
constructs `Vec<Mixed<F, L>>` with per-layer constructor dispatch. Its six tests
are mutation-killed four ways: an interval off-by-one, a matcher that disagrees
with the builder, a layer handed both slots, and `build` passing the slot index
where it must pass the layer index.

`qwen3_5_moe.rs` still carries its own `LayerMixer` and is not migrated onto
`layer_mixer`; that migration is the remaining work, not a blocker.
`google/gemma-4-*`, `openai/gpt-oss-20b` and `google/embeddinggemma-300m` use
the same idiom with `sliding_attention` instead of `linear_attention`, so
`MixerKind` needs a third variant to cover them.

## diarized_json response shape

The shipped wire contract for
`POST /v1/audio/transcriptions?response_format=diarized_json`. Rust and Go
(`internal/stt/http.go`) must agree byte-shape; `client/test_diarized_json.py`
checks that.

```json
{
  "text": "...", "avg_logprob": 0.0, "no_speech_prob": 0.0,
  "segments": [
    {
      "type": "transcript.text.segment",
      "id": "seg_001",
      "speaker": "SPEAKER_00",
      "start": 5.2, "end": 12.8, "duration": 7.6,
      "text": "Hi, I need help with diarization.",
      "avg_logprob": -0.21, "no_speech_prob": 0.01, "confidence": 0.93
    }
  ]
}
```

- `type` and `id` are the OpenAI-required per-segment fields; `id` is `seg_NNN`,
  1-based, zero-padded to three. `start` / `end` / `duration` are seconds,
  converted from the engine's millisecond timings. `avg_logprob`,
  `no_speech_prob` and `confidence` are nullable extensions, `confidence`
  carrying the diarizer's per-turn confidence.
- `speaker` is `SPEAKER_NN` when diarization ran and `null` when it did not; in
  that case one segment is emitted per Whisper segment rather than per speaker
  turn. With diarization on, Whisper segments are bucketed into speaker turns by
  segment midpoint (nearest turn if it falls in none) and each turn's text is
  the joined text of its assigned segments.

**Why this shape.** OpenAI shipped `gpt-4o-transcribe-diarize` with
`response_format: "diarized_json"` and ElevenLabs' Scribe v2 markets an
"OpenAI-compatible format", so this is the converged industry shape. Extending
the transcription endpoint with a `response_format`, rather than inventing a
standalone diarization contract, buys compatibility with any client that already
speaks OpenAI's audio API.
