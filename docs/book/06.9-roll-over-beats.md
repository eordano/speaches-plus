# Roll-over beats: what "beats base" has to mean

[`06.7-continual-lora.md`](06.7-continual-lora.md) closes its loop on one
number: the roll-over is refused unless held-out adapter loss beats base loss
by `--gate-margin`. That is the whole gate. This document specifies what
replaces it, and why a single scalar was never going to be enough.

Scope, decided deliberately: **adapter roll-over only.** Prompt promotion
(data-tournaments `bin/optimize.py`) and finding publication (`SweepSpec`)
keep their own gates for now. Weights are where a bad promotion is hardest to
undo -- an adapter has no tombstone, and a habit distilled into it survives
every later conversation -- so the vocabulary gets designed against the
dangerous case first and generalized only once it has run in anger.

## 1. Three gates, none of which can say "it compiles"

The fleet decides "is the new thing better than the old thing" in three
unrelated places:

| Site | Rule today |
|---|---|
| `scripts/consolidate_trajectories.py` | held-out adapter loss beats base by `--gate-margin` |
| data-tournaments `bin/optimize.py:750` | `improvement > 0` **and** `exact_accuracy >= base` **and** `invalid_rate <= base` |
| data-tournaments `SweepSpec` | `validation.mode` in `red_green \| perf_budget \| rubric_only`, `publish.gate` in `human \| none` |

Only the third has a typed vocabulary, and nothing else consults it. All
three are statistical or declarative; none can express *the code still
compiles*, which is the cheapest and most decisive evidence available.

Worse, the adapter gate is the exact reasoning
[`08.2-quality-verdicts.md`](08.2-quality-verdicts.md) forbids. A fixed
margin -- "+0.3 ppl is a REJECT" -- means nothing without a measured null,
and `--gate-margin` is a fixed margin with no null at all. A gate that cannot
return "inconclusive" will eventually roll noise into weights and call it an
improvement.

## 2. Beats

A **beat** is one piece of evidence about a candidate, with a verdict. The
gate is an ordered list of them. Three classes, distinguished by what
produces the verdict, not by what they measure:

- **Deterministic** -- a command in a sandbox; the exit code is the verdict.
  `lint`, `compile`, `e2e`, and anything else with a runner and an exit
  status.
- **Human** -- a recorded judgement by a person about a specific artifact.
- **Metric** -- a statistic over a held-out split.

The three are not interchangeable and must not be summed. A weighted score
lets a metric gain buy off a compile failure, which is the one thing the
deterministic beats exist to prevent; you would need infinite weights for the
vetoes, which is a veto ladder wearing a disguise.

### 2.1 The ladder

Beats run cheapest-first. Any failure ends the candidate immediately and the
remaining beats do not run.

```
lint      fail -> REJECT        (sub-second)
compile   fail -> REJECT        (seconds)
e2e       fail -> REJECT        (minutes)
human     fail -> REJECT        (cached; never promotes -- see 4)
------------------------------------------------------------------
metric    decides among survivors: SHIP | REJECT | UNRESOLVED
```

Clearing every veto is not a pass. It only earns the right to be measured.
The metric beat is the only one that can return SHIP, and it returns it
against a measured noise floor, not a fixed margin, per §2 of
[`08.2`](08.2-quality-verdicts.md).

**A beat is a gate, never a fixer.** `lint` sits first because it is the
cheapest rung, and it is only safe there because it *rejects* rather than
reformats. A rung that rewrote the candidate to satisfy itself would put
renames, reindentation and trailing-whitespace churn into the same diff as the
change under review, and a human reading that diff has to separate the two by
eye -- which is the real cost of a lint step, and it is a review cost rather
than a compute cost. Ordering by cost is free only under this rule. A candidate
that cannot lint is a REJECT, and repository-wide formatting is somebody else's
pass.

**UNRESOLVED does not roll.** An adapter whose held-out delta sits inside the
floor changes no default, exactly as an UNRESOLVED arm changes no default
today. This is the single most important line in this document: the common
outcome of a consolidation round on a quiet week is *no roll*, and that must
be reported as a verdict rather than a failure.

The ladder inherits the existing structure rather than replacing it. The
non-finite-gradient gate and the dead-module check already fail a job before
registration; they are deterministic beats that happen to live inside the
trainer, and they keep that position.

## 3. A beat result is keyed by what it verified

Every beat result records the hash of its subject, and a result whose subject
hash no longer matches is not a result -- it is history.

This one rule does three jobs at once:

**It makes results cacheable.** An `e2e` beat that took four minutes need not
run again while nothing it looked at has changed.

**It makes them invalidatable.** Change the adapter weights, the corpus, or
the worktree and the cached pass stops counting, automatically, with no
expiry heuristic.

**It answers the stale-human problem.** A human approval is evidence about a
specific artifact under a specific rubric. If either changed, the approval no
longer certifies anything.

Subject hash composition, by beat class:

- deterministic: `sha256(adapter_weights_digest || beat_inputs_digest)`. A
  LoRA adapter changes no file in any worktree, so a command like `cargo
  check` cannot observe the candidate: it would return one verdict for every
  candidate in a round while its cache key moved with each -- a guaranteed
  miss on a result that provably cannot depend on the input, which is the
  inverse of what this section exists to do. **A deterministic beat over an
  adapter must therefore be adapter-shaped**: a fixed prompt set replayed
  under the candidate with an exit-code oracle, hashed over that runner's own
  inputs. `worktree_hash` belongs only to beats that run against a checkout,
  and a code candidate is a different subject from a weights candidate.
- metric: `sha256(adapter_weights_digest || holdout_digest)`.

`adapter_weights_digest` is the sha256 of the adapter's `safetensors` bytes,
not `persist::adapter_tag_that_changes_when_the_weights_change`. That tag is
path, length and mtime, which is fail-safe in its original job of deciding
whether to resume a KV snapshot and **fail-open** here: two adapters of equal
rank and target set share a byte length, `load_inplace` makes same-path
replacement routine, and mtime is whole seconds -- so a rejected adapter
overwritten in place inside one second inherits the first one's cached passes.
It is also path-dependent, so a rollback that reloads identical bytes from
another directory always misses. Leave the cheap tag where it works.
- human: `sha256(artifact_content || rubric_id || rubric_version)`.

Prime Agent arrived at the same mechanism from the other direction: before
rerunning a previously-failed autonomous gate it hashes the git worktree
(`git status --porcelain=v1 -z -uall` + `git diff --binary HEAD` + sha256 over
untracked files) and refuses to rerun against an unchanged tree, recording
`"not rerun: workspace unchanged since previous failed gate"`. That is this
rule applied to one beat class. Generalizing it to all of them is the cheapest
correctness win available here.

## 4. The human beat never promotes

A human beat has three states, and only two of them are verdicts:

- **fresh reject** -- subject hash matches, verdict is negative: REJECT.
- **fresh approve** -- subject hash matches, verdict is positive: the veto is
  cleared. It does *not* make the candidate a winner; the metric still
  decides.
- **stale** -- subject hash does not match. The approval degrades to
  advisory: it may still block if it was a rejection, and it may never clear a
  veto or contribute to a win.

The motivating case is precise. A candidate that happens to reproduce a
golden output has proved only that it agrees with something a person approved
at some earlier time, about an artifact that may since have changed under a
rubric that may since have been rewritten. Reproducing a golden is evidence of
*not being worse than what was approved*. It is not a Pareto win, and the gate
must not be able to mistake it for one.

Time-boxed expiry was considered and rejected: it is wrong in both directions.
A verdict about code that changed yesterday is stale immediately; a verdict
about a stable rubric is good for months. Time is a proxy for the thing that
actually matters, which is whether the subject moved.

The join is already available. data-tournaments judgements carry `rubric` and
`rubricVersion`, and the JSONL export now carries each judged card's title,
body and `source_ref`, so the artifact side of the hash is computable without
new plumbing. On the speaches side the label channel
(`POST /v1/trajectory/label`, joined by id or tag) is the same shape of
evidence one level down, and its `matched` flag already refuses to claim a
join that did not happen.

## 5. Where beats execute

Deterministic beats mean nothing except against a real checkout, so they run
where agent work already runs: the **sandboxed-agents hermes VM**.

No such runner exists yet. data-tournaments' `RunnerSpec` is not it and is not
being adapted into it -- that type carries a driver, a model and a parallelism
count, and has no command, no timeout, no network flag and no exit-code
contract. The hermes VM builds one qemu guest to launch an agent CLI
interactively; there is no warm image and no overlay pool, so the cost argument
below is a requirement on machinery to be built, not a description of machinery
that exists. This section is a specification with an owner still to be named.

The contract a beat runner must satisfy:

- one command, run in a fresh overlay over the hermes VM image, with the
  candidate's checkout mounted;
- a timeout, after which the beat is a REJECT with reason `timeout` -- never
  an UNRESOLVED, because a beat that cannot finish is not inconclusive
  evidence, it is a failure to produce evidence;
- exit code is the verdict and nothing else is parsed, matching Prime Agent's
  gate contract, which spawns with `shell:true` and reads `status === 0`;
- stdout and stderr are captured, truncated, and retained as the beat's
  provenance, not interpreted;
- no network unless the beat declares it, because a beat that can reach the
  internet can be made to pass by something other than the candidate.

The overlay framing matters for cost. Booting a VM per beat would make the
ladder's cheap rungs expensive and destroy the point of ordering by cost; an
overlay over a warm image keeps `lint` in the sub-second class where the
ladder assumes it lives.

## 6. Shapes

Nothing here is a new storage system. Beats attach to the artifacts that
already exist: the adapter directory is already the rollback artifact, and the
job already reports metrics.

```jsonc
// BeatSpec -- declared per consolidation round
{
  "id": "compile",
  "class": "deterministic",          // deterministic | human | metric
  "command": "cargo check --workspace",   // deterministic only
  "timeout_s": 600,
  "network": false,
  "order": 20                        // ascending; cheapest first
}

// BeatResult -- recorded per candidate, per beat
{
  "beat_id": "compile",
  "verdict": "pass",                 // pass | fail | unresolved | stale | skipped
  "subject_sha256": "...",           // §3; a mismatch demotes this to history
  "ran_at": "2026-08-27T04:12:00Z",
  "duration_ms": 8400,
  "exit_code": 0,                    // deterministic only
  "evidence": "…truncated stdout/stderr…",
  "reason": "timeout"                // set when the verdict needs one
}

// GateOutcome -- what the round decides
{
  "decision": "ship",                // ship | reject | unresolved
  "decided_by": "metric",            // the beat that produced the decision
  "vetoed_by": null,                 // first failing beat, when rejected
  "beats": [ /* BeatResult, in execution order */ ],
  "adapter_id": "ft:…",
  "rolled": true
}
```

`skipped` is a real verdict and it is not a pass: it is what a beat below a
failed rung records, and what an unavailable runner records. A gate whose
`e2e` beat was skipped may not report SHIP.

## 7. Where it plugs in

Step 4 of the loop in [`06.7`](06.7-continual-lora.md) -- "Gate" -- becomes
"run the ladder". The surrounding steps are unchanged: filter, judge, train
with a holdout, and on a SHIP, roll by unloading older `ft:*:<suffix>:*`
adapters so exactly one rolling adapter remains.

Three consequences for the existing surface:

- **`--gate-margin` is retired, not reinterpreted.** The metric beat needs a
  measured floor, and a flag that invites a hand-picked threshold is the
  hazard `08.2` was written about. A round with no floor measurement produces
  UNRESOLVED, which does not roll.
- **The refused-adapter behaviour is kept and extended.** Today a refused
  adapter stays loaded for inspection and nothing is unloaded. That stays
  true for every REJECT and every UNRESOLVED, and the `GateOutcome` is written
  beside the adapter directory so the refusal is inspectable later.
- **`metrics.eval_loss_adapter` / `metrics.eval_loss_base` remain the metric
  beat's input.** The job does not change; only the interpretation does.

## 8. What we take from Prime Agent, and what we do not

The review of `PrimeIntellect-ai/prime-agent` recovered what the paper omits.
Two mechanisms are worth taking now, one shape is worth taking later, and the
rest is not ours to copy.

**Take now.** The worktree-hash anti-spin rule, generalized in §3. And the
plan/apply split with optimistic concurrency: their refiner captures a
baseline state before the model call and re-reads the store before applying,
rejecting edits whose entry changed in between (`"entry changed during
refinement planning"`). Any gate that runs for minutes needs the same
discipline -- a beat ladder that decides against an adapter that has since
been replaced is deciding about history.

**Take later.** Their Continual Harness is one JSON blob per scope
(`~/.prime/agent/harness/harness_state.json`, local copy under
`session-artifacts/<id>/`) holding four artifact kinds -- `prompt`, `memory`,
`skill`, `subagent` -- under a single `HarnessEntry` schema with `version`,
`source`, `created_at`/`updated_at`, plus a `refinements[]` event log and
before/after snapshots that make rollback mechanical. We already have three of
those four kinds on disk in Claude Code's format, with `originSessionId`
provenance; what we lack is versioning and an automatic consolidation pass.
That is a separate document and a separate decision.

**Do not copy.** Three things in that codebase read as machinery and are not:
`subagent` and `skill` entries are inert prose that nothing dispatches on;
every artifact kind -- `prompt` included -- is injected into the system prompt
truncated to 180 characters, six per kind, so a "prompt note" is a routing
hint rather than prompt text; and the store has no eviction at all, so it
grows unbounded while only the view is capped. Most relevant here: **their
refine loop has no regression check.** `expectedOutcome` is free text that is
never evaluated, and nothing re-runs a test or replays a trajectory to see
whether an edit helped. That absence is precisely the hole this document
fills, and it is why the beats work belongs on our side of the line rather
than being adopted from theirs.

## 9. Open

- The noise floor for the metric beat is unmeasured. `08.2` requires a null
  that performs the arm's own operation; for an adapter that plausibly means
  a same-shape adapter trained on shuffled labels, but this has not been run.
- Beat declaration has no home yet. A per-round CLI flag and a file beside the
  corpus are both plausible; the choice should follow whoever ends up owning
  round scheduling. **It is never a field on the fine-tuning job request.** The
  beat list is operator configuration, and a candidate that can declare the
  gate that judges it is not gated at all. Prime Agent has this right: its gate
  config is CLI and SDK only, with no settings key and no repo-local override,
  so the tree under test cannot define its own gate.
- Whether a human beat can be *requested* by a round -- pausing a roll until
  someone judges -- or only consulted if it already exists. Requesting turns
  the loop synchronous on a person, which is a different product.
- Cross-consumer generalization is explicitly deferred. When prompt promotion
  adopts beats, `optimize.py:750`'s three conditions become one metric beat
  plus two deterministic ones, and `SweepSpec.validation` becomes a beat list;
  neither should happen before the vocabulary has survived a few real
  roll-overs.
