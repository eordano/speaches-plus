## Serving support matrix -- model x backend

Authority is the code: `backend_select::ModelClass` and
`cuda_model_unservable_reason` / `wgpu_model_support` for what the selector
answers; `chat_engine/build.rs`'s `detect_family` and `try_load` for what the
engine will load; `chat_engine_wgpu::classify_wgpu_model` for the wgpu side.
`GET /v1/backends` (`backends_report()`) is the live machine-readable form, and
`backend_wgpu_gate.rs` derives its assertions from the same two functions so a
new family cannot silently stale it.
[`02.1-model-compat-matrix.md`](02.1-model-compat-matrix.md) carries
per-checkpoint blocker detail.

**Three selector/engine divergences are live and are the first thing to check
when a model refuses on one path and loads on the other:**

1. `cuda_model_unservable_reason` refuses `Qwen35Dense` unconditionally while
   `detect_family_with_dense_cuda_serve` honours `NV_QWEN35_DENSE_CUDA_SERVE`.
   `Qwen38Dense` checks that same variable, so qwen3.5-dense is refused by the
   selector where qwen3.8-dense is not.
2. `NV_E4B_CUDA_SERVE` has opposite polarity on the two sides: the selector
   demands `=1`, the engine bails only on `=0`.
3. `ModelClass::Unknown` falls into the catch-all `None` arm, so an
   unrecognised model id is reported cuda-servable.

`QWEN35_DENSE_NO_CUDA`'s message still says cuda has no loader for the family;
`Qwen3Moe::from_loader_dense_quantized` is that loader, so the message is stale.

### Cold-start / TTFT (CUDA)

The first CUDA forward of a process pays ~5-6 s of one-time module/workspace
init, and a first spec-decode request pays the drafter's own ~1.1 s equivalent;
both are engine-independent (measured at the same magnitude on Qwen38Dense
graphed-NVFP4 and Gemma4E4b eager-Marlin). Boot-warm envs run one throwaway
chunk (and, for q38, one throwaway drafter catch-up + draft) at build so the
cost lands at boot instead of in the first request's TTFT; each is opt-in and
bit-identity-gated (E4B's gate is control-bounded: Marlin rebuilds carry
inherent 0.5-0.75 max-abs logit noise, so the bar is argmax equality plus
2x the measured rebuild control).

| env | scope | first-request effect when set |
|---|---|---|
| `NV_Q38_BOOT_WARM_PREFILL` | trunk, `GraphedQwen3Moe` build | TTFT 7.0->1.9 s class @8k |
| `NV_Q38_BOOT_WARM_DRAFTER` | MTP head build (sibling env so the A/B arm stays expressible) | removes the 1.1 s drafter catch-up init; first request equals steady state |
| `NV_E4B_BOOT_WARM_PREFILL` | `Gemma4E4b::from_loader`, CUDA device only | TTFT 7.8->1.9 s @8k; wgpu needs nothing (`NV_WGPU_WARMUP` default-ON already covers it) |
| `NV_OAPI_PHASE_WALLS` | serving request path, stderr walls | off = zero extra syncs; the instrument that attributes TTFT |

E4B decode-at-depth rule, measured (rows `e4b decode-depth`): decode is
attention-read-bound and LINEAR in depth — ms/tok ~= 4.56 + 0.049 us x depth
on CUDA (the 7 full-attention layers' KV reads; the 35 sliding layers and
graph replay live in the flat intercept), same slope on wgpu measured to
120k (rows `e4b wgpu deep`: within ~7 % of CUDA's, intercept +2.1 ms; 142.7
tok/s @8k -> 78.0 @120k, 55 % retention — better than CUDA's 48 %). 200.6
tok/s @8k -> 126.9 @64k -> 95.5 @120k on CUDA, ~77 projected at the 131k
window edge, 42.8 GiB peak — long-context serving is decode-viable to the
window edge on BOTH backends and the binding cost at depth is prefill TTFT
(CUDA 105 s @64k, 346 s @120k). wgpu prefill does NOT share CUDA's shape:
it is superlinear (avg cost 2.6 -> 14.9 ms/tok over 8k->120k, segment slope
nearly doubling past 64k), giving 7.9-min TTFT @64k and 29.9-min @120k —
wgpu E4B at depth is decode-viable, prefill-bound: fine for sessions that
arrive shallow and grow, not for cold 64k+ ingest. E4B keeps ~48 % of its 8k decode rate at
120k where qwen3.8 (all-layers-full-attention) keeps ~26-33 % at comparable
relative depth: sliding-window layer mix is the structural depth-robustness
lever.

E4B prefill-at-depth rule, measured (rows `e4b cupf`/`e4b deep`/`e4b fixedkv`/
`e4b swnarrow`): the depth term (78 % of warm wall @8k on the full-width arm)
is the eager full-width SDPA -- all 42 layers scored `512 x total` per chunk
while the 35 sliding layers' mask then discarded everything past the window.
Note 512 is BOTH the serving chunk and the true sliding window
(config `sliding_window = 512`; 131072 is `max_position_embeddings`).
Cat-cache reallocation traffic is NOT the cost (`NV_E4B_PREFILL_FIXED_CACHE`
measures a wash -- do not re-litigate). The narrowing lever is BUILT:
`NV_E4B_PREFILL_SLIDING_NARROW=1` (opt-in, default untouched) scores the 35
sliding layers against only the last `window + chunk` K/V rows with a
width-matched shifted mask (cache writes, RoPE, decode layout all unchanged;
KV sharing never crosses the sliding/full boundary -- `kv_source_layer` picks
same-type writers). Measured: prefill 4151->7344 tok/s @8k (1.77x),
632->2309 @64k (3.65x), 347->1328 @120k (3.82x); 120k TTFT 345.6 s -> 90.4 s;
argmax-identical seeds, control-bounded gate (3-rebuild control -- single-pair
W4A16 rebuild controls understate the noise spread at partial-chunk depths).
Residual depth term is the 7 full-attention layers. wgpu needs no port: its
prefill flash already windows sliding layers per-row, which is why the
cuda-vs-wgpu deep-prefill gap existed.

### wgpu serving (`NV_SERVE_BACKEND=wgpu` + `NV_WGPU_CHAT_MODEL_DIRS`)

`chat_engine_wgpu.rs` runs one worker thread per model, official-template-only
prompts, host or in-shader sampling, LoRA adapters (E4B only; runtime
load/unload and the trajectory-consolidation loop live in
[`06.7-continual-lora.md`](06.7-continual-lora.md)) and spec decode
(E4B only, `NV_WGPU_SPEC` default-on: suffix automaton plus a learned assistant
drafter auto-discovered from the HF cache). Batched decode is opt-in
(`NV_WGPU_BATCH>1`, Gemma4Dense graph only -- measured a LOSS on this kernel, so
the default stays single-stream). Model-crate default flips (int8 lm_head,
W8-FFN, fp8 attn formats, NVFP4-v2 routing) are read from env inside the
`nv-models` constructors, so the serving path inherits them with no plumbing lag.

**Chunked prefill is default-on and universal.** All seven `WgpuModelKind`
decoders implement `prefill_tokens`; `chunked_prefill_enabled()` is
`NV_WGPU_CHAT_CHUNKED_PREFILL != "0"` and engages wherever
`prefill_chunk_len() > 0`. Per-decoder widths default to 16 (qwen3.5-dense,
gpt-oss) or 64 (qwen3.5-moe, laguna), overridden by `NV_WGPU_PREFILL_M` or the
per-model `NV_*_WGPU_PREFILL_M` (`NV_G4_WGPU_PREFILL_M` and friends); `0` or `1`
disables. What is *not* universal is media-row splice prefill, which exists only
for qwen3.5-dense, qwen3.5-moe and gpt-oss (image rows) and gemma4 dense/moe
(embed rows).
**On gemma4-dense the only epilogue that disables chunking outright is the
legacy row-scale one (`NV_WGPU_ATTN_FP8_LEGACY`)**, which scales after the
reduction and has no mk twin; the other disablers are the 256-byte
storage-offset shape rule, any nvfp4 projection surviving to the graph, and a
prefill width of 0 or 1. `NV_WGPU_PIPELINE_LOG` (default off; `1` = stderr,
another value = an append-to-file path) dumps the per-boot pipeline set.

`NV_DETERMINISTIC=1` is required for exact-match quality gating and is not a

non-deterministic at a per-position rate that matters without it.

## Laguna (Poolside Laguna XS/S 2.1)

Architecture (`nv-models/src/laguna.rs`): mixed sliding(512)/full attention 3:1,
per-layer query-head counts (XS: 48 full / 64 sliding, kv=8), per-head QK
RMSNorm, dual rope (YaRN partial-0.5 θ=5e5 + attention_factor on full layers;
plain θ=1e4 on sliding), softplus per-head output gating before o_proj,
sigmoid-router MoE (256 experts top-8, `e_score_correction_bias` selection-only
bias, norm_topk, routed_scaling 2.5, ungated shared expert), dense layer 0.
`LagunaKvCache` implements the `Gemma4Cache` trait (sliding compaction, bf16);
NVFP4 experts load via the compressed-tensors path; EOS ids [2, 24]. **No
numerical parity claim** -- architectural verification plus greedy-agreement and
near-tie gates only.

**Defaults on:** grouped MoE prefill and device-side MoE routing for decode;
device argmax plus incremental detokenization (`NV_LAGUNA_HOST_SAMPLE=1`
reverts); `NV_LAGUNA_M1_FLASH`, `NV_LAGUNA_M1_QKV`, `NV_MOE_TAIL_FUSE` (`=0`
disables each); `NV_LAGUNA_LMHEAD_FP8` scoped-on — fp8 head on the base tiers
(M=1 step graph, eager decode, serve-spec no-draft) and bf16 head inside the
DFlash speculative round, because the fp8 head shifts prose τ there; and
`NV_LAGUNA_SERVE_SPEC` + dflash draft at k=4 with the checkpoint rope-θ fixed
policy.

**Prefill is grouped MoE, chunked at 256 tokens**, because the sliding cache
caps at `window + slack = 768`.

**`NV_LAGUNA_HOST_MOE` is present-at-all, not a boolean.** It reads through
`nv_config::env_arm_present_at_all_reread_every_call`, so `=0`, `=off` and
`=false` all select host MoE exactly as `=1` does; the only way to keep the
grouped path is to leave the variable unset. Set at all, it skips the grouped
prebuild in `Laguna::from_loader_quantized` entirely and decodes severalfold
slower. **Host prefill is never faster than grouped prefill.**

**UNVERIFIED -- budget the resident plateau as holding both copies.** Whether
the per-expert NVFP4 copies survive the grouped prebuild is not settled here:
`MoeGroupedWeights::build_from_experts` reads `moe.experts` and no release, no
degradation notice and no `NV_LAGUNA_KEEP_EXPERT_COPIES` gate exists anywhere
in the tree, so the reclaim this page once claimed (1.6875 MiB/expert x 256 x
39 sparse layers) cannot be quoted. Read the boot VRAM delta before sizing a
host against it.

Two opt-in decode-MoE arms (both default-off, argmax-class not bitwise):
`NV_MOE_FP4_DECODE_GEMV=1` swaps the CUTLASS m=1 grouped GEMMs for the
weight-streaming grouped GEMV (`moe_grouped_fp4_gemv_m1_bf16`);
`NV_MOE_SHARED_FOLD=1` folds the shared expert into the grouped decode pipeline
as a fixed extra tile — routing writes k routed slots plus a weight-1.0 shared
slot per token (`moe_route_topk_shared_tail`), the shared expert's activations
quantize through the same nvfp4 path as routed experts, and the aux-stream
candle shared path drops out of the M=1 step entirely. Fold applies to the
single-token grouped decode (eager and captured); grouped prefill and the
verify path keep the separate shared expert, which is why the shared expert's
weights stay resident.

`NV_LAGUNA_SERVE_SPEC` routes eligible greedy requests through a persistent spec
engine (`laguna_serve.rs`) on a dedicated `laguna-spec-serve` thread, with the
identity-safe M=1 whole-step graph as the default spec path and a persistent
DFlash draft + `DflashGraphProposer` + `LagunaVerifyGraph` above it. All
captures happen at engine-build warmup, so the first request runs at full speed.
Routing is gated on `is_greedy` ∧ no penalties ∧ no guided ∧ empty `logit_bias`
∧ `!logprobs` ∧ `NV_LAGUNA_HOST_SAMPLE` unset ∧
`prompt + max_new + k + 2 <= max_seq`. **Spec-vs-normal identity is asserted
byte-identical on the no-draft path** (text, finish_reason, completion_tokens,
including EOS-terminated and max_new-truncated cases, and across sequential
requests on one reused engine) and **not** asserted on the draft path, where
M-shape verify numerics can flip near-ties.

**The 300 tok/s target is not met, and round cost is not the reason.** The
graph-capturable timestamp profiler (`NV_LAGUNA_VERIFY_PROF=1`, zero nodes
captured when off) measures overhead-above-compute far under the threshold the
launch-fusion / PDL / megakernel family needed to be worth starting, so that
whole family is NO-GO **on Laguna**; the M=5 verify residual is real compute
(MoE ffn roughly doubles vs M=1). **The sole remaining blocker on Laguna is τ**
— drafter quality against the NVFP4 target.

**That NO-GO is Laguna-scoped and does not generalize; re-measure the launch
budget per model before quoting it.** Two shapes measure the opposite of
Laguna's on their own profiles, so launch fusion is a live avenue there, not a
closed question:

- **gemma4-31B cuda** is 97.3% GPU-busy and byte-bound overall, yet its CUPTI
  budget still attributes 2.54 ms/step to 480 norm/rope launches moving roughly
  4 MB — a quantified small-op lever, tempered by `MEGAKERNEL_FUSE1` measuring
  no change alone or stacked, so the win has to come from a fusion that arm does
  not implement.
- **qwen3.5-9B cuda** is launch-bound outright: 94% of its 1.56 ms residual is
  dispatch latency plus near-zero-byte kernels at 451 launches/step.

The same launch-retirement lever is what produced the gemma4-26B-A4B wgpu
record, where fusing a latency-bound dispatch into a co-tenant's tail (rather
than making passes cheaper) cut dispatches per step from 963 to 428.

**Long context:** the graphed stack runs to 52 K tokens bf16 with needle recall
exact; the depth cost is entirely verify round time and τ is content-dominated,
not monotonic. **fp8 KV composed with speculation is a net effective-tok/s
LOSS** — the verify graph is bf16-ring-only, so fp8 falls back to eager verify;
do not compose them. With fp8 KV alone the smem cap is raised via
`attention_fp8_decode_gscores` (a global-scratch scores sibling; sub-cap
dispatch is the old kernel byte-for-byte) plus the `kv_fp8.cu` token-axis grid
fix: needle FOUND and spec identity EXACT at 69,675 and at 254,823 tokens.

### Laguna kill list -- reviewed, rejected, do not re-litigate

L2 hot-expert cache / expert reordering (the routed-expert line is a tiny slice,
the per-token expert stream dwarfs L2, the free-repeat ceiling is sub-noise).
Sliding-layer KV in smem or persistent-kernel residency (the entire sliding KV
read is sub-noise). fp8 hidden states / activations end to end (sub-noise
ceiling; M=1 is weight-bandwidth-bound, and accuracy risk runs through q/k-norm,
partial rope, softplus and the router). Multi-block (k=2, 32-token) verify (each
extra block consumes gigabytes of extra unique experts, consumed only when all
15 drafts accept). Tree verification, EAGLE-2 style (the τ gain cannot pay the
round-cost growth — fine-grained 256-expert top-8 MoE inverts dense-model tree
economics). Router-gate quantization (sub-noise, in the checkpoint's ignore
list, top-8 selection flips under noise). Embed-row quantization (8 KB/token).
KVFlash-style host-RAM KV paging (exists to fit 24 GB cards; revisit only for
multi-request serving). Multi-step N-token single-graph capture (obsoleted by
the draft + block-verify step structure). Adaptive block truncation
(measured-negative at k=4, stays opt-in off, bucketed verify-graph
infrastructure retained). Confidence-truncated drafting as a serving win (Laguna
verify is width-flat, so the maximum width-proportional saving is
sub-millisecond per round).

Deferred rather than killed, and Laguna-scoped like the rest of this list:
persistent megakernel, Blackwell PDL on graph nodes, w4a16 attention (needs a
quality-eval harness first), prefill chunk 256->1024 (decode-neutral).

## Qwen3.6 (Qwen3.5-MoE)

Device-routed grouped MoE is default ON (`GroupedMoeDispatch` in
`qwen3_5_moe.rs`: per-layer grouped NVFP4 weights prebuilt eagerly, one
persistent `GroupedDecodeContext` across the 40 layers, `moe_route_topk` softmax
mode 0, capture-safe shared-expert tail; `install_grouped_moe()` wires it and
any build error leaves the hook uninstalled, falling back to the existing clean
refusal). Its gates are green: answer-agreement 8/8 on real 35B against the i64
integer-lattice oracle, flip gate all 11 controls 100% token-exact. Grouped is a
different-but-valid activation-rounding realization, not a bit-exact one.
**Cost:** the grouped expert copy holds a large extra VRAM block on top of the
host-path weights and the boot line WARNs; `NV_QWEN_MOE_GROUPED=0` restores host
dispatch and frees it.

**Capture is wired into serving, but only on request.** `build.rs` builds
`GraphedQwen3Moe` when `NV_QWEN_GRAPH=1` or when `NV_DRAFTER=mtp` selects
captured serving, and installs the grouped MoE hook on it; with neither set it
boots `QwenMoeShared::Eager`. The bench-side arm is `NV_QWEN_MOE_GROUPED=1
NV_GRAPH_CAPTURE_FORWARD=1`. Root cause of the historical capture failures:
**candle ops are not graph-capturable** —
candle uploads `[dims, strides]` metadata per call via `clone_htod` of a
temporary host `Vec`, so a single `index_select` inside a capture replays against
freed host memory. The graceful-fallback path is in place, so a capture failure
degrades instead of wedging.

**Spec decode:** `NV_DRAFTER=mtp` serves greedy requests self-speculatively with
the checkpoint's own MoE MTP head (`model_mtp.safetensors`, loaded by
`nv_models::qwen3_5_mtp::MtpHead`; `NV_MTP_K` sets the chain depth,
`NV_MTP_DRAFT_DIR` overrides the shard dir). A missing or misshapen shard is a
loud boot failure; sampled requests decode normally. Greedy requests serve
through `MtpMoeGraphedDecodeSession` by default -- the boot builds the
`GraphedQwen3Moe` engine and the session captures its m=k+1 verify lane --
with `NV_Q36_MTP_EAGER=1` (or opting out of grouped MoE) as the escape onto
`MtpMoeEagerDecodeSession` (m=k+1 grouped-dispatch verify, lin-state rollback,
hidden reanchor at the accepted row); both stream through
`run_qwen36_moe_mtp_greedy_rounds`, which logs the served arm and
`capture_active`. The correctness bar is draft-policy invariance on both arms
(junk drafts emit the identical stream; the suite covering it is
`qwen36_mtp_serving_session.rs`, `NV_QWEN36_MTP_SERVE=1`) plus byte-identical
greedy repeats through HTTP on whichever arm the env selects (the suite
covering it is `qwen36_mtp_serving_e2e.rs`, `NV_QWEN36_MTP_E2E=1`). The
grouped m>1 forward is capture-safe: its historical host stall in `nv_layers`
`forward_grouped_decode` survives only as the opt-in diagnostic
`NV_MOE_MT_STALL=1` (the suite covering stall-off bit-identity, rows-keyed
verify-graph capture at rows 3/4/5/8 and finite eager grouped prefill is
`qwen36_moecap_stall_bisect.rs`, `NV_QWEN36_MOECAP=1`, zero-env and the full
record stack). `MtpMoeGraphedDecodeSession` therefore captures its m=k+1
verify lane and runs roughly half the eager session's ms/tok, but spec still
does not reach the captured m=1 record step: with the verify captured the
bound moves to grouped m>1 kernel cost plus acceptance (k=2 floor at
accept=1.0 sits just above the record). `NV_QWEN_GRAPH=1` plus
`NV_Q36_MTP_EAGER=1` is refused at boot because the eager session serves
only off the eager engine. The harness is `qwen36_mtp_econ.rs`,
`NV_QWEN36_MTP_ECON=1`; captured m=1 baselines still run one per process via
`NV_Q36_ECON_CAPTURED_BASELINE_ONLY_DEPTH`. Sessions stash and restore the
installed MoE dispatch across resets
(`take_moe_dispatch_for_host_routed_prefill_then_restore_...`): under
`NV_Q36_MOE_SHARED_FOLD=1`, dropping and rebuilding the fold hook after a
captured graph's teardown poisons the context (the next CUDA call dies with
CUDA_ERROR_INVALID_VALUE), so hook reuse, not rebuild, is the rule after any
capture. Prefill around the sessions routes host-side
(`PREFILL_ROUTES_HOST_BECAUSE_THE_GROUPED_MULTI_TOKEN_COST_EXPLODES_WITH_M`),
which also makes the MTP evidence test's speculative and reference streams
token-identical.

**Two rules left by the closed grouped-MoE-under-capture defect** (one
unconditional `stream.synchronize()` ending `forward_grouped_decode` for
`n_tokens>1`, which also took the `install_grouped_moe` all-NaN eager-prefill
defect with it). First: **any dynamic-smem kernel raises its grant through
`raise_dynamic_smem_optin_never_lowering_it`** (`nvk_smem_optin.cuh`), a
mutex-serialized raise that never lowers — `gemv_bf16.cu`, `moe_gemv.cu`,
`gdn_decode.cu` and `gdn_recurrent.cu` all route through it, and a new kernel
calling `cudaFuncSetAttribute` directly reintroduces the "wrong,
nondeterministic, fixed by any stall" shape. Second, do not re-attempt hoisting
`disable_event_tracking` out of `GraphedQwen3Moe` (measured to make every eager
forward all-NaN; only the ordering half can land) or relaxing
`gemma4_verify_batch_vs_sequential`'s tolerance (the 5-9 logit-unit
disagreement is batch-invariance seeded by M=1 in cuBLASLt, not precision).

**Instrument rule:** thinking-ON packs measure CoT-trace stability, not answers.
`NV_CHAT_EVAL_THINKING=0` is the eval-correct rendering for thinking-default
models.

### Engine / serving

0. **The engine generate task must yield after every channel send.** The task
   does sync GPU work and never hits a pending await, so a woken HTTP/SSE
   reader lands in that tokio worker's non-stealable LIFO slot and sits there
   until the 64-cap event channel fills — first bytes wait ~64 tokens at every
   depth (client TTFT was 1011 ms on a 60 ms engine session at 196-token
   prompts). The q38 graphed loop carries the fix
   (`yield_so_the_woken_reader_escapes_this_workers_unstealable_lifo_slot`,
   now the shared helper in `chat_engine/stream.rs`); streamed bytes are
   byte-identical and request walls unchanged. **Every CUDA family loop now
   carries it** (eager qwen3/q36-rounds/q38-solo, gemma4 all arms, E4B,
   gemma4-moe, gpt-oss, laguna, omni — the eager-loop fix measured TTFT
   1542->30 ms short-prompt). Old client-side rows predating the fixes are
   burst-flattered — read them against `wall_s`. `NV_OAPI_PHASE_WALLS=1` is
   the attribution instrument. Concurrency truth on the default q38 arm
   (rows "q38 concurrency"): the per-engine tokio Mutex gives a clean FIFO
   staircase — one solo-wall per queue position, decode spacing IDENTICAL
   under 2x/4x, control plane sub-ms during an 8k prefill, STT contends on
   GPU compute only; `NV_Q38_BATCH=1` is the multiplexing answer. Hazard
   states: (a) CLOSED — every scheduler→client send AND every solo-body
   send in `chat_engine/qwen.rs` (dense, moe-mtp rounds, graphed, qwen3)
   honors `NV_SSE_SEND_TIMEOUT_MS` (default 10 s): on timeout or close the
   request's generation aborts and its stream drops, so a non-reading
   client can no longer park the `NV_Q38_BATCH=1` dispatcher or pin a
   model mutex on the engine runtime (the bare sends held the model mutex
   across the stall — one stalled client starved every request for that
   model on the normal path too). Escape hatch: `=0` restores the
   infinite wait on the scheduler entries; the engine runtime keeps the
   surface's 1 ms clamp. Covered by the suites covering group-member
   eviction (`qwen38_sched_stall_eviction_e2e`, NV_Q38_SCHED_STALL_TEST=1)
   and solo eviction with a queued successor
   (`qwen38_solo_stall_eviction_e2e`, NV_Q38_SOLO_STALL_TEST=1), plus
   `solo_send_discipline_tests` at unit level. Open hazards needing decisions:
   (b) block_in_place asymmetry — nine sync paths hold tokio workers for
   their whole GPU stretch, so 32 concurrent requests can pin all 32
   workers; (c) `VramGate::admit` is barge-in (large-request starvation);
   (d) permit/VRAM sheds surface as 500 `engine_error` not 503; (e) the
   global bf16-GEMM `with_handle` mutex spans every launch process-wide;
   (f) `get_embedder()` cold-load runs outside the embed gate.

1. **Batched paged-attention kernel** — one call for all B rows, taking a `[B]`
   block-table array and `[B]` context lengths; the per-row loop body in
   `forward_decode_batched` is the drop-in seam.
2. **Spec `Verify` batches through `BatchEngine`** — the scheduler supports the
   batch kind; `step()` returns an explicit error for it.
3. **Stepper-side chunked prefill** — the scheduler splits at the token budget,
   but the shipped Gemma4 steppers do not override `step_mixed`, so non-final
   chunks are deferred rather than executed.
4. **Qwen3 steppers** mirroring `Gemma4PagedBatchStepper`.
5. **Continuous-batching throughput ramp** — blocked by GPU OOM under co-tenant
   load; needs a quieter box.
6. **Engine-path chunked prefill for sliding fp8 layers** —
   `LagunaDflashEngine` prefills the whole prompt in one shot into the sliding
   fp8 cache and fails cleanly past capacity, which blocks the fp8 spec depth
   datum.
7. **CUDA loops do not emit `ChatEvent::StoppedBy`.** The shared `StreamEmitter`
   records the matched stop string, but only the wgpu path and `EchoEngine` emit
   the event, so `/v1/messages` responses served by the CUDA loops report
   `end_turn` and a null `stop_sequence` on a stop-string hit. The fix is one
   `if let Some(s) = emitter.matched.take()` push before each loop's `Done`
   send, across `chat_engine/{qwen,gemma4_loop,gemma4_moe_loop,laguna_loop}.rs`.

### Registry / adapter bugs

1. **`ChatRegistry::resolve` silently serves the default engine for ANY unknown
   model string when exactly one engine was loaded at boot** (the
   `allow_unknown` arm, gated by `NV_CHAT_ALLOW_UNKNOWN_MODEL`; the count it
   reads is the boot engine count, so runtime adapter loads and unloads never
   flip the behavior). Today a convenience; under LoRA a correctness bug — a
   typo'd adapter name quietly serves the base model with a 200 instead of a
   404, where vLLM 404s any name that is neither a base model nor a registered
   adapter. What shipped instead is a boot-time warning
   (`lora::typo_swallow_risk`).
2. **`admission::init_gemma4`'s `GATE` is a `OnceLock` computed once at
   startup** from a measured static footprint (capacity =
   `NV_VRAM_BUDGET_GIB - measured_static_bytes`, frozen at first call). Loading
   a LoRA adapter later allocates slot stacks and adapter weights invisible to
   the gate, so the KV-admission budget overstates free VRAM by the adapter
   residency and unload never returns budget. The gate needs a mutable
   static-bytes component or an explicit `reserve`/`release` API.

   `finish_reason:"stop"` with `content:""`.

   hardcodes `Device::Cpu` although `nv-tts` wires the `metal` feature.

**Capacity note**: `nvidia/Gemma-4-31B-IT-NVFP4` peaks at **63.3 GB RSS** during
weight streaming before settling at 5.2 GB. Size hosts by the transient, not the
32.67 GB checkpoint.

## #53 long-context spec-decode crossover

Eagle3/dflash spec decode crosses to a net LOSS at roughly 9.4 K ctx on both
code-long and chat-long prompts. **The root cause is the PRODUCT of two
effects**: verify ms/round grows superlinearly (M=k+1 rows each pay long-KV
attention) while no-spec decode is weight-bound and flat, AND τ collapses with
depth. Holding either constant flips it back to a win. The k=3 ctx gate is
validated optimal — k=4 at depth is worse, because draft cost exceeds
position-3 acceptance.

`NV_MK_VERIFY_HD512` (default ON) cuts verify round time enough to turn
code-long from LOSS to WIN and chat-long from LOSS to break-even, leaving short
ctx untouched. **`NV_SPEC_CTX_DISABLE` is the guaranteed-no-regression floor**
(default off, byte-identical when off): above the configured prompt length the
gemma4 serve loop falls through to non-spec, so spec can never lose. Set it to
8192 with hd512 off, or ~9-16 K with hd512 on, per deployment.

Two related standing results. DFlash rope-theta at long ctx: the shipping
default (fixed = checkpoint theta 500000) is optimal at >=16k for code and prose
alike, and `NV_DFLASH_ROPE_THETA_POLICY=auto` is dominated there — use
`policy=depth` for per-class picks below 8192 ctx. And **the prose tau deficit
is drafter capability, not a serving bug**: prose mean accepted prefix is
roughly half of code's on real 31B + DFlash, nearly all prose prefix-kills are
content-word starts, and drafter confidence discriminates match from mismatch
cleanly.

## Operational notes

- Work directly in the tree on `main` and isolate concurrent agents by disjoint
  file ownership, not by worktrees or branches.
- `/tmp` is a 32 GB tmpfs mounted at root and can fill under concurrent cuda
  builds. Set `TMPDIR=$HOME/.cache/cargo-tmp` for cuda invocations, and reclaim
  stale scratch with `find /tmp -name 'nix-shell.*' -mmin +60 -exec rm -rf {} +`.
- `scripts/strip-comments.py` is the canonical formatter for new code.
- **No-spec serving arm (gemma4): the only working switch is `NV_NO_SPEC=1`**
  (accepts anything except empty/`0`/`false`). `NV_SPEC_DECODE` is read nowhere
  in the tree, and `NV_DRAFTER=none` is an invalid arm that warns then defaults
  to `eagle3` — both produce spec-enabled "no-spec" runs.
- **Benchmarking: there is one GPU and a permanent idle co-tenant.** Idle-gate
  to 0% external util before and after every run, keep runs strictly serial, and
  record `nvidia-smi` occupancy with each number.
- **Silent-failure guards.** A zero-init Qwen3-TTS vocoder is **fatal at boot**,
  with `NV_TTS_ALLOW_SILENT_VOCODER` as the opt-in restoring the silent path and
  `503 tts_vocoder_zero_init` at request time, and `/v1/audio/speech` answers
  `404 model_not_found` rather than silently substituting Kokoro.
  `EOU_AUDIO_REQUIRED` mirrors `NV_EAGLE3_REQUIRED`/`NV_DFLASH_REQUIRED` for
  `EOU_KIND=audio|fusion` with no smart-turn model — boot logs an error naming
  `EOU_AUDIO_MODEL_PATH` and the flag makes it fatal — and the absent audio head
  scores `NaN` (`MissingAudioEouModel`) instead of a constant `1.0`, so fusion
  degrades to the text head instead of being pulled toward "turn complete".
  `/v1/ocr` refuses an unqualified request with `400 ocr_backend_ambiguous` once
  two or more backends are loaded, and `x-spec-decode` plus `spec_decode` on
  `/v1/models` expose the spec state.
