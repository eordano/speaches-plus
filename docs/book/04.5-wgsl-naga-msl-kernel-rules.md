# Kernel design rules: WGSL -> naga -> MSL on Apple GPUs

**Target: an Ultra-class Apple-silicon part, 192 GB unified, Metal via
wgpu/naga.** Every rule states the relationship its measurement evidenced and, where
one exists, names the harness that re-establishes the magnitude. Anything not
measured is labelled **HYPOTHESIS**. No raw log behind any rule is in the tree,
so this page carries no figures; current numbers live only in `perf/runs.jsonl`.

## 0. The machine, in the four numbers that decide kernel design

| quantity | value |
|---|---|
| spec bandwidth | **800 GB/s** (1024-bit x LPDDR5-6400 = 819.2 raw; *not* 900) |
| measured stream-read roofline | shape-dependent: near spec at the large 43008x5376 gate_up-class shape, down to well under two-thirds of spec at 2560x2048 (`wgpu_decode_structure_ladder.rs`; numbers: `perf/runs.jsonl`) |
| FP32 ALU peak (spec) | ~27.2 TFLOP/s (76 cores x 128 ALU x 2 x ~1.4 GHz) |
| subgroup width | **32**, runtime-probed by `probe_subgroup_width` (`device.rs`); wgpu *reports* the range `4..64` |

Arithmetic intensity of decode GEMV is ~2 FLOP/byte. Against 800 GB/s and
27 TFLOP/s the machine balance is ~34 FLOP/byte, so **decode is 17x on the memory
side of the balance point**. Every rule below is a corollary, and the single most
important consequence is: *the achievable rate is strongly shape-dependent, so
"% of roofline" is meaningless unless you name the shape's own roofline.*

## R1. Accumulators: never index a function-space array under a runtime bound or guard

**Rule.** In a hot loop, accumulators must be **named scalars** (`acc0`, `acc1`,
...) generated by the host -- not `var acc: array<f32, M>` indexed by a loop
variable whose bound is a uniform, and not indexed under `if (live)`. naga's MSL
backend lowers such an array to a **thread-local (spilled) array**, so every FMA
becomes a memory round-trip instead of a register update. Replacing two E4B
verify kernels' guarded arrays with host-generated scalar accumulators plus
per-row uniform guards, bit-identical by construction, won several-fold on the
spilled kernels and moved E4B decode measurably and prefill roughly two-fold end
to end, because prefill runs the same kernels.

The three spilling shapes, all still in the tree:

```wgsl
var acc = array<f32, 8>(0.0, ...);                      // indexed by a loop var
for (var j = 0u; j < m; j = j + 1u) { acc[j] = fma(f, x(j), acc[j]); }   // bound is a uniform

var vbits: array<u32, 16>;                              // indexed under a runtime guard
if (kb < n_blocks) { for (var i = 0u; i < 16u; i++) { vbits[i] = ...; } }

var ssc: array<f32, 32>;                                // read under a runtime-bounded loop
for (var s = 0u; s < fd_params.splits; s++) { acc += ssc[s]; }   // splits is always 16
```

The fast form does not spill:

```wgsl
var acc0 = 0.0; var acc1 = 0.0; ...                     // host-generated scalars
for (var v = lane; v < kv; v = v + 32u) {
    let ww = w[wo]; let wl = bf16_lo(ww); let wh = bf16_hi(ww);
    if (0u < mm) { let xw = x[xo];      acc0 = acc0 + (wl*bf16_lo(xw) + wh*bf16_hi(xw)); }
    if (1u < mm) { let xw = x[xs + xo]; acc1 = acc1 + (wl*bf16_lo(xw) + wh*bf16_hi(xw)); }
}
```

Note what survives: the *guard* is still runtime (`mm` is a uniform), but it
guards a **scalar**, so the register allocator keeps `accN` in registers on both
paths. **Guarding is free; indexing is not.** Live fast examples:
`mk_unrolled_source`, `mk_unrolled_i8_source`, `verify_smk_live_source` in
`gemma4_e4b_wgpu.rs`. Live slow ones: `qwen3_5_moe_wgpu.rs`'s `taken[256]` /
`chosen[16]`, `flash_decode.wgsl`'s `acc: array<f32,16>` under `d < hd`, the
`ssc: array<f32,32>` under `fd_params.splits` in `gemma4_wgpu.rs` and
`gemma4_e4b_wgpu.rs`, and `laguna_wgpu/gpu.rs`'s `vbits[16]`.

**It is not universal.** The w4a16 *subgroup* mk kernels were never
spill-dominated -- naga handles their `ptr<function, array>` accumulators far
better than the bf16 kernels' guarded arrays -- and the same unroll bought only a
percent-class win there against a multi-fold win on the bf16 twin. **Confirm the
spill in the emitted MSL, or in a timing, before attributing a win to it.**

**Corollary -- the cheaper root fix.** A uniform that is fixed per model (splits
= 16, GQA ratio, KV strides) should be a WGSL `override` constant baked per
pipeline. That converts "runtime-bounded loop" into "compile-time loop" and
removes the whole class at the root. Cheap; do it on any kernel you touch.

## R2. Reduction: subgroup butterfly, but only once you are off the roofline

**Rule.** Use the 5-step `subgroupShuffleXor` butterfly (32-wide) over the
`array<f32,256>` + `workgroupBarrier` tree. The gain is **small when the kernel is
already at the roofline and larger when it is not** -- reduction style buys you a
fraction of your *distance from roofline*, nothing more. Measured across all four
Gemma4-31B decode shapes (qkv, o, gate_up, down) and four formats, the butterfly
won every cell and the ordering was monotone in distance from roofline: bf16 and
int8 sit near their shape's stream ceiling and gain least; fp8 and mxfp4 sit well
below it and gain several times more. **A barrier-serial tree is only expensive
when there is slack to expose it.**

**The butterfly is a free swap under a bit-exactness mandate.** It is exactly
`log2(32) = 5` shuffles with no barrier and no threadgroup memory, and it is
*order-isomorphic to the tree at lane 0 by construction* -- both sum in the same
pairwise binary order over the same 32-lane K partition (tree: strides 16,8,4,2,1
through smem; butterfly: `subgroupShuffleXor` 16,8,4,2,1), so lane 0 accumulates
the identical expression tree. Every `max_abs`/`max_rel`/`rms` column measured is
identical between tree and sg to all printed significant figures, at every shape
and format.

Corollaries of width 32:

- Partition K across **32 lanes**, one row per subgroup:
  `rows_per_group = workgroup_size / 32`.
- You may run **narrower than the hardware subgroup**: the shipping w4a16 `sg_pk`
  kernel uses 16 *virtual* lanes per row (`vlane = slane & 15u`, XOR steps
  8/4/2/1), packing two output rows into one physical 32-wide subgroup, which is
  how it reaches 16 rows per 256-thread workgroup (`sg_pk_source` in
  `gemv_w4a16.rs`).
- `SUBGROUP_BARRIER` is **requested but not available** on this adapter.
  Cross-subgroup fan-in still needs `workgroupBarrier` + a small `var<workgroup>`
  array -- which the `sg_pk` kernels use, for the two-row output pack only.
- Subgroup builtins compile with **no `enable` directive** (`quant_gemv.wgsl` has
  none). `enable f16;` and `enable wgpu_cooperative_matrix;` *are* emitted, but
  only by the coop sources. Do not add `enable subgroups;` speculatively; it is
  not needed and its acceptance is naga-version dependent.

**Counterexample -- lm_head, n = 262144.** At the vocab shape the butterfly
*loses*: `sg256` (8 rows/group, same workgroup count as the tree) ties the tree
exactly, while `sg128` (4 rows/group) collapses to a fraction of the tree's rate
on bf16 and int8/fp8/mxfp4 `sg` lose only marginally. This reproduces the
recorded `NV_E4B_LMHEAD_SG_WG=128` trap (`05.6-macos-port-status.md` §A8). The
mechanism is **not resolved**: the obvious candidate -- 2x the workgroups, half
of them dead past the 65535 per-dimension grid limit -- is *falsified* by the
int8/fp8/mxfp4 `sg` rows in the same ladder, which really do wrap to a 65535x2
grid with 65534 dead workgroups and lose only marginally. Treat the *rule* as
measured and the *explanation* as open: **at n ≳ 10⁵, do not reduce
rows-per-workgroup below what the tree kernel uses; A/B the vocab shape
specifically.**

## R3. Workgroup memory is zero-filled per workgroup launch, and that is the whole story

**Rule.** Every byte of module-scope `var<workgroup>` costs a zero-fill on
**every workgroup launch**, because WebGPU mandates it and naga emits it. Budget
`var<workgroup>` as re-initialized memory traffic, not as free scratch. Three
independent confirmations: a 12 KB workgroup staging array for GEMV activations
regressed severely (pure zero-fill, not staging cost);
`flash_splitk_stage1_fp8kv` with 19.5 KB of module-scope workgroup memory at 128
workgroups x 42 dispatches/token spent most of its per-token cost on zero-init
and a minority on attention math, so turning it off roughly halved E4B decode;
and even `[1,1,1]`-grid elementwise kernels paid a large multiple of the
empty-dispatch floor, most of it zero-fill.

**The opt-out is per pipeline stage**, not per device --
`wgpu::PipelineCompilationOptions::zero_initialize_workgroup_memory` -- which is
why the allowlist is a list of entry points rather than a device flag. 65 entry
points are on the audited no-zero-init allowlist and default ON
(`NOZI_AUDITED_ENTRIES` in `nv-kernels/src/wgpu_backend/dispatch.rs`; two more,
`NOZI_PENDING_ENTRIES`, behind **`NV_WGPU_NOZI_NVFP4_V2=1`** -- read by
`nozi_pending_enabled`, and **not** `NV_WGPU_NVFP4_V2`, which is the unrelated
v2-GEMV routing knob in nv-models; global escape `NV_WGPU_NOZI=0`, read by
`nozi_env_enabled`). What the flag turns off is naga's in-kernel prologue that
memsets the module-scope arrays, and its barrier -- so **the hazard is a
workgroup read-before-write, not an uninitialised storage buffer**, and
re-enabling it costs a store per thread inside every workgroup rather than a
separate dispatch. The audit gate is `wgpu_flash_zeroinit_ab.rs`: it runs the
kernel with zero-init off **and a poisoned workgroup buffer** and requires
bit-identical output, and it is what proved the fleet's zero-init was 100%
redundant (0 of 65536 words stale with it on, 36 576 stale with it off).

**Limit.** With zero-init off the staging experiment becomes *legal* again but is
still not obviously a win: mlc-llm's Apple-Ultra-tuned GEMV independently chooses
`LOAD_V_SHARED = False`. Expect neutral, measure before believing better.
Threadgroup memory remains genuinely necessary for exactly two things:
cross-subgroup fan-in, and coop-matrix tile staging. **Order of preference:**
(1) no `var<workgroup>` at all -- the butterfly needs none; (2) an array sized
*rows per group* (4-16 floats) for the output pack; (3) kilobyte-scale staging
only with zero-init off and a poison A/B in the suite.

## R4. Memory access shape: 128-bit loads, SIMD decode, packed-pair stores

**Loads.** Read weights and activations as `array<vec4<u32>>` (128-bit). Scalar
`u16_at(word, i)` element access costs a large slice of your bandwidth: the
ladder from scalar `u16_at` through one-`u32`-word to `vec4<u32>` climbs
monotonically, with the `vec4` forms (bf16 bitcast, `unpack2x16float`, native
`vec4<f16>` with either accumulator) all clustered at the top, and `vec4<u32>`
bf16 reaching essentially the probe's own f32 `vec4` ceiling. There is almost
nothing left on the load path.

**Decode.** Decode a whole 32-bit word at once with SIMD ops, never
element-by-element with shifts. The shipping w4a16 `sg_pk` kernel is the
reference form:

```wgsl
let qe = vec4<f32>(unpack4xU8(pv & 0x0f0f0f0fu)) - vec4<f32>(8.0);  // 4 low nibbles
let qo = vec4<f32>(unpack4xU8((pv >> 4u) & 0x0f0f0f0fu)) - vec4<f32>(8.0);
let xe = bitcast<vec4<f32>>(xw << vec4<u32>(16u));                  // bf16 lo -> f32, no fn call
let xo = bitcast<vec4<f32>>(xw & vec4<u32>(0xffff0000u));           // bf16 hi -> f32
```

versus the slow form in the same file (`w4a16_q` in `gemv_w4a16.wgsl`):
`f32(u4_unpack(pv, elem)) - 8.0`, called eight times with a per-element shift.
Same format, same shapes, measured severalfold apart.

**Stores.** Two bf16 outputs pack into one `u32`, and every fast kernel in the
tree does it: the even-slot lane reads its odd neighbour's total out of a tiny
`var<workgroup>` array and writes one word.

```wgsl
if (vlane == 0u) { sgp_row_tot[slot] = acc; }
workgroupBarrier();
if (vlane == 0u && live && (slot & 1u) == 0u) {
    let lo = bf16_encode(acc) & 0xffffu;
    let hi = bf16_encode(sgp_row_tot[slot + 1u]) & 0xffffu;
    sgp_y[dst_word_off + (row >> 1u)] = lo | (select(0u, hi, row + 1u < n_rows) << 16u);
}
```

This halves output-write traffic *and* keeps the activation buffer in the packed
layout the next kernel wants, so no repack dispatch is needed. It is also why
`rows_per_group` must be even.

**Counterexample -- `vec4` is not an unconditional win.** Adding `vec4` loads on
both operands to a *warp-structured* nvfp4 GEMV **regressed** both 31B shapes
(`05.6-macos-port-status.md` §C6). Wide loads pay only in combination with
row-blocking **and** a float decode, and at k=512 they are actively harmful
because there are fewer `vec4` pairs than lanes. If your K per lane drops below
~4 `vec4`s, go back to `u32`.

## R5. Dispatch geometry: 8 rows x 32 lanes, and count your workgroups against 65535

**Defaults that measure well** (`quant_gemv.wgsl`, `gemv_bf16.wgsl`):
`@workgroup_size(256)`, `TREE_ROWS_PER_GROUP = 8`, 32 lanes per row, K strided by
32 with `vec4` loads; or `@workgroup_size(128)` with 4 rows for the butterfly. On
the four non-vocab shapes, 128 threads/4 rows beat 256 threads/8 rows in 3 cases
and tied in the fourth. Prefer 128 unless n is very large -- see the R2
counterexample.

**Grid limit.** `max_compute_workgroups_per_dimension = 65535`. Above it,
`dispatch::workgroup_count_1d` wraps to `(65535, ceil(g/65535), 1)` and the kernel
must recover the row as `(wid.x + wid.y * groups_x) * rows + slot`. At n = 262144
with 4 rows/group this is 65536 groups -> wraps to 131070, of which 65534 are
dead.

**Dead workgroups are nearly free -- if you guard the trip count.** The
`int8`/`fp8`/`mxfp4` `sg` kernels all wrap to 131070 groups with 65534 dead and
pay only a percent-class cost, because every one of them writes

```wgsl
let kv = select(0u, params.k_elems >> 4u, live);   // dead rows loop zero times
let wbase = select(0u, row * row_words, live);
```

The bf16 subgroup kernel does **not** (`gemv_bf16.rs`: `let kv =
sg_params.k_elems >> 3u;` with no `live`), so its dead workgroups run the full K
loop against row 0. **Always guard the trip count, not just the base address.**

**Host-side dispatch cost is not your problem.** CPU command encode is
sub-microsecond per dispatch with pre-encoding, and the reported per-dispatch
"wall tax" was profiler inflation -- with `NV_WGPU_PROFILE=1` the GPU-attributed
total *exceeds* the unprofiled wall (**UNVERIFIED**: re-derive by running the same
decode with and without the flag and comparing wall clocks). The per-token cost
that *is* real is the readback + device drain, and it is dispatch-count
independent. **Do not fuse kernels to save launches; fuse them to save a memory
round-trip.** Two measured falsifications of launch-count fusion:
attention-head-chain fusion removed 114 dispatches/token for a null-to-negative
delta, and the head-argmax fold saved a dispatch for a small regression
(`05.6-macos-port-status.md` §A8).

## R6. Decode-format ALU: fewer bits is *not* faster here, and the reason is structure before ALU

**Rule.** On this GPU, pick the widest format that fits your capacity budget.
Measured kernel rates at 31B decode shapes (best kernel per format, at the
`>=1.5 GB` replica-cycling policy that defeats the 96 MB SLC, independent runs
agreeing) rank bf16 and int8-rowscale together at the top, fp8 below them, and
both 4-bit formats (mxfp4, nvfp4 tree, w4a16 row) far below -- so far below that
the projected weight-stream time favors int8 over every 4-bit format despite the
byte advantage. int8 runs at essentially bf16's kernel efficiency at half the
bytes with kernel-level rms error an order of magnitude better than any 4-bit
format measured; both 4-bit formats surveyed are *slower in wall time* than bf16.
This is not only our kernels -- llama.cpp's own Metal Q4 back-computes to a rate
well under int8 on this chip.

**But the mechanism is usually structure, not decode ALU**, and that is the
correction that matters most for a kernel author. Measured against each kernel's
own **free-decode ablation** (identical load pattern, decode arithmetic deleted;
numerically invalid, a ceiling probe only), every kernel sat at a high fraction of
its own ceiling: bf16 and w4a16 `block` essentially at it (memory/structure-bound;
deleting all decode ALU buys a few percent), `v4`/`sg16` with some decode
headroom, nvfp4 `tree` structure-bound one stage earlier. So: **fix the access
pattern first (R4), then the decode arithmetic.** A slow 4-bit kernel is usually a
slow kernel that happens to be 4-bit. The residual after both is small -- the
entire remaining kernel headroom on E4B's 4-bit linear GEMV is a
low-single-digit-percent e2e effect.

**The byte cut is collectable but capped.** At identical bytes and elements,
swapping only the kernel moved E4B e2e by a double-digit percentage across the
`block` -> `v4` -> `sg16` ladder, and a byte cut can never buy more e2e than the
linear GEMV's minority share of the token allows.

**Quantization granularity, not bit width, is what breaks accuracy.** Four
flip-battery runs: nvfp4 (4-bit, per-16 scales) -> int8 group-128 ACCEPTed; the
*same* conversion at per-row (2048-element) scales REJECTed by orders of
magnitude on mean KL. Quantizing from the model's native precision is genuinely
lossy and grouping does not rescue it (bf16 -> int8 REJECTs at both per-row and
group-128). And **MoE routers amplify**: Qwen expert int8 REJECTed even at
group-128, because a small hidden-state delta flips discrete expert selection (a
step-KL spike -- a discrete event, not smooth noise). **A dense-FFN ACCEPT does
not port across the dense/MoE boundary.**

## R7. M > 1: replicate the GEMV, do not write a GEMM (until you have a real tile)

**At decode (M <= 4)**: one row per subgroup, one output per row. Do not batch
into a GEMM. **At prefill (M >= 8)**: load the weight `vec4` **once per k-step**
and reuse it across all M activation rows in scalar accumulators (the "mk"
pattern, R1). Landing that pattern on E4B roughly halved prompt prefill, and the
sg-order mk kernels reproduce the single-token accumulation order exactly, so
chunked prefill writes bit-identical KV to stepped decode.

**A naive GEMM is a trap.** `gemm_nvfp4::scalar` is a per-output-element kernel
(one thread per `mxn` output, each re-reading a full K row, so traffic is
O(M·N·K)): at n=k=4096 it is an order of magnitude worse at M=1 and still
severalfold worse at M=256 than brute-force re-running the GEMV M times,
saturating at a tiny fraction of the chip's FP32 peak
(`probe_coop_mat_m_crossover`). A GEMM only earns its name once it stages a tile
and reuses it; until then, M-row GEMV wins at every M measurable here. Secondary
result from the same ladder: encoding the M dispatches into **one submit** instead
of M is worth a real margin at large M -- free.

**Counterexample -- M does not scale monotonically on the WGSL path.** The E4B
prefill M-ladder is essentially flat from M=10 through M=128 with a dip at M=16
("16 accumulators spill harder than 10" -- R1 again, with a wider unroll). The
WGSL path is flat in M because it is bandwidth-bound; only the tensor-ops path
scales with M. **Raising M on a bandwidth-bound kernel buys nothing; raising it
past your accumulator budget costs.**

## R8. `shader_f16`: available, unused, and not worth taking at decode

`SHADER_F16 = true`, `f16_in_f32 = true` on this adapter, and no production kernel
uses it. **Decode verdict -- do not bother.** On the load path, native
`vec4<f16>` reads only marginally above `vec4<u32>` bf16 and both are essentially
at the probe's f32 `vec4` ceiling; f16 *accumulation* measures the same as f32,
because at 2 FLOP/byte the accumulator type is invisible. Adopting f16 for decode
would also cost a checkpoint conversion (all our weights are bf16/int8/nvfp4) and
a dynamic-range hazard bf16 does not have. **Prefill verdict -- it is a
prerequisite, not a win**: the only reason to plumb `enable f16;` is that
coop-matrix tiles are f16-only (R9). Judge it there.

**The ALU probe in the tree cannot support a stronger claim.**
`probe_alu_throughput` reports an f16:f32 fma advantage at matched ILP. **Do not
quote its absolutes**: its reported f32 rate is a multiple of the Ultra-class part's FP32
spec peak, so the fixture is partly optimized away -- the loop is an affine
recurrence `a = fma(a, c, d)` with loop-invariant `c`,`d`, which is exactly the
"the fixture itself was free" trap CLAUDE.md records. The *ratio* is measured on
identical shapes and is probably directional; the *levels* are not physical. Fix
the probe (data-dependent `c`/`d`, or a verified-non-foldable chain) before
anyone plans against it.

## R9. `coop_mat` / `simdgroup_matrix`: two independent gates block it, and one is real

The capability line is `coop_mat=true(3 cfg, gemm_tile=None)`: the feature is
exposed and our GEMM cannot use it. `coop_gemm_reason()` (`qualify.rs`) fails in
order on:

1. `subgroup_min_size != 32 || subgroup_max_size != 32` -- wgpu reports this
   adapter as `4..64`, so this fires first (`coop_mat unavailable: subgroup size
   4..64 is not exactly 32`). **This gate is spurious here**; the probed width is
   32 (R11).
2. `coop_gemm_tile().is_none()` -- we search for a **16x16x16 f16xf16->f32**
   config and Metal reports only **8x8x8**, with **no bf16 config**. **This gate
   is real** and survives fixing (1). Using coop on Apple means rewriting the tile
   schedule around 8x8x8 and casting weights to f16.

**Where it would and would not pay.** *Decode, M = 1-4: never* -- 2 FLOP/byte, all
three fast stacks (llama.cpp, MLX, mlc-llm) decode without simdgroup_matrix, ORT
measured decode unchanged after adding it, and R7's ladder shows the GEMV already
beats a non-tiled GEMM by an order of magnitude at M=1. *Prefill / verify,
M >= 32: the largest untapped lever we have* -- prefill is *unbatched* on the
dense graphs today (`prefill_chunk_len() == 0` for Gemma4Dense and Qwen3_5Moe
means one full decode graph per prompt token, putting a long prompt's 31B prefill
at tens of seconds), and anything that turns that into a real tiled GEMM is worth
more than every decode rule in this document combined -- but R7's ladder says the
*scalar* GEMM is not that thing. **HYPOTHESIS:** an 8x8x8 f16 coop path with
cooperative dequant into a threadgroup tile (zero-init off, R3) beats the mk M-row
GEMV somewhere in M = 8-32; llama.cpp's analogous crossover is ~5-8. Unmeasured
here -- `probe_coop_mat_m_crossover` prints `coop n/a` until the 8x8x8 tile
schedule is written.

**Also unused and also gated:** `create_shader_module_passthrough` (raw MSL /
metallib, binds like any WGSL module -- the pragmatic path to
`simdgroup_bfloat8x8`, which works via air intrinsics though it is absent from
the MSL spec table) and `create_shader_module_trusted` / `ShaderRuntimeChecks`
(bounds-check removal on audited kernels).

## R10. Never ship a `@workgroup_size(1)` kernel

**Rule.** A serial kernel on this GPU costs orders of magnitude more than its work
is worth, and it serializes the graph around it. `q3w_router_topk`
(`qwen3_5_moe_wgpu.rs`) is the live example: `@workgroup_size(1)`, a k-pass linear
scan over 256 experts with `taken: array<u32,256>` and `chosen: array<f32,16>` --
a serial kernel *and* an R1 spill. The shape is source-verifiable at HEAD; the
per-dispatch split is **UNVERIFIED** (`NV_WGPU_PROFILE=1` on a qwen3.5-moe decode
is what reproduces it).

**The top-k selection costs an order of magnitude more than the GEMV that produces
the logits it selects from**, and around half of the whole GPU token on
Qwen3.6-A3B at a tiny fraction of roofline -- this model is kernel-bound, not
bandwidth-bound. A bit-exact 256-thread replacement exists
(`q3w_router_topk_par`) behind `NV_Q3_WGPU_ROUTER_PAR=1`, **default OFF and still
unmeasured e2e**. Measuring it is the single highest-value open kernel item in the
tree.

**How to write the parallel twin without changing a bit.**
`q3w_router_topk_par` is the template: make the reduction operator associative
*and* commutative **including the tie-break** (carry the index, break ties toward
the lower index), so any reduction shape yields the identical winner; leave any
float accumulation whose order is observable (the softmax) serial on thread 0. It
differs from the serial version only on NaN input.

## R11. Capability gates are code, and a too-strict one silently deletes your fast path

**Rule.** Never gate a kernel on `subgroup_min_size == 32 && subgroup_max_size ==
32`. wgpu reports Apple GPUs as `4..64`. Gate on the **runtime-probed** width:

```rust
pub fn subgroup_ok(ctx) -> bool {        // FALSE on the Ultra-class Apple part
    ctx.caps.subgroup && ctx.caps.subgroup_min_size == 32 && ctx.caps.subgroup_max_size == 32
}
pub fn sg32_ok(ctx) -> bool { subgroup_ok(ctx) || ctx.subgroup_width() == Some(32) }  // TRUE
```

Consequences already found: `wgpu_quant_gemv.rs` used the strict form, so the
format survey benched **only** `tree` variants and the tree-vs-butterfly question
had never been measured on this hardware -- one-line change to `sg32_ok` produced
the whole of R2, with the `tree` rows reproducing the earlier survey within noise.
`gemv_nvfp4::subgroup_ok` gates `select_variant`, `select_variant_for_shape` and
`SgwConfig::supported`, so **the entire nvfp4 subgroup GEMV family (`sg`, `sgw`,
`sgq`) is unreachable on the Ultra-class Apple part** and 31B NVFP4 serving takes the `tree` path;
fixing it is a **HYPOTHESIS** worth one A/B, and likely a small win rather than a
large one, because the nvfp4 deficit is structural (R6), not reduction-shaped. The
same strict predicate is the *first* of the two coop-matrix gates (R9).

**Corollary -- the repo-wide failure mode.** A green test here may have run
nothing (five distinct mechanisms are catalogued in `CLAUDE.md`). Before believing
a kernel measurement: grep the output for `skip`/`SKIP`, check the variant list
actually printed, and check that the number of rows matches the number of
variants you asked for. The survey above printed a clean, plausible table for
months while silently omitting half its arms.

## R12. Bit-exactness is the gate that makes all of this cheap

Every optimization in R1-R7 was landed **bit-identical by construction** and
verified: the scalar unroll generates the same arithmetic sequence as the array
form; the butterfly is order-isomorphic to the tree at lane 0; the parallel router
carries a tie-break that makes its reduction order-independent; zero-init removal
is gated by a poison A/B. When a change *cannot* be bit-exact it needs the quality
harness, and the bar is high -- the attention-verify seam replacement was reverted
precisely because verify must stay argmax-equal to `decode_step` on every token.
**Prefer the transformation that is provably order-preserving. It ships the same
day; the one that changes accumulation order waits for a battery.**
