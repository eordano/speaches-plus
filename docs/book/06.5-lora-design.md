# LoRA in speaches-plus

**The substrate is built; the multi-adapter serving layer is not.** The PEFT
loader, the slot stacks with LRU eviction, the grouped/fused shrink-expand
kernels on both CUDA and wgpu, the `Linear` delta hook and the per-token
slot-mapping metadata all exist and are tested. What no request path reaches is
any of it above the kernel level: **the server registers one complete engine per
adapter**, so one adapter costs one full copy of the base weights, and slot
residency, the token→slot state machine, the `-1` no-adapter cohort and LRU
eviction are all unused by serving. §12 is that gap; training an adapter and
getting it served is [`06.6-lora-training.md`](06.6-lora-training.md).

Design decisions are ported from vLLM 0.26.0 and cited by symbol. **Public vLLM
docs are stale relative to that tree**: `--enable-lora-bias`,
`--long-lora-scaling-factors` and `--lora-extra-vocab-size` do not exist in
0.26.0, and extra-vocab support was removed.

> **This file publishes design constants and correctness figures, never a
> timing.** No adapter timing is worth taking until §12's gap closes: it would
> attach a number to an interim shape.

## 1. Math

For `y = W x` with `W: [N, K]`, an adapter contributes
`y = base(x) + scaling * B (A x)` with `A: [R, K]` and `B: [N, R]` — the PEFT
`lora_A.weight` / `lora_B.weight` layouts verbatim. `scaling = lora_alpha / r`,
or `lora_alpha / sqrt(r)` under rsLoRA. DoRA, adapter bias and `modules_to_save`
are rejected at load, matching vLLM's `peft_helper`. **`scaling` is folded into
`B` once at load** (vLLM's `LoRALayerWeights.optimize`, ours
`nv_weights::lora_adapter::LoraLayerWeights::optimize`); the kernels keep a
`scaling` parameter for tests and are passed 1.0 in serving.

## 2. Two-stage shrink/expand, layouts, dtypes

One projection with an adapter costs two extra kernels regardless of slice
count: **shrink** writes `buffer[s] = scaling * (x @ A_s^T)` per slice into a
single **fp32** buffer of shape `[num_slices, num_tokens, R]`, zeroed inside the
op; **expand** does `y[:, off_s : off_s + N_s] += buffer[s] @ B_s^T`,
accumulating **in place into the base output** as a masked load/add/store of the
output tile. Shrink inputs and A weights must be fp16/bf16 and identical; shrink
accumulates in fp32 and atomically adds fp32 partials with relaxed semantics
under split-K (inherently non-order-stable); expand downcasts activation tiles
to the B dtype inside the k-loop and stores in the output dtype. **Adapters are
always bf16/fp16** — there is no quantized-adapter path, and vLLM's fp8 LoRA
kernels are exported but never called by `PunicaWrapperGPU`.

**Weight residency layout.** All `max_loras` slots live in one contiguous tensor
per slice, allocated once as zeros at maximum size:
`lora_a_stacked[s]: [max_loras, 1, max_lora_rank, input_size]` and
`lora_b_stacked[s]: [max_loras, 1, output_size_s, max_lora_rank]` —
`nv_layers::lora_slots::LoraSlotStack`'s shapes exactly. Both are stored
"transposed" relative to the GEMM (shrink reads A as `[R rows, K cols]`, expand
reads B as `[N rows, R cols]`), matching PEFT files byte-for-byte, and the
kernels index them with explicit strides rather than transposing. Activating an
adapter into slot `i` is a pure in-place copy into the top-left
`[rank_used, dim]` corner **after zeroing the slot** — zeroing matters because a
lower-rank adapter must not see a previous tenant's tail rows.
`LoraSlotManager::activate` does first-free-slot assignment with real LRU
eviction and zero-fills the stacks an adapter omits. **Per-adapter selection is
stride arithmetic, not a pointer table**: the slot's weights are
`ptr + lora_d0_stride * lora_index`; a pointer array exists only ACROSS slices,
as a fixed 2-3-element `uint64` tensor built once and cached by data-pointer key.

## 3. Fused-projection slicing

Fused projections (qkv, gate_up) keep **per-slice A and per-slice B**. Not
optional: each packed sub-projection is an independent adapter pair with its own
rank usage, and A cannot be shared because PEFT checkpoints store
`q_proj`/`k_proj`/`v_proj` separately. Cost stays at two launches — the slice id
is a grid axis selecting both the weight pointer and the output offset. The
shrink buffer's slice axis is dim 0; the expand output offsets are the **running
cumsum of per-slice output widths**, computed host-side once per weight-set and
shipped as a `slice_start` tensor. **GQA breaks the equal-width assumption** (q
width != k/v width), so the expand grid is sized by `MAX_N = max(hidden_sizes)`
and each CTA loads its slice's true `curr_N` from a per-slice tensor,
early-exiting when its tile starts past that width; when all slices match, a
`SAME_STRIDE` specialization collapses the stride/width tensors to scalars.
Gemma4's fused QKV is 3 slices, one shrink launch writing `[3, T, R]`, one
expand launch with offsets `[0, q_width, q_width + kv_width]`; Qwen is the
degenerate 1-slice case (Appendix).

## 4. Multi-adapter batching metadata

There is **no BGMV and no SGMV on vLLM's CUDA path in 0.26.0** — those ops exist
only under the torch and xpu op trees. CUDA uses one unified grouped GEMM for
prefill and decode alike, differing only in group sizes. **Port ONE kernel
family.** `nv_kernels::lora_meta::LoraKernelMeta::prepare(token_lora_mapping,
max_loras)` is the whole per-step state, with all tensors allocated once at max
size and mutated in place:

| tensor | meaning |
|---|---|
| `token_lora_mapping` | slot index per token, `NO_LORA = -1` for no adapter |
| `token_indices_sorted_by_lora_ids` | token row indices, stably sorted by slot |
| `active_lora_ids` | distinct slot ids in the batch, `-1` first if present; unused tail stays `-1` |
| `num_tokens_per_lora` | group size per entry of `active_lora_ids` |
| `lora_token_start_loc` | exclusive cumsum of group sizes; `[i]` plus `num_tokens_per_lora[i]` delimits group `i` in the sorted index array |
| `no_lora_flag` / `num_active_loras` (host) | true iff every token maps to `-1`; count of distinct groups |

The `+1` on the id and count arrays is because "no adapter" forms its own group.
Recomputation is a stable sort, a unique-with-counts and a cumsum, run once per
forward pass and **skipped when neither the token→adapter mapping nor the slot
layout changed** — the slot-layout half exists because an out-of-band `add_lora`
can LRU-reassign slots under an unchanged batch, so a pure-decode steady state
with the same adapters recomputes nothing.

Kernel-side, each CTA identifies its group from a grid axis, loads its slot id
and group size, and gathers its rows through the sorted index array. Two early
exits: `lora_id == -1` (the no-adapter group and every surplus z-program return
immediately — surplus programs exist because grid z is an upper bound, §5), and
`cta_m_offset >= lora_m_size` (m-tiles past this group's token count return, so
**small groups waste only early-exiting CTAs, never compute**). The expand
kernel has a third, per-slice-width exit (§3), and a host-side whole-op
short-circuit fires on the no-LoRA flag. Row gathering uses
`offset_m = arange(BLOCK_M) % cta_m_len` so masked lanes re-read valid rows
instead of faulting.

## 5. CUDA graph capture

Everything device-side is graph-safe by construction: weights, metadata tensors
and the shrink buffer are allocated once at max size and only ever mutated in
place, so replay sees fresh data for free. The contract is that **scalars freeze
at trace time, dynamic control flow is impossible, and host-side state must be
disguised as device or CPU tensors read inside the op.** Exactly **two
quantities are host-read and therefore frozen at capture**: the grid z-extent,
sized from the active-lora count, which in the default configuration is the
CONSTANT `max_loras + 1` (surplus z-programs load `-1` from the reset
`active_lora_ids` tail and take early exit 1); and the zero-LoRA short-circuit,
where a graph captured with LoRA active permanently contains the kernel launches
and one captured with the flag set permanently contains nothing — which is why
vLLM keys graphs on `has_lora`.

So: capture the decode graph with the LoRA kernels inside (grid z =
`max_loras + 1`), and batches with zero LoRA tokens pay only early-exit CTAs;
optionally keep the no-LoRA graph too and choose at the callsite, a host
decision living outside the captured region. `gemma4_batch_graph.rs` already
implements the in-place-mutation-inside-capture pattern for
tokens/positions/block-tables — `memcpy_htod` into fixed device buffers happens
INSIDE the captured body, so the copies are graph nodes and replay picks up
mutated host-pinned staging — and LoRA metadata slots into the same structure.
**A TLS-based adapter selector is the wrong design**: a captured graph never
re-reads a `thread_local` on replay and would silently serve the wrong adapter.

## 6. The three techniques copied verbatim

Ported as-is; do not redesign them.

1. **Slot-stacked weight tensors + stride-arithmetic selection**
   (`nv-layers/src/lora_slots.rs`). One allocation per slice for the process
   lifetime makes the weights graph-retainable, keeps kernel addressing to a
   single multiply, and makes activation a bounded in-place copy with no
   allocator involvement.
2. **Grouped-GEMM batching metadata** — stable sort by slot, gathered rows, grid
   groups, the two early exits (`nv-kernels/src/lora_meta.rs`). This is what
   makes prefill and decode the same kernel: arbitrary token→adapter mixes cost
   one launch, group imbalance costs only early-exiting CTAs, and the sort is
   O(T log T) host work only on steps whose mapping changed.
3. **PEFT-compatible load pipeline with scaling folded into B**
   (`nv-weights/src/lora_adapter.rs`). Adapters load byte-for-byte as published
   — no transposition, no re-quantization step to get wrong — and validation
   failures reproduce vLLM's behavior, which §8 shows is API-visible.

Additionally, prefix-cache hashing is extended so blocks computed under adapter
X can never be reused for adapter Y or the base model: `nv-engine`'s
`compute_block_hash_tagged` folds the adapter name into the xxh3 seed.

## 7. Hook points

- **Single delta site**: `out2` inside
  `nv_layers::linear::Linear::forward_inner`, covering both `forward` and
  `forward_dense` for all three `LinearKind`s (`Bf16`, `Fp8E4m3`, `Nvfp4`), with
  the delta accumulating into `out2` (`[leading, out_features]`) before the
  reshape and bias add. **Quantization needs nothing special**: every storage's
  `matmul_impl` already yields an activation-dtype output. The trait is
  `nv_layers::backend::LoraDeltaHook`, attached with `Linear::attach_lora` /
  `detach_lora` / `has_lora`.
- **Row-sliced paths**: `forward_rows` and `forward_dense_det` (both bf16-only)
  compute only rows `[row_off, row_off + rows)`, so their delta must use
  `B[row_off .. row_off + rows, :]` — a row slice of the expand, shrink
  unchanged.

## 8. Interface contract

| vLLM flag | default | status here |
|---|---|---|
| `--enable-lora` | off | **unbuilt** as a switch -- discovery is `NV_LORA_ADAPTER_DIRS` presence |
| `--max-loras` | 1 | constructor arg to `LoraSlotStack::new` / `LoraSlotManager::new`; **no env equivalent** |
| `--max-lora-rank` | 16, allowed `{1,8,16,32,64,128,256,320,512}` | **no cap check** -- `PeftConfig` validates only `r > 0` |
| `--lora-dtype` | `auto` -> base dtype | implicit: adapters are bf16 |
| `--max-cpu-loras` | `max_loras` | absent (no host cache) |
| `--lora-modules` | none | `NV_LORA_ADAPTER_DIRS`, `name=path` or bare path |
| `--fully-sharded-loras`, `--lora-target-modules`, `--default-mm-loras`, `--specialize-active-lora`, `--enable-tower-connector-lora`, `--enable-mixed-moe-lora-format`, `--enable-moe-shared-loras` | | TP/MM/MoE features we do not implement |

**Adapter selection via `model`**: vLLM looks the request's `model` string up in
the live adapter table FIRST, falls through to base-model matching on a miss,
and 404s an unknown name. Ours reaches the same *observable* result by a
different mechanism (§12). **`/v1/models`** lists base models and adapters
together; vLLM's adapter card carries `id` = adapter name, `root` = adapter
path, `parent` = its base model's served name, while ours emits `parent` and a
`lora` object (`rank`/`alpha`/`scaling`/`target_modules`/`path`) through
`lora::model_rows`, merged into the matching registry row by
`models_handler.rs`. **`root` is still missing** — the `Model` struct has no
such field, and `parent` arrives via `extras`.

**Load/unload endpoints** (`POST /v1/load_lora_adapter`,
`POST /v1/unload_lora_adapter`, mounted only under
`VLLM_ALLOW_RUNTIME_LORA_UPDATING`) are **not built here at all**. Quirks to
reproduce exactly if they ever are: success bodies are **bare strings, not
JSON** (`Success: LoRA adapter '<name>' added successfully.`);
**rank-over-limit returns 500, not 400**, because `validate_legal` raises a
`ValueError` inside `add_lora` and the HTTP layer special-cases only
`LoRAAdapterNotFoundError` (missing name/path and duplicate-name without
`load_inplace` are proper 400s; unload of an unknown name is 404); **unload
deregisters without freeing memory**, deleting only the registry entry so the
GPU slot is reclaimed by LRU pressure from later loads; and load is idempotent
in id assignment.

## 9. Determinism

The port relaxes bitwise determinism where LoRA requires it, by decision: the
expand accumulates a delta into an existing output, introducing a new reduction
order relative to the pure base matmul, and vLLM's own shrink uses split-K
`atomic_add` with relaxed semantics (`split_k=64` for small batches, forced to 1
only under `VLLM_BATCH_INVARIANT`), **so run-to-run nondeterminism is upstream
behavior, not a porting artifact.** The existing apparatus — `_det` GEMM
variants, `NV_BF16_SMALLM_DET`, `forward_dense_det`, `fused_qkv_bitwise_safe`,
`NV_DEBUG_DETERMINISM` — stays intact for the no-adapter path, and determinism
assertions that fail only when an adapter is active get **scoped to the no-LoRA
case, not deleted.** Relaxed means "not bitwise-stable across runs"; deltas must
still be numerically correct against a reference `x @ A^T @ B^T * scaling`.

## 10. Deliberately out of scope

**Marlin / Gemma4-E4B CUDA** (Marlin is not a `LinearKind`; it is a private
`QLinear` enum inside `gemma4_e4b.rs`, and no LoRA touches any `QLinear`
variant); **quantized adapters** (no such path exists in vLLM either, §2);
**MoE expert adapters** (the Appendix shows why they cannot be ported without
abandoning our fast path — dense projections inside MoE models still work
through the §7 hook); **tensor parallelism** and S-LoRA sharding; **embedding /
logits-head LoRA** (extra-vocab was removed upstream); **graph specialization on
the active-lora count** (we capture the single `max_loras + 1` case); and
**DoRA, rsLoRA-beyond-scaling, adapter bias** (rejected at load).

## 11. Dependency order

The PEFT loader (`nv-weights`), the slot stacks (`nv-layers`) and the
shrink/expand kernels are the foundation; the `Linear` delta hook and its
fused-slice offsets sit on those; graph integration and the HTTP surface sit on
the hook. All three foundation layers exist. The HTTP surface additionally
needs the two fixes tracked in [`01.4-STATUS.md`](01.4-STATUS.md) § "Open
follow-ups": `ChatRegistry::resolve`'s single-engine fallback must stop
swallowing unknown model names (it would serve the base model with a 200 where
vLLM 404s a typo'd adapter name), and `admission::init_gemma4`'s `OnceLock` gate
must gain a `reserve`/`release` path so adapter residency is visible to the KV
budget. Neither is fixed; what shipped for the first is a boot-time warning
(`lora::typo_swallow_risk`).

## 12. What actually serves, and the gap

**LoRA serves on wgpu, for `gemma4_e4b_wgpu` only.** An adapter directory named
in `NV_LORA_ADAPTER_DIRS` is discovered at boot by `lora::catalog_from_env`,
validated by `probe_adapter`, and registered in `ChatRegistry` as an
*additional engine keyed by its adapter id*, selected by naming that id in the
`model` field — no new request field and no new route. Discovery failures warn
and continue; `check_lora_target_kind` refuses an adapter aimed at a non-E4B
graph or a gguf checkpoint before opening a weight file. `fine_tuning.rs`'s
`run_job` produces adapters the same way, calling `probe_adapter` +
`register_adapter` after `train_runner::run`.

**The `LoraDeltaHook` seam of §7 cannot reach any wgpu chat path.** The hook
lives on `nv_layers::linear::Linear`; no `*_wgpu.rs` graph uses `Linear` — they
are hand-built `GpuTensor` pass lists. The E4B sites (`E4bLora`, `E4bLoraSite`,
`emit_lora_site`, four per layer: qkv, o, gate_up, down) are hand-plumbed into
the pre-recorded `Pass` list, and every additional graph costs the same
hand-plumbing until a shared seam exists for pass lists.

Five wgpu-vs-CUDA kernel deltas are invisible from the host API and bind
anything built on top:

1. **`y` is one bf16 per 32-bit word on wgpu**, to avoid a sub-word
   read-modify-write race, while `x`, `A` and `B` stay packed two-per-word, so
   any resident caller must widen its packed activation before the kernel and
   repack after. **This is the single biggest porting hazard.**
2. CUDA indexes `a_ptrs[slice]` / `b_ptrs[slice]` as independent allocations;
   WGSL uses one concatenated `A` and one concatenated `B` with a
   `slice_id * a_slice_stride` plus prefix-sum offset table — legal only because
   all slices share rank and `in_features`.
3. CUDA memsets the shrink buffer every launch; wgpu gets it zeroed per call, so
   a resident port must re-establish that.
4. The fused reduction is `__shfl_down_sync` on CUDA and a workgroup-storage
   tree with barriers on wgpu. Both LoRA shaders write every slot they later
   read, so LoRA does not depend on workgroup zero-initialisation.
5. `lora_shrink` fakes `widths = vec![1; n]` and so cannot validate a bad
   slice-width table. **Prefer `lora_grouped`, which validates both.**

**`WGPU_FUSED_MAX_M` is a host path-selection heuristic, not a kernel limit** on
either backend; the only fused-kernel bound is `rank > 64` (`FUSED_MAX_RANK`).
The real wgpu bound is `max_compute_workgroups_per_dimension`, and
counter-intuitively the grouped path (16-column expand tiles) caps `m` *lower*
than fused (512-column chunks) — so a naive `m > 64 -> grouped` branch moves you
onto the *more* constrained kernel. `WgpuLoraDispatch::plan(m, win)` makes the
branch grid-aware and falls back between the two rather than erroring.

**A full-model bitwise gate against merged weights cannot exist by
construction**: the base gemv rounds to bf16 before the delta is added, so
runtime-LoRA and merged-weights differ in rounding whatever the fixture. What
replaces it is a site-level bitwise gate plus a model-level gate whose oracle is
a second graph built from exactly-merged weights, with the tolerance calibrated
in-test from a one-ulp weight perturbation rather than set as a constant. The
load-bearing pair is **bit-identity under a zero adapter** (rules out a dead
code path *and* a mis-scaled hook) and **divergence under a nonzero adapter**
(rules out a hook that is wired but inert). Neither alone would do.

**Module count is not `layers x targets`.** E4B has 18 kv-shared layers that
compute no k/v, so a rank-r adapter over 7 projections and 42 layers matches
`5*42 + 2*24 = 258` modules, not 294. `E4bLora::skipped_modules` carries the
leftovers so the gap is never silent.

### The gap, precisely

Not present on any backend: LoRA sites in any graph other than
`gemma4_e4b_wgpu`; any quantized-base adapter (adapters are bf16-only, and
`LinearStorage::Nvfp4` is cuda-only); CUDA serving of any kind; and dynamic
load/unload. Three specific dangling ends, each small and well-defined:

- **The type bridge.** `nv_weights::lora_adapter::LoraAdapter` and
  `nv_layers::lora_slots::LoraAdapter` are unrelated structs and nothing
  converts between them. Scaling is already folded into `lora_b` at load, so the
  bridge passes `scaling = 1.0`.
- **The rank cap.** `PeftConfig` validates `r > 0` and nothing else; a
  `max_lora_rank` check belongs at registration (§8).
- **The slot plumbing.** `emit_lora_site` calls the metadata prepare with
  `max_loras = 1` and every token mapped to slot 0, recorded once into the pass
  list at build time; `chat_engine/batch.rs` hardcodes `lora_slot: -1` on the
  CUDA batched path; and `gemma4_batch_graph.rs`'s `arm_lora` / `arm_lora_multi`
  / `LoraMode::PerRow` have no callers outside their own tests, as do
  `LoraSlotManager` and `nv-specdecode`'s `LoraTokenMap` / `WgpuLoraRuntime`.
  Closing it means teaching the E4B graph to hold a `LoraSlotStack` and take a
  per-request slot id instead of baking one adapter into the recorded pass list.

`lora::annotate_models` is dead code duplicating `lora::model_rows` — it has no
caller anywhere, while `model_rows` is the one `models_handler.rs` uses. Delete
it rather than wiring it.

## Appendix. Qwen / MoE extension

The primary target is the cached `RedHatAI/Qwen3.6-35B-A3B-NVFP4` (hidden 2048,
40 layers, 256 experts, top-k 8, 10 full-attention + 30 linear-attention
layers).

**A.1 The landed pieces are model-agnostic.** Grepping for `gemma|qwen` over the
loader, the slot stacks, the KV-hash tagging and the kernel metadata returns
nothing: `PeftConfig` parses only r/alpha/target_modules/rslora and
`parse_fine_tuned_lora_name` handles generic PEFT paths; per-model shape info
enters the slot stacks purely as data via `&[LoraModuleSpec { name, in, out }]`,
matched to stacks by name string with omitted stacks zero-filled;
`compute_block_hash_tagged` folds the adapter name into the seed; and the
grouped kernel is slice-table-driven. **The only genuinely per-model content is
a declarative module-map table**: PEFT module name -> owning `Linear` +
`slice_start`/`slice_n`, plus prefix normalization. That is data, not code, and
one implementation serves all three models. **The fork risk is the
not-yet-landed module-map type** — if each model hand-rolls its PEFT-name →
stack-name matching, three copies appear; its recommended home is nv-layers next
to `LoraModuleSpec`.

**A.2 Qwen dense LoRA.** **No projection in either Qwen model is fused**, in
contrast to Gemma4's `qkv_proj` and `gate_up_proj`: Qwen3 dense has q/k/v/o as
four separate fields and gate/up/down via `Mlp`; Qwen3.5-MoE has q/k/v/o on its
full-attention layers, a router gate plus shared_expert gate/up/down and
`shared_expert_gate` in the MoE block, and in_proj_qkv/z/a/b plus out_proj on
its linear-attention layers. Every one reaches the single delta site through
`Linear::forward -> forward_inner -> matmul_impl`, and `qwen3.rs`,
`qwen3_5_moe.rs`, `moe.rs`, `mlp.rs` and `linear_attn.rs` use **zero**
`forward_dense` / `forward_rows` / `forward_dense_det`, so the §7 hook covers
all of them including the `leading==1` gemv branch. On the cached NVFP4
checkpoint q/k/v/o and the shared-expert/expert gate/up/down are `Nvfp4`, while
the router `mlp.gate`, `shared_expert_gate` and all `linear_attn.*` projections
are `Bf16` — all covered.

**The one width quirk**: `attn_output_gate=true` on Qwen3.5-MoE doubles q_proj's
out_features to `16 x 256 x 2 = 8192` with a per-head `[value | gate]` interleave
split after projection. Still one Linear, still 1:1 for LoRA — only the
spec-table width doubles. **An adapter trained without gate awareness (lora_B
rows 4096) would pass `set_lora`'s `b_rows <= out_features` check and silently
leave the gate lanes un-adapted**; reject, warn or zero-pad is an open policy
question. Attention quirks add nothing, since q_norm/k_norm, partial RoPE and
GQA grouping are all strictly downstream of the hook, where the delta lands on
`out2` before any reshape. **Name mapping is identity plus one prefix rule**:
`model.language_model.layers.N` ↔ `model.layers.N`. What drops out relative to
Gemma4: all fused-projection slicing (§3), row-sliced delta variants (§7), the
`fused_qkv_bitwise_safe` determinism interplay, and CUDA-graph capture
integration (§5) — Qwen has no batch-graph runner, `forward_with_cache` is
eager, so the delta rides the eager path unconditionally.

**A.3 MoE-expert adapters stay out of scope.** Qwen LoRA covers attention
q/k/v/o plus the shared expert's gate/up/down, and rejects adapters shipping
`experts.*` or router-gate tensors at load.

**Memory is disqualifying on its own.** At vLLM's buffer shapes, rank 16, bf16,
per layer per adapter slot (hidden 2048, 256 experts, moe intermediate 512):
w13-A 32 MiB + w13-B 8 MiB + w2-A 4 MiB + w2-B 16 MiB = 60 MiB, x 40 layers =
**2.34 GiB per adapter slot** (1.26B adapter params, ~3.6% of the base model),
preallocated at `max_loras` regardless of occupancy. Attention plus shared
expert across all 40 layers is ~35 MiB per slot at rank 16, so **routed-expert
LoRA costs ~70x everything else combined**, against an admission gate that
cannot see adapter memory at all (§11).

**vLLM -- the reference -- refuses LoRA on every FP4-activation MoE kernel,
including the family ours mirrors.** `FusedMoEWithLoRA` asserts non-monolithic
kernels; `supports_lora()` defaults to `False` for every experts impl;
flashinfer-cutlass raises `NotImplementedError`; NVFP4 emulation refuses. For a
compressed-tensors NVFP4 checkpoint — ours — the backend oracle under LoRA can
land only on Marlin, i.e. **vLLM serves NVFP4-MoE + LoRA only by abandoning the
FP4-activation cutlass grouped GEMM for W4A16 Marlin dequant.** It never runs
LoRA through any FP4-activation grouped GEMM, which is exactly what our MoE path
is (`cutlass_moe_grouped_fp4_gemm_sm120_bf16`). **There is no implementation to
port that keeps our fast path.** Supporting it natively would need a new
(expert x adapter) 2D-grouped LoRA kernel family plus a bf16 materialization of
the intermediate activation for the w2 shrink — our `silu_mul_quantize` fuses
activation directly into NVFP4 re-quantization, so the down-proj input never
exists in bf16.

**Shared-expert adapters are the sanctioned substitute and suffice to condition
the full depth**: ours is an `Mlp` with three separate Linears through the §7
hook, and it runs for **every token**, so an adapter there conditions the whole
MLP stack without touching routing. (vLLM's `--enable-moe-shared-loras` is
unrelated: one w13-A/w2-B factor shared across *routed* experts.) **No adapter
on the router gate or `shared_expert_gate`** — the router gate would technically
flow through the hook, but perturbing routing silently invalidates
adapter-vs-base comparisons beyond what KV-hash tagging covers, and
`shared_expert_gate` is a `[1, hidden]` projection where rank-16 on a 1-row
output is meaningless.

**If expert LoRA ever enters scope**, the answer is "widen the bins", not "add a
second pipeline": expert-LoRA weights are indexed by BOTH adapter and expert, so
the two groupings compose as a cross product, and a composite (expert-major,
adapter-minor) counting sort keeps expert groups contiguous while exposing
(expert, adapter) subgroups for the LoRA GEMMs. Our `moe_permute` is a 3-kernel
counting sort parameterized only by bin count, so 256 -> 1280 bins generalizes
it. Whether the saved gather traffic beats the loss in base-GEMM group
granularity is a measurement, not a design argument. Note vLLM does *not* share
the sort, and its decode-path `naive_block_assignment` skips the LoRA sort
entirely for every batch <= 16 tokens on this model.

**Linear-attention projection adapters** (30/40 layers) are hook-reachable in
principle and vLLM's Qwen3-Next is `SupportsLoRA` there, but its packing
(`in_proj_qkvz` / `in_proj_ba`) differs from our four-way split, so HF-format
adapters would need a split-resolver. Optional later scope.
