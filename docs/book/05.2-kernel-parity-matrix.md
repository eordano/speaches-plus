# Kernel parity -- what would catch a wrong number

The useful question about a kernel is not do CUDA and wgpu agree. It is
what turns red if this kernel starts returning subtly wrong numbers. This
page answers that question, names the suite for each answer, and names the
kernels that have no answer.

`docs/book/05.1-wgpu-status.md` §2 is the narrative companion;
`docs/book/05-backends.md` covers backend selection and the feature graph.

## Agreement between two implementations is not an oracle

A cross-backend comparison passes whenever both sides carry the same bug. That
is not a theoretical hazard in this tree, it is the recorded failure mode:

- The wgpu w4a16 family and its own host oracle carried the same group-16
  scale-indexing bug. Every agreement test between them was green while the
  kernel was wrong at 6 of 12 group sizes. The gate that could have caught it
  is `gemv_w4a16_cpu_ref.rs` -- CUDA against a scalar host reference derived
  from the documented dequant rule, which cannot share a bug with either GPU
  path. `wgpu_gemv_w4a16_group_sizes.rs` now holds the divisibility contract.
- One ue4m3 subnormal omission existed independently in `gemv_nvfp4_v2.wgsl`,
  in two CUDA sources, and in a Rust CPU oracle. Each copy survived because the
  check it faced compared two copies of the same error, or drew inputs that
  never reached the subnormal band.

So a census beats a comparison: enumerate every site that implements a rule
and assert each one obeys it, from source, with no second implementation in the
loop -- list every decode site, assert the rule's branch sits where it must, and
refuse to let a shader assembled in Rust hide from the enumeration. No census
suite of that shape exists in the tree; prefer it when adding a gate.

**A cross-backend agreement test earns its place only where the shipping backend
has no independent host oracle for that entry.**

## What compares CUDA to wgpu today

Each of these compares only when built with both `cuda` and `wgpu`:

| suite | what it is the last gate for |
|---|---|
| `fp8_contract_e4m3.rs` (`cuda_vs_wgpu`) | the CUDA e4m3 cast and `rowquant_e4m3` against the wgpu-side host encoders (`quantize_rows_fp8`), byte for byte |
| `wgpu_lora.rs` (`cuda_ref::cross_check`, `meta_prepare_matches_the_cuda_side`) | every wgpu LoRA case against the CUDA LoRA kernels; the shrink f32 buffer bit-exact |
| `wgpu_moe_grouped.rs` (`moe_grouped_wgpu_matches_the_cuda_cutlass_grouped_path`) | the wgpu grouped MoE GEMM and the CUDA CUTLASS grouped path, each against the blocked CPU oracle |
| `nv-specdecode/tests/lora_spec_backend.rs` (`cuda_and_wgpu_lora_deltas_are_bit_identical`) | the LoRA delta through `Linear` on CUDA against the wgpu hook, bit for bit |
| `nv-specdecode/tests/wgpu_spec.rs` (`wgpu_spec_matches_cuda_chain_path`) | the wgpu spec-decode chain against the CUDA chain path, committed tokens equal |

No suite compares `gdn_gating`/`gdn_recurrent`, the int8 GEMV epilogue
(`rowquant_i8`, `gemv_i8_normed`, `gemv_i8_normed_mk`) or `kv_fp8_paged` across
backends; each rests on its single-backend gates. The standard for deleting any
gate here: **plant a bug in the code it covers and confirm something else still
turns red.** A file count is not the measurement. "parity" in a filename means
nothing -- read the suite's `#![cfg]` header to learn which backends it touches.

## What gates every other kernel

An independent host oracle on the shipping backend, under
`nv-kernels/tests/wgpu_*.rs` (`#![cfg(feature = "wgpu")]`, WGSL against a CPU
reference) or, for CUDA-only kernels, the `*_cpu_ref` suites. This is the
majority and it is the stronger gate, not a downgrade: it can fail on a bug
both backends share.

Two host-oracle shapes are weaker than they look and are worth recognising:

- A shared oracle makes parity transitive, never direct. The
  `quantize_nvfp4_bf16` paths assert byte-exactness against the same
  `nv_quant` oracle on both backends, so the two suites can drift to different
  oracle versions unnoticed.
- A bound derived from the value it bounds survives every mutation. State
  whether a tolerance was measured or picked. The loosest live one is
  `wgpu_lora.rs`'s `assert_close(rtol 2e-2, atol 2e-2)` on the bf16 output
  arm -- picked, three decades looser than anything else, on a kernel that
  fires inside `Linear::forward_inner` on every forward of every attached
  projection. Its shrink buffer is bit-exact against CUDA, so the tightening is
  probably available.

## Reading a green run

A suite here can pass while executing nothing, in four distinct ways.

1. **`#![cfg(all(feature = "cuda", feature = "wgpu"))]` compiles to an empty
   binary** under one feature: `0 passed` in `0.00s`, green. Nothing is left to
   panic, and no census counts these suites -- read the header and the count.
2. The cross-backend tests do not share a skip convention. The `cuda_vs_wgpu`
   tests in `fp8_contract_e4m3.rs` print `SKIP no CUDA device 0` and return
   unless `NV_KERNELS_PARITY_REQUIRE=1`; `nvk.sh` exports it, so nvk-driven runs
   are safe, and a bare `cargo test --features cuda,wgpu` without a CUDA device
   is a false green. `lora_spec_backend.rs` has the safe polarity: it panics
   unless `NV_KERNELS_PARITY_ALLOW_SKIP=1`. Read each suite's skip helper before
   reading its green.
3. The `wgpu_*` convention is inverted, and is the shape to copy. Those
   suites panic unless `NV_KERNELS_WGPU_ALLOW_SKIP=1` /
   `NV_KERNELS_CUDA_ALLOW_SKIP=1` is set -- a skip must be opted into, and a
   gate that cannot run says so instead of reporting success.
4. **`NV_KERNELS_WGPU_REQUIRE` is set by nothing** (`nvk.sh` exports only
   `NV_KERNELS_PARITY_REQUIRE`), and it is the only thing that makes the
   nv-models wgpu suites panic without an adapter: every suite built on
   `ctx_or_skip` in `nv-models/tests/common/mod.rs`, plus
   `deepseek_ocr_decoder_wgpu.rs`, prints `skipping: no wgpu adapter` and
   passes. Those suites are green on nothing by default; converting them to the
   item-3 convention is the fix.

Every real wgpu run prints an adapter banner from `WgpuContext::summary()`
before doing work. A wgpu result with no banner is a skip, whatever the
result line says.

## Keeping this page's citations honest

`rust/scripts/kernel-parity-census.py` is the check. It re-derives the one-sided
enumeration from the tree, resolves every backticked symbol and every
`.rs`/`.cu`/`.wgsl`/`.md` name cited here, and ratchets the count of
`extern "C" nv_kernels_*` host fns named by no test. It owns the generated
appendix at the bottom of this page: every one-sided kernel with its recorded
verdict, regenerated by `--write` and enforced by `--check` from
`parity-audit.sh`. **The appendix follows this page's own rule -- it is derived,
never hand-edited, and a shader added without a verdict fails the gate rather
than silently joining an enumeration.**

Counts of `.cu`, `.wgsl` and entry points are deliberately not recorded here.
They moved by a factor of three in one commit when every static shader was
extracted from `nv-models` into `nv-kernels/wgsl/`, and a transcribed count is
wrong the moment it is read: take them fresh with `grep -c '__global__'` over
`cuda/*.cu` and `grep -c '@compute'` over `wgsl/*.wgsl`.

## One-sided kernels: gap, fusion, or missing test

A file-level census of `cuda/*.cu` against `wgsl/*.wgsl` sends readers at the
wrong targets, because most one-sided files are not ports owed. The
distinction that matters:

- Capability gaps, real -- `dflash_accept` and `moe_route` both run **on
  the host** on the wgpu path (`nv-specdecode/src/wgpu_spec.rs` calls the CPU
  `accept_prefix_argmax`; `nv-layers/src/moe_wgpu.rs::plan_routing` takes
  `topk_ids` as a host slice). These are per-step readbacks CUDA does not pay,
  and they are the two with a measurable cost. `dflash_gate` is a one-entry
  elementwise op and the cheapest thing on this list. `capture_copy` exists to
  feed CUDA graph capture, which wgpu has no analog for, so porting the ops is
  trivial and pointless.
- `gdn_decode`, and the more interesting half of it -- no wgpu counterpart,
  and `gdn_gating.wgsl` / `gdn_recurrent.wgsl` are ported and gated but no
  wgpu model wires them: no `nv-models` source references
  `wgpu_backend::kernels::gdn_gating` or `gdn_recurrent`.
- Fusion gaps, running today unfused on wgpu -- `gqa_verify_hd512`
  (hd=512 is reachable on wgpu; the specialised verify kernel is not),
  `laguna_step`, `moe_gemv`, `moe_grouped_fp4_gemv`,
  `rmsnorm_quantize_nvfp4_bf16`. Each costs a pass, not a capability.
- Not a gap at all -- `kv_ring`. Ring-buffer KV is folded inside the wgpu
  kernels under different entry names and gated by
  `splitk_bf16kv_ring_wrap_matches_the_linearized_cache` in
  `wgpu_flash_decode.rs`.
- Undecided, and the largest unexamined surface in the tree -- vendored
  `cuda/marlin/`, gated CUDA-side by `marlin_w4a16_cpu_ref.rs`, with no
  recorded "will not port" decision. `cuda_sm120/` is structural: CUTLASS
  tensor-core paths WGSL has no surface for, and `coop_mat` is not one.

Conversely, the wgpu-only modules (`assistant_drafter`, `attn_decode_small_m*`,
`fused_attn_chain`, `fused_norm_chain`, `gemm_nvfp4`, `gemv_nvfp4_lin/_v2`,
`moe_grouped_gemm`, `quant_gemv`, the `na*` modules and the `gemm_*_small_m`
shaders whose WGSL is emitted from Rust) are **wgpu-native by design, not
CUDA gaps** -- they exist because wgpu needs shapes CUDA gets from cuBLASLt,
CUTLASS or a captured graph. The two generated families are invisible to any
`ls wgsl/` census, which is one more reason not to run one.

## Oracles are themselves gated: two decompositions or it is one opinion

A host reference that shares its decomposition with the kernel it checks can share
its bugs (the recorded w4a16 group-16 incident: green in every
cross-implementation comparison, wrong at 6 of 12 group sizes). So each oracle
family carries **two independent decompositions plus planted-bug negative
controls that must each be caught at every configuration**:

- `w4a16_oracle_fuzz` holds the documented dequant rule as a row-major
  f32-product oracle and a group-major all-f64 oracle, cross-checked over a seeded
  shape grid (60+ cases, groups 16-128, K 16-8192), with planted scale-index
  off-by-one, nibble-order reversal and missing sign offset. It also pins the
  incident's mechanism as a rule: **with one group per row a scale-index
  off-by-one wraps to itself**, so single-group shapes can never gate scale
  indexing and multi-group shapes are mandatory in every w4a16 suite.
- `nvfp4_oracle_fuzz` (nv-quant) cross-checks the shipping log2-route encoder
  byte-for-byte against an independent f32-bit-manipulation route over 450+ fuzzed
  blocks spanning the ue4m3 subnormal region, the 448 clamp edge, exact E2M1
  midpoints and ±0, with planted scale-mantissa truncation, inverse-from-the-
  un-roundtripped-scale, tie direction and pack order. **The un-roundtripped
  inverse is the class to fear**: a quantizer that scales by the ideal scale
  instead of the encoded-then-decoded scale is subtly wrong everywhere and exactly
  right on round-number scales.
- `gdn_host_oracle_fuzz` holds the gated-delta rule (decay, read, beta-scaled
  delta write at k, out = state-transpose q) in a kernel-order f32 reference and
  an independent rank-1-algebra f64 reference at a pinned drift tolerance, with
  planted decay-after-write, read-before-decay, missing beta and k/q confusion.
  One test pins that **T=1 hides every decay-ordering bug**, so multi-token
  sequences are mandatory in every GDN suite. These references are host-only:
  wiring the f64 reference into a GPU GDN suite is what turns oracle
  self-consistency into a kernel gate.

## Generated kernel candidates are gated before they are timed

A candidate kernel is a new WGSL file under `nv-kernels/wgsl/candidates/` carrying
its own entry name (`gemv_w4a16_m1_gen0_w8`, `..._gen1_w8`, `..._gen2_w8`). **The
shipping shader is never edited by a candidate round**, so a round that loses
costs nothing and a round that wins is a routing decision made later, on its own
evidence.

`kernel_forge_gemv_w4a16` is the gate adapter. It reads candidates off disk -- no
crate rebuild per candidate -- compiles each through naga on the host, requires
the proto binding contract (packed / scale / x / y / params at bindings 0-4) and a
256-invocation entry, then dispatches at the shipping launcher's own geometry via
`gemv_w4a16_m1_proto::variant_for` and `max_v_for`. **Acceptance is not a fresh
`allclose`**: `tests/support/w4a16_host_oracle.rs` holds the two independent
decompositions and is `include!`d by both `w4a16_oracle_fuzz` and the forge, so
the candidate is graded against the same row-major f32-product and group-major f64
oracles, cross-checked at the same `3e-5` drift bound before grading, and accepted
only inside the `1e-2` relative bound `gemv_w4a16_cpu_ref` and
`gemv_w4a16_m1_proto` already pin. One oracle, not a copy of one.

Three rules make the pipeline worth trusting. Gate first, time second:
latency lives in a separate `#[ignore]` test the runner invokes only after the
correctness gate is green, because a faster kernel that is wrong is not a result
and a number taken before the gate is not evidence. **The candidate set always
carries a planted-bug member**: `gemv_w4a16_m1_planted_bug_scale_off_by_one` reads
the next group's scale -- the recorded group-16 incident class -- and the gate
asserts it is REJECTED at every shape, so if it ever passes, every green candidate
in that run is void (gate shapes are multi-group for the same reason). **Failures
are recycled, not discarded**: compile, dispatch and oracle failures append
`stem<TAB>stage<TAB>detail` to `$NV_KERNEL_FORGE_FAILURE_LOG` and the next attempt
prints them before it generates anything.

`nv-kernels/tools/kernel-forge.sh [gate|bench|all] [-c stem,stem]` is the runner:
its own `NVK_LANE`, logs outside the source tree, and a bounded wait on
`nvidia-smi memory.used` before every GPU run, so a timed arm never shares the
box. The gate arm needs a GPU only for the dispatch; the oracle, the planted-bug
rejection proof and the candidate compile all run on the host.

Cycle one on `gemv_w4a16_m1_proto` (wgpu/Vulkan, one NVIDIA Blackwell adapter,
8 warm-up plus 200 timed dispatches per arm in one pass, GPU idle at 2 MiB, two
runs) settled the shape of the win: all three candidates pass the oracle at
`(67,320)`, `(96,2560)`, `(33,10240)` with max rel `3.2e-3` to `3.8e-3`, the
planted-bug candidate is rejected at all three, and against the shipping shader at
N=20480 K=2560 the barrier-count variant `gen0` and the dual-accumulator variant
`gen1` land inside run-to-run spread while the `vec4<u32>`-load variant `gen2`
roughly halves the kernel time at both shapes. **Wide loads are the lever on this
kernel; barrier count and ILP are not.** Nothing routes to `gen2` on that evidence
alone -- the shipping wgpu path changes only through the performance-default rule.

## Subnormals are the one class no adapter can be promised bit-exact

CUDA builds with nvcc's `--ftz=false` default: denormals preserved. Vulkan/WGSL
exposes no denormal mode to a shader -- the WGSL floating-point rules leave
subnormal handling implementation-defined, and
`VkPhysicalDeviceFloatControlsProperties` only reports flush-to-zero
behaviour, it does not let a shader select it. Any cross-backend gate must
therefore scope bit-exactness to chains with no subnormal intermediate and
bound the tainted lanes separately.

Only integer, copy and LUT surfaces are spec-deterministic and should transfer
across adapters: gather_rows, moe_permute, the token_map / incr_pos halves of
graph_decode, KV byte-moves, and the e2m1 / ue4m3 table decodes. Everything
else on this page was executed on one NVIDIA Vulkan adapter. Metal coverage is
separate and functional-only (`docs/book/05.6-macos-port-status.md`); no suite
audits the MSL naga emits.

## What a wgpu decode step still lacks

Kernel coverage is not the blocker. Every primitive of a dense decode step
exists on wgpu -- embed, rope, the norm families, attention in four shapes, KV
read/write, the GEMV/GEMM families, and logits-to-token. What is missing is
structural, and the ordering matters: buffer lifetime comes first.
`wgpu_backend/buffer.rs` defines `GpuTensor<T>` and `dispatch.rs` defines
`run_resident`, but `run_resident` has exactly one occurrence in
`nv-kernels/src/` -- its definition -- and no kernel module uses `GpuTensor`
either; it is consumed above nv-kernels, in `nv-layers` and heavily in
`nv-models` and `nv-specdecode`, while the kernel entry fns still take host
slices. Threading `GpuTensor` through them is the single highest-leverage change,
and it is now a migration with callers waiting, not a design. A command-buffer
reuse layer -- wgpu's equivalent of what `CudaGraphRunner` amortizes -- only
becomes possible after it, and **the two host-resident steps are made worse
rather than better by it**: MoE routing and spec-decode accept run on the host, so
a device-resident tensor that has to come back for routing buys less than it
looks. `tree_verify_*` remains without a wgpu value gate, so a wgpu spec-decode
verify step would run two modules whose output nothing checks.
