# Charter -- what the native Rust port is for, and what would count as done

The normative charter: goals, acceptance bar, numerics contract. What is
implemented is [`01.4-STATUS.md`](01.4-STATUS.md); how to quote a number is
[`08.4-PERFORMANCE.md`](08.4-PERFORMANCE.md); the crate layout is
[`01-architecture.md`](01-architecture.md).

**Every threshold below is a target, never a measurement. Nothing on this page
is quotable as a result.**

## 1. The goal

Reimplement, in Rust, the four Python subsystems that exist only in the parent
`nano-qwen3-omni` repo -- the vLLM-style inference engine (`nano_vllm`), the
Qwen3-Omni / Gemma 4 multimodal wrappers (`omni`), the Qwen3-TTS voice-cloning
stack (`tts/qwen3`), and the Qwen3 forced aligner (`aligner`) -- as crates under
`rust/`, linked into the existing Axum server, replacing the `reqwest`-based
upstream chat-completions forwarder. **Done means `rust/` is a single
statically-linked binary owning the entire realtime + chat + TTS + ASR +
alignment stack, with no Python at runtime and no sidecar.**

- **G1 -- Functional parity** with the parent's seven user-visible OpenAI
  endpoints (`/v1/chat/completions`, `/v1/audio/transcriptions`,
  `/v1/audio/translations`, `/v1/audio/speech`, `/v1/voice-profiles`,
  `/v1/audio/diarization`, `/v1/audio/embeddings`) **and** the realtime/inspect
  surface speaches-plus already ships.
- **G2 -- Model parity** for `Qwen3`, `Gemma4-MoE`, `Qwen3-Omni-30B-A3B-Instruct`
  (thinker + talker + audio encoder + codec), `Qwen3-TTS-12Hz`
  (Base + VoiceDesign + CustomVoice), `Qwen3-ForcedAligner-0.6B`.
- **G3 -- Numerics parity**: bit-identical to the Python reference under fixed
  seeds with matching `compute_dtype`, or within the §4 tolerance band. No
  silent drift.
- **G4 -- Performance floor**: equal-or-better throughput than the parent's
  Python path at FP8 and BF16.
- **G5 -- Conformance**: the `conformance/` corpus keeps passing, with new
  fixtures for chat, TTS and alignment.
- **G6 -- Single binary**: one `cargo build --release` produces one executable.

## 2. Scope

**In:** inference on CUDA, on wgpu (Vulkan and Metal), and on ROCm/HIP for
`nv-kernels`; single-node tensor parallelism; the HuggingFace weight layouts the
parent loads, plus GGUF.

**Out, and staying out:** a Go port of any of this; multi-node distributed
inference; Intel SYCL; inspector-frontend changes; and replacing the existing
Kokoro / whisper.cpp / CT2 backends -- those coexist, and `nv-tts` / `nv-omni`
are *additional* model routes, not replacements.

**Out of the original charter and in the tree anyway:** LoRA (design, training
and wgpu serving) and the `nv-train` crate, governed by
[`06.5-lora-design.md`](06.5-lora-design.md) and
[`06.6-lora-training.md`](06.6-lora-training.md), not by this page. The scope
moved; do not re-derive "LoRA is out of scope" from a stale non-goal.

## 3. System shape

**One process.** The HTTP/WS server (axum + tokio) lives on the main runtime; a
dedicated `nv-engine` worker thread owns the CUDA context, taking
`EngineRequest`s over an `mpsc` channel and streaming `EngineEvent`s back.
`nv-tts` runs on its own worker with a separate stream; `nv-aligner` is a lazily
loaded pool; tensor parallelism ships as one worker thread per rank with its own
device and context. **Process-per-rank -- the parent's pattern -- is rejected**:
in one process there is one allocator and one log stream.

**Tensor library: candle for storage and shape ops, cudarc for direct device
API** (kernel launches, NCCL, FP8 dtype management, paged KV allocators, graph
capture), interoperating through raw device pointers -- candle's
`.storage().slice()` re-wrapped as `cudarc::CudaSlice`. Not Burn (less mature
ecosystem here), not tch-rs (drags libtorch), and not mistral.rs as a crate
dependency -- specific kernels and modules are copied in, but the engine is
nano_vllm semantics, which differ in EAGLE3 and in scheduling. `nv-kernels` is
the only crate with a non-trivial `build.rs`, and the crate graph is acyclic:
config below everything, weights and kernels below the layer crates, layers
below the model crates, models below the engine, engine below the binary.

## 4. Numerics-parity strategy

The single biggest risk is silent numerical drift across 30B parameters. The
mitigation is a tiered tensor-equivalence harness, and these tier names are the
vocabulary the rest of the book uses:

| Tier | Scope | Tolerance |
|---|---|---|
| T0 -- bit-identical | Per-kernel unit tests with fixed inputs (deterministic algorithms only) | `==` |
| T1 -- ULP-bounded | RMSNorm, Linear forward, RoPE | <=4 ULP in compute dtype |
| T2 -- RMS-bounded | Per-layer activations of a 200-token forward pass | RMS <= 1e-3 (BF16), <= 1e-5 (FP32 reference) |
| T3 -- token-identical | End-to-end LM forward, greedy decode, fixed seed | exact token-ID match for first 100 tokens |
| T4 -- distribution-equivalent | Sampled decode, eval-set perplexity | within 1% perplexity, KS test p>0.05 on top-1 distribution |
| T5 -- audio-perceptual | TTS / Omni audio output | RMS <= 0.5 dB on 24 kHz waveform; STT round-trip edit distance <= 1 |

The instrument is a golden-tensor harness: a pyo3 dev-dependency embedding
CPython for parity tests only, driving the parent's module with a fixed-seed
input, capturing intermediate tensors at named hook points, running the Rust
path on the identical input, and diffing at every hook point under the tier's
tolerance. All Rust paths force deterministic algorithms under it -- no
`atomicAdd` in reductions, deterministic sort for top-k. **A tier named here is
a contract, not a running gate**; whether any tier has an owner is a
[`01.4-STATUS.md`](01.4-STATUS.md) question.

## 5. What "done" requires

- **Functional** -- endpoints match the parent's shape and status codes.
- **Numerics** -- golden-tensor diffs under the §4 thresholds.
- **Performance** -- targets stated against the parent's Python `nano_vllm` +
  `transformers` on a single H100 SXM. A quantization or scheduling change that
  is not faster has no case.
- **Memory** -- KV-cache utilization within 5% of the parent at equal batch/seq.
- **Stability** -- 24 h soak with no leak, panic or unrecoverable device error;
  request error rate < 0.01%.
- **Build** -- every shipped devshell produces a working binary on both
  Linux-x86_64 and Darwin-aarch64.
- **Conformance** -- 100% over the full fixture set: the existing realtime
  fixtures plus `020-chat-completions-*` (greedy, sampled, tool-call,
  structured-json), `030-voice-clone-*` (Base + VoiceDesign + CustomVoice),
  `040-align-*` (5 languages x per-word and per-segment), and a golden audio set
  diffed under T5. The existing `client/test_e2e*.py` suites **must pass
  unchanged**.

## 6. Hardware

| Tier | Coverage |
|---|---|
| Tier-1 (must work) | Hopper-class and newer NVIDIA: full FP8, paged flash attention, Marlin |
| Tier-2 (best-effort) | Ada: FA2 paged + Marlin; FP8 falls back to BF16 |
| Tier-3 (must run, may be slow) | Ampere: FA2 paged + Marlin; no FP8 |
| Tier-4 | Apple silicon and other non-CUDA: the wgpu backend, no paged KV, no CUDA graphs |

Tier assignment is enforced by feature-detect at startup: log a warning and fall
back where unavailable; refuse to start only on a Tier-4 box with a Tier-1-only
model. **This table describes classes, not the fleet** -- the development box
and the primary measurement box both sit outside the tier that shipped with the
original charter, which is exactly why a per-class rule beats a named part
number.

## 7. Standing risks

- **R1 -- numerics drift in the Qwen3-Omni flow-matching codec.** An iterative
  ODE solver compounds error; prove the T5 tolerance on a golden clip set, and
  if drift exceeds budget freeze the codec to the vendored Python implementation
  behind a thin pyo3 bridge.
- **R2 -- upstream weight-format changes.** A loader that checks
  `config.architectures` and refuses unknown shapes loudly; new variants are
  explicit work items, never silent upgrades.
- **R3 -- third-party kernel API churn.** Pin SHAs; every bump triggers a full
  golden re-validation of the kernel tier.
- **R4 -- tensor-parallel correctness on >1 GPU.** Gate on a 2-GPU correctness
  test before claiming TP; feature-flagged off until then.
- **R5 -- voice-profile schema lock-in.** The on-disk `/v1/voice-profiles`
  schema is forever once shipped: it carries a `schema_version`, forward
  migrations live in the loader, and the tests land before the feature does.

## 8. Rollout

The parent's Python implementation continues to exist as the parity reference;
**this charter does not deprecate it.** The `reqwest`-based forwarder is removed
only after one full release of dual-shipping.
